2328 — sm keeps the handoff note

Author: sm-2328 c6f0a143 · Ticket #2328 · Revision 3 · 2026-10-19

Memo

I recommend that sm own the handoff note from start to finish, and that the agent's part be the thing models do best: fill in a file. When sm asks for a handoff, it has already written a draft at .sm/handoff.md in the agent's worktree. The draft is pre-filled with everything sm knows: the agent's tickets and PRs, running queue jobs, pending reviews and children. The agent fills in the rest with its normal file tools, re-reads it, and runs sm handoff, one step in one turn. sm checks the note still covers what it knows, takes it into its own database, and deletes the draft. The successor starts with the note in its first prompt, followed by your own messages to that line of work, word for word, the one thing a summary always blurs. You find the note in the agent's existing Docs list on the app and the web. It opens in the in-app reader, with no new screen and no app release. sm keeps notes indefinitely, as it keeps messages.

Handoff
When an agent's context fills up, sm asks it to stop. It writes down where the work stands and runs sm handoff. sm then starts a fresh agent of the same kind in the same worktree, moves the tickets, PRs and pending wakes onto it, and retires the old one. The old agent is the predecessor; the new one is the successor. Its name gains -h2, -h3, …
Handoff note
What the predecessor writes for the successor. Today it is a link to a PR or ticket comment, or a path to a file anywhere on disk. sm never reads the file. It only passes the path along.
Line of work
An agent and all its successors, for example far-2221 → far-2221-h2. The line ends when its latest agent retires without a successor.
Compaction
What Claude Code and Codex do when one agent's context fills up. The tool has the model summarise the conversation, then restarts that same agent on the summary. A handoff does the same job, except that a fresh agent takes over.
Worktree root
~/worktrees, the folder that holds every agent's worktree.

The second row is the lesson the current design misses. The tool keeps the user's words itself and never trusts the summary to restate them. sm can do better than Codex here, because sm knows which messages came from you. For far-2221 that is under 1 KB, and the 20,000-token cap almost never binds.

How a handoff runs

What the agent sees. sm writes the draft before it asks, so the ask names the file and one command:

[sm context management] Your context is at 36%. Stop at a logical point. sm will move your
claims (ticket #2221, PR #2240) and pending wakes to a fresh agent. Your handoff note is drafted
at /Users/rajesh/worktrees/2221-c2-run-schedule/.sm/handoff.md with what sm knows. Fill in the
rest, re-read it against the checklist at its end, then run `sm handoff` and end your turn.

The path is in the agent's own worktree, where it already writes files freely, so no permission prompt fires. The .sm/ folder is hidden from git, so it never shows up in a commit or blocks worktree cleanup. An agent that has to fix its note does it the normal way, with targeted edits, and never retypes it.

The draft has six sections, each with a one-line hint: where the work stands; decisions and dead ends; your instructions, especially any that came through the terminal; what is running and what to do when it lands; next steps in order; and files and data outside git. sm fills in what it knows. The "where the work stands" section lists the tickets, PRs and branch. The "running" section lists each queue job, pending review and child, each followed by a blank for the agent: what to do when it lands. A checklist at the end asks the agent to read the note as if it had never seen the work. Is anything here only clear from your memory? Is anything missing that only you know, such as a promise to Rajesh, a workaround or a flaky test? Appendix B has the text.

sm's check. When the agent runs sm handoff, sm makes sure the note still mentions everything sm pre-filled. If the agent deleted an item, sm refuses once and names it:

Your note does not mention: queue job 2221-c2-smoke.
Say what the successor should do about it, then run `sm handoff` again.
(Run it again unchanged to hand off anyway.)

What the successor sees. It starts with one prompt: sm's usual brief (what it now holds, where it works), then the note, then your messages to the line:

[sm handoff] You are taking over from far-2221 (6f7e5a31), which stopped at 36% context.
Working directory: ~/worktrees/2221-c2-run-schedule (branch ticket/2221-c2-run-schedule)
You now hold: ticket #2221, PR #2240
…
=== Handoff note from far-2221 ===
# Handoff note — far-2221 (6f7e5a31), 2026-10-19
## Where the work stands …
=== Rajesh's messages to this line, verbatim (oldest first) ===
[2026-10-18 17:52 · terminal] Ensure you have all the code needed to run …

sm hands that prompt to the successor at launch, the way sm spawn delivers a large brief, not by typing it into the terminal. sm handoff show prints the same note and messages again, for an agent that later needs to re-read them.

Where you see the note

The note joins the place where an agent's documents already appear. The expanded agent on Watch and each card on History have a Docs list. Today it holds the docs the agent published, and a tap opens the in-app reader. The note becomes one more row in that list:

  • on the predecessor's History card: Handoff note → far-2221-h2;
  • on the successor's Watch entry: Handoff note from far-2221.

The row looks like every other doc row, and the reader shows the note like every other doc. sm serves both the row and the page, so neither the app nor the web page needs a new element, and the app needs no release. I considered three other places and rejected them. The Inbox would add three items a day you did not ask for. A link on the context-ring line would add a new kind of control to a crowded row. A separate screen would hide the note from where you look at the agent.

Loose files beside the note

The far-2221 agent also left ~/worktrees/2221_scripts/, seven scripts and logs that a queue job ran. Custody of notes does not stop that. Nothing cleans the worktree root because nothing owns it. I recommend the rule you set for ~/Artifacts in #1588. sm's hourly worktree check lists every entry in ~/worktrees that is not a git checkout on the existing leftover worktrees page. It deletes such an entry 14 days after first seeing it, unless you keep it, it changed in those 14 days, or a running queue job uses it.

A. The sm handoff command and the draft

sm handoff                   # submit the draft (creating it first if missing)
sm handoff --link <url>      # unchanged
sm handoff --path <file>     # import a file; same as the positional form
sm handoff <file>
sm handoff show [<session>] [--line]

A.1 Draft location. The draft is <working dir>/.sm/handoff.md, where the working dir is the session's registered working_dir, never the shell's cwd, which drifts. Whoever writes it (A.2) creates .sm/. When the working dir is inside a git work tree, the writer also appends the line .sm/ to the file that git rev-parse --git-path info/exclude names, unless the line is already there. That file is local to the repository, never committed, and shared by all its worktrees, so this happens once per repository.

A.2 Who writes the draft, and when. sm writes it before it delivers any ask, so the ask can name it:

AskWriter
Context threshold (1651 C.1), reminder (C.2), Hand off now (C.4)The server. It writes directly for the primary node. For another node, it writes over that node's existing ssh connection (nodes.registry.<node>.ssh, the connection sm already uses for tmux there). If the write fails, sm sends the E.1b fallback ask instead, and the CLI writes the draft on the agent's first sm handoff.
Review request (1651 C.3), printed by sm request-codex-review or sm doc publish --reviewThat CLI, which runs where the agent runs. The server returns the pre-fill (B) in the response, beside handoff_ask.
Voluntary (the agent runs sm handoff unasked, with no draft)The CLI, on that run. It prints E.3 and exits 0. This is the only case that takes two runs.

An existing draft is never overwritten. A reminder whose draft already exists names it again. When an ask is withdrawn (1651 C.5), sm deletes the draft only if it is still byte-identical to what sm wrote; otherwise it leaves it for the next ask. At retire, sm deletes any draft still present (primary node, or over ssh).

A.3 sm handoff with no arguments.

DraftOutcome
MissingFetch the pre-fill from GET /sessions/{id}/handoff-draft, write it (A.1), print E.3, exit 0. The handoff state does not change.
Byte-identical to what sm wrote (the server keeps its sha256 on the handoff record as draft_sha256)Exit 2: The note at <path> is still sm's draft. Fill it in, then run sm handoff again.
ChangedStrip HTML comments (<!-- … -->), trim, check the A.5 limits, and POST note: {"kind":"text","value":…,"source":"draft"}. On 200, delete the draft, delete .sm/ if empty, print E.4. On 409 incomplete (A.4), print the server's E.5 text, keep the draft, exit 3.

A.4 Completeness check (server). The items are the ones the pre-fill lists (B): active ticket claims (ticket #N), active PR claims (PR #N), unfinished queue jobs whose requester_session_id or notify_session_id is the session (queue job <label>, or the job id when there is no label), open review requests the session made (review of PR #N) and live children (child <name>). The server computes them at submission time, so an item that appeared after the draft was written counts too. An item is mentioned when the note contains its number (#N, or a bare N on a word boundary), its label, its job id or its name, ignoring case. If any item is unmentioned and the handoff record has no completeness_warned_at, the server sets that field, changes nothing else, and returns 409 {"error":"incomplete","missing":[…],"message":"<E.5>"}. Any later submission, changed or not, skips the check. A link note is never checked: sm does not read links. Reaching accepted clears the field.

A.5 Limits apply to drafts and --path files alike. The note must be valid UTF-8 and at most 262,144 bytes after comment stripping. The errors are handoff note is not valid UTF-8 and handoff note is <n> bytes; the limit is 262144. The largest note on disk today is 7.7 KB.

A.6 --path. The CLI checks the path names an existing regular file, canonicalizes it, reads it, applies A.5, and sends note: {"kind":"text","value":…,"source":"file","source_path":"<path>"}. HTML comments are kept here, since the file is the agent's own. A.4 applies. On 200 the CLI removes the original, unless one of these holds. In each case it leaves the file and says why (E.4):

  • git tracks it: git -C <dir> ls-files --error-unmatch -- <file> exits 0;
  • its size or mtime changed since the read;
  • the unlink fails. The CLI prints the error and still exits 0.

The CLI removes only that file, never a folder. It reports the outcome with POST /sessions/{id}/handoff-note/source {"removed":bool,"reason":string|null}. A --path handoff also deletes an unchanged sm draft, if one exists.

A.7 sm handoff show is for re-reading, for example after the successor's own compaction. The launch prompt (C.4) already carries the same content. With no argument, it shows the note the calling session took over with: its predecessor's. With <session> (an id or exact name), it shows that session's note. --line shows every note in the line, oldest first. It calls GET /sessions/{id}/handoff-note (C.3) and prints the C.4 sections Handoff note and Rajesh's messages, followed by Earlier notes in this line: sm handoff show --line when the line has more than one note. For a link note it prints <name> handed off with a link: <url>, then the messages. With no note at all, it exits 1 with <name> has no handoff note. Any managed session and the owner may call it.

C. The store, routes and persisted shapes

C.1 Table handoff_notes in message_queue.db, next to the existing handoff override tables:

CREATE TABLE handoff_notes (
  session_id    TEXT PRIMARY KEY,   -- the predecessor
  line_id       TEXT NOT NULL,      -- session id of the line's first agent
  sequence      INTEGER NOT NULL,   -- 1, 2, … within the line
  text          TEXT NOT NULL,
  source        TEXT NOT NULL,      -- 'draft' | 'file' | 'import'
  source_path   TEXT,               -- for 'file' and 'import'
  source_removed INTEGER,           -- NULL until reported; 0/1
  source_kept_reason TEXT,
  created_at    TEXT NOT NULL
);
CREATE INDEX handoff_notes_line ON handoff_notes(line_id, sequence);

Line id: follow predecessor_session_id back until a record has none, and take that record's id. Sequence: one more than the line's current maximum. Resubmitting in state accepted (1651 E) replaces the row's text and keeps its sequence.

C.2 Accept. HandoffNote::parse accepts request kinds link and text. It rejects path with 400 sm handoff was updated; run sm handoff again, which only a stale CLI sends. For text, accept_handoff runs A.4, then writes the row and records the note in the same step as the state change. If the row write fails, it returns 500 and the state does not change. The session record's note (1651 A) becomes {"kind":"stored","value":"handoff_notes:<session_id>"}. link is unchanged. Old path records stay readable.

C.3 Read. GET /sessions/{id}/handoff-note[?line=1] returns {"notes":[{"session":{id,name},"successor":{id,name}|null,"sequence","kind","text"?,"url"?,"source","source_path","created_at"}],"owner_messages":[…D…],"line_note_count"}. Without line, notes holds the one note. The route resolves its target as A.7 describes, so the CLI can send the caller's own id. Any managed session and the owner may read it.

C.4 Successor launch prompt (changes 1651 F.4 and the order of 1651 G). sm creates the successor's session record without starting its runtime, runs G (moving the work), then starts the runtime with the launch prompt below as its initial prompt, through the atomic spawn-brief transport[11]: persisted to spawn-briefs/<sha256>.md and fed on stdin. The successor still never acts before it holds the work, and nothing is typed into its terminal. If the create path cannot defer the runtime start, ticket 1 splits it into "create record" and "start runtime". On restart, a record in state transferring whose runtime never started gets it started once G completes. Two cases keep today's path, where the brief is queued as the first message, with the E.6 line in place of the two sections: remote nodes, where the atomic transport is unsupported, and providers whose launch takes no initial prompt. The launch prompt:

<1651 F.4 lines, without its "Handoff note:" line and its closing "Read the handoff note first" line>

The messages section is omitted when there are none.

D. Rajesh's messages

owner_messages in C.3 covers every session in the line, newest first, taking messages until the next one would push the total past 20,000 tokens (counted as bytes ÷ 4). It returns them oldest first. Each entry is {"at","source":"terminal"|"inbox reply","session":{id,name},"text"}. There are two sources:

  1. Inbox replies: owner_message_replies.body where delivered_to_session_id is in the line.
  2. Terminal input: user-role text inputs in each session's provider transcript (transcript_path on the record). For Claude these are type:"user" records whose content is text, not tool_result, and type:"queue-operation" records with operation:"enqueue". For codex-fork they are the rollout's user-message events. A transcript input is dropped when any of these holds:
    • it starts with [Input from: , [sm or < (sm sends, sm notices, tool-injected tags);
    • after trimming and collapsing whitespace, it equals the text of a message_queue row delivered to that session, the delivered text of an Inbox reply (already counted from source 1), the session's spawn brief, or its handoff brief;
    • an enqueue and a later user record carry the same text, in which case only one is kept.

Providers without a readable transcript (codex-app, opencode) contribute only source 1. A transcript that fails to parse contributes nothing and logs a warning, and show still prints the note. The far-2221 line today yields one terminal message: "Ensure you have all the code needed to run …".

F. Retention

sm keeps handoff_notes rows indefinitely, as it keeps messages. They are small (the largest today is 7.7 KB) and worth mining later. A daily background task (an existing daily sweep may host it) removes pending import originals (G step 3) once their line has ended. A line has ended when its latest agent (follow successor_session_id forward) is stopped or retired with no successor. The two August files in <state dir>/handoffs/, left by the old /clear handoff, are imported as notes if a record names them, and then ticket 1 deletes that folder.

J. Worktree-root sweep

J.1 What counts. Entries directly inside work_claims.worktree_root[7] (~/worktrees). An entry containing .git (a file or a folder) is a checkout, which the existing cleanup owns. Names beginning with . are ignored. Everything else is a loose entry.

J.2 When. On each hourly cleanup pass (RECHECK_INTERVAL[8]), sm upserts loose entries into a loose_entries table in the work-claims database. Its columns are path (primary key), first_seen_at, last_mtime (the newest mtime inside, walked to depth 4), deleted_at and deleted_reason.

J.3 Delete rule. sm removes the entry (rm -rf of that one path) when all of these hold: it was first seen more than 14 days ago; the newest mtime inside is more than 14 days old; no sm worktree keep names it; no unfinished queue job has its cwd inside it or names it as a prefix of any argv element; and no live session's working directory is inside it. If any check fails, sm re-checks it next hour. The first live pass deletes nothing.

J.4 Page. GET /worktrees/leftover gains "loose":[{path,size_bytes,first_seen_at,deletes_after,blocked_by:null|"keep"|"recent change"|"queue job <id>"|"session <name>"}]. The page lists them under Loose files in ~/worktrees with the existing Keep and Delete buttons. POST /worktrees/delete accepts a loose path and skips the git checks for it.

Z. FAQ

Why a draft file in the worktree and not stdin? A heredoc is write-once: to fix one line, the agent retypes the whole note. A file can be re-read and edited in place, and that edit-and-review loop is what the completeness check relies on. Writing inside the worktree raises no permission prompt for any provider, and .sm/ is excluded from git, so the draft never reaches a commit and never blocks worktree cleanup. sm deletes it on submission.

Why does sm write the draft before asking, rather than on the first sm handoff? The handoff is coming, so a second command and a second turn would buy nothing. Pre-filling also hands the agent sm's facts (claims, jobs, reviews, children) to annotate instead of recall.

How does sm write a draft for an agent on node macbook? Over the ssh connection it already uses for that node's tmux. If that fails, the ask falls back to E.1b, and the CLI, which always runs where the agent runs, writes the draft.

What if the agent's working directory is a data folder, such as ~/Artifacts/2203_chains? The draft sits there until submission, then sm deletes it. A withdrawn ask deletes an unchanged draft, and retire deletes any draft still present.

Why a launch prompt and not a typed first message? Notes run to 8 KB, plus up to 20,000 tokens of your messages. Typing that into a terminal is the fragile path. The atomic spawn-brief transport already delivers large briefs on stdin at launch.

Why only Rajesh's messages? Messages from sm and other agents are mostly wakes and status. Their facts (claims, jobs, reviews) already reach the successor through 1651's brief, and the note covers their meaning. Rajesh's words are the one input a summary distorts.

Why keep --path? Repo instruction files and old habits mention handoff files. Refusing would make a high-context agent retry. Importing costs nothing.

Why not snapshot --link notes? PR and ticket comments are durable, and GitHub is their source of truth.

Could the worktree-root sweep delete something a running job needs? J.3 checks unfinished queue jobs (cwd and argv), live sessions' working directories, and any change within 14 days. An entry also stays listed on the page for 14 days before deletion, and Keep stops it.

Is the completeness check easy to game? Yes: an agent can mention "PR #2240" with nothing useful about it. The check exists to catch forgetting, not to grade the note. It costs one round at most.
