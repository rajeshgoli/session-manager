2328 — sm keeps the handoff note

Author: sm-2328 c6f0a143 · Ticket #2328 · Revision 2 · 2026-10-19

Memo

I recommend that sm own the handoff note from start to finish, and that the agent's part be the thing models do best: fill in a file. When sm asks for a handoff, the agent runs sm handoff. sm puts a template at .sm/handoff.md in the agent's worktree. The agent fills it in with its normal file tools, re-reads it, and runs sm handoff again. sm checks the note against what sm already knows: the PRs the agent holds, its running queue jobs and its pending reviews. It asks once about anything the note leaves out. Then it moves the note into its own database and deletes the draft. The successor runs sm handoff show and gets the note, followed by your own messages to that line of work, word for word, the one thing a summary always blurs. You find the note in the agent's existing Docs list on the app and the web. It opens in the in-app reader, with no new screen and no app release. sm deletes notes 90 days after the line of work ends.

Handoff
When an agent's context fills up, sm asks it to stop. It writes down where the work stands and runs sm handoff. sm then starts a fresh agent of the same kind in the same worktree, moves the tickets, PRs and pending wakes onto it, and retires the old one. The old agent is the predecessor; the new one is the successor. Its name gains -h2, -h3, …
Handoff note
What the predecessor writes for the successor. Today it is a link to a PR or ticket comment, or a path to a file anywhere on disk. sm never reads the file. It only passes the path along.
Line of work
An agent and all its successors, for example far-2221 → far-2221-h2. The line ends when its latest agent retires without a successor.
Compaction
What Claude Code and Codex do when one agent's context fills up. The tool has the model summarise the conversation, then restarts that same agent on the summary. A handoff does the same job, except that a fresh agent takes over.
Worktree root
~/worktrees, the folder that holds every agent's worktree.

The second row is the lesson the current design misses. The tool keeps the user's words itself and never trusts the summary to restate them. sm can do better than Codex here, because sm knows which messages came from you. How a handoff runs

What the agent sees. sm's ask gets shorter. It names one command and lets that command explain the rest:

[sm context management] Your context is at 36%. Stop at a logical point. sm will move your
claims (ticket #2221, PR #2240) and pending wakes to a fresh agent. Run `sm handoff`; it tells
you what to write. (If you already posted a handoff on your PR or ticket: `sm handoff --link <url>`.)

The first sm handoff prints:

Write your handoff note in /Users/rajesh/worktrees/2221-c2-run-schedule/.sm/handoff.md
(sm put a template there). Re-read it once against the checklist at its end, then run
`sm handoff` again.

The path is in the agent's own worktree, where it already writes files freely, so no permission prompt fires. The .sm/ folder is hidden from git, so it never shows up in a commit or blocks worktree cleanup. An agent that has to edit its note does it the normal way, with targeted edits, and never retypes it.

The template asks for six things, each with a one-line hint: where the work stands; decisions and dead ends; your instructions, especially any that came through the terminal; what is running and what to do when it lands; next steps in order; and files and data outside git. A checklist at the end asks the agent to read the note as if it had never seen the work. Is anything here only clear from your memory? Is anything missing that only you know, such as a promise to Rajesh, a workaround or a flaky test? Appendix B has the text.

sm's check. On the second run, sm compares the note with what it holds for the agent: tickets and PRs, unfinished queue jobs, pending review requests and children. If the note omits any, sm refuses once:

Your note does not mention: queue job 2221-c2-smoke, PR #2240.
Say what the successor should do about each, then run `sm handoff` again.
(Run it again unchanged to hand off anyway.)

The far-2221 note would have passed, since it named both running jobs and what to check when each lands. This is a mechanical check, not a judgement, and it costs the agent one re-read at most.

What the successor sees. Its first message no longer carries a path:

[sm handoff] You are taking over from far-2221 (6f7e5a31), which stopped at 36% context.
Handoff note: run `sm handoff show` (the note, then Rajesh's messages to this line, verbatim).

Where you see the note

The note joins the place where an agent's documents already appear. The expanded agent on Watch and each card on History have a Docs list. Today it holds the docs the agent published, and a tap opens the in-app reader. The note becomes one more row in that list:

  • on the predecessor's History card: Handoff note → far-2221-h2;
  • on the successor's Watch entry: Handoff note from far-2221.

The row looks like every other doc row, and the reader shows the note like every other doc. sm serves both the row and the page, so neither the app nor the web page needs a new element, and the app needs no release. I considered three other places and rejected them. The Inbox would add three items a day you did not ask for. A link on the context-ring line would add a new kind of control to a crowded row. A separate screen would hide the note from where you look at the agent.

Loose files beside the note

The far-2221 agent also left ~/worktrees/2221_scripts/, seven scripts and logs that a queue job ran. Custody of notes does not stop that. Nothing cleans the worktree root because nothing owns it. I recommend the rule you set for ~/Artifacts in #1588. sm's hourly worktree check lists every entry in ~/worktrees that is not a git checkout on the existing leftover worktrees page. It deletes such an entry 14 days after first seeing it, unless you keep it, it changed in those 14 days, or a running queue job uses it.

A. The sm handoff command

sm handoff                   # draft flow: create the draft, or submit it
sm handoff --link <url>      # unchanged
sm handoff --path <file>     # import a file; same as the positional form
sm handoff <file>
sm handoff show [<session>] [--line]

A.1 Draft location. The draft is <working dir>/.sm/handoff.md, where the working dir is the session's registered working_dir, which the CLI fetches from the server. It does not use the shell's cwd, which drifts. On the first run the CLI creates .sm/. When the working dir is inside a git work tree, it appends the line .sm/ to the file that git rev-parse --git-path info/exclude names, unless the line is already there. That file is local to the repository, never committed, and shared by all its worktrees, so this happens once per repository.

A.2 sm handoff with no arguments. The CLI decides by the draft's state:

DraftOutcome
MissingWrite the template (B) and print E.3. Exit 0. Nothing goes to the server, and the handoff state does not change.
Byte-identical to the template, or under 200 characters once HTML comments and Markdown headings are removedExit 2: The note at <path> is still the template. Fill it in, then run sm handoff again.
Filled inStrip HTML comments (<!-- … -->), trim, check the A.4 limits, and POST note: {"kind":"text","value":…,"source":"draft"}. On 200, delete the draft, delete .sm/ if it is empty, and print E.4. On 409 incomplete (A.3), print the server's E.5 text, keep the draft, and exit 3.

A.3 Completeness check (server). On a text or file note, the server lists what it holds for the session:

  • active ticket claims, as ticket #N;
  • active PR claims, as PR #N;
  • unfinished queue jobs whose requester_session_id or notify_session_id is the session, as queue job <label> (or the job id when there is no label);
  • open review requests the session made, as review of PR #N;
  • live children, as child <name>.

An item counts as mentioned when the note contains its number (#N or a bare N on a word boundary), its label, its job id, or its name, ignoring case. If any item is unmentioned and the handoff record has no completeness_warned_at, the server sets completeness_warned_at, changes nothing else, and returns 409 {"error":"incomplete","missing":[…],"message":"<E.5>"}. Any later submission, changed or not, skips the check. A link note is never checked: sm does not read links. A handoff that reaches accepted clears the field.

A.4 Limits apply to drafts and --path files alike. The note must be valid UTF-8 and at most 262,144 bytes after comment stripping. The errors are handoff note is not valid UTF-8 and handoff note is <n> bytes; the limit is 262144. The largest note on disk today is 7.7 KB.

A.5 --path. The CLI checks the path names an existing regular file, canonicalizes it, reads it, applies A.4, and sends note: {"kind":"text","value":…,"source":"file","source_path":"<path>"}. HTML comments are kept here, since the file is the agent's own. A.3 applies. On 200 the CLI removes the original, unless one of these holds. In each case it leaves the file and says why (E.4):

  • git tracks it: git -C <dir> ls-files --error-unmatch -- <file> exits 0;
  • its size or mtime changed since the read;
  • the unlink fails. The CLI prints the error and still exits 0.

The CLI removes only that file, never a folder. It reports the outcome with POST /sessions/{id}/handoff-note/source {"removed":bool,"reason":string|null}.

A.6 sm handoff show. With no argument, it shows the note the calling session took over with, which is its predecessor's. With <session> (an id or exact name), it shows that session's note. --line shows every note in the line, oldest first. It calls GET /sessions/{id}/handoff-note (C.3) and prints:

# Handoff note from far-2221 (6f7e5a31), 2026-10-19 01:27 UTC
<note text>

---
# Rajesh's messages to this line, verbatim (oldest first)
[2026-10-18 17:52 UTC · terminal · far-2221] Ensure you have all the code needed to run …
[2026-10-18 23:10 UTC · inbox reply · far-2221] …

---
Earlier notes in this line: sm handoff show --line

The messages section is omitted when there are none. The last line appears only when the line has more than one note. When a session's note is a link, the output is <name> handed off with a link: <url> followed by the messages section. With no note at all, it exits 1 with <name> has no handoff note. A pruned note gives E.7. Any managed session and the owner may call it.

C. The store, routes and persisted shapes

C.1 Table handoff_notes in message_queue.db, next to the existing handoff override tables:

CREATE TABLE handoff_notes (
  session_id    TEXT PRIMARY KEY,   -- the predecessor
  line_id       TEXT NOT NULL,      -- session id of the line's first agent
  sequence      INTEGER NOT NULL,   -- 1, 2, … within the line
  text          TEXT NOT NULL,
  source        TEXT NOT NULL,      -- 'draft' | 'file' | 'import'
  source_path   TEXT,               -- for 'file' and 'import'
  source_removed INTEGER,           -- NULL until reported; 0/1
  source_kept_reason TEXT,
  created_at    TEXT NOT NULL,
  pruned_at     TEXT                -- set by F; text is then ''
);
CREATE INDEX handoff_notes_line ON handoff_notes(line_id, sequence);

Line id: follow predecessor_session_id back until a record has none, and take that record's id. Sequence: one more than the line's current maximum. Resubmitting in state accepted (1651 E) replaces the row's text and keeps its sequence.

C.2 Accept. HandoffNote::parse accepts request kinds link and text. It rejects path with 400 sm handoff was updated; run sm handoff again, which only a stale CLI sends. For text, accept_handoff runs A.3, then writes the row and records the note in the same step as the state change. If the row write fails, it returns 500 and the state does not change. The session record's note (1651 A) becomes {"kind":"stored","value":"handoff_notes:<session_id>"}. link is unchanged. Old path records stay readable.

C.3 Read. GET /sessions/{id}/handoff-note[?line=1] returns {"notes":[{"session":{id,name},"successor":{id,name}|null,"sequence","kind","text"?,"url"?,"source","source_path","created_at","pruned_at"}],"owner_messages":[…D…],"line_note_count"}. Without line, notes holds the one note. The route resolves its target as A.6 describes, so the CLI can send the caller's own id. Any managed session and the owner may read it.

C.4 Successor brief (1651 F.4). The Handoff note: line is E.6 for stored and link notes alike. For a link note, the URL is printed as well: Handoff note: <url> — and run `sm handoff show` for Rajesh's messages to this line. 1651 F.4's other lines are unchanged.

D. Rajesh's messages

owner_messages in C.3 covers every session in the line, newest first, taking messages until the next one would push the total past 20,000 tokens (counted as bytes ÷ 4). It returns them oldest first. Each entry is {"at","source":"terminal"|"inbox reply","session":{id,name},"text"}. There are two sources:

  1. Inbox replies: owner_message_replies.body where delivered_to_session_id is in the line.
  2. Terminal input: user-role text inputs in each session's provider transcript (transcript_path on the record). For Claude these are type:"user" records whose content is text, not tool_result, and type:"queue-operation" records with operation:"enqueue". For codex-fork they are the rollout's user-message events. A transcript input is dropped when any of these holds:
    • it starts with [Input from: , [sm or < (sm sends, sm notices, tool-injected tags);
    • after trimming and collapsing whitespace, it equals the text of a message_queue row delivered to that session, the delivered text of an Inbox reply (already counted from source 1), the session's spawn brief, or its handoff brief;
    • an enqueue and a later user record carry the same text, in which case only one is kept.

Providers without a readable transcript (codex-app, opencode) contribute only source 1. A transcript that fails to parse contributes nothing and logs a warning, and show still prints the note. The far-2221 line today yields one terminal message: "Ensure you have all the code needed to run …".

F. Retention

Once a day, a background task (an existing daily sweep may host it) prunes every handoff_notes row whose line ended more than 90 days ago. Pruning sets text = '' and pruned_at, keeping the row so the history still lists the handoff. A line has ended when its latest agent (follow successor_session_id forward) is stopped or retired with no successor. The end time is that agent's retire or stop time. The same task removes pending import originals (G step 3) whose line has ended. HANDOFF_NOTE_RETENTION_DAYS = 90 is a constant, not a setting. The two August files in <state dir>/handoffs/, left by the old /clear handoff, are deleted by ticket 1, together with that folder.

G. Deploy-time import

On first start after ticket 1 deploys, sm runs this once, marked by a top-level key handoff_notes_imported_at in the session store. For each session record whose note has kind path and whose file exists:

  1. Insert a handoff_notes row with source = 'import', under that record's line. Several records that name one file (far-2170 and far-2170-h2) produce one row, attached to the latest of them. The earlier record's text was already overwritten.
  2. Rewrite the record's note to kind stored.
  3. Remove the original under A.5's git rule if the line has ended. Otherwise add it to handoff_note_sources_pending in the session store, and F removes it once the line ends.

J. Worktree-root sweep

J.1 What counts. Entries directly inside work_claims.worktree_root[7] (~/worktrees). An entry containing .git (a file or a folder) is a checkout, which the existing cleanup owns. Names beginning with . are ignored. Everything else is a loose entry.

J.2 When. On each hourly cleanup pass (RECHECK_INTERVAL[8]), sm upserts loose entries into a loose_entries table in the work-claims database. Its columns are path (primary key), first_seen_at, last_mtime (the newest mtime inside, walked to depth 4), deleted_at and deleted_reason.

J.3 Delete rule. sm removes the entry (rm -rf of that one path) when all of these hold: it was first seen more than 14 days ago; the newest mtime inside is more than 14 days old; no sm worktree keep names it; no unfinished queue job has its cwd inside it or names it as a prefix of any argv element; and no live session's working directory is inside it. If any check fails, sm re-checks it next hour. The first live pass deletes nothing.

J.4 Page. GET /worktrees/leftover gains "loose":[{path,size_bytes,first_seen_at,deletes_after,blocked_by:null|"keep"|"recent change"|"queue job <id>"|"session <name>"}]. The page lists them under Loose files in ~/worktrees with the existing Keep and Delete buttons. POST /worktrees/delete accepts a loose path and skips the git checks for it.

K. Doc theme from Appearance

  • Web reader (web/reader.js, loaded()). After the frame loads, set win.document.documentElement.dataset.theme to light or dark. The value comes from localStorage['sm-theme'], where system resolves through matchMedia('(prefers-color-scheme: dark)'). Re-apply when the outer document's data-theme changes (the attribute is already observed for the terminal) and when the media query changes. The frame is same-origin and unsandboxed, so this works today.
  • App reader (DocReader.kt). After the page loads, run document.documentElement.dataset.theme='dark'. The app has only a dark theme.
  • Markdown shell (owner_docs.rs). Key its colours on :root[data-theme=dark], falling back to prefers-color-scheme when no theme is set.
  • Memo template (docs/memo_template.html). Remove the toggle button and its script. Keep the :root[data-theme="dark"] token block, and add the same tokens under @media (prefers-color-scheme: dark) { :root:not([data-theme]) { … } } so the file still follows the OS when opened outside sm. Existing docs keep their own button until they are next revised. The reader's theme wins either way, because the button sets the same attribute.

Z. FAQ

Why a draft file in the worktree and not stdin? A heredoc is write-once: to fix one line, the agent retypes the whole note. A file can be re-read and edited in place, and that edit-and-review loop is what the completeness check relies on. Writing inside the worktree raises no permission prompt for any provider, and .sm/ is excluded from git, so the draft never reaches a commit and never blocks worktree cleanup. sm deletes it on submission.

Why does the CLI, not the server, create and delete the draft? Agents on node macbook have worktrees the server cannot see. The CLI always runs where the agent runs.

What if the agent's working directory is a data folder, such as ~/Artifacts/2203_chains? The draft sits there between the two runs, then sm deletes it. If the agent never submits (the ask is withdrawn and it retires), the draft can linger in a non-git folder. That is rare, and the folder's own expiry covers it.

Why not inline the note in the successor's first message? sm delivers that message by typing into a terminal. Notes run to 8 KB, and long terminal input is the fragile path. sm handoff show costs one command.

Why only Rajesh's messages? Messages from sm and other agents are mostly wakes and status. Their facts (claims, jobs, reviews) already reach the successor through 1651's brief, and the note covers their meaning. Rajesh's words are the one input a summary distorts.

Why keep --path? Repo instruction files and old habits mention handoff files. Refusing would make a high-context agent retry. Importing costs nothing.

Why not snapshot --link notes? PR and ticket comments are durable, and GitHub is their source of truth.

Could the worktree-root sweep delete something a running job needs? J.3 checks unfinished queue jobs (cwd and argv), live sessions' working directories, and any change within 14 days. An entry also stays listed on the page for 14 days before deletion, and Keep stops it.

Is the completeness check easy to game? Yes: an agent can mention "PR #2240" with nothing useful about it. The check exists to catch forgetting, not to grade the note. It costs one round at most.
