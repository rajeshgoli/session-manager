2328 — sm keeps the handoff note

Author: sm-2328 c6f0a143 · Ticket #2328 · Revision 1 · 2026-10-18

Memo

I recommend that sm take custody of every handoff note written as a file. The agent gives the note to sm with one command, sm handoff <<'EOF' … EOF, the same heredoc habit agents already use for sm send rajesh. sm saves the note in its own state folder, points the successor at that copy, shows it to you on sm.rajeshgo.li, and deletes it 90 days after the line of work ends. The agent no longer picks a location, so it can no longer pick a bad one. The agent's work actually shrinks: today it writes a file and then runs sm handoff --path, two steps; it will run one command. Handoffs posted as a PR or ticket comment (sm handoff --link) are durable already and stay exactly as they are.

Handoff
When an agent's context fills up, sm asks it to stop. It writes down where the work stands and runs sm handoff. sm then starts a fresh agent of the same kind in the same worktree, moves the tickets, PRs and pending wakes onto it, and retires the old one. The old agent is the predecessor; the new one is the successor. Its name gains -h2, -h3, …
Handoff note
What the predecessor writes for the successor. Today it is either a link to a PR or ticket comment, or a path to a file anywhere on disk. sm never reads the file. It only passes the path along.
Line of work
An agent and all its successors, for example far-2221 → far-2221-h2. The line ends when its latest agent retires without a successor.
sm state folder
~/.local/share/claude-sessions/, where sm keeps its databases. It sits outside every checkout, so no cargo clean or worktree cleanup touches it.
Worktree root
~/worktrees, the folder that holds every agent's worktree.
Artifact root
~/Artifacts, the fractal-algo-rust data folder that sm's managed-artifacts feature (#1588) tracks. Each subfolder has a record of who owns it and when it expires.

What goes wrong today

I read every handoff sm has recorded: 64 handoffs between 29 Sep and 19 Oct. 46 point at a PR comment (37) or a ticket comment (9). Those live on GitHub and are fine. The other 18 point at files, and every file location has a problem.

How it works after the change

What the agent sees. sm's ask changes from offering three places to offering one command, plus the link form for an agent that already posted on its PR:

What the successor sees. Its first message names sm's copy, and the command that prints it. If the line has earlier notes, it also names the folder that holds them:

Handoff note: ~/.local/share/claude-sessions/handoffs/6f7e5a31/1-far-2221.md (or run: sm handoff show)

Read the handoff note first, then continue the work.

What you see. Today each agent card on sm.rajeshgo.li shows a line such as → far-2221-h2 after a handoff. That line becomes a link to the note. On the successor's card, took over from far-2221 links to the same note. A note given as a link opens the PR or ticket comment. The handoff note is the best status summary an agent ever writes, and today you can reach it only by opening a terminal.

What this memo does not change

  • When sm asks for a handoff, the thresholds, and how work moves to the successor (spec specs/1651_context_handoff.html). Only the note's storage and the wording of the ask and reminder change.
  • Other files an agent's work produces. Data belongs in ~/Artifacts under #1588's rules. Code belongs in git. A Claude agent's private scratch folder under /private/tmp is outside sm's control. The far-2221 agent ran a queue job inside its scratch folder, and its successor depends on it. If that pattern recurs, it gets its own ticket. Nothing here makes it worse.

A. The sm handoff command

sm handoff <<'EOF'        # note on stdin (new, preferred)
…note text…
EOF
sm handoff -               # same: note on stdin
sm handoff --link <url>    # unchanged
sm handoff --path <file>   # kept: sm copies the file, then removes the original
sm handoff <file>          # same as --path <file>
sm handoff show [<session>] # print a stored note (new)

A.1 Choosing the form. --link and --path are mutually exclusive with each other and with a positional argument, as today. With no argument, or the positional -, the note comes from stdin. The stdin read reuses the rule of read_send_text_from[1]:

InputOutcome
No argument, stdin is a terminalExit 2: sm handoff needs the note on stdin (sm handoff <<'EOF' … EOF) or --link <url>. Nothing is sent.
Stdin empty or only whitespaceExit 2: handoff note read from stdin is empty; nothing was handed off.
Stdin larger than 262,144 bytesExit 2: handoff note is <n> bytes; the limit is 262144. The largest note on disk today is 7.7 KB.
Stdin not valid UTF-8Exit 2: handoff note is not valid UTF-8.
ValidPOST with note: {"kind":"text","value":"<the text, unmodified>"}.

A.2 --path. The CLI checks the path names an existing regular file, as today, and canonicalizes it. It now also reads the file, applying the same size and UTF-8 limits as A.1 (messages say file instead of stdin). It refuses a path inside the note store (B.1) with that file is already in sm's note store; use sm handoff show to read it. It sends note: {"kind":"file","value":"<file text>","source_path":"<canonical path>"}. The CLI reads the file, not the server, so a handoff from an agent on another machine (node macbook) works the same way.

A.3 After a successful POST with --path the CLI removes the original, unless one of these holds. In each case it leaves the file and adds a line to its output (D.4).

  • Git tracks the file: git -C <dir> ls-files --error-unmatch -- <file> exits 0. Example: docs/working/2165_handoff.md committed on a PR branch stays.
  • The file changed between the read and the removal (size or mtime differs). The copy in sm is then stale, so the agent must see the file again.
  • The removal fails (permissions). The CLI prints the error and still exits 0, because the handoff itself succeeded.

Removal uses a plain unlink of that one file. It never removes a folder, even an empty one. An untracked file in a directory that is not a git repository, such as ~/worktrees/2221_HANDOFF.md or ~/Artifacts/2170_shape/HANDOFF.md, is removed.

A.4 sm handoff show [<session>]. This prints a stored note to stdout, verbatim. With no argument, it prints the note this session took over with: the note of its predecessor_session_id. With a session id or exact name, it prints that session's note. It calls GET /sessions/{id}/handoff-note (C.4). It exits 1 with <name> has no stored handoff note when the session has no note, or <name>'s handoff note is a link: <url> for a link note. It is a read: any managed session may call it, and so may the owner.

B. The note store and persisted shapes

B.1 Layout. The store is <state dir>/handoffs/, where the state dir is the parent of paths.state_file. That is the same derivation spawn briefs use[2]; live, it resolves to ~/.local/share/claude-sessions/handoffs/. Inside it:

handoffs/
  <line id>/                      # 0700
    1-<predecessor name>.md       # 0400, the first handoff in the line
    2-<predecessor name>.md       # the second, …
  • Line id is the session id of the line's first agent. sm finds it by following predecessor_session_id back until a record has none. Example: far-2221 is 6f7e5a31, so every note of far-2221, far-2221-h2, … lives in handoffs/6f7e5a31/.
  • Sequence is the number of *.md files already in the folder, plus one. The name is the predecessor's name with any character outside [A-Za-z0-9._-] replaced by _, truncated to 80 bytes.
  • sm writes the file through a temp file in the same folder, fsyncs it, and renames it. A replaced note (1651 E: re-running sm handoff in state accepted) overwrites the same sequence number. It does not take a new one.
  • The two files from August at the top level of handoffs/ come from the old /clear handoff. Ticket 1 deletes them, since their lines ended in August.

B.2 Persisted note in the session record's handoff object (1651 Appendix A). Kinds link and path stay readable for old records. New handoffs write only link or stored:

"note": {
  "kind": "link",   "value": "https://github.com/…#issuecomment-…"
}
"note": {
  "kind": "stored",
  "value": "/Users/rajesh/.local/share/claude-sessions/handoffs/6f7e5a31/1-far-2221.md",
  "source": "stdin" | "/abs/original/path",
  "bytes": 7684,
  "sha256": "…",
  "source_removed": true | false | null     // null for stdin; set by the CLI report, C.3
}

note_value[3] keeps returning value, so the parent notice (1651 D.7) shows the stored path. HandoffNote::parse accepts request kinds link, text and file. It now rejects path with 400 sm handoff was updated; rerun it (the note goes on stdin). Only a stale CLI binary sends path.

C. Server accept, and removing the original

C.1 Accept. accept_handoff[4] keeps every state rule of 1651 E. For kind text or file, it writes the store file (B.1) before it records the note, so an accepted record never names a missing file. Then it records the stored note. A store write failure returns 500 could not save the handoff note: <error>, and the state does not change. The response adds "stored_path".

C.2 Successor brief (1651 F.4). The Handoff note: line becomes:

  • stored: Handoff note: <stored path, with $HOME shown as ~> (or run: sm handoff show)
  • link: unchanged, the URL.
  • old path records: unchanged, the path.

When the line's folder holds more than one note, a new line follows: Earlier notes in this line: <folder>. The brief never inlines the note text. Typing kilobytes into a terminal is the fragile path that 1651 removed.

C.3 Removal report. After A.3, the CLI sends POST /sessions/{id}/handoff-note/source with {"removed": true|false, "reason": "tracked by git" | "changed after sm read it" | "<unlink error>" | null}. The server sets source_removed. If the report never arrives, the field stays null, which is harmless. It exists so the web page (I) can say "original kept: tracked by git".

C.4 Read route. GET /sessions/{id}/handoff-note returns {"kind","value","text"?,"source","line_id","sequence","accepted_at","predecessor":{id,name},"successor":{id,name}|null}. text is present for stored notes. It is readable by any managed session and by the owner. A note holds work status, not secrets, and agents can read each other's worktrees today.

E. Retention

Once a day, in a background task (an existing daily sweep may host it), sm deletes every line folder under handoffs/ whose line ended more than 90 days ago. A line has ended when its latest agent (follow successor_session_id forward) is stopped or retired and has no successor; the end time is that agent's retire or stop time. A folder whose line id matches no session record is deleted when its newest file is more than 90 days old. Session records keep their note after the prune, so the record still says where the note was. GET /sessions/{id}/handoff-note then returns 410 handoff note deleted after 90 days (line ended <date>). The 90 is a constant, HANDOFF_NOTE_RETENTION_DAYS, not a setting.

F. Deploy-time copy of existing notes

On first start after ticket 1 deploys, sm runs a one-time migration, marked done by a top-level key handoff_notes_migrated_at in the session store. For every session record whose note has kind path and whose file exists:

  1. Copy the file into the store as in B.1, using that record's line. Several records that name the same file (far-2170 and far-2170-h2) get one copy, filed under the latest of them. The earlier record's note is rewritten to the same stored path, because the earlier text was already overwritten.
  2. Rewrite the record's note to kind stored, with source set to the original path.
  3. Remove the original, under A.3's git rule, only if the line has ended. Otherwise, add the path to a pending list, handoff_note_sources_pending, in the session store. The E prune task removes each pending original once its line ends.

H. Local judge rule

Local agents run every shell command past the local judge[5]. Its rule stage allows a fixed set of sm verbs, and it rejects any command containing a newline before the rules run, so a heredoc always falls to the model judge. That judge denied sm handoff for draco on 19 Oct. Two changes:

  • Add ("handoff", "show") to SM_READS.
  • Add a heredoc rule, checked before the newline rejection. It allows a command when the first line is exactly sm handoff <<'TAG' or sm handoff <<"TAG" (a quoted delimiter, so the shell expands nothing in the body), TAG matches [A-Za-z_][A-Za-z0-9_]*, the last line is exactly TAG, and the body has no line equal to TAG. The body is data and is not judged. The single-line forms sm handoff --link <http(s) url> and sm handoff --path <file in the checkout> are also allowed, the latter with the same in-checkout check sm doc publish uses. An unquoted <<TAG still goes to the model judge, because the shell expands $(…) in its body.

The local agent addendum, docs/product/local_agent_addendum.md, gains one line: Hand off with sm handoff <<'EOF' … EOF when sm asks.

J. Worktree-root sweep

J.1 What counts. These are the entries directly inside work_claims.worktree_root[7] (~/worktrees). sm ignores any entry that contains .git (a file or a folder): that is a worktree or a checkout, and the existing cleanup owns it. It also ignores names starting with ., such as .DS_Store. Everything else is a loose entry.

J.2 When. On each hourly cleanup pass (RECHECK_INTERVAL[8]), sm lists the loose entries. It records each new one in a loose_entries table in the work-claims database: path (primary key), first_seen_at, last_mtime (the newest mtime of anything inside, walked to depth 4), deleted_at, deleted_reason.

J.3 Delete rule. sm deletes a loose entry (rm -rf of that one path) when all of these hold:

  • first_seen_at is more than 14 days ago;
  • the newest mtime inside is more than 14 days ago, so nothing has written to it recently;
  • no sm worktree keep names the path. The command already accepts --path, so the keep table covers loose entries too;
  • no unfinished queue job has its cwd inside the path, and none has the path as a prefix of any argv element;
  • no live session has its working directory inside it.

An entry that fails a check is re-checked next hour. The first live pass therefore deletes nothing: every entry is first seen then.

J.4 Page. GET /worktrees/leftover gains a list "loose": {path, size_bytes, first_seen_at, deletes_after, blocked_by: null | "keep" | "recent change" | "queue job <id>" | "session <name>"}. The page shows them under a heading Loose files in ~/worktrees, with the existing Keep and Delete buttons. Delete goes through the existing owner-only POST /worktrees/delete. That route accepts a loose entry path in addition to its current inputs, and skips the git checks for it.

Z. FAQ

Why stdin and not a fixed path the agent writes to, such as $SM_HANDOFF_FILE? A fixed path still leaves the file on the agent's side, with all the cleanup questions this memo removes. It also needs a new environment variable in every provider launch path, and an agent at high context forgets environment variables. Stdin needs nothing new: agents already pipe sm send rajesh <<'EOF' daily, and a heredoc costs the same output tokens as writing the file.

Why not inline the note into the successor's first message? sm delivers that message by typing into the terminal. Notes run to 8 KB, and long terminal input is the fragile path (paste truncation on idle Claude, chunked typing). A path plus sm handoff show costs the successor one read.

Why does the CLI, not the server, read and remove a --path file? Agents on node macbook write files the server cannot see. The CLI always runs where the file is.

Why remove the original right away, not when the successor starts? The copy is already safe in sm, and the successor is told to read sm's copy. A later removal would need the server to reach the agent's machine (see above). It would also leave a window in which an agent edits a file that no longer matters.

Why keep --path at all? Agents carry old habits and old instructions, and repo instruction files (fractal-algo-rust's AGENTS.md) mention handoff files. Refusing --path would make a high-context agent retry. Accepting it and cleaning up costs nothing.

Why does a git-tracked file stay? It is already durable and reviewable, and deleting it would dirty the worktree and could block worktree cleanup.

Should sm snapshot --link notes too? No. PR and ticket comments are durable, and GitHub is the source of truth for them.

Does the managed-artifacts scan need a change? No. With the new wording, agents stop writing notes into artifact folders. The four existing ones are handled by F, and the older unreferenced ones expire with their folders.

Could the worktree-root sweep delete something a running job needs? J.3 checks unfinished queue jobs (cwd and argv), live sessions' working directories, and any change within 14 days. Anything else is listed on the page for 14 days before deletion, and Keep stops it.
