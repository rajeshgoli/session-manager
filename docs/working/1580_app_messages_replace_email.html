1580 — Agents message you in the sm app instead of by email

Author: sm-1580-spec-author 45bbc8a4 · Ticket #1580 · Revision 1

Memo

An agent that needs you runs sm send rajesh with markdown, exactly as it messages another agent. Your phone buzzes with the agent's name and the message title. Tapping it opens the message in the sm app, rendered the way memos render today. You reply in a box at the bottom, or select a sentence and comment on it, or both, and press Send. The agent receives your reply as an ordinary message, the same way it receives an sm send from another agent, and answers you with another sm send rajesh. A doc works the same way: sm doc publish --notify buzzes your phone and opens the doc. If the doc is on an open pull request, your reply is a review and reaches the agent as [sm review], as it does today. If it isn't, your reply reaches the agent as a message, like a reply to sm send.

Email stops being the channel and becomes the safety net. Today sm send rajesh quietly sends email, because email is the only way the server can reach you.1 After this change it goes to the app. The server emails you the same message only if your phone does not confirm it showed the notification within 15 minutes, or if phone notifications are not set up. This is the rule the follow-an-agent feature already uses. sm email rajesh stays available for the times you ask for email.

Nearly everything reuses pieces that already ship: the phone notification sender and its email fallback from following agents, the memo renderer and the select-and-comment reader from doc reviews, and the email path for the fallback. What is new: a stored message with its own reader page, a reply that goes to the agent instead of to GitHub, and a Messages list on each agent's card.

Message
What sm send rajesh creates: markdown text from one agent to you, with a title, stored on the sm server (not in git). It has its own page in the app and on sm web.
Reply
What you send back from a message page or a doc page: your overall text plus any comments on selected passages, sent together with one Send. The agent receives it as one message.
Blocking message
A message the agent marks with --blocking because it cannot continue without you. The notification says "needs you", and the agent shows "Waiting for Rajesh" on its card until you reply or tap Handled.
Notification
The Android notification Google delivers to your phone while the app is closed. It carries only the agent name, the title and a link. The app fetches the message itself from the sm server when you tap.
Confirmation
The phone telling the sm server "I showed this notification". No confirmation within 15 minutes means the phone is off, notifications are muted, or the app is out of date, and the server sends email instead.

How it works

An example round trip

The agent runs:

sm send rajesh --blocking <<'EOF'
# Keep the old fills table or drop it?
The migration copies every row into `fills_v2`. I recommend dropping `fills`
after one week of both tables agreeing. Confirm?

Nothing reads `fills` after the cutover.
EOF
# prints: Sent to rajesh in the sm app (blocking) → https://sm.rajeshgo.li/messages/msg_3f9a2c1d

You comment on the last sentence and type "Otherwise yes, drop it." The agent receives:

[Input from: Rajesh via sm app] Re: "Keep the old fills table or drop it?" (msg_3f9a2c1d)
Otherwise yes, drop it.

> Nothing reads `fills` after the cutover.
The month-end recon does. Check it first.

The first line has the same shape as the header an agent sees on a message from another agent ([Input from: <name> (<id>) via sm send]),2 so the agent treats it as conversation and answers with sm send rajesh. Your comments carry the passage they refer to, as review comments do.

What you see

Where you find messages later

Each agent's card in the app gets a Messages list above Docs: one row per message, newest first, with the title, a state (New, Read, Replied, or Needs you for an unanswered blocking message) and its age. A blocking message you have not answered also shows in the card's existing "Waiting for" line as Waiting for Rajesh · <title>, the way a review request shows Waiting for owner review today. The message page lists your earlier replies under the message, so you can see what you already said. On a laptop, every link in the fallback email and in sm send's output opens the same page on sm web.

A. Message lifecycle and states

A message's owner-facing state is derived from its columns (Appendix C); there is no state column. First match wins.

StateConditionShown as
repliedA reply row with status = 'delivered' or 'undelivered' exists for the messageReplied
handledhandled_at setHandled
needs_youblocking = 1, and the sender session is not retiredNeeds you
readfirst_viewed_at setRead
newotherwiseNew

Unread (for the 5-message cap, Appendix D) means first_viewed_at IS NULL, regardless of state. Viewed means the message page was served to the owner (GET /messages/{id} as HTML, not ?format=json) or the owner replied or tapped Handled, all of which set first_viewed_at if null.

Waiting entry. A message in state needs_you adds to its sender's waiting_on in project_session_obligations3: {kind: "owner_message", id, label: "Rajesh · <title>", since: created_at}. Retirement removes it because the state rule excludes retired senders.

B. CLI

B1. sm send <human>

sm send <human> [--title "..."] [--blocking] [text...]      # or markdown on stdin / "-"
  • Target resolution. Unchanged order up to the fallback: virtual target, then lookup_identifier_exact. Where the CLI today calls send_registered_email_fallback, it first asks GET /humans/{target}. A human match posts POST /humans/{canonical}/messages (Appendix D). No match keeps today's registered-user email fallback (POST /email/send) unchanged. rajesh, rajeshgoli, user and operator all resolve through the existing human aliases.
  • Body. read_send_text as today: positional text, -, or piped stdin. The text is markdown.
  • Title. --title if given (trimmed, 1–120 characters, else error). Otherwise the server derives it (Appendix D2).
  • Flags. --title and --blocking are errors when the resolved target is not a human: --title/--blocking only apply to a message to a person. --urgent and --wait with a human target are errors: --urgent/--wait do not apply to a message to a person; use --blocking.
  • Sender. Requires CLAUDE_SESSION_MANAGER_ID; without it: sm send to a person needs a managed session, so the reply has somewhere to go.
  • Multiple targets. A human inside a comma list (sm send rajesh,maintainer) is an error before anything is sent: send to rajesh on its own, not in a list. resolve_send_target checks GET /humans/{t} for each target first.
  • Output. Sent to <canonical> in the sm app → <reader_url>, with (blocking) after the app when set. A 429 prints the server's detail and exits 1.

B2. sm doc publish

  • New flag --notify. The payload to POST /docs gains notify: bool, true when --notify or --review is given. It combines with every other flag, including --no-pr and --commit.
  • Output gains a second line when a notification was queued: Notified rajesh in the sm app.

B3. sm lookup <human>

Output changes to:

Human recipient: rajesh
Aliases: rajeshgoli, user, operator
Default delivery: sm app (email if the phone does not confirm within 15 minutes)
Explicit email: sm email rajesh
Send markdown with: sm send rajesh [--blocking] <<'EOF' … EOF

B4. Unchanged

sm email, POST /humans/{id}/email, POST /email/send and the inbound email webhook behave exactly as today.

C. Persisted shapes

C1. Retained queue database

The database at sm_send.db_path, where owner_docs lives4. Add these tables with the same migration pattern.

CREATE TABLE owner_messages (
  id                   TEXT PRIMARY KEY,     -- "msg_" + 8 lowercase hex
  human                TEXT NOT NULL,        -- canonical human recipient, e.g. "rajesh"
  sender_session_id    TEXT NOT NULL,
  sender_session_name  TEXT NOT NULL,        -- display name at send time
  title                TEXT NOT NULL,
  body_markdown        TEXT NOT NULL,        -- at most 65536 bytes
  blocking             INTEGER NOT NULL DEFAULT 0,
  created_at           TEXT NOT NULL,        -- RFC3339 UTC
  first_viewed_at      TEXT,
  handled_at           TEXT
);
CREATE INDEX owner_messages_sender ON owner_messages(sender_session_id, created_at);

CREATE TABLE owner_message_drafts (      -- passage comments not yet sent
  id          TEXT PRIMARY KEY,          -- same id scheme as owner_doc_drafts
  message_id  TEXT NOT NULL REFERENCES owner_messages(id),
  line        INTEGER,                   -- source line of the markdown; NULL = not placeable
  quote       TEXT NOT NULL,
  body        TEXT NOT NULL,
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);

CREATE TABLE owner_replies (
  id                       TEXT PRIMARY KEY,  -- the client's submission_id
  target_kind              TEXT NOT NULL,     -- 'message' | 'doc'
  target_id                TEXT NOT NULL,     -- owner_messages.id or owner_docs.id
  commit_sha               TEXT,              -- doc replies: the revision replied to
  body                     TEXT NOT NULL,     -- the owner's overall text, trimmed (may be empty)
  comments_json            TEXT NOT NULL,     -- [{line, quote, body}] in delivered order
  delivered_text           TEXT NOT NULL,     -- exactly what the agent received
  status                   TEXT NOT NULL,     -- 'delivered' | 'undelivered'
  delivered_to_session_id  TEXT,
  created_at               TEXT NOT NULL
);
CREATE INDEX owner_replies_target ON owner_replies(target_kind, target_id, created_at);

Doc replies reuse owner_doc_drafts, which is already keyed by doc and commit. Nothing is ever deleted from owner_messages or owner_replies. Drafts are deleted in the transaction that inserts the reply.

D3. Submitting a reply

  1. Idempotency. If a reply row with id = submission_id exists: same target → return it unchanged; different target → 409. Replies are serialized per target with the draft writes, as doc review submissions are.
  2. Content. Load the drafts (message: all of the message's drafts; doc: those for (doc, sha)), ordered by line ascending with NULL last, then created_at. Trim body. If both are empty: 400 Nothing to send.
  3. Recipient. Message: the sender session; doc: the author session. Apply the review wake rule8: that session if it exists and is not retired or killed, else its parent if that exists and is not retired, else none.
  4. Text. Build delivered_text (D4).
  5. Deliver and record, in one transaction on the retained queue database: insert the reply row, delete the drafts, set first_viewed_at if null, and enqueue the text for the recipient on message_queue with delivery_mode = 'sequential', from_sm_send = false, no sender session (so no second header is added). With no recipient, the row is undelivered and nothing is enqueued. After commit, if the runtime is enabled, drain that session's pending messages, as the review wake does. A stopped recipient gets the message on restore.

D4. Delivered text

[Input from: Rajesh via sm app] Re: "<title>" (<message id>)          -- message reply
[Input from: Rajesh via sm app] Re: doc "<title>" (<repo-name>/<path> @ <sha7>)   -- doc reply
<overall body, if non-empty>

> <quote line 1>
> <quote line 2>
<comment body>

> <next quote>
<next comment body>

Rules: one blank line between the overall body and the first comment, and between comments; no blank line after the header. Each quote is trimmed, capped at 300 characters (… appended when cut) and prefixed > per line. "Rajesh" is the same literal the [sm review] wake uses. The doc title is the doc's current title. There is no length cap on the delivered text beyond the 100-draft limit.

E2. Client changes (http/doc_client.js)

  • The config gains mode: "review" (today's behaviour), "reply", or "read"; and apiBase: "/docs/<id>" or "/messages/<id>". api() builds URLs from apiBase instead of the hard-coded /docs/.
  • Mode is chosen by the server. Message page: reply. Doc with an open PR: review (canComment true). Doc with prState unknown: review with commenting off until /head answers, as today. Any other doc (no PR, closed, merged): reply.
  • Reply mode keeps drafts, the composer and pending bubbles exactly as review mode, and replaces the review panel with a panel fixed at the bottom of the visual viewport: a textarea (placeholder Reply to <agent name>…, auto-grows to 6 lines), Handled (messages only, shown only while state is needs_you) and Send, labelled Send (N comments) when drafts exist. Send reloads drafts first; if they changed, it shows the new count and asks again (the review panel's rule). It keeps one submission_id until success, reused on every retry. On success it shows Sent to <session name> (or Not delivered: agent retired), clears the textarea and appends the reply to the replies list.
  • Replies list (reply mode): under the body, heading Your replies, each reply's overall body and comment quotes with its time; none yet when empty. Filled from config replies (message: all replies to it; doc: all doc replies to this doc, any revision, newest last).
  • The doc header bar's read-only label changes from Read-only: no PR / PR closed to Reply goes to <author> in reply mode.
  • Reply mode on a doc sends sha (the viewed revision) and uses the doc's drafts for that revision; drafts from another revision show the existing "N draft comments on <sha7>" prompt.

F. Notifications and email fallback

F1. Who is notified

user_id must be the identity the app's push tokens are registered under, which is the owner's signed-in Google email. So: the human recipient's email channel address, lowercased, when it equals (case-insensitively) a google_auth.allowlist_emails entry; else the first google_auth.allowlist_emails entry; else local_bypass, which is what a local follow uses without sign-in. The lookup of valid tokens is then unchanged. For doc notices the human is the only configured human; with several humans, the first in config order.

F2. Delivery

Extend the follow delivery worker (owner_push::deliver5) to process owner_notices in the same pass, after follows, with the same rules: push to every valid token; success on any token sets notified_at/notified_via='push'; retryable failures back off 30 s, 1, 2, 5, 10 minutes, then email; an invalid token is marked and not retried; no push configured or no valid token → email immediately; a push with no ack within 15 minutes → one fallback email; transient email failures retry every 5 minutes for an hour. Notices have no report grace. A repair pass, every third worker pass, creates a notice for any owner_messages row younger than 24 hours that has none (lookup by subject_id). Runs only when rust_core.runtime_enabled, like follows.

Z. FAQ

Why not store messages in git, like docs? Docs are artifacts with revisions and reviews; git gives them history and GitHub gives them review. A message is one turn of a conversation. Committing each one would put chat into repos and require a push before every question.

Why is the reply not a [sm …] system marker, when follows and reviews are? Those come from sm on your behalf and tell the agent what to do next. A reply is you talking; the agent should treat it as conversation and answer. Using the sm send header shape gets that behaviour from every existing agent without new instructions.

Why not deliver replies as urgent? Urgent interrupts the agent mid-turn. Your reply is usually the answer the agent is idle waiting for, so sequential delivery arrives immediately in that case and never corrupts a turn in progress in the other.

Why cap unread messages instead of rate-limiting per minute? A time rate limit punishes a legitimate burst (three quick findings) and still lets a slow loop through overnight. The unread cap measures what matters: messages you have not seen. It resets the moment you open one.

What if you read the fallback email instead of the page? Email reading does not mark the message viewed, so a long email-only stretch could hit the cap. The email's link opens the page and resets it. Phone-off stretches long enough to hit 5 unread from one agent are rare; widening the cap is a config-free constant change if it bites.

Why does --review notify, but a plain publish doesn't? Agents republish docs for many reasons (fixing a typo, pinning a revision). Only a review request or an explicit --notify asks for your attention now.

What does an old app build do with a message notification? Today's service knows only follow acks, so it never acks a notice, whether or not it shows it. The server then emails after 15 minutes. Tickets (b) and (c) ship together, so this only affects a phone that has not updated.

Why a separate notices table rather than rows in owner_follows? A follow has a target, a trigger and a report grace; a notice has none of those and is born already fired. Sharing the delivery code, not the table, keeps both shapes honest.
