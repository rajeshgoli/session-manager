2472 — Choose the next agent at handoff; let agents work the board

Author: Claude (Opus 5.5) 8156d6df · Ticket #2472 · 2026-10-21

Memo

I recommend two changes, built as one ticket each. First, a handoff can, on the rare occasion a quota runs low, go to a different agent type, once: for example from Claude Opus to Codex Sol, so a line of work continues on the provider that still has quota. The everyday handoff does not change and shows nothing new. Second, agents get the two board actions only you have today: file a ticket onto a lane, and Start an agent on it. An orchestrator then never spawns its workers. It puts work on the board, the board starts the workers, and the orchestrator talks to them with sm send.

Neither change gives an agent a power it lacks today. Agents already pick any model with sm spawn and file issues with gh. The changes move those powers under your rules: your agent types, the launch configuration your board already holds for each ticket, your board gates, and a switch to turn agent starts off.

Agent type
A named preset you keep in Settings → New agents: a provider, model and effort. Today: Top (Claude, Fable, xhigh), Mid (Claude, Opus 1M, high), Low (Claude, Sonnet, high), plus any you added, up to eight. Your board's Start sheet already picks from this list, and a ticket line Tier: Mid preselects one.
Handoff
What sm handoff does: the agent writes a note, ends its turn, and sm starts a fresh agent in the same worktree with the same tickets, PRs, children and pending wakes, then retires the old one. Today the fresh agent is always the same provider, model and effort.
Line of work
One agent and every successor its handoffs produced (names far-2256, far-2256-h2, -h3…).
Start
The board's button that starts an agent on a ready ticket: it claims the ticket, sets up the worktree, writes the brief from your template, and records the start on the lane. Today only you, signed in, can press it.
Launch configuration
The agent type (or provider, model and effort) the board holds for a ticket. A ticket captures its lane's Future lane default when it first appears on the board; your Start sheet, a Tier: line, or a saved selection can change it. It is what the Start sheet preselects.
Board agent
An agent created by Start. It has no parent agent; it shows on the board against its ticket.
Orchestrator
Any agent whose job is to run other agents through a plan. Not a registered role; a description.

1. Handing off to a different agent type

The use case is a provider running out of quota, and it is rare. Claude's weekly meter is low on Tuesday and two Opus lines are mid-ticket. You open each agent's Hand off… menu, tap Next agent: same at its foot, and pick your Codex Sol type. Each line continues on Codex at its next handoff, in the same worktree, with its note, claims and children intact. When the week resets you switch them back the same way, or leave them. Every other handoff looks and behaves exactly as today.

The agent is told before it writes its note. When a choice is pending, sm's handoff request to the agent names the next type (“your successor will be Sol: Codex, high”), so the note is written for that reader.

Switching provider is the main case, and it works. Today's handoff already has a start path for Claude, Codex and the local models; the change is only which one it takes. The Codex successor reads the same note and holds the same claims.

2. Agents on the board

The orchestrator puts work on the board instead of spawning it. Today an orchestrator calls sm spawn, and the worker becomes its child. Its place in the agent tree hangs on the orchestrator, and moves at every orchestrator handoff. The worker never appears as a Start on your board's lane history, and the orchestrator invents its own name and brief. With this change the orchestrator files and starts tickets, and every worker is a board agent with the ticket's launch configuration, your name pattern, your brief template and your checkout. The orchestrator coordinates by sm send and hears back once when each worker finishes.

What an orchestrator types, and what it sees:

$ sm board file --title "Replay start from stage_f.pt" --body-file brief.md \
      --under 2240 --after 2256 --start
Filed rajeshgoli/fractal-algo-rust#2290 under #2240, after #2256. It starts as Mid, the lane's type.
#2290 is blocked by #2256, so it was not started. sm board start 2290 once #2256 closes.

$ sm board start 2289
Started far-2289 (a1b2c3d4) as Mid on #2289, the type the board holds for it. sm will wake you when it finishes.

[sm board] far-2289 (a1b2c3d4), which you started on #2289, finished: ran sm task-complete.

What you see. The ticket row and lane history read Started by far-orch where they read Started today, and the agent's detail page names its starter. Settings → Board gains one switch, Agents can start tickets. Turning it off makes sm board start and --start fail with “Rajesh turned off agent starts”. Filing still works with the switch off.

What agents cannot do. They cannot start a ticket that is blocked by an open ticket, held, waiting on you, or before its not-before time. You can override all four with Start anyway; an agent is told to ask you. They cannot choose the type: the board's launch configuration for the ticket decides. If an orchestrator thinks a ticket needs a different type, it says so to you. They cannot close tickets from the board, reorder lanes, add or remove lanes, or change auto-start. Those stay yours.

Risks

RiskAnswer
A runaway orchestrator starts many agents and burns quota.The same is possible today with sm spawn. The switch stops it in one tap. Each start is visible on the board with its starter. I recommend no per-agent cap until we see the need.
A different model misreads the note.The agent is told the successor's type before writing; the switch is yours, never automatic.
A type is removed from Settings while a choice waits for it.The handoff uses “Same as now” and the new agent's first message says so; your chip disappears with the type.

Build order

Two tickets, independent file sets, either order: (a) next-agent type at handoff (server handoff, three owner surfaces, CLI); (b) agent board actions (sm board file, sm board start, finish wake, switch, “Started by”). Both are middle-tier (Opus) implementation work after this memo converges.

FAQ — what changed since the last revision

  • The handoff switch is now a rare, tucked-away option, framed around a provider (Claude to Codex) running low. It no longer adds a visible control to every handoff. The agent's --type is for when you tell it to switch.
  • Agents no longer choose a type on the board. sm board start and sm board file use the launch configuration the board holds for the ticket, which comes from its lane. Lanes hold one default type today, not a list of allowed types; I recommend not adding a list.

One reading still to confirm: I took “handoff to another agent type as a one-time task” to mean the switch applies to one handoff, after which the new agent carries on as itself (decision 2). If you meant a detour, a cheaper agent does one bounded task and then the line returns to its original type, say so. That is a different feature: it needs a definition of when the detour ends, and I would design it separately.

A. Next-agent type at handoff

A.1 Persisted shape

A per-session pending choice, stored with the session's handoff policy override (handoff/policy.rs session overrides, owner-settings store):1

next_type: {
  name: "Mid",                 // agent type name at choice time
  provider: "claude", model: "opus[1m]", effort: "high",   // snapshot at choice time
  chosen_by: "owner" | "agent",
  chosen_at: RFC3339
} | null

The snapshot is resolved again by name at handoff time. If the name still exists, its current provider, model and effort are used. If it is gone, the choice is dropped (see A.4). The snapshot exists only to render the chip and messages if the type is later renamed.

A.2 Who writes it

  • Owner: PUT /sessions/{id}/handoff-policy accepts {"next_type": "Mid"} to set and {"next_type": null} to clear. "Same" is the same as null. It can be combined with ask_now: true in one body. Owner guard unchanged. Unknown name → 400 No agent type named "X". Choose one from Settings → New agents.
  • Agent: sm handoff --type NAME, sent as a next_type field in POST /sessions/{id}/handoff. The CLI help says it is for when the owner asks for a different type. An agent may also run sm handoff --type NAME with no note change to retarget a handoff it already submitted while still in the accepted state. If an owner choice exists, the agent's is ignored and the CLI prints Rajesh chose Mid for your successor; your --type Low was not used. Exit 0.
  • sm handoff --type accepts type names case-insensitively, and same.

A.3 Use

  • claim_handoff_start (handoff/transfer.rs) builds SuccessorPlan from the predecessor's provider, model and effort, then applies the resolved choice to those three fields. Worktree, node, parent and name are unchanged. create_successor (http/handoff.rs) already branches on plan.provider, so a provider switch takes the right start path.
  • Node support: if the chosen provider cannot run on the predecessor's node (ensure_core_runtime_request_node_supported), the owner PUT and the agent's --type fail at choice time with the node's reason, not at handoff.
  • The choice is cleared in the same transaction that records the successor as started. A failed start (D.6 failure path) keeps it, so a retry uses it.
  • The successor's brief gains one line after the first: You run as Mid (claude, opus[1m], high); your predecessor ran as Top (claude, fable, xhigh). Only when they differ.
  • The context-management ask text (handoff/policy.rs ~736, and its variants in store.rs and notes.rs) gains, when a choice is pending: Your successor will be Mid (Claude, Opus 1M, high); write the note for it. If the choice is set after the ask was sent, sm sends a one-line [sm context management] follow-up with the same sentence.
  • The parent notice (parent_notice_text) names the new type when it differs.
  • Session records already store provider, model and effort per session; nothing else about the line records types.

A.4 Edge cases

B. sm board start for agents

B.1 CLI

sm board start TICKET [--brief-file PATH] [--name NAME] [--repo REPO]

There is no type flag.

TICKET follows the existing sm board ticket syntax (plain number in the cwd repo, or owner/name#N). Requires a managed session (CLAUDE_SESSION_MANAGER_ID); from a plain shell it fails with sm board start runs from an agent; on the board, press Start.

B.2 Route

POST /board/start, session-authenticated like the other agent board routes (ensure_session_allowed_from_parts, http/board.rs). Body: {repo, number, brief?, name?}; an unknown field (including type, provider, model, reasoning_effort) is a 400. It calls the same start() as /client/board/start with:

  • Type: the board's existing resolution for the ticket (board/launch.rs resolve: auto-start authorization, then the ticket's saved selection, then its Tier: line, then its lane's default, then global defaults). It is the same function the Start sheet preselects with, so the two never disagree. The success line names the type and its source, e.g. as Mid (lane default).
  • Brief: the owner's message template as today, with brief, if given, appended under a line From far-orch (8156d6df), who started you:. The brief also ends with: far-orch started you. Reach it with sm send far-orch; sm tells it when you finish.
  • Name: owner's name pattern unless name given; same uniqueness rules.
  • Gates: validate_start with start_blocked=false, plus: not-before must have passed (no early start), not held, not waiting on owner. Owner-only overrides are never available.
  • Switch: if owner_settings.board.agents_can_start is false → 403 Rajesh turned off agent starts. File the ticket and tell Rajesh, or ask him to turn it on.
  • Parent: None, as owner Start.

Refusal texts (409 unless noted), each one sentence naming what to do:

CauseText
Blocked#2290 is blocked by #2256 (open). Start it once #2256 closes, or ask Rajesh to start it anyway.
Held#2290 is held. Only Rajesh can start it.
Waiting#2290 is waiting on Rajesh: <waiting text>.

B.3 Starter record and finish wake

  • New table board_starts(session_id TEXT PRIMARY KEY, starter_session_id TEXT NOT NULL, repo, number, started_at, notified_at NULL), in the board store. Owner starts write no row.
  • starter_session_id is a session-id column: classify it in MOVED_COLUMNS (handoff/execute.rs) as moved, so an orchestrator's handoff carries its starter rows; the started worker's own handoffs move the session_id side too (lineage), so the wake fires when the line finishes, not at each worker handoff.
  • Wake fires once, on the first of: the worker line runs sm task-complete; the worker line is retired other than by handoff. Text: [sm board] far-2289 (a1b2c3d4), which you started on #2289, finished: ran sm task-complete. or …, was retired (<reason>). Delivered through the normal message queue (durable, survives restart). If the starter is gone, no wake.
  • Lane event agent_started records actor (starter id, starter name) and detail started by far-orch; owner starts are unchanged.

C. sm board file

sm board file --title TEXT (--body-file PATH | --body TEXT) [--under GOAL] [--after N...]
              [--start] [--repo REPO]

Route POST /board/issues, session-authenticated. Steps, in order:

  1. Validate everything first: --under and each --after exist in the repo. A body containing a Tier: line is refused (Agents can't set a ticket's type; the lane decides. Remove the Tier line.). Any failure → nothing is created.
  2. Create the issue through the board source's create_issue (the same path the owner's notes use). Body is the given body, then Filed by far-orch `8156d6df` via sm. Then any Starts after #N lines for people, as CLAUDE.md asks.
  3. Record under and after links (same code as sm board under/after). The ticket then captures its lane's default launch configuration exactly as any ticket new to the board does.
  4. If --start: refresh the ticket and run B.2. A refusal is not an error of file: exit 0, print the refusal as a second line (memo example).

Partial failure after the issue exists (step 3 or 4): print the issue number and the failed step with the command to finish it, exit 1. No rollback; the issue stays.

sm board file is not gated by the switch. Lane ownership stays the owner's: --under places a ticket in an existing lane; it cannot create a lane.

Z. FAQ

Why not let the orchestrator be the parent? Parentage ties the worker's life to the orchestrator: retirement cascades, children lists move at every orchestrator handoff, and the worker appears as the orchestrator's helper rather than as ticket work. The finish wake gives the orchestrator the one signal parentage was providing.

Why no early start for agents? A not-before time is your scheduling decision (often device contention or a quota window). An agent overriding it defeats the point.

Why a switch rather than a role? Registering orchestrators as a role adds a step every orchestrator must remember and gives you nothing the switch and the “Started by” trail don't.
