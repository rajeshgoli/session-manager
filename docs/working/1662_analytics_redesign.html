1662 — Analytics: where the quota and the agents' time go

Author: sm-1662-spec-author dbd17da3 · Ticket #1662 · 2026-09-29 · Revision 1

Memo

I recommend replacing everything on today's Analytics screen with three views: Spend, Time and Queue. Spend answers "what used my weekly quota?" as a drill-down, the way the Unix du command shows disk usage: total, then repo, then ticket, then agent, then model. Time answers "what did my agents spend their hours on?" with the same drill-down, ending in buckets such as model working, tools, waiting on a queue job, waiting on a Codex review and waiting on you. Queue holds the two diagnostic cards that leave the Queue tab. Nothing from the current screen survives: its content has not changed since March, its health checks are hardcoded empty, and its live counts repeat Queue and Watch.

Spend needs no new recording: sm already records every model turn with its tokens, and I fitted a conversion from tokens to percent of the weekly quota that reproduces Claude's weekly meter within 4–10% in normal weeks. Time needs one new recorder: the per-turn and per-tool timings exist today only in Claude and Codex transcripts, which Claude Code deletes after about 30 days, so sm must copy them into its own database. No new hooks are needed. The work splits into six tickets, each sized for one agent (§7).

I ran both analyses on live data (backup copies of the databases). This is what the screens will tell you:

Thread
A ticket plus the PRs linked to it; a PR that links to no ticket is its own thread. This matches the History page.
Active time and parked time
An agent's active time runs from its first turn to its last turn and excludes parked time. Parked means the agent finished all its claimed work and sits unretired until someone prompts or retires it. Parked time is reported but not counted in the Time view's bars.

How tokens become percent. Each model gets a rate: percent of the weekly meter per million tokens, where an output token weighs 8, a cache write 1.25–2, a fresh input token 1 and a cache re-read 0.02. I fitted these rates against six weeks of meter readings. On Claude, Fable costs about 3.9× Opus per token and Sonnet about 0.6×. On Codex, Astra costs about 3× Sol. The fitted estimates are then scaled so the week's rows add up to the actual meter reading. In normal weeks the scale factor is 0.9–1.1. The factor is capped at 0.8–1.25; beyond that the screen shows the gap rather than hiding it.

2. Which ticket a turn belongs to

Each model turn and each second of agent time is assigned to one thread by the first rule that applies:

  1. The agent's claims at that minute. If it holds several, the most recently taken wins. A PR claim counts toward the ticket the PR links to.
  2. Its parent agent's claim, by the same rule; this covers helpers that do not claim.
  3. A ticket or PR number in the agent's name (1787-spec-reviewer, sm-1662-spec-author) that exists in that repo. Reviewers and scouts do not claim, so this rule catches most of them.
  4. Otherwise "No ticket" under the repo of the agent's working folder.

Claims have been recorded explicitly only since Sep 25. Before that, sm reconstructed PR claims from history, and those stay open until the agent retires, so older weeks attribute less precisely. The rows still add up correctly; only the ticket-level split is rougher.

Two rules keep this honest. A queue job counts as waiting only while the agent is idle between turns: the sample Claude engineer ran 13 test jobs but waited on them for only 3.5 minutes, because it kept working while they ran. When an idle agent waits on two things at once, for example tests and a review, the time goes to the one that finished last.

What is not measured: time a tool spends waiting on your permission prompt counts as that tool's time (the transcripts do not mark it), and time before an agent's first turn (spawn and boot) is not counted.

B. Converting tokens to percent of the week

B.1 Rate table

A new module crates/sm-server/src/quota_rates.rs holds this table as constants, with FITTED_AT = "2026-09-29". Model family is the first of these substrings found in the lower-cased model name: fable, opus, sonnet, haiku, astra, sol, terra, luna.

ProviderWeighted tokens per turnRate: % of a week per million weighted tokens
Claudeinput + 8·output + 1.25·cache_write_5m + 2·cache_write_1h + 0.02·cache_readfable 0.648 · opus 0.167 · sonnet 0.100 · haiku 0.033 · any other: opus
Codexinput + 8·output + 0.10·cache_read (Codex's output already includes reasoning)astra 0.683 · sol 0.228 · terra 0.137 · luna 0.030 · any other (unknown, codex-auto-review, new models): sol
Codex cloud reviewone per registration with review_landed_at set0.05 each

How the rates were fitted: meter increments (per-window running maximum, differenced in 6-hour slices for Claude and 3-hour slices for Codex) were regressed by least squares, without intercept, on weighted tokens per model family, over periods where the ledger is complete (Aug 16 – Sep 2 and Sep 23 on). Claude R² 0.94 at 6 h; Codex R² 0.88 at 3 h. Sonnet, Haiku and Luna have too little volume to fit, so they are set from list-price ratios (Sonnet 0.6× Opus, Haiku 0.2× Opus, Luna about 0.13× Sol). Cloud reviews fitted at 0.049–0.051 ± 0.009.

B.2 Scaling to the meter

For each account and each weekly window w (from burn_samples: the latest sample's percent is the meter M_w):

F_w   = Σ fitted % of every ledger turn of that account in w  (+ 0.05 × cloud reviews landed in w, Codex only)
s_w   = clamp(M_w / F_w, 0.8, 1.25)          (s_w = 1 when F_w = 0)
row % = s_w × fitted % of the row's turns in w
gap_w = M_w − s_w × F_w                      shown as the row "Not in the ledger" when gap_w ≥ 0.1;
                                             when gap_w ≤ −0.1, a note "Estimates exceed the meter by |gap_w| points"

The meter a cloud review counts against is the Codex account active at review_landed_at (account_timeline, provider codex, from_ts ≤ t < to_ts). A turn's window is its message_window row for weekly_all / codex_10080; a turn without one uses the window whose [window_start, resets_at) contains its bucket_ts, and if there is none, s = 1.

Worked example, Claude this week. M = 35.0, F = 32.8, so s = 1.067 and the gap is 0. The 1787-spec-author seat has 141 Fable turns: output 0.36M, cache writes 0.9M (mostly 1-hour), cache reads 67M. Weighted tokens are 0.36·8 + 0.9·2 + 67·0.02 ≈ 6.0M. Fitted: 6.0 × 0.648 = 3.9%. Shown: 3.9 × 1.067 ≈ 4.1%.

Worked example, Sep 13 week. M = 39, F = 1.2 (turns lost to #1658). s = 1.25, rows add up to 1.5, and "Not in the ledger" shows 37.5.

B.3 Ranges

  • This week: per account, the current window (resets_at > now). For Codex with two accounts active in overlapping windows, each account's rows are scaled to its own meter and summed. The header lists each account's meter.
  • Last week: per account, the window immediately before the current one.
  • 4 weeks: turns with bucket_ts in the last 28 days, each scaled by its own window. The total is shown as "% of a week" and can exceed 100.

Header pace line (this week only): burn per second = M / (observed_at − window_start). If M + rate × (resets_at − observed_at) ≥ 100, show "at this pace runs out <weekday, morning/afternoon/evening>" at the time the meter reaches 100; otherwise show "on pace for N%". Suppress it in the first hour of a window, the same rule as usage_report.rs::build_projection. If the latest sample is more than 10 minutes old, show "meter from <age> ago".

C. Attribution rules

One module, crates/sm-server/src/work_attribution.rs, used by both Spend and Time. Input: seat id, instant t, the seat's working-folder repo. Output: (repo, thread_number | None, basis), where basis ∈ {claim, parent, name, none}.

  1. Claim. Active claims of the seat at t: claimed_at ≤ t < ended_at (open claims have no end), reserved_at IS NULL. Pick the one with the greatest claimed_at; on a tie, the greatest id. Map it to a thread: a ticket is its own thread. A PR goes to its linked tickets from work_links (either source); if one of them is also actively claimed by this seat at t, that one, otherwise the lowest-numbered. A PR with no link is its own thread. Repo is the claim's repo.
  2. Parent. Apply rule 1 to the seat's parent (seat_meta.parent_seat_id, latest observation), then its grandparent, up to 5 levels.
  3. Name. Find the first match of (?:^|-)(\d{3,5})(?:-|$) in the seat's latest friendly_name. If work_items has (repo, number) for the working-folder repo, map it as in rule 1 (PR → linked ticket).
  4. None. Thread "No ticket" under the working-folder repo.

Working-folder repo. project_key is the absolute git common dir (worktrees collapse to the main repo) or a plain folder. Resolve it to owner/name once per distinct key with git -C <key> remote get-url origin and the existing GitHub URL parser used by bin/git_repo (move it into the library if needed). If that fails, use the folder's last path component with .git removed. Cache the result for the process lifetime. Repos are compared lower-cased (work_claims::canonical_repo).

Spend granularity. Ledger rows carry a minute (bucket_ts); evaluate the rules at that minute's start. A claim taken at 12:00:40 therefore first owns the 12:01 minute. Time granularity: evaluate at every span boundary and every claim start and end, so each second is exact.

Cloud reviews take the thread of (repo, pr_number) by the rule-1 PR mapping, not the requester's claims. The agent is requester_session_id, or "You" when it is null.

D. The activity recorder

A new module crates/sm-server/src/activity_ledger.rs and a new SQLite file activity.db, configured as activity.db_path (default ~/.local/share/claude-sessions/activity.db; add it to the installed config explicitly, as for the other stores). A separate file keeps its writes away from the usage ledger's lock contention (#1658). It runs on the same background cadence as the usage ledger scan, reading every artifact_path in seat_sessions incrementally by byte offset.

CREATE TABLE activity_turns (
  seat_id TEXT NOT NULL, source_ref TEXT NOT NULL, provider TEXT NOT NULL,
  started_at_ms INTEGER NOT NULL, ended_at_ms INTEGER NOT NULL,
  prompt_at_ms INTEGER,            -- timestamp of the prompt line that opened the turn
  PRIMARY KEY (source_ref, started_at_ms));
CREATE TABLE activity_spans (
  seat_id TEXT NOT NULL, source_ref TEXT NOT NULL,
  started_at_ms INTEGER NOT NULL, ended_at_ms INTEGER NOT NULL,
  kind TEXT NOT NULL,              -- see D.3
  tool TEXT,                       -- raw tool name, for audit
  item_id TEXT NOT NULL,           -- tool_use id / call id / item id: idempotent re-scan
  PRIMARY KEY (source_ref, item_id));
CREATE INDEX activity_turns_seat ON activity_turns(seat_id, started_at_ms);
CREATE INDEX activity_spans_seat ON activity_spans(seat_id, started_at_ms);
CREATE TABLE activity_scan_offsets (artifact_path TEXT PRIMARY KEY, byte_offset INTEGER NOT NULL,
  mtime_ns INTEGER NOT NULL, pending_json TEXT, scanned_at TEXT NOT NULL);

pending_json holds tool calls and turns opened but not yet closed at the offset, so a pair split across scans still joins. Advance the offset only after the batch commits. On a write error, retry next cycle from the old offset; never skip rows (the #1658 lesson). Delete rows with ended_at_ms older than 90 days daily. On first run, scan every existing file (backfill); expect about 20 s of CPU for a week of transcripts (the prototype took 19 s for 257 agents).

E. Classifying time

For one seat and a range [R0, R1):

  1. Timeline. Merge the seat's turns. The timeline runs from the first turn start to the last turn end, or to now if the session is not stopped. Clip everything to the range.
  2. Inside a turn. Each instant covered by tool spans goes to the span with the latest start; on a tie, the latest end. That is the innermost span, so a Codex exec wrapper yields to the command inside it. Everything else is model.
  3. Between turns. Collect the seat's waits (below). Each instant with at least one open wait goes to the open wait with the latest end (a still-open wait ends at +∞); on a tie, in the order you › review › queue › agents.
  4. No wait open. If the seat holds an active claim, the instant is you when the gap ended with a prompt from you, otherwise idle. If it holds no claim, it is parked, whether its claims have ended or it never held one: a reviewer or scout that did its one job and sits unretired is parked, and so is the gap in an ad-hoc session you drive yourself.

Z. FAQ

Z.1 Why not split a turn evenly when an agent holds two claims? Agents work on one thing at a time and claim new work when they start it. Old claims stay open until GitHub closes them, often hours later. An even split would spread a new ticket's work over every ticket still waiting to merge. With latest-claim-wins, once a newer claim ends the minutes fall back to the older one, which is also right.

Z.2 Why not API list prices instead of fitted rates? List prices charge cache re-reads at 10% of fresh input. The meter charges about 2%. Cache reads are 97% of Claude tokens, so list prices would hand most of the quota to agents with long contexts rather than agents that write a lot. The existing sm usage report uses list prices and also has no entries for the gpt-6 models; that is out of scope here.

Z.3 Why not the tool hooks (tool_usage.db)? No hook posts to it today (0 rows). Wiring it means changing your Claude Code settings, it covers Claude only, and it records nothing before the day it is turned on. The transcripts already hold exact tool timings for both providers.

Z.4 Why is parked time outside the bars? Last week it was 216 hours, 29% of all agent time. Mostly these are finished agents that nobody has retired yet. Counting it as "waiting on you" or "idle" would make those buckets mean "finished" instead of "stuck".

Z.5 Does "waiting on you" overstate? It counts wall-clock hours, including nights. An agent that asks you something at 23:00 and gets an answer at 08:00 shows 9 hours. That is the true cost to the work's lead time, which is what the view is for.

Z.6 Why a separate activity.db? The usage ledger lost turns to lock contention (#1658). A second heavy writer in the same file would make that worse.

Z.7 Codex's two accounts. Both are Pro. Each turn is scaled against its own account's meter, and percentages add because each point is a point of one Pro week. The header shows each account's meter.

Z.8 Prototype. The scripts that produced every number in the memo (rates.py, coverage.py, spend_tree.py, walltime.py, walltime_all.py) are in my session's scratchpad. The implementing agents get the rules from Appendices B–E, not from the scripts.
