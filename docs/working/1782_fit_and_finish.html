1782 — Fit and finish: sm web and the phone app

Author: Claude (design) sm-1782 · Ticket #1782 · Revision 2, 30 September 2026 · screens drawn from live sm data at 12:47 pm PT that day

Memo

This round makes sm easier to read and quicker to act on, on both the laptop and the phone. The type gets two sizes bigger. Each agent shows three separate facts instead of one colour: whether it is working, what its queue jobs are doing, and whether it needs you. You can clear “needs you” by answering in any terminal, or with one click. Pages are ordered by what needs your attention. The ticket, pull request, agent, terminal, queue jobs and inbox thread linked to any item are one click from wherever you see it. The board stops folding away rows it has room for, and it gains Close for finished container tickets and Start anyway for blocked ones. The phone app moves to one visual style and reads inbox threads natively.

Terms used below. An agent needs you when it asked you something with sm send rajesh --blocking, asked for your review of a doc, or is stopped at an Allow prompt in its terminal. An agent has finished when it ran sm task-complete. Its last turn message is the text it wrote at the end of its latest turn, which is usually the summary you read. The attention order ranks agents: needs you first, then finished, then anything stuck or waiting a long time, then working, then idle.

A. Type and colour

A1. Type scale (web)

  • The root font size is set on <html> from localStorage["sm-text-size"], an integer from 13 to 19 px (default 15). A missing or out-of-range value means 15. An inline script in the shell sets it before first paint, beside the theme script. Text size is per browser, like theme, because it depends on the screen.
  • Every font size in app.css, queue.css and devices.css becomes a rem value, by this map (px at the standard size):

  • Widths already in rem (the rail, the panel, the rings) scale with the root size. Pixel widths in the layout become rem using the same 15 px root. Agent cards use minmax(24rem, 1fr).
  • The xterm font size is the root size minus 1 px.
  • Doc pages loaded in the reader keep their own stylesheet.
  • Appearance gains a Text size slider, 13 to 19 px in 1 px steps. It shows the value (“15 px”), applies live, and has Reset (15 px).
  • Phone: Settings › Appearance gains a Text size slider from 85% to 130% in 5% steps (default 100%), stored in SettingsRepository. Theme.kt scales every Typography style's font size and line height by it.

A2. Usage meters (web top bar, Queue page Mac tile, phone)

  • Band is computed from the total fraction f. Memory uses memory_used_bytes ÷ memory_total_bytes; CPU and GPU use percent ÷ 100. Below 0.60 is low, 0.60 to 0.85 is mid, and above 0.85 is high. This is the phone's meterBand (android-app/…/ui/queue/QueueModels.kt:148).
  • Colour: low is green, mid is amber, high is red. GPU in the low band is cyan. The colours are the palette tokens (1710 appendix A).
  • Fill: when the queue share is known, the total bar is the band colour at 40% opacity and the queue share (clamped to at most the total) is drawn over it in solid band colour. When it is unknown, the total is solid.
  • Order: Memory, CPU, GPU, then the Queue link. The labels are 115/256G · queue 98G, 21% and 0%, using gigabytes as ui.js gigabytes() computes them today.
  • Narrow bars: GPU is shed first, then CPU, then Memory, then all meters (app.css container queries).
  • Queue link: the link text turns amber when any waiting job has waited 30 minutes or more.
  • One function, meterBand(fraction, kind) in ui.js, serves the top bar and the Queue page's Mac tile (queue.js:34-43). The Queue chart's line colours do not change.

you. Build candidates in this order and show the first; more counts the rest.

C. Clearing “needs you”

One server function, owner_answered(session_id, via), marks every NeedsYou owner message from that session as handled. It sets handled_at and a new column handled_via (terminal, claude_prompt, manual, inbox). It sends nothing to the agent, because you answered it directly. It is idempotent, it runs at most once per session every 2 seconds, and it calls board::request_recompute when it changed anything. The thread shows an event line: “You answered in the terminal · 12:49 pm”, “…in Claude”, or “Marked answered”. Doc reviews and Allow prompts are never cleared by it.

C1. Enter in sm's terminal

In the terminal bridge (process_mobile_terminal_client_frame, http.rs:8879), pass the ticket's session id and kind. For browser and phone tickets, an input frame whose data contains \r or \n, or a key frame with key enter, calls owner_answered(session, "terminal") after the write to the PTY succeeds.

C2. A prompt you type into a Claude agent

In claude_hook for UserPromptSubmit (http.rs:2163), read the payload's prompt string. It is owner-typed when all of these hold:

  1. After trimming, it is non-empty.
  2. It does not start with [Input from: or [sm (sm's delivery markers: owner_messages.rs:264 and the [sm remind], [sm queue], [sm review] and [sm claim] wakes).
  3. It does not equal, after trimming, any text sm delivered to this session in the last 120 seconds (the message queue's delivered rows), and it is not a /rename that sm queued in that window.

Then call owner_answered(session, "claude_prompt"). Examples:

G4. Direct connection

  1. Ticket. POST /client/sessions/{id}/browser-attach-ticket adds server_instance (random, fixed per server start) and direct, which is a list of {url, probe}:
    • {"url":"ws://localhost:8420/client/terminal","probe":"http://localhost:8420/client/terminal/probe"} is always present.
    • {"url":"wss://{lan.hostname}:{lan.port}/client/terminal","probe":"https://{lan.hostname}:{lan.port}/client/terminal/probe"} is present when terminal_direct.lan.enabled.
    • The port for the localhost entry is server.port.
    Browser tickets record the owner email that minted them.
  2. Probe route. GET /client/terminal/probe returns {"instance": server_instance}. It sends Access-Control-Allow-Origin: https://{cloudflare_access.browser.hostname} and Vary: Origin. OPTIONS answers the preflight with Access-Control-Allow-Private-Network: true, Access-Control-Allow-Methods: GET and the same origin. It needs no login, because it reveals only a random id.
  3. Client.
    • Before each connection, fetch every probe in parallel with a 700 ms timeout.
    • Use the first entry, in list order, whose instance equals the ticket's server_instance. A probe that answers with another instance (for example the MacBook's own node server) is skipped, so the ticket never goes to it.
    • If no probe matches, use today's relative ws_url through Cloudflare.
    • If a direct socket closes before attached, mint a new ticket and connect through Cloudflare.
    • Remember the chosen route in sessionStorage["sm-term-route"] for 10 minutes, and skip the probes while it holds.
  4. Server acceptance. /client/terminal also accepts a request that did not come through the Browser Access host when all of these hold:
    • the auth frame carries a browser ticket (single use, unexpired, as today);
    • the upgrade's Origin equals https://{cloudflare_access.browser.hostname};
    • either the peer address is loopback and Host is localhost or 127.0.0.1 with the server port, or the request arrived on the LAN TLS listener.
    Every other path is unchanged. Each direct attach logs “browser attach direct {localhost|lan} {email} {session}”.
  5. Chrome. A public https page may open ws://localhost, because Chrome treats localhost as secure. Reaching localhost or a private address prompts once for local network access; if you decline, the probes fail and Cloudflare is used.
  6. LAN listener (ticket S7, decision 4).
    • Config: terminal_direct.lan: {enabled: false, hostname: "studio-lan.rajeshgo.li", port: 8443, cert_dir: "~/.config/session-manager/certs/lan" }. There is no separate token.
    • Listener: when enabled, sm-server binds 0.0.0.0:8443 with rustls. It serves only /client/terminal and /client/terminal/probe, and everything else is 404.
    • Certificate: Let's Encrypt, via ACME DNS-01 through the Cloudflare API. sm-server renews it when fewer than 30 days remain, checking daily.
    • DNS: the A record studio-lan (DNS only, not proxied) points to the Studio's LAN IPv4, taken from the default-route interface. sm-server rechecks it every 10 minutes and updates the record when the address changes. The server's existing Cloudflare API client makes the calls with cloudflare_access.api_token. If Cloudflare refuses a DNS change with that token, the listener stays down, the log names the missing permission (Zone › DNS › Edit on rajeshgo.li), and the ticket asks Rajesh to add it to that token.
    • Failure: if the certificate or the record fails, the listener stays down and logs why, and Cloudflare remains the route.

G5. Relay latency

  • Cause. The output reader (mobile_terminal_output_reader, http.rs:9195-9220) reads a non-blocking PTY and sleeps 25 ms whenever no output is waiting. An echo that arrives during the sleep waits for it to end, which adds up to 25 ms (12.5 ms on average) to every keystroke, on every route, for the phone as well.
  • Fix. Wait for readiness instead of sleeping: poll(2) on the master fd with a 250 ms timeout, which only bounds the time to notice stop, then read. The input writer's 10 ms retry on EAGAIN (:9244) gets the same treatment, waiting for POLLOUT.
  • Measure. The ticket records the median echo time for 50 single keystrokes through the ping-free path (keystroke to first output frame, timed in the browser) before and after, for localhost and Cloudflare, and puts the four numbers in the PR. The target is at most 5 ms on the direct localhost path.

Tests.

  • A loopback direct upgrade with the right Origin and a browser ticket attaches.
  • The wrong Origin is refused.
  • A phone ticket without its signature on the direct path is refused.
  • A non-loopback peer on port 8420 without Access is refused.
  • The probe returns the instance and the CORS headers.
  • Ping gets a pong.
  • The client skips a probe whose instance does not match.

Live check. On the Studio, open a terminal in Chrome, confirm “Direct · n ms” against “Cloudflare · n ms” with direct disabled, and put both numbers in the PR.

Z. FAQ

Why not clear “needs you” when the agent starts working again? Agents often keep working while a question waits, for example on another part of the ticket. Clearing on activity would hide real questions. Your own input is the only signal that you answered.

Why can sm tell your typing from its own deliveries only for Claude? Claude reports each submitted prompt to sm through its hook, with the text. sm marks everything it delivers, so unmarked text came from a person. Codex does not report prompts that way today; appendix C2 has the ticket check the codex-fork event stream.

Is the direct terminal path safe? Yes. The ticket is still minted behind the Cloudflare login, it can be used once within 30 seconds, and the direct socket must carry sm's own page origin. On the Studio the socket never leaves the machine. On the home network it is encrypted with a real certificate. The probe answers only a random id, so a ticket is never sent to a different server.

Where does the terminal lag come from? Two places. The route through Cloudflare adds a round trip to Cloudflare's edge on every key; from the Studio today, a small request through it takes tens to hundreds of milliseconds, against under 1 ms locally. sm's own relay adds up to 25 ms more, because it checks for output every 25 ms (G5). Terminal attach in tmux has neither, which is the difference Rajesh noticed.

Why not show GitHub pages inside sm? GitHub forbids it (X-Frame-Options: deny, checked 30 September 2026). sm shows the text itself instead, which also works when GitHub's page is slow.

Why does the server compute the attention order? The web, the phone and sm watch must agree, and the rules depend on queue positions, quiet jobs and the stall threshold, which only the server has in one place.

Why a separate Finished group instead of Needs you? A finished agent does not block anything, and mixing the two would dilute the magenta that means “an agent is stuck on you”.
