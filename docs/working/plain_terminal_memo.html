Plain Terminal — zsh seats on web and mobile

Author: opencode agent c20b80f2 · doc-only memo, no ticket yet · 2026-10-18

Memo

Conclusion: add a terminal seat — an interactive zsh running on the Mac inside the same tmux machinery that carries agents — visible in the watch list and attachable from the web terminal page and the phone's existing terminal screen. No new transport, no new identity, no new secret path: the shell rides the same guard chain that already protects phone attach (Cloudflare Access + device certificate + bearer token + signed per-session attach ticket). You approved that security posture on 18 Oct ("fine as long as the same device certificate guards it"); this memo spends its remaining surface on lifecycle, caps, and the two user experiences, each with a recommended call.

Terms

Terminal seat
A first-class session record whose pane is a plain login zsh, not an agent. It is listed like a session, openable like a session, killable like a session, and it runs nothing until a human types.
Device certificate / device key
The per-phone identity: a client certificate issued by the private CA in ~/.config/session-manager/certs whose common name is the registered device-key id, plus the matching signing key used to prove attach-ticket requests. Both are per-device revocable from the app and the web Settings.
Attach
A live, interactive terminal stream to a seat's pane, time-limited by max_attach_seconds and capped by concurrency limits. Distinct from watching a transcript.

What already exists, and what this memo actually adds

Three facts keep this cheap, and they are the reason it is feasible rather than merely imaginable:

Existing factConsequence for plain terminals
The server's tmux launcher takes any command string; agent providers are only arguments (runtime.rs create_session).Launching zsh is one new command shape, not a new runtime. The relay side already streams pane bytes both ways for the web terminal page and the phone terminal screen (specs 1710/1782).
Every phone terminal attach already passes a four-gate chain: Cloudflare Access + device certificate at the edge, bearer token, attach ticket, signature proof against the device's registered public key (android-app/README.md, spec 703).Plain terminals inherit that chain by being attachable seats. Your "same device certificate" requirement is met by construction; the only new security choices are caps and a kill switch.
Terminal attach limits are owner-adjustable at runtime (/client/settings, Settings screen in both clients), and device revocation is one action.A kill switch for plain terminals lands in the same settings surface and needs no restart. The escape hatch exists before the risk does.

The security position, stated so it can be re-read in public

Your ruling is that the device certificate is enough guard. Two clarifications you should see rather than discover later, both yours to re-confirm with one word:

(a) The chain above was designed for observing and steering agents, which is strictly weaker than arbitrary execution. A stolen-but-still-registered phone, unlocked, becomes a working shell on the Mac — including everything your user account can touch. The mitigations that make "same cert" defensible are already in place (per-device revocation from both clients, time-limited attaches, concurrency caps) or are decisions 2 and 4. This memo takes your "fine" as fine and layers exactly those.

(b) A terminal run from the phone works over exactly the same three routes agent terminals use: public edge (Cloudflare Access + your device cert), the home-LAN certificate-backed listener, and localhost/direct browser. "Same cert guards it" therefore means: a device without a valid, unrevoked certificate never sees the gate, on any route.

Appendices

A. Data model and interfaces

A.1 — Terminal seat records. New table in the usage DB alongside seat_sessions (do not reuse seat_sessions; that table maps provider transcripts for the usage ledger and a shell has none):

CREATE TABLE IF NOT EXISTS plain_terminals (
  id                 TEXT PRIMARY KEY,   -- "term-" + short random
  cwd                TEXT NOT NULL,
  created_by_user    TEXT NOT NULL,      -- owner user id
  created_by_device  TEXT NOT NULL,      -- device_key_id that spawned it
  created_via        TEXT NOT NULL,      -- "web" | "mobile" | "cli"
  tmux_session       TEXT NOT NULL,
  state              TEXT NOT NULL,      -- live | retired
  last_attach_at     TEXT,
  last_input_at      TEXT,
  created_at         TEXT NOT NULL,
  retired_at         TEXT
);

A.2 — Listing. /watch/state session entries gain shell terminals with kind: "shell", name term- (n = per-user counter), cwd, and a last-activity fact. The web terminal switcher and the phone terminal list group them in a Terminals section (after Agent sections, before Idle).

A.3 — Endpoints. Create: POST /terminals body { "cwd": "~" | path } → 201 with the terminal id and terminal URL. Retire: DELETE /terminals/{id}. Both owner-gated (decision 1). Attach: no new endpoint — the existing per-session attach-ticket and /client/terminal must accept kind: "shell" targets (today they resolve agent sessions; the identity of the guard chain is what must not change — see B.3). Directory picker source: the existing project-folder discovery that feeds launch defaults, plus Home.

A.4 — Launch plumbing. Reuse TmuxRuntime::create_session with command /bin/zsh -l in the requested cwd. Do not wrap in managed_session_command: terminal seats are unmanaged on purpose — no CLAUDE_SESSION_MANAGER_ID, so sm commands typed there are unattributed reads (precedent: sm watch from a plain terminal, operator docs). Pane logging uses the existing session-log path unchanged (decision 7). Kill uses existing kill_session.

A.5 — Config. terminal_limits gains: plain_terminal_enabled (default true), max_plain_terminals (default 4), idle_reap_minutes (default 180). Owner-editable at runtime like the other four limits; values outside documented ranges rejected.

B. Security: the exact check order, testable as written

B.1 — Create requires, in order: mobile terminal enabled → plain_terminal_enabled → actor is a visible allowed user with interactive_shell_access and owner flag → device key present, enabled, unrevoked → signature proof (timestamp window, one-time nonce, verify against registered public key) → concurrency limits → max_plain_terminals not exceeded. Each failure: 401/403 with the existing audit-denied reason codes; add three new reasons (plain_disabled, not_owner, too_many_terminals).

B.2 — Attach to a shell seat requires the same chain minus owner (creation was the owner gate) and checks the terminal is live. Shell mobile_terminal.supported is true when the toggle is on; its reason text explains the false case on the phone card.

B.3 — Parity rule: the shell path shares create_mobile_attach_ticket, ticket TTL, nonce recording, and active-attach accounting with agent attach. A test must assert shell attach consumes the same per-user and per-session concurrency slots and expires with max_attach_seconds.

B.4 — Residual risk (accepted by ruling): registered+unlocked stolen device ⇒ full user-level shell. Controls: device revocation from app/web (immediate), kill switch (kills new creates and attaches), reaper + cap, pane logs. No attempt is made at per-command approval; that is decision 8's out-of-scope, not an oversight.

B.5 — Required tests: toggle-off blocks create and attach (both clients); non-owner create denied; revoked device denied; proof replay denied; cap enforced; reaper retires exactly on the A.5 semantics (idle window, input resets); restart re-adopts unretired terminals whose tmux session is still alive and retires the rest.

C. Web user experience

C.1 — Terminal page: Terminals section in the switcher; rows show name, cwd tail, last-input fact. "New terminal" button in the page header opens a picker (Home, then recent project folders, then an entered path); creating immediately attaches in the same view.

C.2 — Desktop gets full xterm.js behavior (real keyboard, no key row). RTT readout and route choice (relay vs direct localhost/LAN, terminal-route.js) work unchanged for shells.

C.3 — Retire: same control as agent Retire. Killed seats drop from the switcher and list within one poll.

C.4 — Settings: the three new limit fields appear on the existing Terminal limits section, same validation and no-restart semantics.

C.5 — Target use cases the UX must serve without leaving the terminal page: (1) check on a build you started in a terminal; (2) run gh/git while away from the Mac; (3) open a shell in a project to steer a manual deploy step; (4) use the Mac's tmux session from the browser on another machine at home; (5) kill the shell when done.

D. Mobile user experience

D.1 — Watch list: Terminals section; row fact = "open · last input 12m". Tap → the existing terminal attach screen (it already keys off mobile_terminal.supported); "Open terminal" pill unchanged in wording.

D.2 — Create: terminal screen's top-bar "+" → directory sheet (Home + recent project folders) → creates and attaches. No separate launch window, no model/tier prompt (there is no model).

D.3 — Keys: phone-key row becomes Esc | Tab | Shift+Tab | ↑ | ↓ | Ctrl-C | Ctrl. The Ctrl key is a sticky modifier: armed for one next keypress, shows armed state visually; Ctrl+letter uses the same send-keys plumbing as existing combos. Layout change keeps every current key reachable; the row stays one row under portrait width or the modifier lives above the row.

D.4 — Terminal limits: the three new fields join TerminalLimitsSection, and a "Kill all terminal seats" affordance exists next to the toggle (one action, two taps, confirms).

E. Lifecycle

E.1 — Reaper: sweep every minute; retire when now − max(last_attach_at, last_input_at) > idle_reap_minutes. Retiring kills the tmux session and marks the record; logs follow normal retention.

E.2 — Server restart: unretired terminals whose tmux session survived are re-adopted (record stays live); dead sessions are marked retired. Terminal state is therefore safe to reason about from either side.

E.3 — Non-interactions: terminal seats never hold queue slots, never take a perf-machine claim, never receive sm send routing, never auto-ping. Explicitly: no queue.rs or contention code changes beyond exclusion.

E.4 — Limits interplay: a terminal's attach is bound by the same max_attach_seconds as agents, so a parked phone terminal self-exits its stream; the seat stays open for re-attach until reaped or retired.

Z. FAQ

Why not a bare tmux window without a seat record? Attach authorization, naming, retirement, logging, and the switcher all key off session identity (specs 703/1710). A shell without a record would need a shadow version of all five.

Why "seat" and not "session kind"? Seat is this repo's word for a tracked tmux slot bound to a provider; shell is a seat whose provider is a human. The memo uses terminal seat to keep it from colliding with agent session kinds.

Precedent for non-agent panes? The test suite already launches bare shell fixtures (runtime-sh entries in read_only_http.rs) to exercise the launch plumbing, confirming the plumbing is provider-agnostic; this memo promotes that to product.

Why does the phone keep a Ctrl-C button and get Ctrl-D/L/Z via modifier instead of buttons? Ctrl-C is common enough to keep one tap; the rest are a modifier's worth of frequency, and the key row width is the scarcest real estate on the screen.

What if I want the shell to have my agent tools' context (sm id)? Deliberately absent: unattributed keeps sm reads safe to type there. A future "pilot this shell as a managed session" could add attribution back; it is not needed for C.5.

Cost/split hint for implementation: three natural tickets — (1) server: shell seat, endpoints, reaper, limits, tests; (2) web: switcher/New terminal/Settings; (3) mobile: section, create sheet, Ctrl modifier, limits UI. (1) blocks the others; (2) and (3) are independent.
