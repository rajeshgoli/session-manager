Plain Terminal — zsh seats on web and mobile

Author: c20b80f2 (revisions 1–3), sm-2314-h2 (revision 4) · doc-only memo, no ticket yet · 2026-10-19

Memo

Conclusion: add a terminal seat — an interactive zsh on the Mac, in the same tmux machinery that carries agents — and attach to it over SSH with a key that lives on the device. At home the phone and laptops reach the Mac over the home network and nothing public is open. Away from home, the Cloudflare SSH tunnel opens only when a device asks to attach, and closes again after use. You start a shell from the web terminal's ⋯ menu ("New shell here"), from the phone's New session sheet, or with sm shell. A shell that is running something is never cleaned up behind your back.

This adopts your hardening idea from the last review. The reason to prefer it over the previous design (attach through the same relay agents use): today a stolen, unlocked phone with a valid device certificate is enough to reach a shell. With SSH, the attacker also needs that device's SSH key, which you can revoke on its own. And at home, no public door opens at all.

Terms

Terminal seat (shell)
A session record whose tmux pane is a plain login zsh, not an agent. It is listed, opened and retired like a session, and it runs nothing until you type.
Studio SSH
The existing SSH server for the Mac that you toggle in Settings: a dedicated sshd on 127.0.0.1:22222, published through the Cloudflare tunnel studio-ssh.rajeshgo.li and reached with ssh studio-away. It is key-only and off by default.
Termux
The terminal app on your phone. The sm app already hands it SSH commands to attach to tmux sessions on the Mac. The SSH key it uses lives in Termux, not in the sm app.
Device key
An SSH public key registered in sm and bound to one device (your phone's Termux, your MacBook). Revoking the device revokes its key.
Home route / away route
Home: the Mac's address on your home network, studio-lan.rajeshgo.li, which the web terminal already uses for its direct LAN connection. Away: the Cloudflare tunnel.

How a shell is reached

Decision surface

Each row is one call. I have made every call not reserved to you; confirm or override.

QuestionRecommendationWhy
1. How does a device reach a shell?Over SSH with a key registered for that device: Termux on the phone, ssh on a laptop. The web page attaches shells only on the home routes, never through Cloudflare. Agents keep today's relay.A stolen phone needs its SSH key as well as its certificate, and at home nothing public opens.
2. When is SSH reachable?Home listener up while at least one shell is open. Tunnel up only after an away device asks to attach; it closes 15 minutes after the last away connection ends, and at once when the last shell closes. The Studio SSH switch stays a manual override ("always on").Your idea: nothing public stays open by default, and the public door costs a request through the device certificate to open.
3. Which SSH keys are accepted?Only keys registered to sm devices, kept in a key file of their own. Revoking a device deletes its key and drops its open SSH connections.Today Studio SSH accepts every key in ~/.ssh/authorized_keys, and revoking a device leaves its SSH access in place.
4. Where do I start a shell?Web: ⋯ → New shell here, in the folder of the agent you are looking at (the menu that already holds Clone). Phone: New session sheet → Terminal. Desktop: sm shell [dir].Every entry point already exists and already creates things. Starting where the agent works is the common case: steering or checking its work.
5. What happens to a shell running a background task?It is never cleaned up. Only a shell sitting at an idle prompt, with nothing running under it and nobody attached for 3 hours, is closed. Retire always works. At most 4 shells are open; at the cap, sm names the open ones.Your build, tail or deploy survives any length of time. Forgotten idle shells still disappear.
6. Who may create a shell?Owner only.You are the only human; a wider circle adds risk for no use.
7. Kill switch.One toggle in Settings, default on. Off closes every shell, the home listener and the tunnel (the tunnel stays up only if you switched Studio SSH on yourself).One action undoes the whole feature without a restart.
8. Do shells show up like agents?Plain rows in today's lists, marked ▹, with "last input" as the fact. Never pinged.You want to see a shell is open, not be messaged because zsh is idle.
9. Is shell output logged?Yes, like agent panes, with the same retention."What ran?" keeps an answer after an incident.
10. Should agents move to SSH too?Not now. Revisit after shells have run on SSH for a few weeks.See below.

On agents over SSH (your question). It would harden agent attach the same way, but it costs three things you use daily. First, the browser: the web terminal cannot attach over SSH, so web attach to agents would end away from home. Second, legibility: sm counts and limits attaches, and shows who is attached, because every attach passes through its relay; an SSH login bypasses sm entirely. Third, the in-app terminal screen and its phone keys would give way to Termux. Shells are the right place to prove the SSH path first, because a shell is the case where arbitrary execution is the point.

What it looks like

Hardening, in one place

You asked what else I would do. These are the layers, strongest first. The first four are new in this revision; the last was already in revision 3.

What stays true: anyone holding an unlocked registered phone and its Termux key, or a laptop with a registered key, has your user's shell on the Mac. That is the feature. Revocation from the web or the app ends it in one action.

FAQ — what this revision changes

Transport. Shells now attach over SSH with a device key, not through the relay that carries agents. Revision 3 relied on the device certificate alone. This follows your review.

Creation on the web. Revision 3 had no way to start a shell from the web; you asked where. The web terminal's ⋯ menu now holds "New shell here".

Cleanup. Revision 3 closed shells after 3 hours without typing, which would have killed a running build. Now only an idle prompt is closed.

Phone keys. The Ctrl modifier for the in-app key row is gone. Shells open in Termux, which has its own Ctrl and Alt keys.

SSH command. The returned command explicitly selects Session Manager's tmux server, so the laptop and phone reach the shell that was created.

Figures. The web figure now follows the real page: top bar, switcher sections and ⋯ menu.

Appendices

A. Data model and interfaces

A.1 — Shell records. A new table in the usage DB, beside seat_sessions. Do not reuse seat_sessions: it maps provider transcripts for the usage ledger, and a shell has none.

CREATE TABLE IF NOT EXISTS plain_terminals (
  id                 TEXT PRIMARY KEY,   -- "term-" + 4 hex
  cwd                TEXT NOT NULL,
  created_by_user    TEXT NOT NULL,      -- owner user id
  created_by_device  TEXT,               -- device id, NULL for CLI
  created_via        TEXT NOT NULL,      -- "web" | "mobile" | "cli"
  tmux_session       TEXT NOT NULL,
  state              TEXT NOT NULL,      -- live | retired
  last_attach_at     TEXT,
  last_input_at      TEXT,
  busy_since         TEXT,               -- set while a process runs under the shell (E.1)
  created_at         TEXT NOT NULL,
  retired_at         TEXT,
  retired_reason     TEXT                -- "owner" | "idle" | "kill_switch" | "tmux_gone"
);
CREATE TABLE IF NOT EXISTS device_ssh_keys (
  fingerprint   TEXT PRIMARY KEY,        -- SHA256:… of the public key
  device_id     TEXT NOT NULL,           -- existing mobile device id, or a named computer
  public_key    TEXT NOT NULL,           -- one authorized_keys line, no options
  added_at      TEXT NOT NULL,
  revoked_at    TEXT
);

A.2 — Listing. /watch/state entries gain shells with kind: "shell", name zsh · <cwd basename>, and the fact "running · <command>" while busy, otherwise "last input <age>". A busy shell sits in the moving section and an idle one in idle, with a ▹ mark and neutral tone. Shells are never in a waiting section and never raise attention.

A.3 — Endpoints. All are owner-gated (decision 6), and each returns 403 plain_disabled when the kill switch is off.

CallBody / result
POST /terminals{"cwd": path, "from_session": id?}. With from_session and no cwd, the shell opens in that session's working directory ("New shell here"). Returns 201 {id, tmux_session, cwd}, or 409 too_many_terminals with the list of open shells.
DELETE /terminals/{id}Retire: kills the tmux session and marks it retired with reason owner.
POST /terminals/{id}/route{"where": "home" | "away"} → {ssh_host, ssh_port, ssh_user, tmux_session, command}. away starts the tunnel if it is off and returns once it is ready (status on), or 503 after 20 s. home never touches the tunnel.
POST /devices/{id}/ssh-keys, DELETE /devices/{id}/ssh-keys/{fingerprint}Register or remove one public key for a device. Ed25519 keys only. Registration rewrites the key file (F.2). GET /devices/{id}/ssh-keys lists keys; for imported it also returns compatible import_candidates. An explicit POST with {"import_authorized_keys":true} imports that preview under imported.

The command field is exactly ssh -t -p <port> <user>@<host> tmux -L '<tmux_socket_name>' attach-session -t <tmux_session>. At home the host is studio-lan.rajeshgo.li and the port is 22222. Away, the host is studio-away, the alias the Studio SSH setup already installs on a client, with a port-less form for that alias. The response also includes tmux_socket_name; omit -L when it is null. This selects the same tmux server that owns the shell.

A.4 — CLI. sm shell [dir] creates a shell (dir defaults to the current directory), prints its id, and attaches in place with tmux attach when run on the Mac. Run elsewhere, it prints the A.3 command. sm shell ls lists shells, and sm shell rm <id> retires one.

A.5 — Launch. Use TmuxRuntime::create_session with /bin/zsh -l in the cwd. Do not wrap it in managed_session_command: shells carry no CLAUDE_SESSION_MANAGER_ID, so sm typed there runs unattributed, as from any plain terminal. Pane logging uses the existing session-log path.

A.6 — Config. terminal_limits gains plain_terminal_enabled (default true), max_plain_terminals (default 4, range 1–16), idle_reap_minutes (default 180, range 15–1440) and tunnel_linger_minutes (default 15, range 1–120). All are owner-editable at runtime, like the existing limits.

B. Security: check order, testable as written

B.1 — Create (POST /terminals) requires, in order: plain_terminal_enabled; the actor is the owner; the request came through the existing guard chain for its route (Access plus device certificate plus bearer on the public route; localhost or the direct LAN listener for the web page); and the count is below max_plain_terminals. Denials use new reason codes plain_disabled, not_owner and too_many_terminals in the existing audit log.

B.2 — POST /terminals/{id}/route with away requires the same chain, plus a device that has at least one unrevoked SSH key. A device without a key gets 409 no_ssh_key, and the app offers Termux setup (D.3).

B.3 — The SSH login itself needs a key from the device key file (F.2). sm never holds private keys.

B.4 — The web page attaches shells only when its chosen route (terminal-route.js) is localhost or the direct LAN listener. On the Cloudflare route the shell row opens a panel with the A.3 away command and a copy button. The server enforces this too: the relay refuses kind: "shell" targets on any connection that did not arrive on localhost or the LAN listener.

B.5 — Every shell create, and every SSH login on the tunnel (read from the sshd log, F.4), sends an owner push: "Shell opened · <cwd> · from <device>" or "SSH login over tunnel · <key comment>".

B.6 — Tests: kill switch off blocks create, route and relay attach, and closes the listener and the tunnel; a non-owner create is denied; away from a device without a key is denied; a revoked key is gone from the key file and its live SSH connection is dropped within 5 s; the relay refuses a shell over the Cloudflare route; and the cap is enforced.

C. Web user experience

C.1 — The ⋯ menu on the terminal page gains "New shell here" after Clone. It calls POST /terminals with from_session, then switches the page to the new shell. On a shell's own page, the ⋯ menu shows "New shell here" (same cwd) and "Copy ssh command". It drops agent-only items: Hand off now, Clone, Follow.

C.2 — The main page's New agent popover gains a Terminal type that asks for a folder only.

C.3 — Shell rows follow A.2. Opening a shell on a home route is the ordinary terminal view, with no key row on desktop. On the Cloudflare route, the view is replaced by a panel: "Shells attach over SSH away from home", the away command, Copy, and "Open tunnel" (A.3 away).

C.4 — The top bar for a shell shows Notes, Details and Retire. Hand off… is hidden.

C.5 — Settings → Terminal limits gains the four A.6 fields. Settings → Devices lists each device's SSH keys, with Add key (paste a public key) and Remove.

D. Mobile user experience

D.1 — Watch list: shell rows as in A.2. A shell's card shows "Open in Termux" in place of "Open terminal".

D.2 — Create: the New session sheet gains a Terminal chip among the agent types. With it selected, the sheet shows Directory and Name only. Create calls POST /terminals, then opens Termux as in D.4.

D.3 — Termux setup, done once per phone. If the device has no SSH key in sm, Open in Termux shows "Set up Termux for shells". That sends Termux a RUN_COMMAND with a result intent. Termux creates ~/.ssh/id_ed25519 if it is missing and returns the public key. The app registers it with POST /devices/{id}/ssh-keys and writes the Termux ~/.ssh/config host entries studio-lan and studio-away. The away entry uses the cloudflared ProxyCommand the Studio SSH setup documents.

D.4 — Open in Termux: the app probes the LAN listener's probe URL with a 700 ms timeout, the same probe the web terminal uses. On success it asks for route home; otherwise away, showing "Opening tunnel…" until the call returns. It then runs the returned command through the existing TermuxBridge.termuxAttach.

D.5 — The in-app terminal screen and its key row are unchanged; they are used for agents only.

E. Lifecycle

E.1 — Busy: every minute, sm checks whether the shell's pane process (#{pane_pid}) has any descendant processes. If it has, the shell is busy, busy_since is set, and the row's fact names the foreground command (#{pane_current_command}). Background jobs started with &, and anything under nohup or disown, are descendants until zsh exits, so they count as busy.

E.2 — Idle cleanup: a shell is retired with reason idle only when all three hold: it is not busy; nobody has been attached (relay or SSH, F.4) for idle_reap_minutes; and no input for idle_reap_minutes. Example: a cargo bench running for 9 hours stays open. A prompt last touched 3 hours ago, with no attach, closes.

E.3 — Server restart: live shells whose tmux session survived stay live. The rest are marked retired with reason tmux_gone.

E.4 — Shells never hold queue slots, never take a perf-machine claim, never receive sm send, and never ping.

F. SSH transport

F.1 — Home listener: the Studio SSH sshd config gains a second ListenAddress on the Mac's LAN address, the address studio-lan.rajeshgo.li already resolves to for the direct web terminal. The loopback listener the tunnel uses stays. The LAN listener runs while at least one shell is live, or while the Studio SSH switch is on. sm adds or removes the address and reloads sshd, which keeps existing connections.

F.2 — Keys: sshd uses AuthorizedKeysFile ~/.config/session-manager/ssh/device_keys, written by sm from device_ssh_keys where revoked_at is null. It is mode 0600 and replaced atomically. Each line carries restrict,pty, so no port forwarding or agent forwarding is allowed. ~/.ssh/authorized_keys is no longer read by the Studio SSH sshd. Migration: the setup flow offers to import its current lines as keys of a device named "imported", for you to sort or remove.

F.3 — Tunnel: the cloudflared agent starts on route away, or when the Studio SSH switch is on. It stops tunnel_linger_minutes after the last SSH connection that came through the tunnel closes. It stops at once when the last shell retires and the switch is off.

F.4 — Connection tracking: sm reads the sshd log in LogLevel VERBOSE, which records the key fingerprint and source of each accepted login. Logins from loopback are tunnel logins; logins from the LAN are home logins. sm keeps a live connection count per source, plus the last-attach time per shell. Device revocation removes the key (F.2), then terminates sessions whose login fingerprint matches.

F.5 — Studio SSH is a shipped spec (specs/900_studio_ssh_toggle.md). The implementing ticket updates it in the same PR: the LAN listener, the device key file, and on-demand tunnel start and stop. The switch keeps its meaning of "always on".

F.6 — Kill switch off: retire all shells, remove the LAN address, stop the tunnel unless the Studio SSH switch is on, and keep the key file.

Z. FAQ

Why not a bare tmux window without a seat record? Naming, retirement, logging, the switcher and cleanup all key off session identity. A shell without a record would need a shadow version of each.

Why does the web page attach shells at home but not away? The browser cannot carry an SSH key. At home, reaching the page needs your Access login and your home network. Away, the only door is SSH with a device key.

Why read the sshd log instead of wrapping ssh? A ForceCommand wrapper could record attaches directly, but it would make sm part of every SSH login and break a plain ssh studio-away for other uses. The log already names the key and the source.

Precedent for non-agent panes? The test suite launches bare shell fixtures (runtime-sh in read_only_http.rs), which shows the launch plumbing does not care what runs in the pane.

What happens to the Ctrl modifier from revision 3? Dropped. Shells open in Termux, which has its own key row. The in-app key row serves agents and is unchanged.
