An Inbox for agent messages

Author: sm-inbox-designer 519d87fe · Design proposal, no ticket yet · Revision 1 · Builds on the shipped design in specs/1580_app_messages_replace_email.html

Memo

Yes: agent messages belong in an Inbox, a tab of its own, not on the Watch page. Watch answers "what are my agents doing?" and is sorted by repo and agent tree. Messages answer a different question, "what is waiting on me?", and want to be sorted by urgency and time. Hanging them off agent cards, as the app does today, makes you scan every card to find what needs you, splits one back-and-forth across several pages, and hides a conversation once its agent's card leaves the screen.

The design below adds a third bottom-nav tab, Inbox, next to Watch and Analytics. Each row is one conversation with one agent. Opening a row shows the whole conversation as a single scrolling page: the agent's messages, your replies, its review requests and its finish report, oldest at the top, with a reply box at the bottom. A notification opens that page, and Back returns to the Inbox, so you can work through several agents in a row without passing through Watch. The Watch card keeps a one-line pointer into the conversation instead of its own message list.

Almost nothing new is stored. Messages, replies, review requests and follow results already sit in the server's database; the Inbox is a new way to list them. The new pieces are two list views (a native Inbox tab in the app, and the same list on sm web), a conversation page built from the existing message reader, a Done action, and the ability to write to a live agent from its conversation without waiting for it to write first.

Terms used here

Message
What an agent's sm send rajesh creates today: a titled markdown note stored by the sm server, with its own page at /messages/<id>. Unchanged by this design.
Blocking message
A message sent with --blocking, meaning the agent cannot continue without you. It shows as Needs you until you reply or clear it.
Review request
What sm doc publish --pr N --review creates: a doc the agent asks you to review on GitHub. Unchanged by this design.
Follow result
What you get after tapping Follow on an agent or a queue job: a notification when the agent finishes (with its report) or dies, or when the job ends. Unchanged; it now also lands in the Inbox.
Conversation
New. Everything between you and one agent, in time order: its messages, your replies, its review requests, follow results for it and its queue jobs. One agent, one conversation, because each agent works one task.
Inbox
New. The list of conversations, one row each, with the ones that need you on top.
Done
New. Your "I have dealt with this" on a conversation. It moves the row out of the open list and clears every open ask in it without sending the agent anything. The row comes back if the agent sends something new.

What is wrong with messages on the Watch page

Four concrete problems with today's layout, all from the shipped design:

  1. Finding what needs you means scanning. The Messages list sits on each agent's card, and cards are grouped by repo and parent agent. With fifteen agents running, a blocking question from one of them is a line on one card among fifteen.
  2. A back-and-forth is split across pages. Every sm send rajesh makes a new message page, and your reply is stored under the message you answered. When the agent answers your reply, that is a new page, which does not show the earlier exchange.
  3. History disappears with the agent. The card shows the last 30 days and at most 20 messages1, and a retired agent's card leaves Watch, taking its messages with it. The notification or email link is the only way back.
  4. Three kinds of "for you" live in three places. Messages are on the card's Messages list, review requests on its Docs list, and follow results only in the notification shade.

What the Inbox looks like

The Watch card after the change. The Messages list comes off the card. In its place is one line, for example 2 new from this agent · open conversation, or Waiting for Rajesh · Keep the old fills table or drop it?, which opens the conversation. The Docs list stays on the card, because docs are the agent's work product, not mail to you. A review request appears in both places: as a doc on the card and as an ask in the Inbox.

How it behaves

SituationWhat happens
An agent sends a blocking questionYour phone buzzes, as today. The tap opens its conversation, scrolled to the question. The row sits under Needs you until you Send or tap Done.
You reply, and the agent answers with another sm send rajeshThe answer lands in the same conversation under your reply. You see the whole exchange on one page.
You want to tell a running agent something it has not asked aboutOpen its conversation from the Inbox or from the Watch card and type. It arrives as [Input from: Rajesh via sm app], the header agents already answer. Today this needs the terminal's "Message agent" box.
An agent asks for a reviewAn ask card in its conversation with Open doc and No review needed. Your review still goes to GitHub and wakes the agent with [sm review], as today.
A followed agent finishes, or diesThe notification, as today, plus a line in its conversation: Finished · report: <title> linking the report, or Ended without finishing.
A followed queue job endsA grey line in the conversation of the agent that submitted it: Queue job <label> failed · 12m.
You tap Done on a conversationIt moves to the Done filter. Any open blocking message becomes Handled and any open review request becomes No review needed, without messaging the agent, which are the two clear actions that already exist. The next thing the agent sends reopens the row.
The agent has endedThe conversation stays in the Inbox with its full history. The reply box says where a reply would go: to the agent's live parent, or nowhere, in which case it is hidden, as the current message page does.
Fifteen agents are running, three want youThe badge says 3. The top three rows are theirs. Agents that only sent notes show a dot, not a number, so the badge means "you are blocking someone".
On a laptopsm web gets the same Inbox at /inbox. Links in sm send output and in fallback email open the conversation, scrolled to that message.

Decision surface

QuestionRecommendationWhy, in one line
1. Is the Inbox its own tab?Yes: bottom nav becomes Inbox · Watch · Analytics. The app still opens on Watch; the Inbox badge tells you when to switch."What needs me" and "what are agents doing" are different questions with different sort orders.
2. What is one row?One conversation per agent, not one row per message.Each agent works one task, so one agent is one topic, and agents already answer your reply with a fresh message rather than threading it.
3. What lands in the Inbox?Messages, review requests, and follow results. Not plain doc publishes and not agent status changes.These are the three things addressed to you; everything else is the Watch page's job.
4. Can you write first?Yes, to any live agent, from its conversation.With a reply box on every conversation, refusing to let you use it until the agent speaks is an artificial limit. The shipped design left this out of scope.
5. What does Done do?One Done per conversation that clears every open ask in it (Handled, No review needed) without messaging the agent. A new item reopens it.One gesture to clear your list; no separate archive, snooze or per-message clearing.
6. What stays on the Watch card?A one-line pointer into the conversation replaces the Messages list. The Docs list stays.A second full message list would drift from the Inbox and clutter the card.
7. What does the badge count?Only conversations that need you (a blocking message or a review request). Unread notes show a dot.A badge that counts FYI notes trains you to ignore it.
8. How is it built?The Inbox list is native in the app; the conversation page is a server-rendered page shown in the app's existing reader and on sm web.The current message page already renders markdown and takes quotes this way, and one page then serves phone and laptop.
9. How many build tickets?Two, in order: (a) server: the Inbox list, the conversation page, Done, writing first; (b) Android: the Inbox tab, the Watch card pointer, notification taps opening the conversation. Mid tier (Opus 1M, high) for both.The server half is testable on sm web before the app changes, and each fits one agent without compaction.

Not in this design

Browser or desktop notifications on sm web. Search across conversations (the Done filter plus scrolling covers two weeks of history; search can follow if it proves too little). Grouping conversations by repo or by parent agent. Messages from agents to anyone other than you. Changes to how sm send rajesh, --blocking, the unread cap or the email fallback work: agents see no difference.

B. Server additions (ticket a)

  1. Conversation key. The sending agent's session id. Items: that session's messages and their replies, its review requests, follow results for the session, and follow results for queue jobs it submitted. Your first-written messages (section D) belong to the addressed session.
  2. Done state. New table owner_inbox_threads(session_id TEXT PRIMARY KEY, done_at TEXT, last_read_at TEXT). A conversation is Done when done_at is later than its newest item. Tapping Done also calls the existing handled and no-review-needed paths for every open ask in it.
  3. GET /inbox: one row per conversation with activity in the last 30 days (Open) or ?filter=done. Row fields: session id and name, repo, agent status (live or ended), group (needs_you, new, earlier), newest item preview (title or "You: …"), newest item time, counts of messages and open asks. Sort: group, then newest item time descending. Also needs_you_count for the badge. Protected the same way /messages/ is (is_protected_read_surface in http.rs).
  4. GET /inbox/{session_id}: the conversation page, server-rendered, reusing the message reader's markdown rendering and reply client. Items in time order. Opening it sets first_viewed_at on its unread messages and last_read_at on the conversation. ?at=msg_… scrolls to that message. /messages/{id} keeps working and redirects to /inbox/{sender}?at={id}, so old links in email and agent output still land correctly.
  5. Send from the conversation. A quote targets the message it was taken from. The whole send is one delivered message, as today. If the conversation has an open blocking message, the reply is recorded against the newest one (making it Replied); otherwise against the newest agent message; otherwise it is a first-written message (section D).
  6. Notification tap target. Message and review notices link to /inbox/{session_id}?at=… instead of /messages/{id} or the doc.

C. Android additions (ticket b)

  1. Bottom nav gains Inbox as the first tab (AppBottomNav.kt, AppNavigation.kt), with a badge from needs_you_count and a dot when any row is new. Start destination stays Watch.
  2. Inbox screen: native list of GET /inbox rows grouped as in Figure 2, pull to refresh, Open / Done filter, swipe right for Done.
  3. Row tap opens /inbox/{session_id} in the existing reader overlay (DocReader.kt); Back closes the overlay onto the Inbox list.
  4. Watch card: the Messages section in WatchScreen.kt is replaced by the one-line pointer; the server's messages list on the session feed becomes a count plus the newest title.
  5. Notification taps (push/NoticePush.kt) switch to the Inbox tab and open the conversation.

D. Writing first

A message you start is stored as a reply with no agent message above it: owner_message_replies.message_id becomes nullable and a session_id column is added. Delivery, header, deduplication and the "no live agent" rule are the same as a reply. The first line reads [Input from: Rajesh via sm app] with no Re: part.

Z. FAQ

Why not thread by message, with a --re flag for agents? Agents would have to remember to pass it, and they answer your reply with a fresh sm send. Grouping by agent needs nothing from them and is correct because each agent works one task.

What if one agent raises two unrelated questions? They appear as two message cards in one conversation, each with its own title and its own Needs you tag. Quoting a paragraph makes clear which one you answer.

Why keep the Docs list on the Watch card? Docs are what an agent produced, which belongs with its status. The Inbox only carries the ask to review.
