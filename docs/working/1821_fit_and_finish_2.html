Scenario 1 · An agent deploys a fix while you are reading

“Restart sm without taking it away from me.”

Today every restart takes sm away for 12 to 16 seconds, and agents restart it often: the server's own 5-second machine samples show a gap of that size 48 times on 29 September and 25 times by 6 pm on the 30th. In the gap the web and the phone show errors, terminals drop, an agent's sm send fails, and a hook that fires is simply lost, because hooks give up after a 1 to 2 second connect timeout and never retry. A lost end-of-turn hook means sm misses that an agent went idle or finished.

The gap exists because the old server is stopped first. The restart script builds the new binary while the old one serves, then boots the old one out, starts the new one, and waits for it to finish its startup checks (recovering sessions, queue jobs, reviews and the board) before it answers anyone.

How it works. sm gets two launchd jobs, a blue slot and a green slot, and runs in one at a time. A restart installs the new build into the idle slot and starts it. The new server prepares without touching anything shared, then asks the old one to hand over. The old server stops taking new work, finishes requests already in flight, and passes its listening socket to the new one. The socket never closes, so a request that arrives during the switch waits in line for a second instead of being refused. The old server stays parked for 30 seconds: if the new one dies in that time, the old one takes the socket back and serves again. A Mac reboot starts only the active slot.

What you notice: live pages and terminals reconnect once, as on a network blip. Nothing else. Cost: two Mid tickets, one for the server and one for the restart script.

FAQ — what changed since revision 2

Auto-start is new, from your review: scenario 6, decision 9, appendix F, and two tickets (twelve in all). Agent types are named in Settings, and the auto-retire ticket now also waits on the auto-start tickets because both edit the same settings files.

FAQ

Why not just make hooks and clients retry? It turns errors into waits only for clients we write. The browser, the phone and Cloudflare would still see 14 seconds of nothing, and a broken build would still take sm down until someone fixes it.

Why not keep finished agents alive forever? An idle agent costs no tokens, but it holds memory, a tmux window, a worktree and a ticket claim, and it clutters Agents and the Board. After an hour it has lost its token advantage too.

Will Restore always work? For Claude and Codex agents on the Studio, yes, once it rebuilds the worktree; today Restore relaunches in the folder retire deleted, where Claude cannot find the conversation, because Claude looks a conversation up by its folder. Agents on another machine, and providers that cannot resume, are never auto-retired.

A. Restart handover

A1. Today

  • scripts/restart-rust-server.sh phase 1 (lock, build, sign, --check-config) leaves the live job alone. Phase 2 (~line 911) boots the job out, waits up to 10 s, moves the staged binary onto .local/bin/sm-server, bootstraps and kickstarts the job, polls /health (60 s), requires a stable pid for 20 s, runs scripts/verify_queue_authority.py, compares session counts and refreshes the CLI.
  • main.rs:125 binds 127.0.0.1:8420 (the only TCP listener until #1794 adds the home-network TLS listener); main.rs:131 binds the queue authority socket queue-runner/authority.sock, whose remove_stale_socket refuses to start while another server answers on it. AppState::try_new (http.rs:611) and router() (http.rs:1594-1615) run recovery synchronously before axum::serve. There is no signal handling and no graceful shutdown.
  • The plist (scripts/rust-service-cutover.sh:316-358): label com.rajeshgoli.session-manager-rust, RunAtLoad, KeepAlive true, ThrottleInterval 10.
  • Hooks: hooks/notify_server.sh:155 uses --connect-timeout 2 --max-time 5; hooks/context_monitor.sh:75 uses 1 and 2. Neither retries.
  • Queue jobs run in their own process group and survive restarts; startup recovery re-polls them (queue.rs:1905-1987, log line “recovered_running: 4”). Tmux and agents are separate processes and survive.

A2. Slots

  • Two launchd labels, com.rajeshgoli.session-manager-rust.blue and ….green, with binaries .local/bin/sm-server-blue and .local/bin/sm-server-green. A slot's binary is written only while that slot's job is booted out, which keeps the launch-constraint lesson (docs/product/lessons.md:77).
  • ~/.local/share/claude-sessions/active-slot holds blue or green, written by the new server after it takes over. .local/bin/sm-server becomes a symlink to the active slot's binary for anything that runs the server by path.
  • Only the active slot's plist exists in ~/Library/LaunchAgents; the script deletes the other after booting it out. A reboot therefore starts one server.
  • KeepAlive becomes {SuccessfulExit: false}: a server that exits 0 after handing over is not relaunched; a crash still is.
  • Migration: the first run of the new script boots out the legacy label, installs blue, and starts it the old way (one last gap). verify_queue_authority.py takes the active slot's label.

A3. Protocol

  1. The script installs the build into the idle slot, writes its plist with the extra argument --take-over, and bootstraps it.
  2. With --take-over, the new server loads config and opens nothing for writing. It may read databases to warm caches. It must not run schema changes, recovery, background loops, or bind any listener.
  3. It connects to ~/.local/share/claude-sessions/handover.sock (mode 0600, served by every server) and sends {"schema":"sm.handover.v1","version":…,"pid":…}. The old server checks the peer is its own user and that the peer pid belongs to the other slot's launchd job (the same SMJobCopyDictionary check the verifier makes).
  4. The old server: stops accepting on every listener; sets the shutdown signal (A4) so every background loop exits at its next wake; closes terminal websockets and event streams with close code 1012 (“service restart”); waits for in-flight HTTP requests to finish, up to 10 s, then drops the rest; and stops serving the authority socket.
  5. It passes the listener file descriptors (8420, the #1794 TLS listener, the authority socket) to the new server with SCM_RIGHTS (nix, add the socket and uio features), keeping its own copies, and replies {"handed_over":true}.
  6. The new server runs today's startup steps that write (schema ensure, try_new recovery, the router() init calls), starts loops, adopts the listeners with TcpListener::from_std and the authority socket with UnixListener::from_raw_fd, serves, writes active-slot, and sends {"serving":true}.
  7. The old server waits 30 s. If the new server's connection closes or /health through the socket fails in that time, it runs its own startup recovery, accepts on its copies and serves; the script reports “rolled back” and boots out the new slot. Otherwise it closes its copies and exits 0.
  8. The script, seeing serving and then the old pid gone, boots out the old slot, deletes its plist, and runs today's checks (stable pid 20 s, queue authority, session count, CLI refresh).

Any failure before step 5 leaves the old server serving: it resumes accepting and the new server exits non-zero. Steps 4 to 6 are the only time requests wait. Target: median under 2 s, never over 4 s (under the hooks' 5 s limit), measured on a scratch server against a copy of live state (docs/product/lessons.md scratch-server recipe) with 30 live-like sessions, and reported in the PR.

A4. Shutdown signal

  • One tokio::sync::watch plus an AtomicBool in AppState. Every loop started in main.rs and router() (follow delivery, reparent reconcile, queue completion retry, reminder dispatcher, handoff sweeper, memory guard, utilization recorder, usage scans, Studio SSH reconcile, board and review recovery, admission retries) checks it at each wake and returns.
  • Queue job monitor threads stop polling without touching their jobs; the new server's recovery re-adopts them exactly as after today's restart.
  • SIGTERM sets the same signal and then exits after the 10 s drain, so a plain launchctl bootout is also graceful.

A5. Tests

A handover between two in-process servers on a temporary port: a request in flight during the handover completes; a request sent during it waits and succeeds; no loop runs in both (a counter per loop); a new server that dies within 30 s gives the socket back; a bad --take-over peer is refused. Live proof: run curl /health every 100 ms during a real restart and report the longest wait and that nothing failed.

B1. Store

  • The path is a config key paths.notes_db, set explicitly in the installed config like the other stores.
  • A save writes notes and a revision, but a revision is kept only when the previous kept revision is older than 10 minutes or differs by more than 2,000 characters; otherwise the latest revision is overwritten. Revisions older than 90 days thin to one per day. Deleting a note sets deleted_at; it is purged after 30 days.
  • Body limit 2 MB. Title is the first line of the body without leading #, up to 80 characters, unless set.

B2. Routes (owner and phone guards only; no agent access)

  • GET /notes → [{id,title,updated_at,chars}]. GET /notes/{id} → {id,title,body,version,updated_at}.
  • POST /notes {title?,body} → the note. PUT /notes/{id} {body,title?,if_version} → the note, or 409 with the current note when if_version is stale. DELETE /notes/{id}.
  • GET /notes/{id}/revisions, GET /notes/{id}/revisions/{version}, POST /notes/{id}/restore {version} (writes a new version).
  • GET /notes/search?q=&regex=0|1 → up to 50 hits [{note_id,title,updated_at,start,end,text}]. Returns matching notes, newest edited first, up to 100, as [{id,title,updated_at,chars,snippet,matches:[{start,end}]}]. snippet is the whole body when the note is under 1,200 characters, else the paragraph (text between blank lines, or a whole fenced code block) holding the first match. Case-insensitive substring by default; regex=1 uses Rust regex with a 100 ms budget. An empty q returns every note in the same shape.
  • POST /notes/import (multipart .md/.txt) splits the file before every line starting with # and at every line that is exactly ---, drops empty parts, and creates one note per part; it returns the ids. Download (one note, or all as a zip) is client-side.
  • POST /github/issues {repo,title,body} runs gh issue create as the Board's Close runs gh issue close (http/board.rs:1150) and returns {number,url}. Repos offered are those sm knows from claims and lanes.

  • New keys, in order of preference:
    1. ticket:<owner/repo>#<n>. For an agent item (message, owner note, fired follow, finished row): the sender's ticket claim open at the item's time, the earliest-claimed when several. For a doc: the ticket claim of the author session open at its first publish, else the ticket that the doc's PR closes (the Board's PR-to-ticket link).
    2. pr:<owner/repo>#<n> when there is no ticket. For an agent item: the sender's PR claim open at the item's time. For a doc: its PR.
    3. docpath:<owner/repo>/<path> for a doc with neither (published without a PR): every doc for that path joins.
    4. agent:<session> for an agent item with neither.
  • Example. sm-1782 holds #1782 and sends two messages; its successor sm-1782-2 claims #1782 and sends one; the memo is published on PR #1785 and again on PR #1802 by those agents. All five items share ticket:rajeshgoli/session-manager#1782. sm-maintainer, holding no ticket, keeps agent:….
  • done_items and Done move to the new keys. Migration maps an old agent or doc key's watermark onto the new key it falls under, taking the item count as of migration, so nothing marked done reappears.
  • Row: title is #n {ticket title}, else PR #n {PR title}, else the doc title, else the agent name. Group is the highest of its items (needs you, finished, new, earlier). Preview is the newest item that set the group. The second line lists the thread's agents and “{d} docs, {r} revisions”.
  • Thread JSON (GET /inbox/thread/{key}?format=json, replacing /inbox/agent/{id} and the doc thread page, which redirect) lists items oldest first, each with sender {id,name,status}; doc revisions become {"type":"doc_revision", doc_id, pr, sha, at, review_state} cards.
  • Reply target: the newest sender in the thread that is live; else the newest sender whose reply would restore it (appendix E3); else today's live_recipient on the newest sender. The JSON carries reply_to {id,name,restores:bool,retired_at} and reply_options (every sender in the thread), which the ▾ selector uses. POST /inbox/thread/{key}/send {text, to?}.

C2. The fold and Archive

  • A thread is ended when it holds no doc, every sender in it has ended (session_ended, http/messages.rs:76, or absent from the registry), it is not needs-you, and it has no finished row with read_at null. A thread holding any doc is never ended.
  • Archive: POST /inbox/archive {thread_key} stores archived_items = item count beside done_items (owner_inbox.rs). A thread is archived while its item count equals that value. Archive is offered on every thread row and thread header (shortcut y), and does what Done does too. POST /inbox/unarchive clears it.
  • Ended and archived threads leave the groups and sort, newest first, under one fold row “Folded · {n} threads ({first three names}, …)”, collapsed by default (state in localStorage["sm-inbox-folded-open"]). JSON: group:"folded", with folded_by:"ended"|"archived".
  • Any new item (message, finished row, doc revision) brings a thread out: an ended thread because its sender is live or was just restored, an archived one because its item count passed the stored value.
  • Example. The #1768 thread holds memo 1768 and messages from sm-1768, now retired. It stays under Earlier however long ago it merged. You press Archive and it moves to Folded. A later revision of memo 1768 brings it back.

E. Auto-retire and restore on message

E1. Eligibility

A session is auto-retire eligible when all hold:

  • It was started by sm: it has a spawn launch intent (sessions.rs SpawnLaunchIntentRecord), or is a handoff successor, or a reader agent; and it holds no role registration (sm roster), and its node is the primary node, and its provider is claude, codex or codex-fork (the providers History can restore, http/agent_history.rs:116).
  • It is finished (agent_task_completed_at set) and idle, and both have held for the delay (default 60 minutes) measured from the later of task-complete and the last activity.
  • Nothing waits on it: no open blocking owner message from it; no doc of its with an open review request; no queue job of its running or pending; no Codex or local review request of its outstanding; no live child session; Rajesh does not Follow it.

E2. The sweep

  • Every 60 s, and only on the serving server (A4 signal), sm retires each eligible session through retire_core_session_with_runtime_authorized with a new authority RetireAuthority::auto_retire(), recording retirement_intent: "auto" and terminal provenance “auto-retire after {n} minutes finished and idle”.
  • Settings: owner_settings gains auto_retire {enabled: true, idle_minutes: 60} (range 15 to 1440). GET/PUT /settings/auto-retire, owner and phone guards. Web Settings › New agents and the phone's Settings show a toggle and the minutes (round 1 Toggle).
  • History rows show “retired automatically”. The Finished Inbox row stays until Done (round 1 D3), and C2 keeps it out of the fold until then.

E3. Restore on message

  • live_recipient (http/messages.rs:87-115) gains a first step: when the session ended with retirement_intent: "auto" and has no live successor, the recipient is the session itself, marked restores: true. Sessions retired any other way keep today's chain (successor, then parent).
  • Sending to a restores recipient restores it (restore_session, http.rs:10726), then queues the message; today's “a stopped one gets it on restore” delivery applies. This covers the Inbox reply, the doc review wake (doc_agent, http/docs.rs:1540, uses the same rule), and agent-to-agent sm send to that session.
  • Worktree. Before relaunch, when working_dir does not exist and a claim of the session recorded it as worktree_path with a branch: run git worktree add {path} {branch}, fetching the branch from origin when it is not local; when the branch is gone (merged and deleted), git worktree add --detach {path} origin/{default} and tell the agent so in a one-line note delivered before the message. The path must be identical, because Claude finds a conversation by its folder. When neither applies, restore fails with “worktree {path} is gone and has no branch to rebuild from”, and the message falls back to today's chain.
  • Claims. Claims that the auto-retire ended (end_reason “retired”, ended at the retire time) are reopened, unless another live session has claimed the same item since.
  • Undo on #1826's retire toast calls the same restore, for 10 s.
  • Tests: each eligibility exclusion; the sweep respects the setting and delay; a reply to an auto-retired agent restores it and delivers; a reply to a manually retired one goes to the parent; worktree rebuilt at the same path from branch, from origin, detached; claims reopened unless taken; doc review wake restores.

F2. Store and routes

F3. Trigger

  • In each board recompute (board.rs:1534 run_pass), after pushes::decide (board/pushes.rs:31) finds the tickets that just became Ready, and also for any waiting row whose ticket is Ready (so a missed pass or a restart catches up): unless auto_start_paused, and when the ticket has no open ticket claim, call the same start path as client_start with the stored choice and the rendered or stored brief, under board_lock so one ticket starts once.
  • Success: state = started, session_id set. The ready alert for that lane drops the started ticket and a per-ticket owner notice “Started #{n} as {name} ({model}, {effort})” goes out the same way (follow worker push).
  • Failure: attempts + 1, last_error, notice “Could not start #{n}: {error}”; retried on later passes while attempts < 3, then failed, shown on the chip with Retry (which PUTs again).
  • Never starts a ticket while it is Blocked, nor one in Close ready (container) or Done state. A ticket that closes, or that someone claims or starts by hand, moves its row to cancelled with that reason.
  • Only the serving server runs the trigger (A4 shutdown signal).

Z. FAQ

Why pass the socket rather than run a small proxy in front? A proxy is one more always-on process that itself needs restarting, and it would still need the old and new servers to agree who runs the background work. Passing the socket needs only that agreement.

Can both servers ever run background work at once? No. The old server stops its loops and drains before it passes the socket, and the new one starts loops only after it has the socket. The 30-second parked old server runs nothing unless it takes the socket back.

What about schema changes in a new build? They run in step 6, after the old server stopped. A rollback in step 7 then runs old code against a newer schema; migrations in this repo only add tables and columns, which old code ignores. A ticket that needs a destructive migration must say so and restart the old way.

Why not let agents read notes? Notes are your scratch space, and may hold half-formed thoughts about agents' work. Start agent and File ticket are how a note reaches an agent.

Why is a reader agent Sonnet? It reads one doc and some code and answers questions: low-tier work under CLAUDE.md §2.
