1452 — Agent work claims and the history page

Author: sm-1452-spec-author b1f9510b · Ticket #1452 · Revision 1 · 2026-09-24

Memo

Agents will tell sm which ticket and which pull request (PR) they are working on, and sm will use that to do three things it cannot do today. It will show you, on one page, which agent worked on which ticket, opened which PR, wrote which docs and asked for how many reviews. It will refuse to let two unrelated agents work the same ticket or PR at once. And it will notice when an agent looks finished but its ticket or PR is still open, and ask that agent to close it out or write down what remains.

The agent does this with two new commands, sm ticket <N> when it starts a ticket and sm pr when it opens a PR. sm also infers a PR claim whenever an agent runs sm request-codex-review or sm doc publish on a PR, so the record fills in even when an agent forgets. GitHub stays the source of truth for tickets and PRs; sm stores only who held what, and when.

I recommend building it as four tickets under #1452. The decisions I need from you are in the table below; every one has a recommendation.

Claim
A record that one sm session is working on one ticket or one PR, from the moment it runs sm ticket or sm pr until the work closes on GitHub, the agent is retired, or it hands the claim over. The agent holding it is the holder.
Same line
Two sessions are in the same line when one is the parent, grandparent or other ancestor of the other in sm's parent–child tree. Siblings are not in the same line.
Collision
Two live sessions that are not in the same line both claiming one ticket or PR.
Implicit claim
A PR claim sm records on the agent's behalf when it runs sm request-codex-review <PR> or sm doc publish on a PR.
Open-work check
sm's test for "this agent looks finished, but its ticket or PR is still open". When it fires, sm sends the agent a message starting [sm claim].
History page
A read-only web page, at /history on the sm server, listing tickets and PRs with the agents, PRs, docs and review counts attached to each.

The agent contract

This paragraph goes into AGENTS.md, section 3, right after "Worktrees", in this repo and in the shared template your other repos use:

**Claim your work.** When you start on a ticket, run `sm ticket <N>`. When you open
a PR, or take over someone else's, run `sm pr` from its branch. Put `Closes #<N>` in
the PR body for each ticket the PR finishes; "Implements #N" does not close it.
Reviewers and scouts don't claim; only the agent doing the work does. If `sm ticket`
or `sm pr` refuses because another live agent holds it, stop and tell me; use
`--take` only when I say so. A `[sm claim]` message means sm found your ticket or PR
still open when you look finished: do what it says.

C. Claim rules

Let C be the claimant and item the ticket or PR. The server evaluates, in order, inside one DB transaction after the GitHub check (appendix D) succeeds:

  1. Validate. Kind must match (__typename Issue for ticket, PullRequest for PR). Ticket must be open; PR must be open. Else the error rows of appendix B.
  2. Already held by C (active row, same session) → "already yours". Nothing written.
  3. Other active holders H. Classify each:
    • dormant: H's session is stopped but not retired → end H's claim with superseded, ended_by_session_id = C, and enqueue to H (delivered on restore, as all sends to stopped sessions are): [sm claim] While you were stopped, <C name> (<C id>) took over <ticket|PR> #N. Don't continue it; tell your parent or Rajesh what state you left it in.
    • retired: cannot occur (retire ends claims); if found, end it with retired and continue.
    • same line: H is an ancestor or descendant of C, walking parent_session_id on live session records (cap 32 hops) → allowed; note for output.
    • unrelated live: any other case → a collision holder.
  4. Collision holders exist:
    • explicit claim without --take → refuse (exit 3), write collision_refused, write nothing else;
    • explicit claim with --take → end every collision holder's claim with taken, enqueue to each: [sm claim] <C name> took <ticket|PR> #N from you. Stop working on it, and tell your parent or Rajesh the state you left it in., then insert C's claim;
    • implicit claim → insert C's claim, write collision_recorded, return a warning the calling command prints: Warning: PR #N is also held by <H name> (<H id>), working. Two agents on one PR collide at merge; tell Rajesh.
  5. Insert C's claim and a claimed event. For a PR claim, insert a work_links row (source = claim) to every ticket in the same repo that C holds actively at this moment.

D. GitHub sync

  • One query shape. Per repo, one GraphQL call through gh_command_output (http.rs:708) with one alias per number, at most 50 aliases per call: 
    query { repository(owner:"o", name:"n") {
  i1449: issueOrPullRequest(number: 1449) { ...F }
  i1460: issueOrPullRequest(number: 1460) { ...F } } }
fragment F on IssueOrPullRequest {
  __typename
  ... on Issue { title state stateReason closedAt url }
  ... on PullRequest { title state mergedAt closedAt url headRefName headRefOid
    closingIssuesReferences(first: 20) { nodes { number repository { nameWithOwner } } } } }
    PR state is OPEN | CLOSED | MERGED; map to open | closed | merged. Ticket state is OPEN | CLOSED.
  • Partial failures. gh api graphql exits 1 when any alias fails but still prints data for the rest (appendix K). Parse stdout whenever it is valid JSON, whatever the exit code. A null alias with a NOT_FOUND error → set that item's sync_error = "not found" and leave its state. Invalid JSON or a transport error → set sync_error on every item in the batch; keep states.
  • Claim-time fetch: the same query with one alias; the result is upserted into work_items before the claim rules run. Transport failure → the "GitHub unreachable" error; nothing recorded.
  • Periodic sync: a background task every 300 s (config work_claims.sync_interval_seconds, default 300, minimum 60). Tracked set: every work_items row whose state = open and which has an active claim or a work_links row to an item with an active claim; plus tickets linked from any open tracked PR. Closed items are never re-polled.
  • On each item: upsert; if state changed, write state_changed and apply the claim-ending rules; for PRs, insert work_links rows (source = closing_ref) for each closingIssuesReferences node whose nameWithOwner equals the PR's repo, and upsert those tickets into work_items (fetched in the same or next sync).
  • After a sync pass, run Check A for PRs that turned merged in it (appendix F), then Check C.
  • Rate: one call per repo per 5 minutes is ~12 GraphQL points an hour per repo, against 5,000 (appendix K).
  • The history page, /session-obligations and sm ticket listing read stored rows only and never call gh (same rule as the docs spec's list projection).

F. Open-work checks

All messages go through RetainedQueueStore::enqueue_message(target, text, "important", Some("work_claim")) (queue.rs:1529), the same durable path as [sm task-complete]. Each enqueued message writes a nudge event on every item it names. Open item = work_items.state = open after the fetch that precedes the check.

Check A — merged, ticket still open

  • When: sync records a PR open→merged transition. If merged_at is less than 60 s before the fetch, defer this PR's check to the next pass (GitHub closes linked tickets asynchronously).
  • Tickets considered: every ticket linked to the PR (work_links, either source), freshly fetched in that pass; keep those still open.
  • Recipients: the live-or-dormant holders of each open ticket, plus the PR's holders whose claim just ended merged. Deduplicate by session; one message per session naming all its tickets. Retired recipients are skipped; if no one remains, the nudge event is written with message_id = null and the page shows Open after merge.
  • Text (one ticket): as in the memo. Several tickets: [sm claim] PR #<P> merged, but tickets #a ("…"), #b ("…") are still open. If the PR finished them, close each: gh issue close <n> --repo <repo> --comment "Done in #<P>". If work remains, comment on the ticket what remains. Then carry on.

Check B — at task-complete

  • When: after SessionStore::task_complete (sessions.rs:8273) succeeds. Run in a spawned task; never delay or fail the task-complete response or the parent notification.
  • Fetch the caller's actively claimed items fresh (one query per repo). If any is open, send the caller one message listing each, with the open-PR clause when a claimed PR is open: [sm claim] You ran sm task-complete, and you still hold: ticket #1452 (open), PR #1468 (open, not merged). If you're finished: merge the PR once its review is clean, make sure the ticket closes, and run sm task-complete again. If not: comment on #1452 what remains, then continue or stand by. Omit the clauses that don't apply (no PR clause when no open PR is held; no ticket clause when no open ticket is held).
  • Sets nudged_idle_at = now on the claims named, so Check C does not repeat it.

Check C — idle with open work

  • Evaluated after each sync pass, per session with at least one active claim on an open item. Fires when all hold:
    1. the session is not stopped and its status is idle, continuously for ≥ 30 min (config work_claims.idle_nudge_minutes, default 30), measured from last_activity;
    2. the session's entry in project_session_obligations (http.rs:6253) has an empty waiting_on (no queue job, Codex review or owner review outstanding);
    3. at least one named claim is armed: nudged_idle_at is NULL, or the session started a turn more than 30 min after nudged_idle_at (use activity_turn_start_hook_at where the provider sets it, else the last idle→running transition of status).
  • Message: the idle text in the memo, listing every armed open item, same clause rules as Check B. Set nudged_idle_at = now on those claims.
  • Why the re-arm rule: the nudge itself starts a turn within seconds, so it cannot re-arm itself. A later turn more than 30 minutes on means new work arrived (you, a parent, a queue wake), and the next idle stretch deserves a fresh check.

sm pr closing-keyword warning

After a successful explicit or implicit PR claim, if C actively holds tickets in the same repo that are not in the PR's closingIssuesReferences, print: Note: PR #1468 doesn't close ticket #1452. If it finishes the ticket, add "Closes #1452" to the PR body (gh pr edit 1468 --body ...). One line per ticket. A warning only; the claim stands.

G. Worktree cleanup at retire

Runs in a spawned task after the claims end at retire. Candidates: each distinct worktree_path on the session's PR claims (any end reason), plus the session's working_dir if its current branch equals the head_ref of a merged PR the session claimed. Sessions on remote nodes are skipped (the path is not local). For each candidate, all must hold, else write worktree_left with the first failing reason:

#ConditionReason when it fails

Write worktree_removed. The retire response gains worktrees: [{path, removed: bool, reason}]; sm retire prints one line each: Removed worktree ~/worktrees/sm-1449-owner-docs (PR #1460 merged). or Left worktree ~/worktrees/x: git refused: contains modified or untracked files. Because cleanup runs asynchronously, the response reports results available within 10 s and says cleanup pending otherwise; the page always shows the final event.

Remote branches are not touched; that is GitHub's "Automatically delete head branches" setting (memo row 6): gh api -X PATCH repos/rajeshgoli/<repo> -F delete_branch_on_merge=true. It is off for this repo today (appendix K).

Z. FAQ

Why not infer tickets from branch names like 1452-spec? Branch names are a convention, not a contract; the primary repo's branches don't follow it, and a wrong inference would create false collisions. A PR's "Closes #N" is GitHub's own link and is used.

Why do reviewers not claim? A claim means "I am changing this"; a reviewer changes nothing. If reviewers claimed, every review would be a collision.

Why not block sm task-complete until the ticket is closed? A blocked completion strands the parent's wake and can loop an agent that legitimately left work for a follow-up ticket. One message is enough; the history page shows anything left open.

Why 30 minutes for Check C? Long enough that an agent between two quick steps, or one briefly waiting on a reply, is left alone; short enough that a stalled finish is caught the same hour. It is config (work_claims.idle_nudge_minutes).

What about an agent waiting on the owner in chat? sm cannot see that, which is why the texts say "if you are waiting on Rajesh, stay idle". It costs one short turn once per stretch.

Why a server page rather than the unmounted web/sm-watch React app? The Rust server serves no web app today (web/sm-watch was a Python-era mount). A plain server page matches the doc reader, works in the app's WebView with the existing auth, and needs no build pipeline.

Relation to the direction in #1399. Claims here are the "claims" primitive that direction names: mutual exclusion bound to session liveness, with tickets and PRs staying in GitHub. The per-ticket timeline page is a first version of a stable per-ticket page.

Cross-repo links (a PR in one repo closing a ticket in another) are ignored in this version; GitHub reports them, and work_links can take a ticket_repo column later.
