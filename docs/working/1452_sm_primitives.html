1452 — Agent work claims and the history page

Author: sm-1452-spec-author b1f9510b · Ticket #1452 · Revision 4 · 2026-09-24

Memo

Agents will tell sm which ticket and which pull request (PR) they are working on. sm will use that to do four things it cannot do today. It will show you, on one page, which agent worked on which ticket, opened which PR, wrote which docs and asked for how many reviews. It will refuse to let two unrelated agents work the same ticket or PR at once. It will tell an agent that looks finished, in plain facts, that its ticket or PR is still open. And it will own each agent's worktree from creation to deletion. Alongside, sm watch gets a web version on the laptop, and both show docs as a first-class section.

The agent uses two new commands: sm ticket <N> --setup-worktree when it starts a ticket, and sm pr when it opens a PR. sm also infers a PR claim whenever an agent runs sm request-codex-review or sm doc publish on a PR, so the record fills in even when an agent forgets. GitHub stays the source of truth for tickets and PRs; sm stores who held what, and when. sm's messages state facts only; what an agent does about them is written in AGENTS.md.

You approved the design in revision 2. Your revision-3 comments add six decisions, at the top of the decision surface. Two of them keep this work on the path to the design in #1399, which the next section maps.

Claim
A record that one sm session is working on one ticket or one PR, from sm ticket or sm pr until the work closes on GitHub, the agent is retired, or the claim is handed over. The agent holding it is the holder.
Same line
Two sessions are in the same line when one is an ancestor of the other in sm's parent–child tree. Siblings are not.
Collision
Two live sessions, not in the same line, both claiming one ticket or PR.
Implicit claim
A PR claim sm records on the agent's behalf when it runs sm request-codex-review <PR> or sm doc publish on a PR.
Open-work check
sm's test for "this agent looks finished, but its ticket or PR is still open". When it fires, sm sends the agent a message starting [sm claim] that lists the facts.
Managed worktree
A git worktree that sm ticket --setup-worktree created for the claim. sm deletes it when the agent is retired, unless it is unsafe or the agent asked to keep it.
History page and web watch
Read-only pages on the sm server. The web watch is the home page, sm.rajeshgo.li/: the browser version of the sm watch terminal view, with live sessions, what each is doing, what it holds and the docs it wrote. /history lists tickets and PRs with their agents, PRs, docs and review counts, and /t/<repo>/<n> is one ticket's whole story.

The agent contract

This goes into AGENTS.md, section 3, right after "Worktrees", replacing that paragraph's "create your own worktree" guidance. It goes into this repo and into the shared template your other repos use. The policy lives here, not in sm's messages:

**Claim your work.** Start a ticket with `sm ticket <N> --setup-worktree` and work in
the worktree it prints (plain `sm ticket <N>` if you already have one). When you open
a PR, or take over someone else's, run `sm pr` from its branch. Put `Closes #<N>` in
the PR body for each ticket the PR finishes; "Implements #N" does not close it.
Reviewers and scouts don't claim. When you are retired, sm deletes your worktree if
nothing would be lost; if something there must outlive you (a running server,
results not yet pushed), run `sm worktree keep --reason "<why>"`.

`[sm claim]` messages state facts. Act on them like this:
- Your claim is refused because another live agent holds it: stop and tell me.
  Use `--take` only when I say so.
- Another agent claimed your ticket or PR: stop working on it and tell your parent
  or me the state you left it in.
- A merged PR's ticket is still open: if the PR finished it, close it
  (`gh issue close <N> --comment "Done in #<P>"`); otherwise comment on the ticket
  what remains.
- You hold open work at task-complete or while idle: if you are waiting on me, stay
  idle. If you're finished, merge the PR once its review is clean, make sure the
  ticket closes, and run `sm task-complete`. If not, comment on the ticket what
  remains, then continue or stand by.

  • Without --repo, the repo is the cwd's; outside a git repo the command fails with "run this from the repo's checkout, or pass --repo owner/name".
  • sm pr with no number runs gh pr view --json number,state in the cwd, as resolve_doc_publish does (bin/doc/mod.rs:340-351). No open PR → "No open PR for branch <b>. Open one first (gh pr create) or pass the PR number."
  • --ticket T (repeatable) names the tickets the PR is for; each must be an open ticket in the same repo, else the claim fails with the ticket errors of the table below. It links; it does not claim the ticket.
  • The CLI sends worktree_path = git rev-parse --show-toplevel and branch = git branch --show-current (empty → NULL) when the cwd is inside the claimed repo; otherwise both NULL.
  • --release and --take together is a usage error.
  • sm spawn --ticket N adds ticket and ticket_repo (default: the spawn's working directory's repo) to the spawn request. The server runs the claim rules (appendix C) for the new session before creating it, with the spawner as its parent, so a ticket the spawner holds is shared (same line). A collision refuses the whole spawn with the appendix B refusal text and exit 3, and no session is created. Sessions live in the session store's JSON file and claims in SQLite, so the two writes use a reservation instead of one transaction:
    1. Allocate the new session's id first (generate_unique_session_id, sessions.rs; create_core_session* takes a pre-allocated id).
    2. Insert the claim with reserved_at = now, source = spawn, worktree_path = the spawn's working directory when it is inside the repo. A reserved claim counts as a holder for collisions, but pages and checks ignore it and no event is written yet.
    3. Create the session with that id. If creation fails, delete the reserved claim and return the spawn error.
    4. Confirm: clear reserved_at and write claim.taken.
    Recovery at server start and on every sync pass: a claim reserved more than 5 minutes ago is confirmed if its session exists in the session store, and deleted otherwise. Every completed spawn ends with both records and every failed spawn with neither. The claim exists before the child's first turn, since that turn starts only after step 3. No --take on spawn.

C. Claim rules

Let C be the claimant and item the ticket or PR. The server evaluates, in order, inside one DB transaction after the GitHub check (appendix D) succeeds:

  1. Validate. Kind must match (__typename Issue for ticket, PullRequest for PR). Ticket must be open; PR must be open. Every --ticket number must also be an open ticket (Issue) in the same repo, checked from the same claim-time fetch. Any failure aborts the whole claim and writes nothing, with the error rows of appendix B naming the failing number.
  2. Already held by C (active row, same session) → no new claim row. If --take is given, first run steps 3–4 against the other holders as for a new explicit claim with --take (this resolves a collision that an implicit claim recorded), adding Took … from … notes. For an explicit PR claim, still apply step 5's linking rule (so sm pr <P> --ticket <N> after an earlier claim adds the link) and fill worktree_path and branch if they are NULL (an implicit claim later made explicit). Output "already yours", plus Linked PR #P to ticket #N. per new link. Otherwise nothing is written.
  3. Other active holders H. Classify each:
    • dormant: H's session is stopped but not retired → end H's claim with superseded, ended_by_session_id = C, and enqueue to H (delivered on restore, as all sends to stopped sessions are): [sm claim] While you were stopped, <C name> (<C id>) claimed <ticket|PR> #N. Your claim on it ended.
    • retired: cannot occur (retire ends claims); if found, end it with retired and continue.
    • same line: H is an ancestor or descendant of C, walking parent_session_id on live session records (cap 32 hops) → allowed; note for output.
    • unrelated live: any other case → a collision holder.
  4. Collision holders exist:
    • explicit claim without --take → refuse (exit 3), write claim.refused, write nothing else;
    • explicit claim with --take → end every collision holder's claim with taken, enqueue to each: [sm claim] <C name> (<C id>) claimed <ticket|PR> #N. Your claim on it ended., then insert C's claim;
    • implicit claim → insert C's claim, write claim.collision, return a warning the calling command prints: Warning: PR #N is also held by <H name> (<H id>), working.
  5. Insert C's claim and a claim.taken event. For an explicit PR claim, insert work_links rows (source = claim): to each --ticket given; if none is given and C actively holds exactly one ticket in the same repo, to that ticket; if C holds several and names none, to none, and print You hold tickets #a, #b; PR #P is linked to neither (--ticket links one). Implicit claims never create claim links. GitHub closing references add links independently (appendix D). A wrong link would misfile the PR on the page and make Check A ask about an unrelated ticket, so ambiguity links nothing.

F. Open-work checks

All messages go through RetainedQueueStore::enqueue_message(target, text, "important", Some("work_claim")) (queue.rs:1529), the same durable path as [sm task-complete]. Each enqueued message writes a claim.nudge event on every item it names. Open item = work_items.state = open after the fetch that precedes the check.

Check A — merged, ticket still open

  • When: sync records a PR open→merged transition → set merge_check = pending in the same write. After each pass, for every pending PR whose merged_at is at least 60 s before now (GitHub closes linked tickets asynchronously), run the check and set merge_check = done in the same transaction that enqueues the messages. A pending PR younger than 60 s stays pending for the next pass; a restart keeps it pending.
  • Tickets considered: every ticket linked to the PR (work_links, either source). Run the check only when every linked ticket is settled: either it was fetched successfully in this pass, or an earlier fetch already recorded it closed. A ticket that is a never-fetched stub (for example a closing reference first seen in the same pass as the merge), or whose fetch failed this pass, leaves the PR pending; the tracked-set rule fetches it next pass. Keep the settled tickets that are still open.
  • Recipients: the live-or-dormant holders of each open ticket, plus the PR's holders whose claim just ended merged. Deduplicate by session; one message per session naming all its tickets. Retired recipients are skipped; if no one remains, the claim.nudge event is written with message_id = null and the page shows Open after merge.
  • Text: [sm claim] PR #<P> merged <age> ago. Linked ticket #<n> "<title>" is open. For several tickets: … Linked tickets #a "…", #b "…" are open. Facts only; what the agent does is in AGENTS.md.

Check B — at task-complete

  • When: after SessionStore::task_complete (sessions.rs:8273) succeeds, set check_b_due_at = now on the session's active claims before the handler responds (one SQLite write; if it fails, log it and still respond, since task-complete must not fail). Then run the check in a spawned task. Any rows still due are also processed at server start and on every sync pass, so a crash or failed task only delays the check. Processing clears check_b_due_at in the same transaction that enqueues the message and writes claim.nudge. If the session has been retired by then, clear without a message. The check never delays or fails the task-complete response or the parent notification.
  • Fetch the caller's actively claimed items fresh (one query per repo). If any is open, send the caller one message: [sm claim] At task-complete you hold: ticket #1452 (open), PR #1470 (open, not merged). The list names every open claimed item, tickets first, in claim order; a PR is described as (open, not merged). Facts only.
  • Sets nudged_idle_at = now on the claims named, so Check C does not repeat it.

Check C — idle with open work

  • Evaluated after each sync pass, per session with at least one active claim on an open item. Fires when all hold:
    1. the session is not stopped and its status is idle, continuously for ≥ 30 min (config work_claims.idle_nudge_minutes, default 30), measured from last_activity;
    2. the session's entry in project_session_obligations (http.rs:6253) has an empty waiting_on (no queue job, Codex review or owner review outstanding);
    3. at least one named claim is armed: nudged_idle_at is NULL, or the session's persisted last_activity is more than 30 min after nudged_idle_at. last_activity is stored on every provider's session record and survives restarts, so no new signal is needed.
  • Message: [sm claim] Idle <minutes>m, nothing pending. You hold: … with the list as in Check B, naming every armed open item. Set nudged_idle_at = now on those claims.
  • Why the re-arm rule: the agent's reply to the nudge is a short turn right after it, so its activity lands well inside 30 minutes and cannot re-arm the check. Activity more than 30 minutes later means new work arrived (you, a parent, a queue wake) or the agent kept working, and the next idle stretch deserves a fresh check.

sm pr closing-reference note

After a successful explicit PR claim, for each ticket linked to the PR with source = claim that is not in the PR's closingIssuesReferences, print: Note: PR #1470's closing references don't include ticket #1452. One line per ticket. A warning only; the claim stands.

G. Worktree lifecycle

Creating: sm ticket <N> --setup-worktree[=<slug>] [--base <ref>]

The CLI runs the git commands in the agent's cwd, which must be inside a checkout (main or linked) of the ticket's repo; otherwise it fails with --setup-worktree must run inside a checkout of <repo>. Order: claim first (appendix C). If the claim is refused, no worktree is created. Then:

  1. Names. slug = the given slug, or the ticket title lowercased, with runs of non-alphanumerics turned into -, the first 4 words, cut to 30 characters and trimmed of -. Branch = <N>-<slug>. Path = <root>/<prefix>-<N>-<slug>, where root = config work_claims.worktree_root (default ~/worktrees) and prefix = work_claims.worktree_prefixes[<owner/name>], defaulting to the repo name. The installed config sets rajeshgoli/session-manager: sm. Example: ticket #1452 "Agent work claims (sm ticket / sm pr) and an agent history page" → ~/worktrees/sm-1452-agent-work-claims-sm, branch 1452-agent-work-claims-sm.
  2. Base. git fetch origin, then base = --base if given, else origin/<default branch> (git symbolic-ref refs/remotes/origin/HEAD, falling back to origin/main). Record base_sha = the resolved commit.
  3. Reuse. If the claim already has a managed worktree, reuse its recorded path and branch whatever slug is given now (a title change never makes a second worktree); if a different slug is given explicitly, fail: This claim already has worktree ~/worktrees/…. Otherwise, if the path is already a worktree of this repo on that branch, reuse it (idempotent rerun). If the path exists as anything else, fail: ~/worktrees/… exists and is not this ticket's worktree.
  4. Intent. POST /claims/worktree with state: "intent" records worktree_path, branch and base_sha on the claim with managed_worktree = 1 before any git write. If that request fails, stop with exit 1 and create nothing.
  5. Create. If the branch exists locally: git worktree add <path> <branch>; else git worktree add -b <branch> <path> <base>. On failure, the claim stands and the CLI prints git's error with exit 1.
  6. Confirm. POST /claims/worktree with state: "created". If this call fails, nothing leaks, because the intent already names the path and retire deletion finds it (a path that was never created is simply absent). Print Worktree ~/worktrees/sm-1452-… on branch 1452-… from origin/main (a1b2c3d).

The agent's shell working directory is not changed; agents address the printed path (Claude Code resets its shell cwd between calls anyway).

Keeping: sm worktree keep [--path P] --reason "<why>" and sm worktree keep --off [--path P]

P defaults to the git top-level of the cwd. Stored in worktree_keeps (appendix A), keyed by absolute path, with the session and reason; --off deletes the row. A keep outlives the session that set it and ends when the owner or any agent runs --off or the path no longer exists. Output: Keeping ~/worktrees/x: <reason>. / No longer keeping ~/worktrees/x.

Deleting at retire

Durable by derivation. Candidates are deduplicated by path, across sessions, so a parent and child sharing one worktree produce one candidate. A candidate path is pending until a worktree.removed event, or a worktree.left event with a final reason, exists for that path. A candidate whose path no longer exists is settled: nothing is written if a worktree.removed already exists for it, else worktree.left with the final reason absent. That covers a setup intent whose git write never happened, or a worktree the agent removed itself. Reasons kept, process … runs in it and in use by are retryable (payload.retryable = true): the candidate stays pending, so it is deleted on a later pass once the keep is cleared, the process exits or the other session is retired. A retry writes a new worktree.left event only when the reason changes. The other reasons are final. The deletion pass runs right after retire (once the claims end and the session's tmux panes are gone), at server start, and after every sync pass, and it processes every pending candidate. A crash mid-cleanup therefore retries on the next start; a finished candidate is never processed twice. The pass holds a process-wide lock so two runs never act on one path. Candidates: each distinct worktree_path on the session's claims (any kind, any end reason), plus the session's working_dir if its current branch equals the head_ref of a merged PR the session claimed. Sessions on remote nodes are skipped (the path is not local). For each candidate, all must hold, checked in this order; the first failure writes worktree.left with its reason:

#ConditionReason when it fails
1The path exists and is a linked worktree: git rev-parse --git-dir ≠ --git-common-dir. A main checkout is never deleted.not a linked worktree
2No worktree_keeps row for the path.kept: <reason>
3No other non-retired session (working, idle, or stopped but restorable) has a working_dir equal to or inside the path; deleting it would break that session's restore.in use by <name>
4No process has its current directory inside the path: lsof -a -d cwd -Fpcn, run by the server from outside the path, lists no n path equal to or under it (appendix K).process <pid> (<command>) runs in it
5Nothing committed would be lost: git -C path rev-parse HEAD equals the frozen head_sha of a merged PR the session claimed in this repo, or the claim is a managed worktree and HEAD equals its base_sha (nothing was ever committed).commits not in a merged PR
6git -C <common repo> worktree remove <path>, without --force, exits 0. Git refuses modified or untracked files and removes ignored ones such as build output (appendix K).git refused: <stderr first line>

After a deletion, delete the local branch with git branch -D <branch> only if branch is set and its tip still equals the HEAD checked in condition 5 (-D is needed because a squash merge never makes the branch an ancestor of main). Write worktree.removed. The retire response gains worktrees: [{path, removed: bool, reason}]; sm retire prints one line each, as in the memo: Deleted worktree <path> (PR #P merged)., Deleted worktree <path> (no commits)., or Kept worktree <path>: <reason>. Cleanup is asynchronous: the response carries results available within 10 s and cleanup pending for the rest; the page always shows the final event.

Remote branches are not touched; GitHub's "Automatically delete head branches" setting handles them. It is on for session-manager and fractal-algo-rust since 2026-09-24 (gh api -X PATCH repos/rajeshgoli/<repo> -F delete_branch_on_merge=true).

O. Web watch

What it is. GET / (and GET /watch) is the browser version of sm watch (bin/watch/mod.rs): the same sessions, tree, states and obligations, rendered as cards (memo mock). It is read-only. It has no send, retire, kill, restore or attach actions; the attach command is shown as copyable text.

Data. GET /watch/state returns one JSON document that the page renders:

{ "schema_version": 1, "generated_at": "…",
  "sessions": [ { "id", "name", "provider", "role", "state",      // working | idle | waiting | stopped
                  "status_text", "status_at", "last_activity", "parent_session_id", "depth",
                  "repo", "node", "context_percent",
                  "claims": [...], "docs": [...], "waiting_on": [...], "review_history": [...],
                  "jobs": [ {id, label, state, started_at} ],
                  "attach": "sm attach <name>" } ],
  "counts": { "live", "waiting_on_owner" } }
  • Built server-side from the same sources sm watch polls (/sessions, /queue-jobs, /session-obligations, per bin/watch/mod.rs refresh()), by calling the same internal functions rather than HTTP. claims, docs, waiting_on and review_history are the session-feed fields verbatim (appendix J). waiting_on_owner counts sessions with an owner_review waiting entry.
  • Ordering and tree are those of sm watch's default view: top-level sessions by the TUI's default sort, children indented under their parent (depth). Stopped sessions are excluded unless ?stopped=1. Filters mirror the TUI flags: repo, role, top_level=1, node.

Page. Server-rendered first paint (so it works with scripts off), plus an inline script under 10 KB, no dependencies, that fetches /watch/state every 3 s (config web_watch.refresh_seconds, minimum 2) while the tab is visible, and re-renders in place, keeping open cards open. Z. FAQ

Why not infer tickets from branch names like 1452-spec? Branch names are a convention, not a contract; the primary repo's branches don't follow it, and a wrong inference would create false collisions. A PR's "Closes #N" is GitHub's own link and is used.

Why do reviewers not claim? A claim means "I am changing this"; a reviewer changes nothing. If reviewers claimed, every review would be a collision.

Why not block sm task-complete until the ticket is closed? A blocked completion strands the parent's wake and can loop an agent that legitimately left work for a follow-up ticket. One message is enough; the history page shows anything left open.

Why 30 minutes for Check C? Long enough that an agent between two quick steps, or one briefly waiting on a reply, is left alone; short enough that a stalled finish is caught the same hour. It is config (work_claims.idle_nudge_minutes).

What about an agent waiting on the owner in chat? sm cannot see that. AGENTS.md tells an idle agent that is waiting on the owner to stay idle when a [sm claim] arrives. It costs one short turn once per stretch.

Why do sm messages carry no instructions? Policy changes more often than facts, and differs by repo. Keeping it in AGENTS.md means changing what agents do never needs an sm release, and sm stays a set of primitives, as #1399 intends.

Why not detect running servers some other way? A process whose current directory is inside the worktree covers servers, watchers and shells started there. A process started elsewhere that only holds files open inside is not detected; sm worktree keep is the agent's way to cover it.

Why server pages rather than reviving the unmounted web/sm-watch React app? The Rust server serves no web app today (web/sm-watch was a Python-era mount). Server pages with a small inline script match the doc reader, work in the app's web view with the existing auth, and need no build pipeline. The visual design comes from the shipped Watch app instead.

Relation to the direction in #1399. Claims here are the "claims" primitive that direction names: mutual exclusion bound to session liveness, with tickets and PRs staying in GitHub. The per-ticket timeline page is a first version of a stable per-ticket page.

Cross-repo links (a PR in one repo closing a ticket in another) are ignored in this version; GitHub reports them, and work_links can take a ticket_repo column later.
