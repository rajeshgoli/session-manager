1710 — sm on the web: one page for everything

Author: Claude (design) sm-web-redesign-spec-author · Ticket #1710 · 29 September 2026 · every screen below is drawn from live sm data at 5:25 pm PT that day

Memo

sm.rajeshgo.li becomes one page on the laptop that does everything the phone app and the Studio do. A left-hand menu replaces the five tabs. A side panel opens any agent, doc, queue job or ticket without leaving the page. The page follows the Mac's light or dark setting. It keeps the phone app's look (its palette, context rings and cards) and adds what only a wide screen can show: timelines, two-pane reading, and a live terminal.

One idea runs through every screen: colour tells you who has the ball. The server already knows this. It is scattered across the agent state, queue jobs, Codex reviews and your inbox, and today you piece it together in your head. The redesign shows it as a single status per ticket and per agent:

Scenario 4 · A job that might be hung

“This job has run an hour on almost no CPU. Is it stuck?”

A job that sits at 0% for a long time is often hung or buggy, and today nothing tells you. In the redesign, clicking a running job opens its panel, which puts the job's CPU and GPU over its run beside the tail of its log. sm calls a job quiet, and turns it red on the Queue page and the Board, only when all three have stopped for 20 minutes: CPU, GPU and log output. The live case below shows why the log matters. At 5:54 pm, #1848's purchase job had run 1h 04m on 0.8 seconds of CPU, which looks hung. FAQ — what changed since the last revision

Queue page: the Mac tile now shows GPU, and the phone's Mac usage chart sits above the job timeline (24 hours of real data).

Start and Settings: agent names come from a pattern in Settings. With no model or effort set, sm leaves the choice to Claude Code or Codex. The popover points to Settings for the first-message template.

Terminal and Claude: as in the phone app, Open in Claude is the main action when the agent has a claude.ai session. It opens a Claude window docked beside sm; claude.ai cannot be embedded in the page. Otherwise the main action is Terminal, which is now its own page with a slim top bar rather than a side-panel tab.

New: the build spec (appendix D) and the ticket plan (appendix E).

Device sign-in (scenario 9, decision 7): the laptop and the Studio sign in with device certificates, as the phone does.

Hung jobs (new scenario 4): a running job with no CPU, no GPU and no new log output for 20 minutes is “quiet” and turns red on the Queue page and the Board. #1848's purchase job shows why the log counts: it barely uses the CPU but is healthy.

Memory figures (#1714): memory is Activity Monitor's “Memory Used” (135 of 256 GB now, not “212 GB free”), and each live bar shades the queue's share.

D. Build spec

This appendix is for the implementing agents. The memo screens are the visual reference, and appendix A holds the tokens. Code references are to crates/sm-server/src at ceab81a.

D1. Where the page is served

Path (browser hostname)Serves
/, /board, /queue, /inbox, /analytics, /analytics/{spend|time|queue}, /history, /history/agents, /guestbook, /settings, /terminal/{session_id}The shell: one HTML document that loads the web app. The app routes on the client with history.pushState.
/watch301 to /.
/docs/…, /messages/{id}, /t/{repo}/{n}Unchanged pages, plus the back bar (D6.7). The shell opens them in its reader frame.
/assets/{name}Web app files (D2) with Cache-Control: public, max-age=31536000, immutable. The shell references them as /assets/{name}?v={build_id}.
  • Hostname rule. A request whose Cloudflare Access application is Browser (request_cloudflare_access_application, http.rs:13287), or a loopback request with no Access headers, gets the shell. Every other hostname, including the phone app's hostname, keeps today's page at each path. The app's reader loads /inbox, /history and /guestbook and must keep working.
  • Every ?format=json response and every Accept: application/json response is unchanged on all hostnames.
  • The shell uses today's read guard, ensure_owner_page_read_allowed (http.rs:14534).

D2. Front-end stack

D4. Owner settings

Storage. Add a table owner_settings(key TEXT PRIMARY KEY, value TEXT NOT NULL, updated_at TEXT NOT NULL) in the session store, next to handoff defaults. value is JSON.

API. GET /client/settings returns the full object with defaults filled in. PUT /client/settings merges a partial object: null clears a key back to its default. The response is the full object. Both routes use owner_web_guard and the phone guard.

{
  "new_agent": {
    "provider": "claude",                 // "claude" | "codex-fork"
    "claude": { "model": null, "effort": null },   // null = provider default
    "codex":  { "model": null, "effort": null },

  },
  "queue_limits": { "max_running": null, "tests": null, "perf": null, "background": null, "service": null }
}

Validation. A failed check returns 400 and names the field.

  • Claude effort must be one of low, medium, high or max. Codex effort must be one of medium, high or xhigh.
  • A model must be in GET /client/session-models for that provider, or be a non-empty string when free text is chosen.
  • Workspaces must be absolute paths.
  • Patterns and templates may use only these placeholders: {ticket} (“#1706”), {number} (“1706”), {repo} (“rajeshgoli/session-manager”), {repo_name} (“session-manager”), {title} and {url}. An unknown placeholder is rejected.
  • Each queue limit must be an integer from 0 to 16, or null.

Where settings apply.

  • start_options_payload (http/board.rs:850) renders the name and brief from the settings and adds provider, model and reasoning_effort.
  • A rendered name is lower-cased, has every run of characters outside [a-z0-9-] replaced by -, and is cut to 32 characters.
  • POST /client/board/start and POST /client/sessions leave out model or reasoning_effort when either is null, so the provider chooses.
  • The phone already calls start-options, so it picks up the settings with no app change.

Migration. On first read with no stored new_agent, seed the provider, model and effort from board.start_defaults if that config block is present. The cleanup ticket (E, ticket 10) removes the config key.

D5. Queue limits that change without a restart

Today the queue runner copies the limits from config once at startup (main.rs:156). HTTP code rebuilds them from config on each call (queue_admission_policy, http.rs:7485).

  • Replace both with one shared Arc<RwLock<QueueAdmissionPolicy>>, built as config overlaid with owner_settings.queue_limits.
  • The runner reads it on every admission pass.
  • PUT /client/settings rebuilds it before responding.
  • Lowering a limit never stops running jobs. It only holds new starts.
  • GET /client/queue reports the effective limits in slots.by_type.*.max as it does today.
  • Test: with background limit 2 and 3 pending background jobs, PUT background 3 starts the third job on the next pass without a restart.

  • Cloudflare. Z. FAQ

Why not embed claude.ai? claude.ai sends X-Frame-Options: SAMEORIGIN, so browsers refuse to show it inside any other site. I checked this on 29 September 2026. Routing claude.ai through sm to strip that header would break its sign-in and security checks, so it is not an option. The closest you can get is a docked window: sm opens claude.ai in a separate window placed over the right half of the screen and reuses it for that agent.

Does the phone app change? Not in this work. The phone keeps loading today's pages. A later pass can give the app the light theme and the ticket clock, since both come from the same server data.

Why are the Iter8 strips only three hours long? The window can be 3, 6 or 24 hours. Three hours fits today's example. In these mockups, the segment before each agent's first queued job is drawn from the agent's last recorded activity. The shipped version reads Analytics › Time for the exact split.
