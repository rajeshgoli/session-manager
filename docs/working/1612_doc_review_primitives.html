1612 — Long-running docs: merge hold, the doc's agent, reviewing a merged doc, and sm doc cat

Author: sm-1612-spec-author 541d1e04 · Ticket #1612 · Revision 1 · 2026-09-28

Memo

Four small primitives let a document that changes for days or weeks, such as an iteration plan, live on one pull request (PR) that merges once at the end. You direct its agent from the doc itself. None of the four is specific to plans:

  1. Merge hold. You, or an agent, put a hold on any PR. sm keeps it from merging until the hold is released, and tells the agents working on it.
  2. The doc's agent, on the doc. The reader's header shows which agent is working the doc: whether it is busy, how many turns it has run, how full its context is, and whether it has marked its task complete. A Retire button sits alongside.
  3. Reviewing a merged or closed doc. When the doc's PR is already merged, you still select text and comment. On Submit, sm opens a new PR from wherever the doc now lives, posts your review there, and wakes the doc's agent. If none is live, the existing Assign to a new agent button appears.
  4. sm doc cat. Any agent prints a published doc, or any local HTML file, as Markdown in one command. The conversion is compiled into sm; nothing gets installed.

Most of the machinery already exists. The doc reader already turns a selection into a GitHub review and wakes the agent. sm already knows which agent holds each PR, and already offers "Assign to a new agent" when the author has ended. This memo connects those pieces and adds one GitHub-side lock.

Terms

Doc
A file an agent published for you with sm doc publish. sm stores where it is in git (repo, path, PR number, commit), never the file itself. You read it in the reader, the page at sm.rajeshgo.li/docs/<repo>/<path>, in a browser or the app.
Publish, revision
Each sm doc publish records one revision of the doc: the commit it was published at. The reader opens the latest revision.
Author
The agent that last published the doc. If it has ended, the next agent to publish becomes the author.
Claim
Existing (#1452). A record that one live agent is working a ticket or a PR, made by sm ticket or sm pr. It ends when the agent is retired or the PR closes.
Review wake
Existing. When you submit a review in the reader, sm posts it to GitHub and sends the agent a [sm review] message. If nobody can receive it, the reader offers Assign to a new agent (#1580), which starts a fresh agent with the review as its task.
Draft PR
A GitHub PR state meaning "not ready". GitHub refuses to merge a draft by any route, whether the web button, gh pr merge or the API.
Merge hold
New. A record in sm that a PR must not merge until whoever placed the hold, or you, releases it. It is enforced by making the PR a draft.
The doc's agent
New name for an existing idea: the live agent a review of this doc goes to. Today that is the author, or the author's parent if the author has ended. This memo adds one rule on top: the agent holding the claim on the doc's PR comes first.
Turn
One stretch of agent work, from a prompt or a delivered message until the agent goes idle.

What goes wrong today

The iteration 7 plan (fractal-algo-rust, docs/working/1746_iter7_plan.html) went through four update PRs in 28 hours, each opened, reviewed, merged and cleaned up by an agent: #1756, #1793, #1806 and #1819. A feature PR, #1820, then edited the plan once more on the epic branch without republishing it. Three things follow:

  • Churn. Every table update is a new branch, a new PR, a merge and a cleanup. Every future plan will do the same.
  • The doc goes read-only between updates. Commenting needs an open PR. Once #1819 merged, the reader says "Read-only: PR merged", and the next round of comments has to wait until you ask an agent to open another PR.
  • You can't see the agent from the doc. To know whether the agent that did the update is finished, or how full its context is, you leave the doc and find the agent in the app. To retire it, you do it by hand.

1 · Merge hold

A hold is a fact sm records and enforces. It is not an instruction to agents. Anyone can place one:

  • You: the Hold merge button in the doc header, or a checkbox on the review you are submitting.
  • An agent: sm merge-hold <PR>. For example, a spec waiting on your ruling.

When a hold is placed, sm does three things:

  1. It makes the PR a draft on GitHub, so nothing can merge it. I verified this on a throwaway PR: the merge API, gh pr merge and the GraphQL merge all refuse with "Pull Request is still a draft".
  2. It tells the agent working the PR, in plain facts:
    [sm hold] Merge hold on PR #1830 (fractal-algo-rust) requested by Rajesh: do not merge until released.
    If the hold rides on your review, this line goes inside the [sm review] message rather than as a separate message.
  3. It shows the hold everywhere the PR shows: the reader header, the agent's claims in the app and sm watch, and the ticket history page. When the agent runs sm task-complete, sm lists the PR as PR #1830 (merge hold by Rajesh). The agent can mark its task complete without merging, and you retire it.

On release, sm takes the PR out of draft, if the hold is what put it there, and sends [sm hold] Merge hold on PR #1830 (fractal-algo-rust) released by Rajesh. What the agent does next is up to its brief. The message carries no instruction.

Two guards keep the hold honest:

  • If anyone marks a held PR ready for review, sm puts it back to draft at its next regular check of open PRs (every five minutes by default, work_claims.sync_interval_seconds), and says so.
  • If a held PR merges anyway, for example before that check, sm tells whoever placed the hold.

A manual Codex review (sm request-codex-review) still runs on a draft. I checked on a second throwaway PR and Codex posted its review. Codex's automatic reviews do skip drafts, but this setup asks for Codex reviews by hand.

A hold ends when it is released, or when the PR closes or merges. Only two parties can release a hold: you, and the agent that placed it. An agent cannot lift your hold.

2 · The doc's agent, on the doc

The reader header gains one line, the session card:

1746 — Iteration 7 plan·d2d566e·PR #1830 ⏸ merge hold · Rajesh │ sm-iter7-plan● idle14 turnsctx 38%✓ task complete 12m ago RetireRelease hold

Figure 2. The session card in the reader header, with a held PR and an agent that has finished.

  • Which agent it shows: the live agent holding the claim on the doc's PR. Failing that, today's rule applies: the author, or the author's parent if the author has ended. Reviews go to the same agent, so the card always names who will receive your next review. The claim rule matters when an agent takes over a PR (sm pr) before it republishes. Today your review would go to the old author's parent instead.
  • What it shows: working or idle; turns run since the agent started; context used, as a percent; and "task complete" with its time once the agent runs sm task-complete. sm already records all of this except the turn count, which is a new counter.
  • Retire: always available, highlighted once the agent has marked its task complete. Two taps, like Delete on a draft comment. It retires only the agent on the card; if a different agent has taken over since the page loaded, it refuses and refreshes.
  • No agent: the card reads "No agent". Your next review is then undelivered, and the existing Assign to a new agent button starts one with the same kind of agent and model as the author, in the repo's checkout.

The card rides on the check the reader already makes every 60 seconds for newer revisions, so it adds no new polling.

3 · Reviewing a merged or closed doc

The reader keeps commenting on when the doc's PR is no longer open. The Submit button says what will happen:

PR stateSubmit becomesWhat sm does
OpenSubmit (unchanged)Posts the review; wakes the doc's agent.
Closed, not mergedReopen PR and submitReopens the same PR on GitHub, then as above. If the branch is gone, the doc stays read-only.
MergedOpen PR and submit, naming the branch, e.g. "from epic/1746-iter7"Opens a new PR from wherever the doc now lives (below), republishes the doc on it, posts the review, and wakes the doc's agent. If nobody is live, you get the Assign button.

Where the doc now lives. sm starts at the branch the doc's last PR merged into. It follows that branch's own merges for as long as the branch saw no new work after merging, and stops at the first branch still in use. That tip is the base for the new PR.

It follows GitHub's PR records rather than git history. A squash merge leaves no ancestry, so asking git "which branch contains this commit" loses the doc after the first squash.

What happened after the doc's PR mergedPath sm followsNew PR's base
Merged into mainmainmain
Merged into epic, which is still in use (the iteration 7 plan today)epic/1746-iter7epic/1746-iter7

A branch merged into two places, or a branch deleted without a merged PR, or the doc missing at the tip—Refused with the reason. Your comments go to the doc's agent as a message instead.

What the agent receives. GitHub accepts line and file comments only on files the PR changes. I verified that anything else fails silently. The new PR starts with one empty commit, because GitHub needs a commit to open a PR and sm must not edit your doc. So your comments go into the review's overall text as a numbered list, each quoting the text you selected. The agent works from the quotes, as it does today for any comment that can't sit on its line.

If the doc at the new base differs from the revision you commented on, the message says so. On the iteration 7 plan it does today: #1820 edited the plan on the epic after its last publish.

The doc follows onto the new PR. Today a doc is keyed by repo, path and PR, so a new PR would start a second doc with its own history. Instead, when a doc's PR is merged or closed and a new PR publishes the same path, the existing doc moves to the new PR and keeps its revisions and reviews. Two PRs that are both open still make two docs, because they are genuinely different edits.

4 · sm doc cat

sm doc cat <doc or local path> prints the doc as Markdown. It takes a doc name or link (latest revision, or --version), or a local file, which covers unpublished specs. --raw prints the original. The reader's address also serves Markdown with ?format=markdown, so agents on other machines get the same result.

Converter: htmd, a Rust library compiled into sm, plus three house rules:

  • Diagrams. Each SVG diagram becomes one line: its accessible name and its text labels, e.g. [figure: Who reads whom in the iteration 7 run] Labels: ES 5-minute · 479 updates a pass · ….
  • Definitions. Definition terms become bold.
  • Tables. Tables drop column padding.

I tested three libraries on three real docs: the iteration 7 plan and memos #1452 and #1182.

OptionResult on the three docsVerdict

Markdown is 16–33% smaller than the HTML, but size isn't the main gain. These memos are mostly prose, so the HTML was never mostly markup. The gain is that the whole doc reads in one command with its structure intact. My first pass at this design read memo #1452 by grepping its headings, and never saw the body.

How the iteration 7 plan runs with these

  1. The next time you comment on the plan, its PR (#1819) is merged. You select a row in section 9, write the change, tick "Hold merge until I release it", and press Open PR and submit, which names epic/1746-iter7.
  2. sm opens the PR, say #1830, makes it a draft under your hold, posts your review and wakes the plan's agent. If none is live, you tap Assign to a new agent.
  3. The agent pushes to #1830 and republishes. The card shows it working, then idle with its turn count. You comment again as needed, and each round lands on the same PR.
  4. When the agent marks its task complete, the card shows ✓ and you tap Retire. With no agent left, your next review offers Assign again, and the new agent lands on the same held PR.
  5. When iteration 7 closes, you tap Release hold. The agent's brief, or you, merges #1830. One squash carries the final plan.

Meanwhile, any agent running the plan reads the current version with sm doc cat fractal-algo-rust/docs/working/1746_iter7_plan.html, not a stale copy on its branch.

What I'm leaving out

  • A separate "ask the agent" command. Reviews already reach the doc's agent. With the PR held open, the existing review loop does the job.
  • Auto-retire on task complete. The card makes retiring one tap, and the decision stays yours.
  • Chat inside the doc, or a plan-specific agent type. Both would lock in today's workflow.
  • Docs published without a PR (commit-only). They stay read-only. Nothing in them records which branch to open a PR from, and the agents that write them can open a PR themselves.

B. Merge hold

B.1 Storage

This lives in the work-claims database, next to the PR items the sync already tracks. Follow that module's schema pattern (init_work_claims_schema).

CREATE TABLE merge_holds (
  id TEXT PRIMARY KEY,                 -- 8 hex chars
  repo TEXT NOT NULL,                  -- owner/name, canonical (canonical_repo)
  pr INTEGER NOT NULL,
  placed_by_session_id TEXT,           -- NULL = the owner
  placed_by_name TEXT NOT NULL,        -- "Rajesh" or the session's display name at the time
  reason TEXT,
  made_draft INTEGER NOT NULL,         -- 1 if placing the hold converted the PR to draft
  placed_at TEXT NOT NULL,
  ended_at TEXT,
  ended_by_session_id TEXT,            -- NULL with end_reason 'released' = the owner
  ended_by_name TEXT,
  end_reason TEXT                      -- released | pr_merged | pr_closed
);
CREATE UNIQUE INDEX merge_holds_active ON merge_holds(repo, pr) WHERE ended_at IS NULL;

Every change also appends to the claims events table: hold.placed, hold.released, hold.ended and hold.redrafted, with {by, reason} as the payload. That puts holds on the ticket and PR history page (/t/<repo>/<N>) with no further work.

B.2 Who is acting

  • A request carrying requester_session_id (every CLI call from an agent, via CLAUDE_SESSION_MANAGER_ID) acts as that session.
  • A request from the reader, the app, or the CLI with no session id, run by the owner at the studio, acts as the owner. Its display name is config.owner_name.
ActionOwnerA session
Place a hold on an open PRYesYes
Release a hold the owner placedYesNo: 403 "Merge hold on PR #N was placed by Rajesh; only Rajesh can release it."
Release a hold a session placedYesOnly that same session. Any other gets 403 "… placed by <name>; only <name> or Rajesh can release it."

B.3 Placing a hold

  1. Fetch the PR (gh pr view N --repo R --json state,isDraft,id,headRefOid, through the existing gh helper). Not found → 404 "PR #N not found in R". Merged or closed → 409 "PR #N is <state>".
  2. If an active hold exists, return it with already_held: true. This does nothing else: no GitHub call and no message.
  3. If the PR is not a draft, run convertPullRequestToDraft(input:{pullRequestId}) and set made_draft = 1. If it is already a draft, set made_draft = 0.
  4. Insert the row and the event, and send the placed message (B.5) in one transaction after the GitHub call succeeds. If GitHub fails, write no row and return 502 with GitHub's error.

B.4 Releasing a hold

  1. Check authority (B.2). No active hold → 404 "No merge hold on PR #N".
  2. If made_draft = 1 and the PR is open and still a draft, run markPullRequestReadyForReview. If made_draft = 0, leave the draft alone: someone else made it a draft for their own reasons.
  3. End the row with end_reason = released, write the event, and send the released message.

If the ready-for-review call fails, the release still ends the hold. The reply includes warning: "PR is still a draft: <error>", because a hold that cannot be released is worse than a draft someone has to un-draft by hand.

B.5 Messages

Messages go out on the normal durable sm send path, as [sm hold]. They state facts and carry no instruction.

EventText
Placed[sm hold] Merge hold on PR #1830 (fractal-algo-rust) requested by Rajesh: do not merge until released. Adds Reason: … on a second line when one is given.
Released[sm hold] Merge hold on PR #1830 (fractal-algo-rust) released by Rajesh.
Marked ready while held[sm hold] PR #1830 (fractal-algo-rust) was marked ready for review while a merge hold by Rajesh is in place; sm returned it to draft.
Merged while held[sm hold] PR #1830 (fractal-algo-rust) merged while a merge hold by Rajesh was in place.

Recipients of placed, released and marked-ready messages:

  • the live holder of an active claim on the PR, if there is one; otherwise
  • for each doc on that PR, the doc's agent (appendix C.1).

Two exceptions:

  • The acting session never receives its own event.
  • A hold placed with a review submission (B.7) sends no separate message. Its line goes inside the [sm review] message.

The merged-while-held message goes to whoever placed the hold. If you placed it, it goes to your inbox through the owner-message path (sm send rajesh, #1580).

Repo in messages is the repo name without the owner, as in doc URLs.

B.6 Drift guard and lifecycle

  • Every PR with an active hold is a tracked item for the claims sync, even with no claim on it. Add it in tracked_items.
  • Add isDraft to the PR fields in ITEM_FRAGMENT (work_claims.rs:303) and to the stored item.
  • On each sync, for each active hold:
    • The PR is open and not a draft: convert it to draft, write hold.redrafted, and send the marked-ready message.
    • The PR merged: end the hold with pr_merged, and send the merged-while-held message.
    • The PR closed: end the hold with pr_closed. No message.
  • The window between someone marking the PR ready and the next sync is at most one sync interval, five minutes by default. That is accepted (appendix Z).

C. The doc's agent and the session card

C.1 Which agent

Replace the body of review_wake_recipient (review.rs:128) with this, first match wins:

  1. The doc has a PR, and a live session holds an active claim on (repo, PR) in the claims store: that session.
  2. live_recipient(author) as today: the author if it hasn't ended, else its live parent.
  3. None.

Every place that asks "who receives this doc's review" uses this one function: the review wake, assign_review's "the doc has an agent again" check, the undelivered state, and the session card. The card can therefore never name a different agent from the one that receives the review.

Example: 1797-revision published the plan and was retired, and sm-plan-2 checked out the PR and ran sm pr 1830 but hasn't republished yet. Today the review goes to 1797-revision's parent. Under C.1 it goes to sm-plan-2.

C.2 Turn counter

Add turns_completed, an integer defaulting to 0, to the session record. Increment it on the event that already marks a turn finished:

  • the Claude Stop hook;
  • the codex-fork turn_complete event (sessions.rs:7735).

Rules:

  • Never reset it: not on clear, not on handoff, not on restore.
  • A provider with no turn-end signal reports null, and the card shows "—".
  • Duplicate Stop deliveries for one turn must not double count. Use the same de-duplication the idle transition uses.

GET /docs/{id}/head adds agent, and the initial page config carries the same object:

C.4 Card rendering

  • The card sits in the existing header bar, after the PR link and hold chip. Order: name · ● state · N turns · ctx P% · ✓ task complete <relative>. Omit a field that is null, except turns, which shows "—".
  • Retire is always shown when agent is non-null. The first tap changes the button to Tap again to retire for 4 s; the second tap sends POST /docs/{id}/agent/retire {session_id}. When task_completed_at is set, the button uses the primary style.
  • When agent is null, show "No agent". The undelivered-review banner and Assign to a new agent behave as today.
  • The card refreshes from each /head reply every 60 s, and immediately after Submit, Assign, Retire, Hold or Release.

C.5 Retire from the reader

POST /docs/{id}/agent/retire {session_id} accepts normal auth or the doc token.

  • If session_id is not the doc's current agent (C.1): 409 "The doc's agent changed; reload".
  • Otherwise, retire through the same code as POST /sessions/{id}/retire, acting as the owner.

This route keeps the doc token's scope to "act on this doc's agent", rather than letting the doc page retire any session.

C.6 Tests

D. Reviewing a merged or closed doc

D.1 When it applies

The doc has a PR and the PR's state is merged or closed. Commit-only docs (no PR) are out of scope and stay read-only. In the reader:

  • canComment is true for merged and closed PR docs, so drafts work as for an open PR.
  • The header reads PR merged — commenting opens a new PR or PR closed — commenting reopens it.
  • When the Submit panel opens, it calls GET /docs/{id}/reopen-target (D.2). The button reads Open PR from <branch> and submit or Reopen PR #N and submit. On a refusal, the button is disabled and the reason is shown.

D.2 Finding the base (merged PR)

Inputs: the doc's repo, path and PR number P. It uses GitHub's PR records only, never local git.

B := baseRefName of P
visited := {}
loop (at most 10 steps):
  if B in visited: refuse "merge history loops at <B>"
  visited += B
  merged := PRs with headRefName = B, state MERGED, mergedAt after the previous step's merge
  open   := PRs with headRefName = B, state OPEN
  tip    := current commit of refs/heads/B, or none if the branch is deleted
  if open is non-empty: stop at B                      # still in use
  if merged is empty:
     if tip is none: refuse "<B> was deleted without a merged PR"
     stop at B                                          # never merged onward
  if len(merged) > 1: refuse "<B> merged into more than one branch (#x, #y)"
  M := the one merged PR
  if tip is not none and tip != M.headRefOid: stop at B # new commits after merging
  B := M.baseRefName                                    # fully merged onward; follow
if the loop ends without stopping: refuse "merge history is longer than 10 steps"
then: the doc must exist at B's tip (contents API); else refuse "<path> is not on <B>"

GraphQL for one step (the verified shape):

repository(owner:$o, name:$n) {
  pullRequests(headRefName:$b, first:10, states:[MERGED, OPEN]) {
    nodes { number state baseRefName headRefOid mergedAt } }
  ref(qualifiedName: "refs/heads/$b") { target { oid } } }

The result also returns tip_sha and whether the file's blob at the tip equals the latest publish's blob (doc_changed).

GET /docs/{id}/reopen-target returns one of three shapes:

  • {kind:"new_pr", base, tip_sha, doc_changed}
  • {kind:"reopen", pr}
  • {kind:"refused", reason}

Cache it for 30 s per doc. Worked example, the iteration 7 plan on 2026-09-28:

  • PR #1819's base is epic/1746-iter7.
  • No PR has that branch as its head, so the rule stops at epic/1746-iter7, whose tip is fc37cdc.
  • The plan's blob there is acfbe98; the last publish is f021e04. So doc_changed = true, because #1820 edited the plan.

D.3 Closed, not merged

If the PR's head branch still exists, return {kind:"reopen", pr}, and on submit run gh pr reopen before the normal flow. If the branch was deleted, return refused with "PR #N is closed and its branch was deleted".

D.4 Submitting (merged)

This extends POST /docs/{id}/review. The body is unchanged, plus hold (B.7). The existing submission_id idempotency covers every step. Each step first checks whether it already happened, so a retry or crash recovery resumes rather than repeats.

  1. Resolve the base (D.2). Store target_base and target_tip on the review row. A refusal fails the submit with the reason and keeps the drafts.
  2. Create the branch. Name it sm-doc/<file stem>-<first 8 of submission_id>, e.g. sm-doc/1746_iter7_plan-3f2a91c0. If it already exists, reuse it. Otherwise create one commit with parent target_tip, the tip's own tree (no file changes), and the message Open <path> for review, then create the branch at that commit.
  3. Open the PR. If an open PR already has this head, reuse it. Otherwise create it with base target_base, title (Docs) <doc title>: review, and body sm opened this PR for Rajesh's review of <path>, from <base> at <sha7>. Store target_pr.
  4. Place the hold if hold: true (B.3).
  5. Publish the doc on the new PR at its head commit, with the author unchanged. This triggers the doc move (D.5).
  6. Post the review with the existing pending-review flow, but add no threads (F.2). The body:

D.5 A doc moving to its next PR

At publish time, for (repo, path, PR N) with no existing doc for that key: look up the most recently updated doc for (repo, path) with a non-null PR M.

  • Move it if M's PR is merged or closed: set pr_number = N on that doc and keep its id, publishes, views and reviews.
  • Otherwise (none exists, or M is open), create a new doc as today.

Mechanics:

  • Add pr_number to owner_doc_publishes, and backfill existing rows from their doc, so each revision remembers the PR it was published on. The revision picker shows #N next to each revision when a doc spans more than one PR.
  • The author rule is unchanged.
  • A sm doc publish --pr N by an agent triggers the same move, so an agent that opens its own next PR gets it too.

E. sm doc cat

E.1 CLI

sm doc cat <doc | path> [--version SHA] [--raw]

How the argument resolves, first match wins:

  1. It starts with http:// or https://: a doc URL, parsed as the other sm doc commands parse one.
  2. A file exists at that path, relative to the cwd: a local file, converted in the CLI process, with no server call.
  3. Otherwise: a doc name, <repo-name>/<path in repo>.

Options and output:

  • --version is only valid for docs; with a local file it fails with "--version needs a published doc".
  • Output goes to stdout. .html and .htm are converted (E.3). Anything else prints as stored. --raw prints the stored bytes for any type.
  • Exit status 1 with a message on "Doc not found", "Version not found" or a conversion error.

E.2 Server

GET /docs/<repo-name>/<path>?format=markdown[&version=…] returns text/markdown; charset=utf-8. It uses the same resolution as the readable URL (latest publish, or the version), the same auth, and the same content cache. The CLI uses it for docs, so agents on remote nodes need no local checkout. format=raw returns the stored bytes. It never records a view, because a view means Rajesh read it.

E.3 Conversion rules

Put the conversion in one module (for example crates/sm-server/src/doc_markdown.rs) that both the server and the CLI call. Use htmd = "0.5.5". Its edition 2024 needs Rust 1.85, within the repo's 1.86.

Z. FAQ

Why not a GitHub label for the hold? A label stops nothing. An agent following its standing "merge once clean" brief merges anyway. The draft makes GitHub refuse.

Why not a required status check? It needs branch protection or rulesets, which the private repo can't have on the current plan (F.6). On repos that can, it would also make sm a gate on every PR, so nothing could merge while sm was down.

What if an agent marks a held PR ready and merges before the next check? The merge succeeds, and sm tells whoever placed the hold. Agents are semi-trusted, and the placed message is explicit, so the draft is a guard against a stale brief, not against an agent determined to merge.

Does a draft stop Codex review? Only automatic reviews. A manual @codex review, which is what sm request-codex-review posts, runs on drafts (F.5).

Why doesn't a hold carry "merge when released"? That is policy. What the agent does on release belongs in its brief. The primitive records who held, who released, and when.

Why an empty commit rather than having the agent open the PR? sm can do it in a few API calls, and your review lands immediately. Waiting for an agent would add a round trip and would still leave most comments off their lines.

Why not branch from main? Docs often merge into an epic or ticket branch first. The iteration 7 plan lives on epic/1746-iter7 today.

Why follow PR records rather than git branch --contains? Squash merges create a new commit with no ancestry link to the branch, so git can't see that the branch was merged.

Why does the doc move to the new PR rather than stay one doc per PR? The header, card, revision picker and review history all hang off the doc. Splitting at each PR recreates the fragmentation the hold removes.

Why count turns and not tokens? You asked for turns. Tokens per session are already on the usage page, and context % covers "how full is it".

Why not pandoc? It's a large system install (a compiled Haskell program) on every machine running sm, including remote nodes, for a job a compiled-in library does in 3 ms.

Why does sm doc cat not record a view? Views drive the "Read" state of a doc for you. An agent reading it must not mark it read.

Can a hold be placed on a PR that has no doc? Yes. The hold is about PRs. Docs are one place its controls appear.
