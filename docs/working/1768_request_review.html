1768 — One review command: sm picks the reviewer and moves on when one can't review

Author: Claude Opus 5.5 8c778c66 (sm-1768) · Ticket #1768 · 30 September 2026 · Revision 3 · figures use live sm data from 30 September; screens are illustrative

Memo

Agents ask for a review with one command, sm request-review, and never learn how the review gets done. sm reads a review policy that you set in Settings, and optionally per repo, per lane or per ticket. The policy names one reviewer, usually GitHub Codex, which answers in about four minutes and costs almost nothing. When that reviewer refuses or goes quiet, sm moves to a fallback within seconds, instead of re-posting @codex review until the request expires. That next reviewer is a review run: Codex's own built-in reviewer, or Claude given the same rubric, started by sm on this machine in a clean checkout of the PR. sm posts the run's findings on the PR the way GitHub Codex does, with comments on the lines they concern. The author is woken once, when a review is on the PR, with the same [sm review] message it gets today.

This fixes today's failure. Since 11:06 pm last night, GitHub Codex has refused every review because the account is out of Codex code-review quota. sm kept posting @codex review every 20 minutes and told each author, 60 minutes later, only that the request "expired". Seven PRs waited a combined 22 hours, and GitHub got 66 identical requests. Under this design, the first refusal pauses GitHub Codex for every repo, tells you once on your phone, and every one of those PRs gets a local Codex review within roughly 20 minutes of asking.

It also answers your two other complaints. sm request-codex-review and sm review merge into the one command. You choose one reviewer per repo, lane or ticket, such as Codex Astra on high effort or Claude Fable for important work. sm handles the fallback itself, and no agent knows any of it.

Review request
What sm request-review 1851 creates: "review PR #1851 at its current head commit and wake me when it is done". This is what sm request-codex-review creates today.
GitHub Codex
OpenAI's review bot on GitHub. It reviews a PR when someone comments @codex review. It runs in OpenAI's cloud and draws on a separate Codex code-review allowance, about 0.05% of a Codex week per review.
Review run
A one-off review that sm runs on this machine, in a fresh read-only checkout of the PR's head. A Codex run is Codex's built-in reviewer (codex exec review): a separate reviewer with a fixed bug-finding rubric that returns findings ranked P0 to P3, each with a file and line. A Claude run gives Claude the same rubric and output format. The run returns its findings to sm, and sm posts them. It is a job in sm's queue, so it shows on the Queue page with its log.
Review policy
The one reviewer to use: GitHub Codex, a Codex run or a Claude run, with its model and effort. You never list fallbacks.
Fallback
What sm uses when the chosen reviewer can't review. For a run, it is the same tier on the other provider, per the tier table in CLAUDE.md: Codex Astra ↔ Claude Fable, Codex Sol ↔ Claude Opus, Codex Luna ↔ Claude Sonnet. GitHub Codex falls back to a Codex Sol run, which is the same review engine on a separate allowance, and then to a Claude Opus run.
Paired reviewer
For a high-stakes ticket only: a reviewer agent that works in the author's own checkout, so it can build the code and run the tests. It starts at the ticket's first review request and stays for every round, remembering its earlier findings. It hands off like any agent and retires when the PR merges.
Scope
Where a policy applies. The four scopes are the default (everything), a repo, a lane on the board, and a single ticket. The most specific scope wins.
Paused
GitHub Codex's state after it refuses for lack of quota. While paused, sm skips it for every repo, and tries it again once every two hours.

How a review request runs

Today, replayed

Normally GitHub Codex is fast and dependable. In the last two weeks it picked up (put 👀 on the request) within 95 seconds on all 697 first requests, and 672 of 677 reviews landed within 10 minutes. That record sets the rules below: five quiet minutes is already abnormal, so sm moves on instead of re-posting.

Scenario 1 · GitHub Codex runs out of quota at night

"Why did #1851 wait two hours for a review that was never coming?"

With this design, the far-1848 agent's session on PR #1851 looks like this. The agent learns only that the request was accepted, and later that the review is on the PR. It hears nothing about which reviewer ran, or about GitHub Codex's trouble, unless nobody at all can review.

far-1848 · ~/worktrees/far-1848-market-data · 12:27 am $ sm request-review 1851 Review requested for PR #1851 at f9d61b2. sm wakes you when it lands. … the agent ends its turn and goes idle … [sm review] Review of PR #1851 @ f9d61b2 is here: https://github.com/rajeshgoli/fractal-algo-rust/pull/1851#pullrequestreview-3391

Behind the scenes, GitHub Codex first refused at 11:06 pm, on sm #1764. sm paused GitHub Codex for every repo, started a Codex review run for #1764 within seconds, and sent you one push: "GitHub Codex is out of review quota. Reviews go to local runs until it recovers; sm checks every 2 hours." So when far-1848 asked at 12:27 am, sm skipped GitHub Codex and started a Codex run at once; its review landed at 12:49 am. Requests skip GitHub Codex until a two-hourly check finds it working again. You can also press Try now in Settings after adding credits.

A paired reviewer is started only at the ticket's first sm request-review, so a ticket that never reaches a PR costs nothing. It stays for every later round and remembers what it found, so it checks the fixes rather than starting over. It hands off at high context like any agent, and retires when the PR merges. It returns its findings with sm review submit, and sm posts them exactly as it posts a run's. Before posting, sm checks that the reviewer left the author's checkout as it found it.

A planning agent can set a ticket's policy as well, when it files a ticket it judges risky, for example sm review-policy set ticket 1848 paired/codex/gpt-6-astra/high. The pill shows who set it. An agent can never set the policy for a ticket it holds itself, so an author cannot choose its own reviewer. Only you set the default, repo and lane policies.

sm posts the review, not the reviewer. An agent that reviews usually posts with its own gh. Here the run has no GitHub access at all: Codex's reviewer runs read-only by design, and a Claude run gets read-only tools. The run returns structured findings, each with a priority, a file and a line range. sm turns them into one GitHub review from your account, with a comment on each line concerned, as GitHub Codex's reviews have. The review carries a hidden tag naming the request and the reviewed commit. That tag is how sm knows the review landed and which request it answers, and it lets sm refuse to post a review of a commit that is no longer the PR's head.

When the author pushes a fix and asks again, sm starts a fresh run at the new head. Its prompt includes the PR's description, the tickets it closes, the lane's goal, the earlier reviews and the author's replies. So it does not re-raise what the author already answered unless it disagrees, and then it must say why. Each run starts clean, so a reviewer never runs out of context and nothing needs handing off. sm deletes the run's checkout when the run ends.

What goes away

  • sm request-codex-review is renamed, not aliased. Ticket 1 changes sm's own messages and opens one PR per repo for the instruction files, merged as soon as the new server is live. An agent still working from the old text gets "unrecognized subcommand", with the tip naming request-review.
  • sm review goes, in all three forms, but its engine stays. --pr posted @codex review once with no retry. --new and the bare form typed /review into a live Codex screen, then waited on fixed timers. Codex's /review is worth keeping: it runs a separate reviewer with a purpose-built rubric, reports only bugs the change introduces, ranks each P0 to P3 with a file and line, and gives a verdict. The Codex run uses that same reviewer through its headless form, codex exec review, so there is no screen, no typing and no timer. No repo's instructions mention sm review.
  • The manual fallback in CLAUDE.md §4 (post @codex review yourself, check at five and ten minutes, re-post at twenty) goes. If sm cannot take a request, the agent tells you. Nobody needs to post @codex review by hand.

Decisions

QuestionRecommendationWhy, in one line
1. One command for agents?Yes: sm request-review [PR], with --steer for a focus note. It replies only "requested; sm wakes you", and the wake says only that the review is on the PR. sm request-codex-review and sm review are deleted, not aliased.The author needs to know when to look, not how the review happened.
2. How does a local review run?As a one-off review run in sm's queue. A Codex run is Codex's own codex exec review. A Claude run uses the same rubric and output. Each run starts fresh with the PR's context and the earlier reviews in its prompt. sm posts the findings. The alternative is a standing reviewer agent kept per PR or per lane, which I don't recommend.Codex's reviewer is purpose-built and returns findings sm can place on lines. A fresh run never needs a context handoff, a nudge or a retirement.
3. Fallbacks?You choose one reviewer; sm falls back by itself. A run falls back to the same tier on the other provider. GitHub Codex falls back to a Codex Sol run, then a Claude Opus run.Last night local Codex worked while GitHub Codex refused; they draw on different allowances. Claude covers an outage of Codex as a whole.
4. Where can a policy be set?Default, repo, lane, ticket; the most specific wins. A PR that closes tickets in two lanes follows the higher-ranked lane. The default is GitHub Codex.These are the units you already think in, and each takes one record.
5. When GitHub Codex refuses for quota?Pause it for every repo, push you once, and check it again every 2 hours, or when you press Try now. The check uses the next real request, and that request moves on within seconds if the check fails.Quota is per account, so one refusal predicts every other request. Checking costs one comment on a PR.
6. When GitHub Codex goes quiet or errors?No 👀 in 5 minutes: move on, and do not re-post. "Something went wrong": re-post once after 2 minutes, then move on. 👀 but no review in 60 minutes: move on.All 697 pickups in two weeks came within 95 seconds, so waiting longer only adds delay.
7. Who may set policies?You set all of them, on the web, the phone or the CLI outside a session. Agents set ticket policies only, and never for a ticket they hold. Every policy shows who set it.Planners know which tickets are risky; authors must not pick their own reviewers.
8. Guard rails on runs?At most 4 review runs at once, and skip a provider whose weekly meter is at 95%. Both are editable in Settings.Tokens matter more than wall-clock. Last night's seven PRs never needed more than four runs at once.
9. Instruction files?Replace the review paragraphs in each repo's CLAUDE.md and AGENTS.md with the text in appendix H, one PR per repo, in ticket 1. You approve each.Those files are yours, and four repos carry the old instructions.
10. A reviewer that runs the code?Yes, as a paired reviewer, on tickets only. You choose it in the Start popover or the ticket's menu. It starts at the first review request, works in the author's checkout, may build and test but never edit, and posts through sm like a run. If it can't review, a run of the same model takes over.Running the code catches what reading misses. Starting at the first review spends nothing until there is a PR.

The build

The build is six tickets, in order. 1 adds the new command, deletes the old two, handles GitHub Codex's refusals, and opens the instruction-file PRs. On its own it ends last night's pattern: a refusal reaches the author and you at once instead of after an hour. 2 adds Codex and Claude review runs and the fallback, which gets the review done. 3 adds repo, lane and ticket policies. 4 adds paired reviewers. 5 (web, including the Start popover's Reviewer row) and 6 (Android, needs an APK install) follow in parallel and move this document to docs/specs/. Appendix J lists what each ticket must deliver and how it is checked.

FAQ — what changed since the last revision

A ticket can have a reviewer that runs the code. The Board's Start popover gains a Reviewer row, and a ticket's policy may be a paired reviewer: an agent in the author's checkout (scenario 4, decision 10). Every other decision stands as you accepted it. The build grows from five tickets to six; paired reviewers are ticket 4.

A5. Codex's built-in reviewer

These are in codex-fork at 76b5f12dd7, under codex-rs/.

  • /review and codex exec review start a separate one-shot review thread (core/src/tasks/review.rs:103-140). Its base instructions are the rubric prompts/templates/review/rubric.md (95 lines). Web search and multi-agent tools are disabled, and approvals are set to never. The rubric flags only discrete, provable bugs that the change introduces, tags each finding P0 to P3, and ends with a verdict: "patch is correct" or "patch is incorrect".
  • The output is JSON: ReviewOutputEvent {findings[], overall_correctness, overall_explanation, overall_confidence_score}. Each ReviewFinding has title, body, confidence_score, priority (0–3) and code_location {absolute_file_path, line_range {start, end}} (protocol/src/protocol.rs:3499-3532). It is parsed at core/src/tasks/review.rs:190.
  • It is recorded as an ExitedReviewMode event in the session's rollout file (rollout/src/policy.rs:128).
  • codex exec review takes --base BRANCH, --commit SHA, --uncommitted or a custom prompt, with - reading it from stdin (exec/src/cli.rs:274-306). The four are mutually exclusive, so sm uses the custom prompt and states the base itself, in Codex's own wording (prompts/src/review_request.rs:21). --ephemeral would skip the rollout, so sm never passes it.
  • Claude Code's headless mode has -p, --model, --effort (low, medium, high, xhigh, max), --output-format json, --json-schema, --allowedTools and --append-system-prompt (claude --help, 30 September).

B. Commands

B1. sm request-review [PR] [--repo OWNER/NAME] [--steer TEXT] [--notify TARGET] [--json]

  • PR: optional. Without it, sm uses the open PR of the current branch (gh pr view --json number in the working directory, as sm pr does). With no open PR, it exits 2 with No open PR for this branch. Pass the PR number.
  • Repo, notify target, conflicts with another owner's active request, same-head reuse, and new-head supersede all behave exactly as sm request-codex-review does today (A1).

D3. Run step

  1. Meter. Read the newest weekly sample (window codex_10080 for Codex, Claude's weekly window for Claude) for the account that provider's new sessions use, which is its most recently observed account_key. If percent ≥ skip_meter_percent, advance with reason {Provider} weekly meter at {p}%. A missing sample never skips.
  2. Checkout.
    • Find the repo's checkout from board.checkouts[repo], else ~/projects/{repo_name}. Missing: advance, reason no local checkout of {repo}.
    • Run git -C {checkout} fetch origin pull/{n}/head {base}.
    • Take {merge_base} = git merge-base {sha} origin/{base}.
    • Run git worktree add --detach ~/worktrees/{repo_short}-{n}-review-r{round} {sha}. {repo_short} comes from owner settings new_agent.repo_short, else the repo name.
    • Any failure: advance, reason failed to start: {first line of the error}.
  3. Prompt. sm writes ~/.local/share/claude-sessions/reviews/{request_id}/r{round}-s{step}/prompt.md (E1), plus rubric.md and schema.json for a Claude run.
  4. Queue job. sm submits a job of the new type review. Its fields:
    • label: review {repo_short} #{n} r{round};
    • cwd: the checkout;
    • command: E2 or E3;
    • wall-clock limit: 45 minutes;
    • owner: review_request:{id}.
    Queue changes this needs:
    • The review type has its own limit, queue_limits.review. It does not count toward max_running, and it waits for perf jobs as every type does.
    • A job with an owner sends no [sm queue] wake. Its terminal state calls the review handler instead.
    Time spent waiting for a slot does not count toward the 45 minutes.
  5. Result. When the job ends:
    • If it exited 0 and E4 yields a valid review, post it (F), then complete the request (D6).
    • If it exited 0 but no valid review came back: advance, reason failed: no review output.
    • On any other exit code: advance, reason failed: exit {code}.
    • If it hit the limit: advance, reason no result in 45 minutes.
    The checkout is removed in every case (D8).

D3b. Paired step

  1. Meter. As D3.
  2. Author's checkout. Use the worktree_path of the active claim on the PR, else on the ticket (work_claims). If it is missing, or not a directory: advance, reason no author checkout.
  3. Reviewer. Reuse the live paired reviewer registered for (repo, ticket) if its provider, model and effort match. If they differ, retire it (step 7) and start a new one. To start one, create a session with:
    • provider, model and reasoning_effort from the policy;
    • working_dir the author's checkout;
    • no parent;
    • name {repo_short}-{ticket}-reviewer, cut to 32 characters, with a numeric suffix if taken;
    • no initial message; the round message follows.
    Register it in a new table paired_reviewers(session_id PK, repo, ticket, pr_number, provider, model, effort, checkout, created_at, retired_at). Any failure: advance, reason failed to start: {error}.
  4. Round. Wait until the reviewer is idle (state waiting_reviewer). Then store checkout_snapshot and send E5 for its first request, or E6 after that (state reviewing). If the checkout's HEAD is not the requested head, the message says so and forbids running code for this round.
  5. Watch.
    • 60 minutes after the round is sent with no submit, and the reviewer idle: send E8, state nudged.
    • At 90 minutes: advance, reason no review after 90 minutes. The reviewer stays for later rounds.
    • If the reviewer is killed or crashes: advance, reason stopped unexpectedly.
  6. Submit (B4) posts (F) and completes the request (D6).
  7. Lifetime.
    • The reviewer follows its provider's handoff defaults. hand_off_rows (queue.rs:2511) also re-points reviewer_session_id and paired_reviewers.session_id to the successor. The review handoff ask (store.rs:280) is not sent to reviewers.
    • Every 10 minutes sm retires the reviewer if its PR is merged or closed, if the author's claim on the ticket has ended, or if the ticket's policy is no longer this paired reviewer. Retiring kills the session as sm kill does; the checkout belongs to the author and is left alone.
    • Paired reviewers do not use review queue slots. Their tests go through the queue like any agent's.

D4. Fallback

"Advance" means moving to the next entry of chain_json (C2), which gives at most three steps for GitHub Codex and two for a run. A step can also be skipped at once, for a paused channel or the meter. When nothing is left, the request becomes no_reviewer (D7).

D5. Head moves

  • A new sm request-review at a new head supersedes the active request, as today (queue.rs:7171). A running review job for the old request is cancelled and its checkout removed. A paired reviewer working on it gets E7 with reason the PR head moved to {new7}. The new request resolves its policy again, and a paired reviewer is reused.
  • If the watcher sees the head move with no new request, the request is superseded and the author gets G3. That check runs before any post, any run start and any posting of a run's result.

D6. Completion

The first review to reach the PR completes the request: a bound GitHub Codex review, a run's review posted by sm (F), or your review (D7). This happens in one transaction with the author's wake (G1), as today (queue.rs:989-1050). A review run still working on the request is cancelled, and its checkout removed.

D7. No reviewer

When the last step advances, the request becomes no_reviewer. The author gets G4 and you get the G6 push and inbox item. Its actions:

  • Retry now creates a fresh request for the same PR, head and author, resolving the policy again. The old row stays no_reviewer.
  • Change policy opens Settings › Reviews.
  • Review it myself reopens the request with state owner. The author gets G7. The request completes when a PR review arrives from your GitHub login (gh api user) after that moment and without the sm-review-request marker. There is no timeout.

A no_reviewer request never retries on its own.

D8. Checkouts

When a run's job reaches any terminal state, sm runs git -C {checkout} worktree remove --force {worktree}. On server start, and every 10 minutes, sm also removes any ~/worktrees/*-review-r* worktree whose request is not active. Runs never commit, so nothing is lost. The prompt and output files under reviews/{request_id}/ are kept for 14 days, for debugging.

D9. Restart safety

The server restarts the watcher for every active request, as recover_codex_review_request_watchers does today. All timers are absolute times on the row. Review runs are queue jobs, so the queue recovers them as it recovers any job. A run that ended while the server was down is processed when the watcher restarts.

E4. Validating the output

A valid review has a findings array, which may be empty, and a non-empty overall_correctness. Each finding is checked:

  • priority must be 0 to 3, or null, which counts as unrated;
  • code_location.absolute_file_path must lie inside the checkout;
  • line_range must have 1 ≤ start ≤ end.

A finding that fails a check is kept, but placed in the review body without a line comment. A title's leading [Pn] tag is removed and re-added from priority.

F. The posted review

sm checks that the PR head is still {sha} (D5). Then it posts one review with gh api repos/{owner}/{repo}/pulls/{n}/reviews --method POST --input review.json:

{ "commit_id": "{sha}", "event": "COMMENT", "body": "{body}",
  "comments": [ { "path": "{path relative to the checkout}", "side": "RIGHT", "line": {end},
                  "start_line": {start, only when start < end}, "start_side": "RIGHT",
                  "body": "**[P{p}] {title}**\n\n{finding body}" } ] }
  • A finding gets a line comment when its file is in the PR's changed files and its end line falls in a hunk of git diff {merge_base} {sha} on the new side. Every other finding goes in the body.
  • COMMENT is required, because GitHub refuses approve and request-changes on a PR by the same account, and all agents post as you.
  • If GitHub answers 422 (a line it will not accept), sm posts again with every finding in the body and no line comments.

Z. FAQ

Why not keep re-posting to GitHub Codex, just less often? Its refusals are not random. A quota refusal repeats until the allowance resets or you add credits, and a missing pickup is already abnormal after 95 seconds. Re-posting only delays the review the PR could have had from a run.

Why runs rather than standing reviewer agents? Revision 1 proposed agents. A standing agent carries memory of earlier rounds, and a lane agent carries knowledge of the plan. A run gets both from its prompt: earlier reviews, the author's replies, the tickets and the lane goal. Against that, runs remove five mechanisms: naming, context handoff, nudging, retiring, and one-PR-at-a-time queueing for lane reviewers. They also use Codex's purpose-built reviewer rather than a general agent following a brief. sm review's old trouble was typing into a live screen on timers. codex exec review has no screen.

How much does a run cost? GitHub Codex costs about 0.04–0.07% of a Codex week per review (fit of 29 September). A Sol run on a PR of typical size is estimated at 0.1–0.2% of a Codex week, and Astra at about three times that. Runs write ordinary Codex and Claude session files, so the usage ledger counts them. Ticket 2 adds the per-review spend to Settings › Reviews.

Did local Codex keep working while GitHub Codex refused? Yes. Between 11:10 pm and 7 am there were 169 Astra and Sol turns, and the Codex weekly meter read 52%. GitHub Codex's refusal names "code reviews" specifically.

What if GitHub Codex's review arrives after a run's? The request is already complete, so sm does not wake the author again. The late review stays on the PR. The author's review loop already requires checking that a review belongs to the current request and head.

Why not let the author choose the reviewer? An author choosing a weaker reviewer is the one conflict of interest in this loop. The author may still steer the review with --steer.

Why does the author not see which reviewer ran? It has nothing to do with that information. The review itself names the reviewer, and sm request-review status shows every step for debugging.

Two reviewers on one PR? Not in this design. A stronger single reviewer, through a ticket policy, covers the cases raised so far.

Why keep the table name codex_review_request_registrations? History (work_history.rs) and analytics read it. Renaming it would change three readers for no behaviour gain.

Does sm doc publish --review change? No. That is your review of a document, with its own marker and wake.

What happens to requests in flight at deploy? Rows with no chain_json run as a one-step [github_codex] chain under the new rules. A request whose posts are already more than 5 minutes old with no pickup advances at the first poll. So it ends as no_reviewer rather than expiring later.

Why can't a run execute the code? A run works in a throwaway checkout with read-only tools, which keeps it cheap and parallel. Building there would mean a cold build for every round. The paired reviewer shares the author's warm build, which is why running code is its job.

Won't a paired reviewer's builds clash with the author's? The author is idle while it waits for the review, and long jobs from both go through sm's queue. sm refuses a review if the reviewer changed tracked files or HEAD. Build outputs such as target/ are shared by design.

Why 2 hours between checks? The allowance's reset time is not in the refusal. A check costs one comment on a real PR and a few seconds of that request's time. Checking every 2 hours finds a reset within 2 hours, at a cost of up to 12 extra comments a day.
