1768 — One review command: sm picks the reviewer and moves on when one can't review

Author: Claude Opus 5.5 8c778c66 (sm-1768) · Ticket #1768 · 30 September 2026 · Revision 1 · figures use live sm data from 30 September; screens are illustrative

Memo

Agents ask for a review with one command, sm request-review, and never learn how the review gets done. sm reads a review policy that you set in Settings, and optionally per repo, per lane or per ticket. It tries the policy's reviewers in order. The first is usually GitHub Codex, which answers in about four minutes and costs almost nothing. When GitHub Codex refuses or goes quiet, sm moves to the next reviewer on the list within seconds, instead of re-posting @codex review until the request expires. That next reviewer is an sm agent that sm starts, briefs, watches, hands off and retires, exactly as it already does for authors. The author is woken once, when a review is on the PR, with the same [sm review] message it gets today.

This fixes today's failure. Since 11:06 pm last night, GitHub Codex has refused every review because the account is out of Codex code-review quota. sm kept posting @codex review every 20 minutes and told each author, 60 minutes later, only that the request "expired". Seven PRs waited a combined 22 hours, and GitHub got 66 identical requests. Under this design, the first refusal pauses GitHub Codex for every repo, tells you once on your phone, and every one of those PRs is reviewed by an agent within roughly 20 minutes of asking.

It also answers your two other complaints. sm request-codex-review and sm review merge into the one command. You can send an important lane or ticket to a stronger reviewer, such as Codex Astra on high effort or Claude Fable, without any agent knowing.

Review request
What sm request-review 1851 creates: "review PR #1851 at its current head commit and wake me when it is done". This is what sm request-codex-review creates today.
GitHub Codex
OpenAI's review bot on GitHub. It reviews a PR when someone comments @codex review. It runs in OpenAI's cloud and draws on a separate Codex code-review allowance, about 0.05% of a Codex week per review.
Review agent
An sm agent that exists to review one PR, or all the PRs of one lane. sm names it after the PR (far-1851-reviewer), gives it a read-only checkout of the PR's head, and tells it what to do. It posts its review through sm with sm review submit.
Review policy
An ordered list of up to three reviewers, for example "GitHub Codex, then a Codex Sol agent on medium effort, then a Claude Opus agent on high effort". sm uses the first reviewer that can do the job.
Scope
Where a policy applies. The four scopes are the default (everything), a repo, a lane on the board, and a single ticket. The most specific scope wins.
Paused
GitHub Codex's state after it refuses for lack of quota. While paused, sm skips it for every repo, and tries it again once every two hours.

How a review request runs

Today, replayed

Normally GitHub Codex is fast and dependable. In the last two weeks it picked up (put 👀 on the request) within 95 seconds on all 697 first requests, and 672 of 677 reviews landed within 10 minutes. That record sets the rules below: five quiet minutes is already abnormal, so sm moves on instead of re-posting.

Scenario 1 · GitHub Codex runs out of quota at night

"Why did #1851 wait two hours for a review that was never coming?"

With this design, the far-1848 agent's session on PR #1851 looks like this. The agent types the same thing it types today, and learns nothing about GitHub Codex's trouble unless nobody at all can review.

Behind the scenes, GitHub Codex first refused at 11:06 pm, on sm #1764. sm paused GitHub Codex for every repo, gave #1764 to sm-1764-reviewer within seconds, and sent you one push: "GitHub Codex is out of review quota. Reviews go to agents until it recovers; sm checks every 2 hours." So when far-1848 asked at 12:27 am, sm skipped GitHub Codex and started far-1851-reviewer at once; its review landed at 12:49 am. Requests skip GitHub Codex until a two-hourly check finds it working again. You can also press Try now in Settings after adding credits.

Scenario 4 · One ticket spends real money

"#1848 buys market data. I want Fable on it, whatever the lane says."

Each ticket row on the Board has the same pill, hidden until a policy is set, and reached from the row's menu. A planning agent can set it as well, when it files a ticket it judges risky: sm review-policy set ticket 1848 claude/fable/max codex-fork/gpt-6-astra/high. The pill shows who set it. An agent can never set the policy for a ticket it holds itself, so an author cannot choose its own reviewer. Only you set the default, repo and lane policies.

When the author pushes a fix and asks again, sm sends the same reviewer a new round: the new head, the author's replies, and the instruction to re-read the whole PR. It remembers its earlier findings, so it does not re-raise what the author already answered, unless it disagrees. When the reviewer's context runs high it hands off like any agent, and its successor (far-1851-reviewer-h2) inherits the review. It retires when the PR merges or closes, or after 24 hours without a request, and sm deletes its checkout.

What goes away

  • sm request-codex-review becomes a second name for sm request-review. It prints one line saying it was renamed, and it is removed once every repo's instruction file uses the new name.
  • sm review goes, in all three forms. --pr posted @codex review with no retry. --new started a Codex agent and typed /review into it. The bare form typed /review into an existing Codex agent. The new command covers the first two, and no repo's instructions mention any of them.
  • The manual fallback in CLAUDE.md §4 (post @codex review yourself, check at five and ten minutes, re-post at twenty) goes. If sm cannot take a request, the agent tells you; sm itself never needs a person to post @codex review.

Decisions

QuestionRecommendationWhy, in one line
1. One command for agents?Yes: sm request-review [PR], with --steer for a focus note and nothing that picks the reviewer. The old name stays working until the instruction files change. sm review is removed.Agents stop needing to know how reviews happen or what to do when they fail.
2. The default policy?GitHub Codex, then a Codex gpt-6-sol agent on medium, then a Claude Opus agent on high.The cheapest reviewer first. A mid-tier Codex agent next, at about a third of Astra's cost. Claude last, because it does not depend on OpenAI at all.
3. Where can a policy be set?Default, repo, lane, ticket; the most specific wins. A PR that closes tickets in two lanes follows the higher-ranked lane.These are the units you already think in, and each takes one record.
4. How long does a review agent live?One per PR by default, kept for every round of that PR. A lane may instead keep one reviewer for all its PRs.Per PR, reviews run in parallel and each reviewer remembers its own findings. The lane option trades speed for knowledge of the plan.
5. When GitHub Codex refuses for quota?Pause it for every repo, push you once, and check it again every 2 hours, or when you press Try now. The check uses the next real request, and that request moves on within seconds if the check fails.Quota is per account, so one refusal predicts every other request. Checking costs one comment on a PR.
6. When GitHub Codex goes quiet or errors?No 👀 in 5 minutes: move on, and do not re-post. "Something went wrong": re-post once after 2 minutes, then move on. 👀 but no review in 60 minutes: move on.All 697 pickups in two weeks came within 95 seconds, so waiting longer only adds delay.
7. Who may set policies?You set all of them, on the web, the phone or the CLI outside a session. Agents set ticket policies only, and never for a ticket they hold. Every policy shows who set it.Planners know which tickets are risky; authors must not pick their own reviewers.
8. Guard rails on agent reviews?At most 4 review agents at once, and skip a provider whose weekly meter is at 95%. Both are editable in Settings.Tokens matter more than wall-clock. Last night's seven PRs never needed more than four reviewers at once.
9. Instruction files?Replace the review paragraphs in each repo's CLAUDE.md and AGENTS.md with the text in appendix H. The cleanup ticket makes the edit; you approve each file in its PR.Those files are yours, and four repos carry the old instructions.

The build

The build is six tickets, in order. 1 adds the new command and GitHub Codex's failure handling. On its own it ends last night's pattern, because a refusal now reaches the author and you at once instead of after an hour. 2 adds review agents, which makes the fallback real. 3 adds repo, lane and ticket policies. 4 (web) and 5 (Android, needs an APK install) follow in parallel. 6 removes sm review and the old name, and moves this document to docs/specs/. B. Commands

B1. sm request-review [PR] [--repo OWNER/NAME] [--steer TEXT] [--notify TARGET] [--json]

  • PR: optional. Without it, sm uses the open PR of the current branch (gh pr view --json number in the working directory, as sm pr does). With no open PR, it exits 2 with No open PR for this branch. Pass the PR number.
  • Repo, notify target, conflicts with another owner's active request, same-head reuse, and new-head supersede all behave exactly as sm request-codex-review does today (A1).
  • Steer: at most 2,000 characters. GitHub Codex gets it after Steer: in the comment, as today. A review agent gets it in its brief or round message.
  • Subcommands list [--all] [--inactive], status [ID] and cancel [ID] carry over unchanged. status adds the policy, its source, and one line per step with its outcome.
  • Success output, exact:
Review requested for PR #{n} at {sha7}. sm wakes you when it lands.
  Reviewer: {step 1}, then {step 2}, then {step 3}
  Policy:   {source}
  Request:  {id}

A step is shown as GitHub Codex, GitHub Codex (paused), Codex {model} agent ({effort}) or Claude {model} agent ({effort}). The source is one of:

  • default (no repo, lane or ticket policy is set)
  • repo {owner/name}
  • lane {rank} · {goal title} (#{goal})
  • ticket #{n}

The existing handoff_ask and claim_warning lines follow unchanged. --json prints the request object from I1.

B2. sm request-codex-review (until ticket 6)

It accepts every argument it accepts today and runs sm request-review with the same PR, repo, steer and notify target. First it prints this to stderr: sm request-codex-review is now sm request-review; running that. --poll-interval and --retry-interval are accepted and ignored, with (--poll-interval and --retry-interval no longer apply). The list, status and cancel subcommands forward too.

B3. sm review submit [--file PATH] [--clean]

Only the review agent of an active request may run this; the body is read from stdin when --file is absent. Checks, in order, each exit 1 with the quoted text:

  1. If the caller is not the reviewer of an active request: You are not reviewing an active request.
  2. If the body is empty or longer than 60,000 characters: The review is empty. / The review is over 60,000 characters; shorten it.
  3. If there are no finding headings and no --clean: No P1/P2/P3 headings found. Add --clean if you found nothing. If there are headings and --clean: You passed --clean but the review has {k} findings.
  4. If the PR head is no longer the request's head: PR #{n} moved to {new7}; your review of {old7} is not posted. Stay idle. sm then treats the request as head-moved (D5).

On success sm posts the review (F), completes the request, wakes the author (G1), and prints:

Posted review on PR #{n} at {sha7}: {p1} P1 · {p2} P2 · {p3} P3
{url}
{author} has been woken. Stay idle; sm sends you the next round if the author pushes.

B4. sm review-policy

sm review-policy show [--pr N | --ticket N | --lane GOAL] [--repo OWNER/NAME]
sm review-policy set   SCOPE REVIEWER [REVIEWER [REVIEWER]] [--lifetime pr|lane]
sm review-policy clear SCOPE
SCOPE    := default | repo [OWNER/NAME] | lane GOAL | ticket N      (repo from --repo or the cwd)
REVIEWER := github-codex | codex-fork/MODEL/EFFORT | claude/MODEL/EFFORT
  • show with no flag prints every stored policy. With a flag it prints the resolved policy and its source, as sm request-review would use it.
  • set validates with C1 and prints the stored policy. --lifetime lane is accepted only for lane scope.
  • Permissions (decision 7):
    • From a managed session (CLAUDE_SESSION_MANAGER_ID set), only ticket scope may be set or cleared. It is refused when that session, or its handoff successor or predecessor, holds the ticket's claim or the claim of a PR linked to it: You hold #{n}; an author cannot choose its own reviewer.
    • Any other scope from a session gives Only {owner} sets default, repo and lane review policies.
    • Without a session id, the CLI acts as the owner.

Examples: sm review-policy set ticket 1848 claude/fable/max codex-fork/gpt-6-astra/high; sm review-policy set lane 1843 codex-fork/gpt-6-astra/high claude/opus/high --lifetime lane; sm review-policy show --pr 1851 prints ticket #1848: Claude fable agent (max), then Codex gpt-6-astra agent (high).

C. Policies: shape, storage, resolution

C1. Shape and validation

{
  "reviewers": [
    { "kind": "github_codex" },
    { "kind": "agent", "provider": "codex-fork", "model": "gpt-6-sol", "effort": "medium" },
    { "kind": "agent", "provider": "claude",     "model": "opus",      "effort": "high" }
  ],
  "lifetime": "pr"          // "pr" | "lane"
}
  • The list holds 1 to 3 reviewers. github_codex may appear at most once. Two agent entries may not be identical in provider, model and effort.
  • provider is codex-fork or claude. model must be in GET /client/session-models for that provider. effort must be in that provider's list (owner_settings.rs CLAUDE_EFFORTS / CODEX_EFFORTS).

C3. Resolution

This runs at request time, for PR P in repo R:

  1. Collect P's tickets: the union of work_links rows for (R, P) and board_prs rows whose pr_repo/pr_number is P.
  2. If any of those tickets has a ticket policy, use it. With several, use the ticket that sorts first by (lane rank, ticket rank in board_ticket_ranks, ticket number). A ticket in no lane sorts after every lane.
  3. Otherwise, take the active lanes those tickets belong to (board_members joined to board_lanes where ended_at IS NULL). Among lanes that have a lane policy, use the one with the lowest rank number.
  4. Otherwise, use the repo policy for R, if one is set.
  5. Otherwise, use the default.

D3. Agent step

  1. Meter. Read the newest weekly sample (window codex_10080 for codex-fork, Claude's weekly window for claude) for the account the provider's new agents use. That is the provider's most recently observed account_key. If percent ≥ skip_meter_percent, advance with reason {Provider} weekly meter at {p}%. A missing sample never skips.
  2. Reviewer.
    • Lifetime pr: reuse the live review agent registered for (repo, PR) if its provider, model and effort match. If they differ, retire it (D8) and start a new one.
    • Lifetime lane: reuse the live agent registered for the lane's goal with the same match. If it holds another request, set state waiting_reviewer and queue first-in, first-out by requested_at.
  3. Slot. A new agent needs a free slot. Slots in use are the live review agents that hold an active request; at most max_agents. With no free slot, set state waiting_slot, first-in, first-out. Waiting does not count toward the step's timers.
  4. Start.
    • Find the repo's checkout from board.checkouts[repo], else ~/projects/{repo_name}. Missing: advance, reason no local checkout of {repo}.
    • Run git -C {checkout} fetch origin pull/{n}/head, then git worktree add --detach {worktree} {sha}. The worktree is ~/worktrees/{repo_short}-{n}-review, or ~/worktrees/{repo_short}-lane{goal}-review for a lane reviewer.
    • Create the session: provider, model and reasoning_effort from the step; working_dir the worktree; no parent; name {repo_short}-{n}-reviewer or {repo_short}-lane{goal}-reviewer, cut to 32 characters, with a numeric suffix if the name is taken; initial message E1.
    • Mark the session record review_agent = {repo, pr | lane_goal}, and register it in a new table review_agents(session_id PK, repo, pr_number, lane_goal, provider, model, effort, worktree, created_at, last_request_at, retired_at).
    • Any failure: remove the worktree and advance, reason failed to start: {error}.
  5. Reuse. Wait until the reviewer is idle. Then run git -C {worktree} fetch origin pull/{n}/head && git -C {worktree} checkout --detach {sha} and send E2, or E1 for a lane reviewer's first request on a new PR.
  6. Watch.
    • 60 min after the step starts with no submit, and the reviewer idle: send E4, state nudged.
    • At 90 min: advance, reason no review after 90 minutes, and retire the reviewer.
    • If the reviewer is killed, retired or crashes (the session store no longer lists it as live): advance, reason stopped unexpectedly.
  7. Submit (B3) completes the request (D6).

D4. Handoff of a review agent

A review agent follows the handoff defaults for its provider (handoff/policy.rs:28-65). When it hands off, hand_off_rows (queue.rs:2511) also re-points reviewer_session_id in codex_review_request_registrations and session_id in review_agents to the successor. The successor keeps the worktree. The review handoff ask in store.rs:280 is not sent to review agents.

D5. Head moves

  • A new sm request-review at a new head supersedes the active request, as today (queue.rs:7171). If a review agent holds the old request, sm sends it E3 with reason the PR head moved to {new7}. The new request then resolves its policy and usually reuses the same reviewer.
  • If the watcher sees the head move with no new request, the request is superseded and the author gets G3. That check runs before any post or agent start, as retry_codex_review_request_in_path does today.

D6. Completion

The first review to reach the PR completes the request: a bound GitHub Codex review, a sm review submit, or your review (D7). This happens in one transaction with the author's wake (G1 or G2), as today (queue.rs:989-1050). Any review agent still holding the request gets E3 with reason {reviewer_label} already posted a review.

D7. No reviewer

When the last step advances, the request becomes no_reviewer. The author gets G4 and you get the G6 push and inbox item. Its actions:

  • Retry now creates a fresh request for the same PR, head and author, resolving the policy again. The old row stays no_reviewer.
  • Change policy opens Settings › Reviews.
  • Review it myself reopens the request with state owner. The author gets G7. The request completes when a PR review arrives from your GitHub login (gh api user) after that moment and without the sm-review-request marker. There is no timeout.

A no_reviewer request never retries on its own.

D8. Retiring review agents

Every 10 minutes, for each live review agent:

  • For a PR reviewer, when the PR is merged or closed (gh pr view --json state), or 24 hours after last_request_at with no active request: retire.
  • For a lane reviewer, when its lane has ended or 24 hours have passed idle: retire.

Retiring kills the session, as sm kill does, runs git worktree remove --force {worktree}, and sets retired_at. Review agents never hold claims, so nothing is released.

D9. Restart safety

The server restarts the watcher for every active request, as recover_codex_review_request_watchers does today. All timers are absolute times on the row. A waiting_slot or waiting_reviewer request is re-queued in requested_at order.

Z. FAQ

Why not keep re-posting to GitHub Codex, just less often? Its refusals are not random. A quota refusal repeats until the allowance resets or you add credits, and a missing pickup is already abnormal after 95 seconds. Re-posting only delays the review the PR could have had from an agent.

How much does a review agent cost? GitHub Codex costs about 0.04–0.07% of a Codex week per review (fit of 29 September). A Sol reviewer reading a PR of typical size is estimated at 0.1–0.2% of a Codex week per round, and Astra at about three times that. Ticket 2 records each reviewer's spend through the existing usage ledger, since review agents are ordinary sessions, and Settings shows it.

Did local Codex agents keep working while GitHub Codex refused? Yes. Between 11:10 pm and 7 am there were 169 Astra and Sol turns, and the Codex weekly meter read 52%. GitHub Codex's refusal names "code reviews" specifically.

What if GitHub Codex's review arrives after an agent's? The request is already complete, so sm does not wake the author again. The late review stays on the PR. The author's review loop already requires checking that a review belongs to the current request and head.

Why not let the author choose the reviewer? An author choosing a weaker reviewer is the one conflict of interest in this loop. The author may still steer the review with --steer.

Why doesn't the review agent have a parent? A child's completion wakes its parent, and the author has no use for that wake. The link between reviewer and author lives on the request, which is what the Agents page shows.

Two reviewers on one PR? Not in this design. A stronger single reviewer, through a ticket policy, covers the cases raised so far. A second reviewer can be added later as a fourth field on the policy without changing anything else.

Why keep the table name codex_review_request_registrations? History (work_history.rs) and analytics read it. Renaming it would change three readers for no behaviour gain.

Does sm doc publish --review change? No. That is your review of a document, with its own marker and wake.

What happens to requests in flight at deploy? Rows with no policy_json run as a one-step [github_codex] policy under the new rules. A request whose posts are already older than 5 minutes with no pickup advances at the first poll, so it ends as no_reviewer rather than expiring later.

Why 2 hours between checks? The allowance's reset time is not in the refusal. A check costs one comment on a real PR and a few seconds of that request's time. Checking every 2 hours finds a reset within 2 hours at a cost of up to 12 extra comments a day.
