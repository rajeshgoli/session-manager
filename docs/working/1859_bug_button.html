1859 — A bug button in the sm app

Author: sm-1859 baa3e909 · Ticket #1859 · Revision 1

Memo

One button files a bug without leaking private work. The top bar of the web app and the phone app gets a bug button. Pressing it captures the screen, then opens a short form: you type what is wrong, see the screenshot, and choose whether an agent starts on it. sm files a GitHub issue in rajeshgoli/session-manager that holds only the words you typed plus a private link. The screenshot and the server facts stay on the sm server, where only you (signed in) and your local agents can read them. The new ticket appears on the board in a standing Bugs lane. If you ticked "Start an agent", the board's usual Start sheet opens on it.

This split matters because session-manager is a public repository and fractal-algo-rust is private. A board screenshot or an agent list names private FAR tickets; neither ever reaches GitHub.

Bug report
What one press of the button produces: your text, an optional screenshot, the page data and the server facts, stored on the sm server under an id like BR-20261001-041502-3fa9c1.
Page data
The data the page you were looking at had loaded from the server — for the board, the board as the server last sent it. It is what the screenshot shows, as data an agent can search.
Server facts
What the server adds at filing time: the server build, every live agent (name, provider, state, ticket), board read status, and running queue jobs.
Owner-only page
A page on sm.rajeshgo.li that opens only for you signed in, like the doc reader. Each bug report gets one.
Bugs ticket and Bugs lane
One open issue titled "Bugs" in session-manager that sm creates on first use and keeps as a board lane goal. Every open bug filed from the app is linked to it as "Bugs starts after this bug" — the same link sm board after makes — which is what puts the bug in the lane.

The one public risk left is your own words: if you type a private ticket's title, it is published. The form says so under the text box.

The Bugs lane, by example

You file three bugs: #1870, #1871, #1872. The first filing creates the Bugs ticket (say #1869), adds it as a lane at the bottom of the board, and links #1870. The lane now shows the Bugs ticket as its goal and the open bugs as rows, each with the usual Start button. An agent fixes #1870 and its PR closes it. When you file #1873, sm first drops the link to closed #1870 and then adds #1873, so the Bugs ticket always links only open bugs. GitHub allows at most 50 such links per issue1, so dropping closed ones keeps the lane working indefinitely.

The Bugs ticket itself never offers Start or Close, even when every bug is fixed. It shows "Standing lane · 2 open bugs" instead. Without this, it would show "All parts done" and Close whenever the lane is empty, and one click would end the lane.

A bug can later move into a plan: sm board under 1871 <plan goal> works, because the Bugs link is the "starts after" kind and an issue can have many of those but only one parent.

Appendices

A. Server ticket

A1. Filing route: POST /client/bug-reports

Replaces the handler submit_client_bug_report (http.rs:3017) at the same path.

  • Guards. owner_guard (http/board.rs:907) — the browser owner login with same-origin check, or the mobile owner guard — then ensure_core_writes_enabled. The old mobile-only guard chain goes. Agent sessions are refused (owner_guard already refuses the agent session header).
  • Request (JSON): 
    {
  "text": "Board shows 'all parts done'…\nMore detail…",   // required; trimmed; 1–4000 chars
  "client": "web" | "android",                              // required
  "client_version": "b3f9…" ,                               // web: build id; android: versionName (versionCode)
  "page": "Board",                                          // required; human page name, ≤ 40 chars
  "route": "/board?lane=3",                                 // private; ≤ 500 chars
  "page_data": { "/client/board": { … } },                  // object; serialized ≤ 300 000 chars
  "screenshot_png": "iVBORw0KGgo…" | null                   // base64 PNG; decoded ≤ 8 MiB
}
  • Validation, before anything is stored or sent: empty text → 400 text is required; text over 4000 chars → 413; client not one of the two values → 400; page empty or over 40 chars → 400; page_data not an object or over its cap → 413; screenshot not valid base64, not starting with the PNG signature 89 50 4E 47 0D 0A 1A 0A, or over 8 MiB decoded → 400 / 413.
  • Order of work, all inside blocking(…):
    1. Build server facts (A3) and store the report (A2). From here the report survives any later failure.
    2. Create the issue (A4). On failure return 502 with body {"detail": "<first stderr line>", "bug_id": "BR-…"}; the stored row keeps status = 'unfiled'.
    3. Record the issue on the row, status = 'filed'.
    4. Take board_lock, ensure the Bugs ticket and lane, drop links to closed bugs, link the new one (A5). A failure here does not fail the request; it sets on_board: false and board_note.
    5. request_pass(state), then wait (at most 10 s, polling the board facts every 250 ms without holding board_lock) until the new ticket has board facts, so that GET /client/board/start-options for it succeeds when the response arrives. If the wait times out, still return 200 with on_board: true; the clients retry start-options (B4, C4).
  • Response 200: 
    {
  "bug_id": "BR-20261001-041502-3fa9c1",
  "issue": { "repo": "rajeshgoli/session-manager", "number": 1870,
             "url": "https://github.com/rajeshgoli/session-manager/issues/1870",
             "title": "Board shows 'all parts done'…" },
  "facts_url": "https://sm.rajeshgo.li/bug-reports/BR-20261001-041502-3fa9c1",   // null when the browser app is off
  "on_board": true,
  "board_note": null      // e.g. "Bugs lane link refused: …" when on_board is false
}
  • The maintainer notification (notify_maintainer_of_bug_report, http.rs:3465, and bug_report_summary) and the maintainer_delivery_result update are deleted. The column stays in the table (existing rows), written as NULL.
  • The filing repo is bug_reports.repo in config, default rajeshgoli/session-manager.

A2. Storage

Reuse bug_reports.db (bug_reports.rs). Add columns by migration (ALTER TABLE … ADD COLUMN, guarded by a column check): client TEXT, client_version TEXT, page TEXT, page_data_json TEXT, issue_repo TEXT, issue_number INTEGER, issue_url TEXT. The existing route, report_text, server_state_json, status, reported_by (owner email when known) columns carry the rest; app_version and artifact_hash are left NULL. The screenshot goes into the existing, unused bug_report_attachments table: kind = 'screenshot', mime_type = 'image/png', payload the decoded bytes. The max_reports pruning already deletes attachments with their report (bug_reports.rs:182). Ids keep the existing BR-… format (bug_id, bug_reports.rs:195).

A3. Server facts

Replace bug_report_server_state (http.rs:15850) with a smaller, fixed shape. Serialized cap 200 000 chars; if over, drop sessions[].activity first, then truncate the sessions list and set "truncated": true.

{
  "captured_at": "2026-10-01T04:15:02Z",
  "server": { "build": "<git sha the binary was built from, if known>", "started_at": "…" },
  "sessions": [ { "id": "baa3e909", "name": "sm-1859", "provider": "claude",
                  "state": "working", "ticket": "rajeshgoli/session-manager#1859",
                  "parent": "…", "activity": "…" } ],     // every non-retired session
  "board": { "last_pass_at": "…", "stale_repos": ["…"], "lanes": [ { "id": 3, "goal": "owner/repo#N" } ] },
  "queue": [ { "id": "job_…", "label": "…", "type": "tests", "state": "running", "since": "…" } ],
  "truncated": false
}

Each field is sourced from what the existing routes already return (sessions list, board badge/status, queue list); no new collection.

A4. The GitHub issue

  • Title: the first non-blank line of the text, trimmed. If longer than 80 characters, cut at 79 characters (character, not byte, boundary) and append ….
  • Body, exactly: 
    <the full text, as typed>

---
Filed from the sm <web|Android> app, <page> page.
Screenshot and server facts (owner only): <facts_url>
Agents: `sm bug show <bug_id>`
    The "owner only" line is omitted when facts_url is null. Nothing else is added: not the route, not the version, not any session or ticket name.
  • Command: gh issue create -R <repo> --title <title> --body-file - with the body on stdin (no shell; avoids argument-length and quoting issues), via the same timeout and transport-retry wrapper as gh_command_output (http.rs:944) — add a stdin-taking variant beside it. Timeout 30 s. Parse the issue URL from the last non-empty stdout line; the number is its final path segment. Non-zero exit or unparseable output → 502 as A1.

A5. Bugs ticket, lane, links

  • Where it is remembered. Board store (the sm_send SQLite db used by board_store, http/board.rs:75): a key–value row bugs_goal = "<repo>#<number>", in a new board_settings(key TEXT PRIMARY KEY, value TEXT NOT NULL) table.
  • Ensure the ticket. If no bugs_goal is stored, or the stored issue is closed or missing on GitHub, create it: title Bugs, body Standing lane for bugs filed from the sm app. sm links every open bug to this ticket so the board shows them in the Bugs lane. Leave it open; closing it makes sm start a new one with the next bug. Store its key.
  • Ensure the lane. If no current lane has this goal, add one via the same path as POST /client/board/lanes (add_lane, http/board.rs:835), recorded as added by the owner. This is also what re-adds a lane you ended (decision 5).
  • Drop closed links. For each "after" edge in the store whose waiter is the Bugs ticket and whose blocker is closed, call board::write_link (board.rs:1643) with remove: true. Errors are logged and skipped.
  • Link the new bug. board::write_link with ticket = Bugs ticket, target = new issue, kind = After. A refusal (for example GitHub's 50-link limit with 50 bugs open) sets on_board: false and board_note to the refusal text.

A6. The "standing" board state

  • TicketState (board/model.rs:130) gains Standing, serialized "standing". In ticket_facts (model.rs:~610) it is decided right after Done: an open ticket whose key equals the stored bugs_goal is Standing. ModelInput carries the bugs goal key so the model stays pure.
  • Standing is in no count (board.rs:1964 counts), raises no ready or lane notices (board/pushes.rs:88), is refused by Start and Close validation (both already accept only other states — keep it that way), and is not a lane-ending condition. The ticket JSON gains nothing new: clients compute "N open bugs" from waits_on entries that are open.
  • CLI sm board text shows standing and N open bugs (bin/board/mod.rs:237).

A7. Owner-only page

  • GET /bug-reports/{id}: a server-rendered, self-contained HTML page (no app shell) guarded by ensure_owner_page_read_allowed (http.rs:15483). Content: the text; a table of client, version, page, route, filed time, issue link; the screenshot (<img src="/bug-reports/{id}/screenshot.png">, width 100%) if any; page data and server facts as pretty-printed JSON inside <details>. Unknown id → 404 page.
  • GET /bug-reports/{id}/screenshot.png: same guard; image/png; 404 if none.
  • Add /bug-reports/ to is_protected_read_surface (http.rs:15161-15225) and a row to the owner web reads test table (OWNER_WEB_READS, http.rs:21087). The installed Android app sends unknown paths to the browser, which is correct here: the page opens in the phone's browser behind the same login.

A8. Agent read: route and sm bug show

  • GET /bugs/{id} guarded by ensure_session_allowed_from_parts (the agent guard used by POST /board/links, http/board.rs:774): JSON {bug_id, created_at, client, client_version, page, route, text, issue, has_screenshot, page_data, server_facts}. GET /bugs/{id}/screenshot.png, same guard.
  • sm bug show <id> (new module bin/bug/, wired in bin/sm.rs): prints the text, a metadata block, then page data and server facts as indented JSON; if there is a screenshot, writes it to $TMPDIR/sm-bug-<id>.png and prints Screenshot: <path>. --json prints the route's JSON unchanged. Accepts the id with or without the BR- prefix.

B1. Button

In TopBar (web/app.js:285-320), an icon button (🐞, title "Report a bug") immediately left of the New agent button, on every page.

B2. Capture

  • Vendor html-to-image (latest release; MIT): web/vendor/html-to-image.js (ES module build), html-to-image-LICENSE, a line in vendor/VERSIONS in the existing prose form, an asset! entry in http/web.rs ASSETS, and a VENDOR_IMPORTS entry.
  • On press, before the form renders: toPng(document.body, {pixelRatio: Math.min(devicePixelRatio, 2), filter: (n) => !n.dataset?.bugExclude}). Capture failure, or a result over 8 MiB decoded at ratio 2, retries once at ratio 1; a second failure opens the form with "Screenshot unavailable" and the checkbox off and disabled.

B3. Page data

The shared api() helper keeps, in memory, the latest parsed JSON response for each GET path (path without query as key, at most 12 keys, oldest evicted). The form sends the entries whose path the current page fetched since it was opened; if their serialized size exceeds 300 000 characters it drops largest entries first.

B4. Form and after

  • Fields and copy as in the memo mock: text (autofocus), the public note, screenshot thumbnail with "Attach screenshot" (on), "Start an agent on it" (off), Cancel, File bug (disabled until text is non-blank). The form root carries data-bug-exclude.
  • page is the nav label of the current page; route is location.pathname + location.search; client_version the build id.
  • On 200: show "Filed #N" linking to issue.url, plus board_note if set. If Start was ticked and on_board, close the form and mount TicketStart (web/board-start.js:40) for {repo, number, title, state: 'ready', warnings: []} in the same overlay the board uses (board.js:210); if start-options returns 404/409, retry every 1 s up to 10 s before showing its error.
  • On error: keep the form and text, show the server's detail.

B5. Standing lane display

In TicketRow (web/board.js) and the lane header: state standing shows the cyan sub-line "Standing lane · N open bugs" (N = open entries of waits_on), no Start, no Close; the ⋯ menu stays.

B6. Web tests

Following the existing web test pattern: page-data ring eviction; capture fallback to ratio 1 then "unavailable"; Start hand-off retries start-options; standing row renders without Start or Close.

Z. FAQ

Why not attach the screenshot to the issue privately? GitHub has no private attachment on a public issue, and its image upload is not available through the API.

Why "starts after" links rather than sub-issues? An issue has at most one parent. A bug that later belongs to a plan would have to be unhooked from Bugs first, and an agent doing sm board under would be refused. "Starts after" links have no such limit.

Why a new board state rather than hiding the Bugs ticket? The ticket is the lane goal and the lane header shows it; it must render, just never as startable or closable.

Why does the server wait for the board before answering? The Start sheet asks the server for the ticket's options, which exist only once the ticket has board facts. Waiting up to 10 s on the server, plus client retries, makes "Start an agent" work on the first try in the common case.

Does the public issue reveal the page I was on? Only its name ("Board", "Inbox"), not its address, which can contain a private ticket number.
