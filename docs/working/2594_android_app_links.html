2594 — Open sm doc links in the phone app

Author: fit-and-finish agent e7838871 · Ticket #2594 · Revision 1

Memo

Recommendation: make exactly one file on sm.rajeshgo.li public, and nothing else. A doc link tapped on your phone opens in Chrome, and Chrome then stops at the Cloudflare login, because Android cannot confirm that the sm app owns sm.rajeshgo.li. Android confirms ownership by fetching a small public file from the site. The file names the app and the certificate that signs it. Today that fetch hits the Cloudflare login page, so the check fails silently and Android hands every sm link to the browser. The fix is for sm-server to serve that file and for Cloudflare to let anyone fetch that one exact path without logging in. Afterwards your doc, ticket and board links open in the app. Nothing a stranger can fetch gets more interesting than one line naming the app.

App Link
Android's name for a website link that opens straight in an app instead of the browser. The app lists the site and paths it wants (the sm app lists sm.rajeshgo.li's /docs/, /t/, /board, /history, /guestbook and /artifacts). Since Android 12, Android honours that list only if the site agrees.
Ownership file (assetlinks.json)
How the site agrees. It is a public file at https://<site>/.well-known/assetlinks.json that names the app's package (li.rajeshgo.sm) and the fingerprint of the certificate that signs the app. Android fetches it when the app is installed or updated. Android follows no redirects and logs in nowhere: either the file comes back directly, or the check fails.
Cloudflare Access
The login wall in front of sm.rajeshgo.li. Every request must carry your Google login (or an enrolled device certificate) before Cloudflare passes it to sm-server.
Bypass rule
A Cloudflare Access setting that lets one named path through the login wall without a login.

What becomes public

This file, and only this file:

[{"relation": ["delegate_permission/common.handle_all_urls"],
  "target": {"namespace": "android_app", "package_name": "li.rajeshgo.sm",
             "sha256_cert_fingerprints": ["FD:BF:0B:BD:…:00:F6:BF"]}}]

It reveals that an Android app called li.rajeshgo.sm exists, plus a certificate fingerprint. That fingerprint is printed inside every copy of the app, so it is not a secret. The file grants exactly one thing: the app may open this site's links. It deliberately leaves out the other grant Android supports, sharing saved passwords between the site and the app.

Security review

RiskWhy it is acceptable, and what guards it
The exception is wider than one file. Cloudflare's documentation does not say whether a rule for a path also covers the paths beneath it.Two independent guards.
  • sm-server answers only the exact path /.well-known/assetlinks.json. Anything below it, beside it, or written to climb back out (/../, including the percent-encoded form) gets "not found". A test covers each case.
  • After the change, a fixed list of curl probes (Appendix B) must show the login redirect for every neighbouring path. If any probe reaches sm-server without a login, the rule is rolled back in one call.
Someone else's app claims your links.Only an app signed with the same certificate can claim them. That certificate is the Android debug key stored on this Mac, so whoever holds it can already build and install a fake sm app today. Even then, the fake app receives only the link address. sm's reader links carry no tokens or secrets, and opening the page still needs your login.
Changing Cloudflare with an API token.The change is one new Access application, scoped to one path, with one Bypass policy. It uses the token already in sm's config, which sm already uses to manage device policies. It is recorded on the ticket with the new application's id, and deleting that application rolls it back. Your existing login application is not edited.
A pre-existing gap the review surfaced: sm-server relies on Cloudflare for the login on most routes.Some sm-server routes check your login themselves (docs, messages, the web app's files). Others trust that Cloudflare already did. This change keeps that gap from widening: only the exact path passes the wall, and that path serves the public file. Closing the gap is decision 4 below.

Decision surface

QuestionRecommendationWhy, in one line
1. Let Cloudflare pass sm.rajeshgo.li/.well-known/assetlinks.json without login?Yes: one exact path, through a separate Cloudflare Access application with a Bypass policy. I make the change by API after this merges and deploys, then run the probe list.It is the only way Android's check can pass while everything else stays behind login.
2. Keep signing the app with this Mac's debug key?Yes, for now. The file lists the debug key's fingerprint.Switching keys means uninstalling the app on your phone (Android refuses an update signed by a new key). The risk above is bounded.
3. Where does the fingerprint live?In sm's config (android_app_links), not in code.A rebuilt or re-keyed app needs a config edit, not a release.
4. Close the reliance on Cloudflare for login?Separate ticket: sm-server refuses any request on the public hostnames without a verified Cloudflare login, except a short list of public paths.It is a real gap, but it is independent of this change and touches every route.

What you do afterwards

Nothing, unless the links still open in Chrome. Android re-checks ownership when the app updates, so the next sm app update picks it up. To pick it up sooner: Settings → Apps → sm → Open by default, switch "Open supported links" off and on. The same screen's "Add link" works today as a manual stopgap.

Appendices

A. sm-server change

  • Route: GET /.well-known/assetlinks.json, registered beside /health in router() (crates/sm-server/src/http.rs). The handler is app_links::assetlinks in crates/sm-server/src/http/app_links.rs. It takes no identity, so it is public on every host, like /health.
  • Response: 200, Content-Type: application/json, with the statement list shown in the memo, when the config holds a valid package name and at least one valid fingerprint. Otherwise 404. It never redirects.
  • Config (AndroidAppLinksConfig in config.rs; defaults are empty, so no file is served): 
    android_app_links:
  package_name: li.rajeshgo.sm
  sha256_cert_fingerprints:
    - fdbf0bbd96cb4f42912a78edb94bca7c4fc10b30302f611731a2bfa00300f6bf
    Fingerprints are accepted as 64 hex digits, with or without colons, and served as upper-case colon pairs. Malformed entries are dropped. The package name must have at least two dot-separated parts, each starting with a letter and containing only letters, digits and _. To read the fingerprint from a built APK: apksigner verify --print-certs <apk>, "Signer #1 certificate SHA-256 digest".
  • Exact path only. The router matches paths literally and does not resolve dot segments or percent-encoding, so no request path other than this one reaches the handler. Test assetlinks_is_public_exact_and_absent_until_configured (http/app_links_tests.rs) checks 404 for /.well-known/assetlinks.json/, …/x, …jsonx, /.well-known/, …/../../health and …/%2e%2e/%2e%2e/health, all sent on the browser hostname with no login. It also checks 404 before the file is configured. The unit tests in http/app_links.rs cover the statement shape, fingerprint normalisation and rejected inputs.
  • Live config: add the block above to ~/.config/session-manager/config.yaml before the deploy that ships this code.

B. Cloudflare change, probes and rollback

The change uses account cloudflare_access.account_id and token cloudflare_access.api_token from the live config. The existing login application (cloudflare_access.browser.app_id) is not modified.

  1. Create a reusable policy: POST /accounts/{account}/access/policies with {"name":"sm assetlinks: public (Android App Links)","decision":"bypass","include":[{"everyone":{}}]}. Record the returned id.
  2. Create the application: POST /accounts/{account}/access/apps with {"name":"sm assetlinks (public)","type":"self_hosted","domain":"sm.rajeshgo.li/.well-known/assetlinks.json","policies":[{"id":"<policy id>","precedence":1}]}. Cloudflare applies the more specific application to that path. Record the application id on ticket #2594.
  3. Probes, run from a machine with no Cloudflare login cookie (curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n'):
    URL on https://sm.rajeshgo.liRequired result
    /.well-known/assetlinks.json200, JSON body naming li.rajeshgo.sm
    /.well-known/assetlinks.json/, /.well-known/assetlinks.json/x302 to the Cloudflare login, or 404 from sm-server
    /.well-known/assetlinks.json/../../health (sent with --path-as-is), /.well-known/assetlinks.json/%2e%2e/%2e%2e/health302 to login, or 404
    /.well-known/assetlinks.jsonx, /.well-known/, /health, /docs/x, /302 to login
    A 404 from sm-server is acceptable, because sm-server's own exact match holds. A 200 on any row except the first is a failure: roll back.
  4. Google's own check: https://digitalassetlinks.googleapis.com/v1/statements:list?source.web.site=https://sm.rajeshgo.li&relation=delegate_permission/common.handle_all_urls lists the statement.
  5. Rollback: DELETE /accounts/{account}/access/apps/{app id}, then DELETE /accounts/{account}/access/policies/{policy id}.

C. Android side

  • No app change. android-app/app/src/main/AndroidManifest.xml already declares the auto-verified link filter for ${smLinkHost} (= SM_LINK_HOST, the browser hostname).
  • Only the browser hostname is checked. The app's own API host (sm-app.rajeshgo.li) is not in the link filter, so it needs no file.
  • Re-check on a connected device: adb shell pm verify-app-links --re-verify li.rajeshgo.sm, then adb shell pm get-app-links li.rajeshgo.sm, which should show sm.rajeshgo.li: verified.

Z. FAQ

Why not only use the manual "Add link" setting? It works for one phone and is undone by a reinstall. It also never shows up as a failure, so the problem quietly comes back.

Why not serve the file from a Cloudflare Worker? It would put the fingerprint in a second place to keep in sync. The bypass rule is still needed either way.

Do the links carry secrets the app would now receive? No. Reader links carry only the doc, message or ticket path and non-secret options (version, format). The doc token used by the page's own requests travels in a header, not in the URL.
