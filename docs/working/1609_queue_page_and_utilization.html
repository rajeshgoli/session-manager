1609 — A Queue page, and a record of whether the queue holds the machine back

Author: Claude Opus 5.5 8f069b36 (sm-1609-spec-author) · Ticket #1609 · 2026-09-28

Memo

I propose four pieces of work. First, a utilization recorder in the server that writes the machine's memory, CPU and GPU use, and each queue job's memory and CPU, every 5 seconds into its own database. Second, a Queue page in the sm app: a live Memory / CPU / GPU bar, then one list — jobs running, jobs queued behind them in start order, and jobs the queue stopped or gave up on — with every row naming the agent and how long it has waited. Third, a "Held back?" card on that page that answers your question from recorded data: of the time jobs spent waiting on a concurrency limit, how much of it had the machine idle enough to run them. Fourth, a Mac usage screen that charts CPU, GPU, memory and queue jobs over the last hour, day, week or month.

The recorder matters most. Thirty days of job history already say the overall limits are not the constraint, while the 2-slot background limit and perf runs account for nearly all of 107 hours of waiting. What the history cannot say is whether the machine had room during those waits, because utilization recording stopped on June 16 when the server moved from Python to Rust. Nothing has written it since.

Queue job
A command an agent submits with sm queue run. The server starts it when the rules allow and wakes the agent when it ends.
Job types
tests (builds and checks), perf (measurements that need a quiet machine), background (work that may be interrupted), service (long-lived processes).
Concurrency limit (slot)
The most jobs that may run at once. Your live config: 8 overall (services count), 6 tests, 1 perf, 2 background, 2 service.
Held, hold reason
A submitted job that has not started. The server keeps one current reason, such as "waiting for a free slot". It erases the reason when the job starts.
Perf rules
A perf job waits for running tests to finish, then a 30-second cooldown. While a perf job runs, or waits for that quiet window, every new job is held.
Displaced
A background job killed to make room for a perf run. It is not restarted.
Gave up
A job that waited past its wait limit (5 minutes unless the agent asked for longer) and never started. Its agent is told.
Headroom
A moment when the machine could have taken more work: CPU under 60% busy, at least a quarter of memory available (64 GB), and the kernel reporting normal memory pressure.

1. The page

Figure 1 shows the page. Top to bottom:

  • Live bar. Memory used of total, CPU busy, GPU busy, refreshed every 5 seconds while the page is open. Below it, how many slots are in use, overall and per type.
  • Running. Oldest first. Each row shows elapsed time against the job's own time limit.
  • Queued. The number is the order in which the server considers waiting jobs: perf first, then tests, background, service, and oldest first within each type. The line under each row says why that job is not running. The number is not a promise: if only the background limit is full, a test queued later starts ahead of a waiting background job, and its reason line says so.
  • Stopped by the queue. Jobs from the last 24 hours that the queue ended without the job finishing on its own: displaced, gave up, over its memory limit, over its process limit, or past its time limit. Cancelled and failed jobs are left out. Someone chose to cancel, and a failure is the job's own result.
  • Held back? Described in section 4.

Where you reach it. A Queue item in the agents screen's top menu, next to Analytics. A Queue icon also sits in the agents screen's top bar whenever a job is running or waiting, with a badge counting the waiting jobs. The app has no live utilization bar today (only a Settings sheet that updates when you tap Refresh), so this page is where live utilization appears.

About 90% of jobs start within 30 seconds. In the same 30 days, 50 jobs gave up without starting, 46 background jobs were displaced, and 8 perf jobs were stopped for exceeding their memory limit.

  • The overall and test limits are not the constraint. Raising them would change almost nothing.
  • The background limit is the largest single cost. The heaviest background users run jobs of 35–70 minutes, so two such jobs hold both slots for an hour.
  • Perf pauses are what perf jobs ask for. Most declare 100% of the CPU and 100–258 GB of the 256 GB of memory. Whether every one of them needs a quiet machine is a question for the agents writing them, not for the queue.
  • What the history cannot answer: whether the machine had room while jobs waited, and how much memory a background job really uses. Both need the recorder.

3. The utilization recorder

Every 5 seconds, while the live server runs the queue, the recorder writes one row for the machine and one row per waiting or running queue job. It writes to its own database, utilization.db, beside the queue's. Its frequent writes therefore never compete with the queue's own bookkeeping.

Cost, measured on this machine. The command today's Settings sheet uses (top) costs 1.3 seconds of CPU per reading, which at 5-second sampling would be a quarter of a core. The recorder avoids it. Kernel counters cost next to nothing, the process listing about 10 ms and the GPU reading about 20 ms, for roughly 30 ms per sample. That is about 0.6% of one core.

Size. About 3 MB a day, or about 300 MB when kept for 90 days. The server deletes older rows each hour.

Memory is measured three ways, all at the same moment:

MeasureValue
Used, as top counts it (includes file cache)87 GB
Apps + kernel + compressed42 GB
Available, as the kernel judges it96% free

The bar keeps showing the first figure, so it reads as it always has. The "Held back?" card uses the third, because the queue uses that same figure when it decides whether a perf job may start.

4. The "Held back?" card

The card splits the time jobs spent waiting by why they waited: limits (a concurrency limit was full), perf rules, memory (a perf job waiting for memory to free up), and other. For the limits share, it reports how much of that waiting happened while the machine had headroom as defined above. A high share means the limit, not the machine, was holding work back. It also reports how much memory and CPU each job type really uses at its peak. That is the number the background-limit decision in two weeks needs.

Worked example. Over one minute (12 samples), two background jobs wait behind the background limit. In 10 samples the machine is 30% busy with 200 GB available and normal pressure; in 2 samples a test build pushes CPU to 90%. Waiting on limits = 2 jobs × 60 s = 2 job-minutes. With headroom = 2 jobs × 10 samples × 5 s = 100 job-seconds = 1.7 job-minutes. The card reads: "Limits held jobs 2 min. The machine had headroom for 83% of it." A sample with a missing CPU or memory reading counts as neither headroom nor its absence; the card reports such time separately as unknown.

5. The Mac usage screen

A second screen charts how the Mac has been used over time, using the recorder's samples. You open it by tapping the live bar on the Queue page, or from Mac usage in the agents screen's menu. Range chips switch between the last hour, 24 hours, 7 days and 30 days. The default is 24 hours.

What each chart shows.

  • CPU and GPU %. The average for each time slice. A faint band behind the CPU line shows that slice's peak, so a short spike stays visible in the 7- and 30-day views.
  • Memory used, out of 256G, the same "used" figure as the live bar. Red shading marks the times the kernel reported elevated or critical memory pressure. Pressure, not the used figure, is what warns of an out-of-memory reboot.
  • Queue jobs running, stacked by type. Read against the two charts above, it shows what the queue was doing while the machine was busy or idle.
  • Summary for the chosen range: average and busy time for CPU, peak memory and time under pressure, and how much of the time the machine had headroom as defined above.

Each chart holds about 240–360 time slices, whatever the range: 15 seconds for the last hour, 5 minutes for a day, 30 minutes for a week, 2 hours for 30 days. Time the server was down shows as a gap, not as zero. Touching a chart shows that slice's time and values.

B. Utilization recorder

B.1 Configuration

utilization:
  enabled: true                        # default true
  db_path: ~/.local/share/claude-sessions/utilization.db   # "~" expanded like queue_runner.state_dir
  sample_interval_seconds: 5           # integer, 1..=60; values outside are a config error at startup
  retention_days: 90                   # integer, 1..=3650

The recorder runs only when utilization.enabled is true and rust_core.runtime_enabled is true. Scratch servers run with the runtime disabled so they stay off live queue jobs; they must not double-record either. On any OS other than macOS the recorder does not start and logs one info line saying so.

B.2 Schema (utilization.db, WAL mode, synchronous=NORMAL)

CREATE TABLE IF NOT EXISTS host_samples (
  sampled_at_ms        INTEGER PRIMARY KEY,   -- unix epoch milliseconds, UTC
  interval_ms          INTEGER NOT NULL,      -- configured interval when written
  cpu_busy_pct         REAL,                  -- 0..100; NULL on first sample after start or on read failure
  gpu_busy_pct         REAL,                  -- 0..100 or NULL
  mem_total_bytes      INTEGER,
  mem_used_bytes       INTEGER,               -- total − (free + speculative); matches top's "used"
  mem_available_bytes  INTEGER,               -- total × kern.memorystatus_level / 100
  mem_free_bytes       INTEGER,
  mem_speculative_bytes INTEGER,
  mem_active_bytes     INTEGER,
  mem_inactive_bytes   INTEGER,
  mem_wired_bytes      INTEGER,
  mem_compressed_bytes INTEGER,               -- pages occupied by the compressor × page size
  pressure_level       INTEGER,               -- kern.memorystatus_vm_pressure_level: 1 normal, 2 elevated, 4 critical
  load_1m              REAL,
  running_tests INTEGER NOT NULL, running_perf INTEGER NOT NULL,
  running_background INTEGER NOT NULL, running_service INTEGER NOT NULL,
  pending_tests INTEGER NOT NULL, pending_perf INTEGER NOT NULL,
  pending_background INTEGER NOT NULL, pending_service INTEGER NOT NULL
);
CREATE TABLE IF NOT EXISTS job_samples (
  sampled_at_ms     INTEGER NOT NULL,         -- equals the host_samples row written in the same transaction
  job_id            TEXT NOT NULL,
  job_type          TEXT NOT NULL,            -- tests | perf | background | service
  state             TEXT NOT NULL CHECK (state IN ('pending','running')),
  holding_reason    TEXT,                     -- pending only; the queue's holding_reason at that instant
  rss_bytes         INTEGER,                  -- running only; sum over the job's process group
  cpu_seconds_total REAL,                     -- running only; sum of cumulative CPU time of live processes in the group
  process_count     INTEGER,                  -- running only
  PRIMARY KEY (sampled_at_ms, job_id)
);
CREATE INDEX IF NOT EXISTS job_samples_by_job ON job_samples (job_id, sampled_at_ms);

Each sample is one transaction: one host_samples row and zero or more job_samples rows. A job in any state other than pending or running is not written.

B.3 How each field is measured

  • CPU busy. Read the host CPU tick counters (host_statistics(HOST_CPU_LOAD_INFO)) each sample. Busy % = (Δuser + Δsystem + Δnice) ÷ (Δuser + Δsystem + Δnice + Δidle) × 100 between this sample and the previous one. The first sample after start, or after a failed read, writes NULL.
  • Memory. host_statistics64(HOST_VM_INFO64) page counts × page size; hw.memsize for total; kern.memorystatus_level (the same percentage memory_pressure -Q prints, which queue admission reads today1) for available; kern.memorystatus_vm_pressure_level for pressure. vm.loadavg for load.
  • GPU. The same ioreg -r -c AGXAccelerator -d 1 read and "Device Utilization %" parse that host_status.rs uses2; move the parser so both call one function.
  • Jobs. Read every pending and running row of queue_jobs while holding the queue's admission lock3, so a sample never sees an admission pass half-way (the pass clears every hold reason, then re-marks them). Release the lock before running any process listing. Then run ps -axo pgid=,rss=,time= once and sum RSS, CPU time and row count for each running job's process_group_id. A running job with no process_group_id, or none of whose processes appear, writes NULLs for those three fields.
  • No top. The recorder must not run top; it costs 1.3 s of CPU per call on this machine.

Scheduling. A dedicated Tokio task with a tokio::time::interval set to MissedTickBehavior::Delay; each tick does the measurement on spawn_blocking. A tick that fails a measurement writes NULL for that field and carries on. A failed database write logs a warning at most once a minute and carries on. The recorder never blocks queue admission beyond the job-list read.

Pruning. Once an hour, delete rows from both tables with sampled_at_ms older than now − retention_days.

Cost check. Before merging, run the recorder on the studio for 10 minutes and report the server's added CPU time per sample in the PR. The bar is under 50 ms per sample.

The old table. queue_resource_samples in queue_runner.db holds June data from the Python server and has no writer4. Leave it untouched.

Sort pending jobs by (index of type in QUEUE_JOB_TYPE_ORDER = perf, tests, background, service; then queued_at; then id). This is the order in which admission examines them.

Ended membership and text.

Every other terminal state (succeeded, failed, cancelled) is excluded. A job is in ended when its state is in the table and finished_at is within ended_hours of now. Durations format as whole minutes ("5m"), or hours and minutes past 60 ("1h 20m"), or seconds under a minute ("40s").

Example. Two tests running, one perf and one test waiting: queued is [perf bench-ledger position 1, tests cargo test position 2] even though the test was submitted first, because perf is examined first.

D. GET /client/queue/stats

Auth. As Appendix C. Query. hours ∈ {24, 168, 720}, default 168; anything else → 400. When the recorder is off or has no rows in the window, return 200 with "available": false and nothing else.

{
  "available": true,
  "hours": 168,
  "window_seconds": 604800,
  "covered_seconds": 598210,          // Σ weight over host_samples in the window
  "thresholds": {"cpu_busy_below_pct": 60, "available_memory_at_least_fraction": 0.25, "pressure": "normal"},
  "waiting": [
    {"group": "limits",     "job_seconds": 40320, "headroom_job_seconds": 35480, "unknown_job_seconds": 120},
    {"group": "perf_rules", "job_seconds": 73440, "headroom_job_seconds": 51000, "unknown_job_seconds": 0},
    {"group": "memory",     "job_seconds": 600,   "headroom_job_seconds": 0,     "unknown_job_seconds": 0},
    {"group": "other",      "job_seconds": 45,    "headroom_job_seconds": 45,    "unknown_job_seconds": 0}
  ],
  "by_type": [
    {"type": "background", "jobs": 41, "peak_rss_p50_bytes": 6.1e9, "peak_rss_p95_bytes": 1.8e10,
     "peak_rss_max_bytes": 2.4e10, "cpu_cores_p95": 5.5}
  ]
}

All four groups are always present, in that order. by_type lists only types with at least one running sample in the window, in QUEUE_JOB_TYPE_ORDER.

Algorithm.

  1. Weight. Each host sample stands for min(interval_ms, gap to the next host sample) milliseconds; the last sample in the window uses interval_ms. A server outage therefore adds no phantom time.
  2. Groups. concurrency_cap → limits. perf_running, awaiting_tests, perf_cooldown, displacing → perf_rules. memory_pressure, resource_budget_missing → memory. Anything else, including NULL → other.
  3. Headroom. A host sample has headroom when cpu_busy_pct < 60 and mem_available_bytes ≥ 0.25 × mem_total_bytes and pressure_level = 1. It is unknown when any of those three is NULL.
  4. For every pending job_samples row, add the host sample's weight to its group's job_seconds, and to headroom_job_seconds or unknown_job_seconds as the host sample dictates.
  5. Peaks. For each job with running rows, peak RSS = max rss_bytes. CPU cores for consecutive running rows of one job = Δcpu_seconds_total ÷ Δ seconds; drop negative deltas (a process exited and took its CPU time with it). Percentiles are nearest-rank over jobs (RSS) or over intervals (CPU).

Worked example (the memo's): 12 host samples at 5 s, all weight 5 s; two background jobs pending with concurrency_cap in all 12; 10 samples at 30% CPU, 200 GB of 256 GB available, pressure 1; 2 samples at 90% CPU. Result for limits: job_seconds 120, headroom_job_seconds 100, unknown_job_seconds 0 → the card shows "2 min … 83%".

Card text (app formats; server returns numbers only): "Limits held jobs {limits job hours}. The machine had headroom for {headroom ÷ (job − unknown)}% of it." — "Perf rules held jobs {perf_rules job hours} (by design)." — "Background jobs peak at {background p95 GB} each (95th percentile)." Omit a line whose group has zero seconds, or whose type is absent. Hours show one decimal; under an hour show minutes.

    "gpu_avg": 9.0,

    "headroom_seconds": 60500, "unknown_seconds": 300

Rules. Averages are the plain mean over the bucket's samples that have a non-null value for that field. If none do, omit that field in that bucket. Maxima and minima likewise. pressure_max is the largest pressure_level (1, 2, 4). Summary weights use Appendix D's weight rule and headroom test. Summary averages are weight-weighted over non-null samples. Computation is one SQL pass over host_samples grouped by (sampled_at_ms − start_ms) / bucket_ms, then filling the empty buckets in Rust. Performance bar: under 300 ms for the 30-day range on 90 days of data (about 1.5 million rows), measured and reported in the PR.

Example. hours=1 at 12:00:07 UTC → end 12:00:15, start 11:00:15, 240 buckets of 15 s. At a 5-second interval, each full bucket has 3 samples. A server restart from 11:30:02 to 11:30:40 leaves the 11:30:15 bucket with samples: 0.

  • Queued rows. Line 1: position numeral, label, agent. Line 2: "{type} · waiting {now − queued_at} · gives up in {wait_deadline_at − now}", or "· giving up" once the deadline has passed. Line 3: holding.summary, else the existing jobSummary fallbacks15.
  • Stopped rows. Icon ✕ for displaced, over_memory, over_process_limit, timed_out; ⌛ for gave_up. Line 2: "{type} · {now − finished_at} ago". Line 3: ended_summary.
  • Empty sections are hidden. When running and queued are both empty: "Nothing running or waiting."
  • Held back? card as Appendix D's card text. When stats are unavailable: "No utilization recorded yet."

H. Evidence queries

Run on a .backup copy of ~/.local/share/claude-sessions/queue-runner/queue_runner.db (the live file is often locked). Window: queued_at > datetime('now','-30 days') on 2026-09-28.

-- Cause of each wait over 30 s, inferred at submit time
with j as (select id,type,julianday(queued_at) q, julianday(started_at) s,
                  julianday(coalesce(finished_at,'now')) f
           from queue_jobs where queued_at > datetime('now','-30 days')),
w as (select a.*, (a.s-a.q)*86400 wait_s,
  (select count(*) from j b where b.type='perf' and b.id<>a.id and
     ((b.s is not null and b.s<=a.q and b.f>a.q) or (b.q<=a.q and (b.s is null or b.s>a.q) and b.f>a.q))) perf_any,
  (select count(*) from j b where b.s is not null and b.s<=a.q and b.f>a.q) running_all,
  (select count(*) from j b where b.type=a.type and b.s is not null and b.s<=a.q and b.f>a.q) running_same
  from j a where a.s is not null and (a.s-a.q)*86400>30)
select case when type='perf' then 'perf job waiting (perf rules)'
            when perf_any>0 then 'behind a perf run'
            when running_all>=8 then 'overall limit of 8'
            when (type='tests' and running_same>=6) or (type in ('background','service') and running_same>=2) then type||' limit'
            else 'unexplained' end cause,
       count(*), round(sum(wait_s)/3600.0,1) hours
from w group by 1 order by 3 desc;

-- Perf budgets
select cpu_percent, gpu_percent, round(memory_bytes/1e9) gb, count(*)
from queue_jobs where type='perf' and started_at is not null
  and queued_at > datetime('now','-30 days') group by 1,2,3 order by 4 desc;

-- Terminal states
select state, count(*) from queue_jobs where queued_at > datetime('now','-30 days') group by 1;

Z. FAQ

Why 5 seconds and not 1? Test builds last minutes; 5 s resolves them. At 1 s the GPU read alone would cost 2% of a core and storage would be 1.5 GB for 90 days, with no decision that needs the extra detail.

Why a separate database? The queue database is written under the admission lock. A write every 5 seconds there would compete with admission for no benefit; the recorder only ever reads the queue.

Why record pending jobs every sample, when the queue already stores a hold reason? The queue overwrites and then erases the reason. Section 2's analysis had to guess causes from what was running at submit time. Sampled reasons make the card exact.

Why is the queued order "consideration order" rather than a predicted start time? Start times depend on when running jobs finish, which the server cannot know. The order admission examines jobs in is exact, and each row's reason tells you when it will not be the next to go.

Why is the stats call separate from the 5-second overview? It scans up to 30 days of samples; the overview only reads current rows. Polling the scan every 5 s would cost more than the recorder.

Why a fixed bucket width per range rather than a requested point count? Fixed widths make every client, and every refetch, agree on bucket boundaries, so a spike never shifts between slices when the screen refreshes.

Why not also build this in the web client or sm queue? The ask was the app. Both endpoints are plain JSON, so a web page or a sm queue stats command can come later without server changes.

What about Linux? The recorder is macOS-only, like host_status.rs. On Linux the endpoints return available: false where they would have used samples.

Does the memory bar change? No. It shows the same "used" figure as today, now from the recorder instead of top. The kernel's "available" figure is added to the response and used only by the card.
