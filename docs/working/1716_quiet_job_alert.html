1716 — Tell the agent when its queue job goes quiet

Author: Claude Opus 5.5 923f2479 (sm-1716) · Ticket #1716 · Fits the web redesign memo, docs/working/1710_web_redesign.html (#1710)

Memo

Recommendation. When a running queue job goes quiet (20 minutes with no CPU, no GPU and no new log output), sm sends one [sm queue] message to the agent that queued it. The message says how much memory the job holds, which slot it occupies, how many jobs wait behind it, and what its log said last. The agent decides: cancel it, or do nothing because the pause is expected. Service jobs never get this message.

This uses the same "quiet" that the web redesign (#1710) already turns red on the Board and the Queue page, so the page and the alert always agree. It also changes two things in the approved 1710 memo. First, sm now tells the agent instead of only marking the job. Second, the 1710 memo measures CPU in a way that marks busy training jobs as quiet, and this memo corrects the measurement. Section 3 explains the flaw.

Queue job
A command an agent submitted with sm queue run. It has a type (tests, perf, background or service), a label, an ID and a log file.
Slot
The queue runs a limited number of jobs of each type at once: 6 tests, 1 perf, 2 background, 2 service. A running job holds one slot of its type until it exits.
The job's agent
The session that receives the job's completion wake (the job's notify target). Usually the agent that queued it.
Memory held
The job's memory as Activity Monitor shows it ("footprint"), summed over all its processes. #1714 records it every 5 seconds.
Quiet
Defined in section 2. In one line: for 20 minutes, the job has used no CPU, no GPU and written nothing to its log.

1. What happened on 29 September

Three training jobs from fractal-algo-rust tickets #1854 and #1856 stopped working between 3:52 and 4:26 pm, but their processes did not exit. The two #1854 probes had crashed: each log ends in a Python FileNotFoundError traceback, written at 3:53 and 4:19 pm. Something in the process kept it alive after the crash. Together the three held about 148 GB, and the two #1854 probes held both background slots. Six to eight background jobs waited behind them while the Mac sat 15–30% busy. Someone noticed and cancelled all three by hand at 5:53 pm, 1½ to 2 hours later. Five of the waiting jobs started within three seconds of the cancel.

The cost was the slots, not only the memory. A background slot is the scarcest thing the queue has, and a hung job holds one until its time limit, which is up to 8 hours. The agent that queued the job is the only one who can tell a hang from an expected pause. Right now nothing tells that agent anything until the job exits.

2. What the agent receives

Here is the message 1854-engineer would have received at 4:21 pm. It goes to the same session and through the same delivery as the job's completion wake:

[sm queue] 1854-es-with has been quiet for 20m: no CPU, GPU or log output since 4:01 pm.
It holds 50.3 GB of memory and one of 2 background slots; 6 background jobs are waiting for a slot.
Last log lines:
  File ".../pathlib.py", line 1013, in open
    return io.open(self, mode, buffering, encoding, errors, newline)
  FileNotFoundError: [Errno 2] No such file or directory: '/Users/rajesh/artifacts/1701_pooled_nocross/run/…/reaction-result-7195.json'
If it is hung, cancel it: sm queue cancel job_4489b0dcd0d9. If this is expected, do nothing; sm will not ask about this job again for 2 hours.
Log: ~/.local/share/claude-sessions/queue-runner/logs/job_4489b0dcd0d9.log. ID: job_4489b0dcd0d9

The last log lines matter most here. The traceback tells the agent in one read that the job crashed, and it needs no investigation to act. The agent does not have to reply. sm queue status on the job also shows "Quiet since 4:01 pm" for as long as the job stays quiet.

The definition. sm records every running job every 5 seconds. A job is quiet when, in each 5-second step for the last 20 minutes, all three of these hold:

  • its processes gained less than 0.05 seconds of CPU time, which is under 1% of one core;
  • its GPU time did not grow;
  • its log file did not grow.

If any step shows activity, the 20 minutes start over. A job's alert is sent once, when the job first becomes quiet. It can only be sent again after the job has shown activity and then gone quiet again, and no sooner than 2 hours after the previous alert.

3. Why the 1710 measurement changes

The 1710 memo calls a job quiet when its CPU time at the end of a 20-minute window is less than 1% of a core above its CPU time at the start. That comparison is wrong for jobs that start child processes. sm reads CPU time only from processes that are alive at the moment of the sample. When a worker process exits, its CPU time leaves the total. A training job that runs a wave of workers can therefore show less total CPU at the end of a busy window than at the start. Over the same 23 hours, the start-to-end rule marks 164 stretches on 20 jobs as quiet, and almost all of those jobs were busy and succeeded. Checking each 5-second step, and counting a drop as zero, marks 5.

The fix moves quiet detection out of the Queue-page ticket (#1723) and into the server, as part of this ticket. That way the alert, sm queue status, the Queue page and the Board's ticket clock (#1719) all read one value. The 1710 memo's appendix D6.6 is updated in the same pull request to point here.

Z. FAQ

A. Quiet: exact rule

Inputs. The utilization recorder (crates/sm-server/src/utilization.rs) already writes one job_samples row per running job every 5 seconds, carrying cpu_seconds_total and gpu_seconds_total summed over the job's process group. Add one nullable column:

ALTER TABLE job_samples ADD COLUMN log_bytes INTEGER;  -- size of queue_jobs.log_path at the sample; NULL if it cannot be read

Add it with the same ensure_column pattern the table already uses for gpu_seconds_total. Rows written before the column exists have NULL.

Steps. For two consecutive running samples p and c of the same job, let Δt be (c.sampled_at_ms − p.sampled_at_ms) / 1000. The step is active if any of these hold:

  1. Δt > 60. A gap in sampling, such as a server restart, restarts the clock. This is the conservative choice.
  2. p.cpu_seconds_total or c.cpu_seconds_total is NULL (unknown counts as active).
  3. max(0, c.cpu − p.cpu) ≥ 0.01 × Δt. A drop, which means a process exited, counts as 0. This matches how job_usage already floors a drop at zero.
  4. Both GPU values are non-NULL and c.gpu > p.gpu. If either is NULL, GPU counts as no growth.
  5. Both log_bytes values are non-NULL and differ. Growth or truncation both count. If either is NULL, the log counts as no growth.

Otherwise the step is idle.

quiet_since. Let last_active be c.sampled_at_ms of the job's most recent active step. If the job has no active step, use the job's first running sample. Let latest be the job's most recent sample. Then:

quiet_since = last_active   if latest − last_active ≥ quiet_minutes × 60 000 and the job is running
            = null          otherwise

quiet_since is therefore the moment activity stopped, not the moment the job crossed 20 minutes. "Quiet for 24m" means now − quiet_since. It is never shown below 20m. Service jobs get quiet_since too, because the Queue page marks them. They are only excluded from the alert.

Determinism. quiet_since must equal the value computed from job_samples rows alone, so a server restart cannot change it except by the gap rule. The detector may keep per-job state in memory. It must seed that state at startup from each running job's samples since started_at.

Evaluation. Run the detector once per recorder tick, after that tick's job_samples rows are written. A job that leaves the running state has quiet_since = null.

Worked example (1854-es-with, job_4489b0dcd0d9). The log last grows at 3:53 pm. The last active step (a CPU blip) ends at 4:01:41 pm, so quiet_since is 4:01:41 pm and becomes non-null at the first sample 20 minutes later, 4:21:41 pm. The alert goes then. At 5:00 pm the job reads "quiet 58m". The memo's chart is generated from the same rule over the live utilization.db.

B. The alert

When. On the tick where a job's quiet_since changes from null to a value, send the alert if all of these hold:

  • the job type is not service;
  • queue_jobs.quiet_alerted_at is null or at least quiet_alert_repeat_minutes (default 120) ago;
  • the job has a non-empty notify_session_id.

Persisted shape. Add queue_jobs.quiet_alerted_at TEXT (RFC 3339 UTC, nullable) with ensure_column. Set it when the message is enqueued. The 2-hour limit survives restarts because the value is on disk.

Delivery. Use RetainedQueueStore::enqueue_message_once_with_metadata, as the owner-forced requeue notice in queue.rs does. Pass message id queue-quiet-{job_id}-{quiet_since_ms}, the target notify_session_id, mode "sequential", and message_category: "queue-completion". The once-only id guarantees at most one message per quiet stretch even if the tick runs twice. Also append the first line of the message to the job's log file, prefixed with a blank line. The requeue notice already writes to the log this way.

Text. Exactly this template. Braces are fields; the square brackets mark an optional clause.

[sm queue] {label} has been quiet for {quiet_age}: no CPU, GPU or log output since {quiet_since_local}.
It holds {memory} of memory and one of {limit} {type} slots[; {waiting} {type} jobs are waiting for a slot].
Last log lines:
{tail}
If it is hung, cancel it: sm queue cancel {id}. If this is expected, do nothing; sm will not ask about this job again for {repeat}.
Log: {log_path}. ID: {id}
FieldValue
labelThe job label. Use the ID if the label is blank, as the other queue notices do.
quiet_agenow − quiet_since, written as 20m, 1h 05m. Minutes are floored.
quiet_since_localServer local time, h:mm am/pm, e.g. 3:52 pm.
memoryThe latest sample's footprint_bytes formatted with the existing memory_amount_text. If footprint is NULL, use rss_bytes; if both are NULL, write an unknown amount.
limitThe live max_concurrent for the job's type.
waitingPending jobs of the same type at the tick. Omit the whole bracketed clause when it is 0.
tailThe last 3 non-empty lines of the log. Read at most the final 64 KiB. Indent each line 2 spaces and cut it to 200 characters with …. If the log is unreadable or empty, write (log is empty).
repeatquiet_alert_repeat_minutes formatted as 2 hours, 90 minutes.

  • sm queue status <job>: when quiet_since is set, add the line Quiet since {h:mm am/pm} ({age}): no CPU, GPU or log output. Holding {memory}. If quiet_alerted_at is set, add Agent told at {h:mm am/pm}.
  • sm queue list: running rows with quiet_since set get the suffix quiet {age}.
  • GET /client/queue: each running job gains cpu_seconds and gpu_seconds (latest sample totals), footprint_bytes, log_updated_at (the time of the last step whose log size changed, RFC 3339, or null), quiet_since (RFC 3339 or null), and quiet_alerted_at. These are the fields 1710 D6.6 names, plus footprint_bytes and quiet_alerted_at. The Queue page's "holding 50 GB" text reads footprint_bytes.
  • Board ticket clock (#1719, rule 3a): reads quiet_since from the same server value. Nothing to change in #1719.

Z. FAQ

Why not cancel quiet jobs automatically? An expected wait, such as the remote-GPU probe, looks the same as a hang. Only the agent knows which it is. The job's own time limit is still the backstop.

Why not detect "the log ends in a traceback" directly? A traceback only covers Python crashes, and some jobs write their output to their own files instead of the queue log (1856-pilot-mac did). The quiet rule catches both cases. The log tail in the message lets the agent see a traceback when there is one.

Why does log output count, when #1714 records only CPU and GPU? Network-bound jobs use almost no CPU but write steadily. The 1848 purchase job is the example. The log keeps those jobs from being called quiet, and costs one file-size read per job every 5 seconds.

Why count a process-count change or a CPU drop as idle rather than active? A drop only tells sm that some process exited; it says nothing about work now. Counting drops as zero matches job_usage. A busy job still shows positive steps around the drop, so it is never quiet. The replay of job_cc4c866663f3 confirms this.

Why 5 alerts, not 4, in the history count? The remote-GPU probe (job_0a3e1fc1a082) is flagged by the CPU and GPU rule alone. Whether its log grew during the 21 minutes is not recorded, so the log rule might have held it back. The memo counts it as an alert to stay conservative.

Data used. utilization.db job_samples and host_samples, 28 September 6:59 pm to 29 September 6:17 pm (Pacific time), 332 jobs. Job records and logs come from queue-runner/queue_runner.db and queue-runner/logs/. The chart and counts come from scripts that read those files directly.
