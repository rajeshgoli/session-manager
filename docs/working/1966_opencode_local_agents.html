Authors: Claude Opus 5.5 sm-1966-h2 691a9d70, contract; Claude Opus 5.5 sm-1966 f3018f36, lifecycle proof · Tickets #1966, #1956 · revision 1, 2026-10-04

Memo

sm gains a fourth kind of agent, opencode, and it is how every local agent runs. You start one with sm spawn local "brief". sm launches the agent’s own opencode server inside the sandbox wall. Everything that today depends on typing into a terminal — the brief, sm send, reminders, queue wakes, status, token counts — sm does over that server’s HTTP interface instead. A tmux session stays, only so you can watch the agent and type to it, as you do today. This memo asks for eight rulings, all with recommendations. The appendices are the build contract for #1956 and the two tickets I propose splitting off it.

What you have already ruled (4 Oct): opencode is the local harness; the model stays Qwen3.8-Flash-Next, with no more model trials; and the local-agents memo (#1784) takes no new information, so this contract is its own document. Where #1784’s appendices still bind, appendix A names them.

Terms

Provider
sm’s name for the program an agent runs in. Today: claude (Claude Code), codex (stock Codex), codex-fork (your patched Codex). This memo adds opencode.
opencode server
opencode serve: opencode running with no screen, answering HTTP on a local port. It holds the conversation, calls the model, and runs the agent’s tools. One per agent.
Attach view
opencode attach: opencode’s own terminal screen, connected to a running server. It shows the live conversation and accepts typing.
Sandbox wall
The macOS sandbox from #1954 that confines a local agent to its checkout and a few local ports. The judge is a second conversation with the same model that allows or denies each action leaving the wall.
Event stream
A long-lived HTTP response on which the opencode server reports what happens: busy, idle, each tool call, each model request with its token counts.
Outbox
sm’s existing durable message queue, used so that a message counts as delivered only when opencode confirms it has it.
MTPLX
The program that holds the model in memory and answers requests, on port 8000.

Why a message is confirmed by asking for it back. sm picks the message’s id before sending and records it. Before every send, it asks opencode for that id; if opencode has it, sm marks it delivered and sends nothing. The proof found that opencode does not refuse a repeated id: resending one appended the text a second time. So the check before sending, not the id alone, is what prevents a message arriving twice. Risks I cannot close from here

  • Compaction near 200K is untested. The largest prompt in the proof was 80K tokens. opencode compacts on its own and tells sm; how well it summarises is unknown. Handoff at 75% means it should rarely matter. #1956 measures where compaction triggers and records it.
  • opencode moves fast. Pinning protects a running system; each upgrade costs a rerun of the proof’s checks (about an hour of model time).
  • First spawn needs the network once. opencode installs its plugin library from npm, and the wall has no network, so sm prepares it outside the wall, once per opencode version. If npm is unreachable then, the spawn fails with a message saying so.
  • The quality evidence is two tickets. Local PRs go through review like any other; if they keep coming back as “large changes” or “wrong”, narrow the Local tier.

FAQ — what changed since the local-agents memo

  • This is the first revision of this memo. It replaces #1784’s appendices B, C, D and G, which specified Claude Code as the local harness; #1784’s appendices E, F (with appendix J’s two substitutions), K and L still bind.
  • sm spawn claude --host local is gone; the command is sm spawn local.
  • #1784’s launch requirement for a Claude Code judge hook is replaced by an opencode plugin that calls the same judge service.
  • A local agent reaches sm only through its own gateway, which tells sm which agent sent each request. #1784 let local agents call sm directly; sm does not check who is calling, so a local agent could have started agents or queued jobs outside its sandbox by leaving out its name. C. Launch

C.1 Entry points

  • CLI: sm spawn local [--name N] [--model M] "brief", sm spawn opencode … (alias) and sm local. --effort is accepted and ignored; the spawn result adds (effort ignored: local).
  • HTTP: POST /sessions/spawn and POST /client/sessions accept "provider": "opencode".
  • Every session-creation route (sm spawn, sm local/POST /sessions, and any other that creates a session) refuses a request from a local agent with 403 local agents cannot spawn agents. The caller is identified by the wall’s sm gateway (I.2 item 8), never by anything in the request: a local agent reaches sm only through its own gateway port, which stamps every request with the agent’s id. A request so stamped is refused on every session-creation route, whatever parent_session_id it claims or omits. Tests: through the gateway, 403 for sm spawn and for a direct POST /sessions with no parent field and with a forged one; a script the agent writes and runs gets the same 403, because the check is on the connection, not the command text. Handoff successors are created by sm itself (handoff/transfer.rs) and are not refused; they inherit provider = "opencode" as successors already inherit provider.
  • Board start, owner settings’ new_agent.provider and the web and Android start sheets do not offer opencode until #1959.

C.2 Checks before launch, in order

  1. Seats. If the number of non-stopped opencode sessions is at least max_agents, refuse with 409 no local seat free (1/1 used by <name>). #1958 later replaces this with waiting. A handoff successor skips this check: it takes its predecessor’s seat, which complete_handoff frees moments later by retiring the predecessor. Counting the predecessor would refuse every local handoff at max_agents = 1 (or, under #1958, wait forever for a seat only the successor’s start can free). Example: sm-2001-fix holds the one seat and hands off; its successor starts with 2/1 seats briefly in use; the predecessor retires and the count is 1/1 again. The overlap costs under 1 GB (two opencode servers on one model). Test: at max_agents = 1 a local handoff completes, while an ordinary second launch is still refused.
  2. Model. Until #1957 ships: GET <model_base_url>/models must answer 200 within 5 s, else 409 no local model loaded. After #1957: the local_model state must be ready. An explicit --model that differs from model_id (or the loaded identifier) is refused with 409 model <m> is not loaded; loaded: <id>.
  3. Version. <binary> --version must print exactly version, else 409 opencode <found> is installed; sm is pinned to <version>.
  4. Plugin library (C.4) is prepared, or preparing it succeeds.
  5. Wall prerequisites from the wall ticket: the judge service answers, the egress proxy is up.
  6. Port. The lowest port in port_range not held by another non-stopped opencode session and not accepting connections. None free: 409 no local port free.

C.4 The plugin library

opencode installs @opencode-ai/plugin into its config folder from npm when it first starts with a plugin present. Inside the wall there is no network, so sm prepares it outside: if <state_root>/plugin-sdk/<version>/node_modules/@opencode-ai does not exist, sm writes a minimal config there and runs opencode debug config with XDG_CONFIG_HOME pointing at it, outside the wall, with a 120-second timeout. At each launch sm copies that folder’s node_modules, package.json and lock file into the agent’s config folder. Failure: 409 opencode plugin library could not be prepared: <last 400 bytes of output>. Never pass --pure: it skips local plugins and with them the judge.

Start sequence.

  1. Write the launch record (status: launching), as today.
  2. Create the state folder, config (C.3), plugin (I.1), library (C.4), wall.sb (wall ticket), the two scripts.
  3. tmux new-session with the serve window; pipe-pane it into serve.log.
  4. Poll GET /global/health every 250 ms until 200, up to health_timeout_secs. Timeout: kill the tmux session, fail the launch with opencode server did not start: <last 20 lines of serve.log>.
  5. POST /session with {"title": "<friendly name>"}; store the returned id as provider_resume_id.
  6. Start the event reader (E).
  7. Create the agent window running launch-attach.sh, select it, and pipe-pane it into the session’s existing log_file (so sm output keeps its meaning: what you would see).
  8. Deliver the brief (D.4). On confirmation, mark the launch applied and the session running, as today.

Readiness, wherever sm asks whether a session can take input (session_input_ready, wait_for_initial_brief_readiness, handoff’s successor wait): the health call answers 200 and GET /session/status answers. Busy or idle does not matter, because opencode queues input.

Tests: a launch against a stub opencode HTTP server (C.7) produces the two windows, the files above with modes, the environment (asserting no ANTHROPIC_ variable), and the three HTTP calls in order.

C.6 Failure handling

Any failure before step 8 removes the provisional session as today and keeps the state folder (named in the error) for diagnosis. A crash of sm between steps is recovered at boot by recover_session_runtime_launches: with a launch record in launching and a conversation id present, sm resumes at step 6; without one, it fails the launch.

D. Delivery

D.1 Modes

Every message to an opencode session — sm send in any mode, reminders, queue completions, parent wakes, stop notices, handoff notices, context-monitor messages, rename requests — is persisted to the message queue and delivered in queue order by D.2. A rename row takes D.2’s rename branch (a title change, not a prompt); every other row is sent as a prompt. The text is exactly what sm types for Claude today (format_send_input_text_raw, PendingMessage::delivery_text). Differences from tmux providers:

  • No ready fence. A message is sent whether the agent is busy or idle; opencode stores it and the model reads it at its next step. Background categories (BACKGROUND_RETRY_MESSAGE_CATEGORIES) need no idle check.
  • Urgent is ordinary. No Ctrl-B, no Escape, no abort. POST /session/{id}/abort is called by sm only in sm clear (F), never for a message.
  • Control predecessors (sessions.rs:11715: after an urgent or rename message the drain stops until the next pass) do not apply; the drain continues in queue order.
  • Gone runtime. A connection failure is not a reason to mark the session stopped. Only an absent tmux session is (unchanged rule).

D.2 One delivery attempt

For the oldest pending row for the session (rows are strictly ordered; a later row is not attempted until every earlier row is delivered). Rename branch: if the row is a rename request, sm sends PATCH /session/{ses} with {"title": "<name>"} instead of steps 1–4. A 2xx marks the row delivered (step 5); anything else, or no connection, leaves it pending and stops this pass. Resending is safe because setting the same title twice changes nothing, so no message id and no GET are needed. Example: rows 50 (rename to sm-2001-fix) and 51 (sm send) are pending; row 50’s PATCH times out, both stay pending; next pass the PATCH succeeds, then row 51 goes through steps 1–5. Every other row:

  1. If provider_message_id is null, generate a message id and a part id (D.3) and store both, with the current provider_resume_id as provider_conversation_id, on the row in one write. From then on the row keeps them, and steps 2–4 address that conversation.
  2. GET /session/{ses}/message/{message id}. 200: go to step 5. 404: continue. Anything else, or no connection: leave the row pending; stop this pass.
  3. POST /session/{ses}/prompt_async with {"messageID": id, "parts": [{"id": part id, "type": "text", "text": text}]}.
  4. Poll the GET of step 2 every 250 ms for up to confirm_timeout_secs. 200: continue. Otherwise leave the row pending; stop this pass.
  5. Mark the row delivered through complete_runtime_message_delivery_raw, which applies the existing side effects (delivery acknowledgements, stop-notify, reminder registration, parent wake) in one transaction.

When attempts run. Immediately when a row is queued (the same call sites that drain today), on every event-reader (re)connection, and in the 5-second background retry sweep (main.rs:335), which for opencode sessions covers every pending row, not only the background categories. Attempts for one session are serialised by the existing per-session input lock.

Once a handoff starts (the successor’s creation begins), no row is attempted to the predecessor: new rows stay pending and move to the successor with the others, so nothing lands in a conversation that is about to retire. Example: sm send arrives while the successor is starting; it stays pending, moves, and the successor receives it first. Test: a send arriving between handoff start and the predecessor’s retirement reaches the successor exactly once and the predecessor never.

Before the conversation changes. sm clear (F) and a handoff that moves pending rows to a successor first run step 2 for every pending row of the session that holds ids, against the row’s stored conversation on the current server: 200 marks it delivered; 404 clears its three ids, so it is sent fresh to the new conversation. If the server does not answer, sm clear is refused with 409 opencode server unreachable; pending messages unresolved; a handoff is deferred: the predecessor is not retired and no row moves until every such row is resolved, retried on each 5-second sweep. If the server still does not answer after 10 minutes, the handoff fails with handoff blocked: unresolved deliveries to an unreachable conversation on the predecessor, rows stay with it, and nothing is sent twice. Restoring the predecessor (C.5) lets the next attempt resolve them. Example: row 60 was posted, then sm crashed before marking it; on restart the owner runs sm clear. The GET answers 200, so row 60 is marked delivered and is not posted again into the new conversation. Test: the same sequence against the stub; one prompt total.

Why step 2 before step 3, every time. opencode does not refuse a repeated message id: reposting one appended the text to the stored message (proof finding P.4 item 1). The GET is what makes a resend after a lost reply, an sm crash or an opencode restart deliver nothing twice.

Example. Row 41 (sm send) is queued while the server restarts. Pass 1: ids msg_10a2…/prt_10a2… stored; GET fails to connect; row stays pending. Five seconds later the server is up. Pass 2: GET → 404; POST; GET → 200 at 0.3 s; delivered; the sender’s --notify-on-delivery acknowledgement fires. If sm had crashed after the POST and before marking, pass 3 (after restart) would GET → 200 and mark it delivered without posting.

Tests (against C.7’s stub): a row is delivered once across a forced failure between POST and marking; with the stub’s repeat-append switch on, the stored text is never doubled; urgent and background rows to a busy session are delivered without waiting; abort is never called; a later row is not posted while an earlier one is pending.

D.3 Ids

opencode orders a conversation by id, so ids are generated at the first attempt, never earlier. Format, as opencode generates them: the prefix (msg or prt), an underscore, 12 lower-case hex digits of (unix milliseconds × 4096 + counter) mod 248, where the counter starts at 1 each new millisecond and increments within one, then 14 random characters from 0-9A-Za-z. Example: msg_1041e3ac0001WxqUWbXtu5JPXu. Test: ids generated in sequence sort ascending as strings. Consequence, accepted: a row that first failed long ago keeps its earlier id, so if you typed in the attach view meanwhile, opencode places the late row before your message in the conversation. The model still reads both.

D.4 The brief

The spawn brief uses D.2 with the ids stored on the launch record (brief_message_id, brief_part_id) instead of a queue row, so that recovery after a crash runs the same check. It differs from D.2 in timing only: the spawn waits for confirmation up to initial_brief_ack_timeout (the existing setting) and retries a failed attempt every second within it. On timeout the launch fails as ProviderAcceptanceTimedOut today, and the brief stays retained as today. Unlike the Claude path (runtime.rs:1568, “no retry after submission”), a retry is safe here because of the check. The brief text is the stored brief artifact with F.6’s addendum prepended.

D.5 What you type in the attach view

A user message that reaches the event stream with an id sm did not generate is yours. sm treats it as Claude’s UserPromptSubmit for an owner-typed prompt (E.1), so owner-answer tracking works as it does when you type into a Claude agent.

E. The event reader

One thread per running opencode session, in the style of the codex-fork event monitor (monitor_codex_fork_event_stream, sessions.rs:8174), started at launch step 6, at restore and at boot for every non-stopped opencode session. It opens GET /event (server-sent events, basic authentication) with the blocking ureq client already in the workspace, reads it line by line, and acts only on events whose sessionID is the session’s current conversation id, read from provider_resume_id on each event, never captured once at start, so it follows sm clear (F) without a restart. Events for an earlier conversation id are ignored. On disconnect it reconnects after 1 s, then 2, 4, up to 5 s. It exits when the session is stopped.

P.3 Adapters and persisted shapes

P.3.1 Exactly-once submission. Every submission has a key: brief- plus the first 16 hex characters of the brief's SHA-256, or one fresh key per delivery. Before the first attempt the bridge appends to ledger.jsonl:

{"key": "brief-ccc62b9be4aca887", "messageID": "msg_1041e3ac0001WxqUWbXtu5JPXu",
 "partID": "prt_1041e3ac0002TY2acF6ctX9NM4", "source": "brief", "chars": 2975, "text": "…", "t": 1791070452.416628}
{"key": "brief-ccc62b9be4aca887", "accepted": 1791070452.431535, "result": "sent"}

Each attempt first asks GET /session/{id}/message/{messageID}; 200 means already accepted, and nothing is posted. Otherwise it posts {"messageID", "parts": [{"id": partID, "type": "text", "text"}]} and records accepted. Attempts repeat every second until accepted; on restart, entries without accepted are replayed. Ids follow opencode's ascending format: msg_ or prt_, 12 hex characters of (milliseconds × 4096 + counter) mod 248, then 14 base-62 characters. They must be generated at submission time, because opencode orders a conversation by id.

P.3.4 The pane. sm delivers by typing into the session's tmux pane, and gates background wakes on the pane showing an empty Claude composer (a last line > with the cursor just after it). Typed text is buffered; carriage return submits it once through P.3.1; line feed stays a newline. P.4 Findings that shape an opencode contract

  1. opencode does not de-duplicate a reposted message id. Reposting the same messageID appended the text to the existing message (“brief one brief one”); with a fixed part id it overwrote the part instead. Exactly-once therefore needs the existence check and outbox of P.3.1, not the id alone.
  2. Urgent delivery must not abort. sm's urgent path (reminders, urgent sm send) sends Ctrl-B, which in Claude Code moves the running command to the background, then Escape. opencode cannot background a running tool, so mapping Escape to abort killed a 20-second command mid-run. Contract: urgent delivery to opencode is a queued prompt, read at the next step boundary; abort is only for an explicit interrupt.
  3. A delivery must be held until opencode accepts it. sm counts a message delivered once it has typed it. With opencode down, the first pane gave up and lost an sm send. After the fix, the message sent during the outage arrived once, 9 s after restart. Contract: sm marks a delivery done only when opencode has accepted it, and the outbox survives restarts of the adapter.
  4. Usage is mis-attributed today. sm filed local tokens under the active Claude account and priced the unknown model at the Opus rate (P.2 row 6). appendix G’s local account is required for either harness.
  5. Launch must prepare opencode's config folder outside the wall (plugin SDK from npm) and must not pass --pure, which skips local plugins and with them the judge.
  6. Model outages are absorbed. opencode retries an unreachable model indefinitely, backing off to about 30 s, and reports retry, which sm shows as working. A yield (1784 appendix F) loses no turn; a resumed turn waits up to 30 s after the model returns.

P.6 Not proved here

  • /clear, /rename and sm btw. sm types these into Claude Code. opencode equivalents exist (new session, PATCH /session/{id} title, a forked session) but none was exercised.
  • Owner typing in the attached view. A prompt typed in opencode attach is a user message that did not come from the outbox; the bridge would report it as owner-typed. Not exercised.
  • Version drift. opencode releases often. The proof pins 1.17.9 with updates off; an upgrade needs P.2's checks again.

Z. FAQ

Why not run opencode with no tmux at all? Every live-agent path in sm assumes a tmux session: delivery, readiness, kill, restore, clear, output capture, attach, the web and phone terminals, and boot reconciliation. Your retired Codex app-server provider ran headless and needed parallel versions of most of these; keeping tmux for viewing removes that work and keeps sm attach meaning what it means for every other agent. sm never reads the opencode screen, so the usual cost of tmux — scraping a pane — does not come back.

Why does the brief retry, when the Claude path forbids it? The Claude path cannot tell whether a lost submission landed, so a retry risks running the brief twice. Here the existence check answers exactly that question before every attempt.

Why is the server password needed if the wall already limits ports? The wall stops other local agents. The password stops anything on this machine that can open a loopback connection but cannot read your files — a web page in your browser, or a stray scan — from driving a local agent. It is not a boundary against your Claude and Codex agents: they run unwalled as you, can read server.secret, and can already type into any agent’s tmux pane. Those agents are trusted to that degree today, and this design does not change it. It costs one environment variable.

Why does sm write usage lines in Claude’s format? sm’s ledger already parses that format exactly, de-duplicates by message id, and the proof showed every token arriving. A separate parser would add code without changing a number.

What happened to the proof’s pane and bridge? They were stand-ins so that the proof needed no sm code: the bridge followed the event stream and called sm’s hook routes, and the pane imitated a Claude prompt box so sm could type. In #1956 both disappear into sm itself (D and E); the pane becomes the attach view.

What does the proof not cover? Spawn through sm spawn (the proof seeded the session), compaction near 200K, clear, rename and typing in the attach view. #1956’s tests and live check (M) cover the first four; compaction is measured (H).
