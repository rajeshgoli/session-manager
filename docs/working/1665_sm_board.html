sm reads the order of your tickets from GitHub, groups them into lanes that you rank, and shows you what can start right now. Agents record "#1654 starts after #1653" with one command. You rank lanes in one list across all repos: fractal iteration 7 first, then context handoff, then this work. The board on sm.rajeshgo.li/board and a new Board tab in the app show every ticket as Ready, In progress, Blocked or Done. A Ready ticket has a Start button that opens the new-agent sheet with the ticket filled in. Ticket
A GitHub issue. Pull requests are never tickets on the board.
Starts-after link
GitHub's built-in "blocked by" link between two issues. "#1654 starts after #1653" means #1654 cannot start until #1653 closes. GitHub shows the link on both issues, and it can point to an issue in another repo.
Sub-issue
GitHub's other built-in link. It puts a ticket under a parent: #1653–#1657 are sub-issues of #1651, context handoff. A parent waits on its sub-issues.
Waits on
Either link. Ticket A waits on B if A starts after B, or if B is a sub-issue of A.
Lane
One goal ticket plus every open ticket it waits on, directly or through other tickets. One iteration in fractal-algo-rust is one lane. Session-manager usually has several lanes running side by side.
Lane rank
The lane's position in your single list across all repos. 1 is the most important. Ranks are always 1, 2, 3 … with no gaps.
Longest chain
The longest run of open tickets in a lane where each ticket waits on the one before it, ending at the goal. With no time estimates, this is the critical path: the lane needs at least this many more tickets merged, one after another.
Start
The new-agent sheet with a ticket filled in. The new agent starts out holding the ticket's claim (the claim sm ticket records).
Needs you
An open ticket whose agent is waiting on you, known from what sm already records. The agent sent you a message with sm send rajesh --blocking that you have not answered, or it asked for your review with sm doc publish --review and you have not reviewed that revision yet. Nothing new for agents to do.

1. What goes wrong today

  • Plans live in chat and ticket text. The context-handoff plan (#1653 first, then #1654, #1656 and #1657) exists as a table in an agent's reply. GitHub has no links on those tickets, and #1651 lists no sub-issues. Fractal's #1775 names its predecessor in a "Starts after: #1774" line that no tool reads.
  • You carry the graph in your head. When #1653 merges, nothing tells you that three tickets just became free. You find out the next time you look.
  • Plans grow silently. An agent that discovers prerequisite work files a ticket, but nothing ties the new ticket to the one it blocks.
  • The queue can't tell important work apart. An iteration 7 test run and a side experiment wait in arrival order.

When two rules match, the higher row wins: a ticket whose agent is waiting on your ruling shows Needs you, not In progress. A row also shows a warning in these cases:

  • An agent is working a ticket that is still Blocked.
  • The agent holding the ticket has stopped.
  • The pull request merged but the ticket is still open. This is the normal case in fractal-algo-rust, where tickets that merge into an epic branch (a long-lived branch that collects one iteration's tickets before they reach main) are closed by hand.
  • Tickets wait on each other in a loop.

7. Queue order

Within each job type, the queue runs the job from the highest-ranked lane first. Jobs from the same lane run in arrival order. A job belongs to a lane when the agent that queued it holds a ticket in that lane. A helper agent counts through its parent, and a job run from a ticket's worktree counts too. Jobs with no lane run after every lane's jobs. Nothing else about the queue changes:

  • Perf still comes before tests, tests before background, and so on.
  • A perf job still runs alone.
  • A running job is never interrupted.

B. Storage

The board tables live in the claims database: the file at config.sm_send.db_path, default ~/.local/share/claude-sessions/message_queue.db, which work_claim_store() opens (http/claims.rs:81). board::init_board_schema(conn) creates them with CREATE TABLE IF NOT EXISTS. It is called beside every existing call to init_work_claims_schema (queue.rs:2963, work_claims.rs:627). Timestamps are RFC 3339 UTC strings, the format the claims tables use. Repos are canonical owner/name in lower case (canonical_repo, work_claims.rs:545).

  • Lane ranks. Active lanes' ranks are exactly 1..n. Adding a lane gives it n+1. Ending a lane sets rank to NULL and renumbers the rest in their existing order, in one transaction.
  • board_members holds each active lane's members and their state as of the last recompute. Pushes and the "new" marker compare against it (D, I). It is rewritten for a lane on every recompute; joined_at keeps its first value while the ticket stays a member.
  • board_ticket_ranks holds every open member of an active lane with the best (lowest) rank among the lanes containing it. It is rewritten on every recompute, and the queue reads it (H).
  • board_events kinds: lane_added, lane_moved, lane_ended, link_added, link_removed, ticket_joined, ticket_left, became_ready, became_needs_you, ticket_closed, cycle_found, agent_started, push_sent, push_failed, sync_failed. Rows older than 90 days are deleted at the end of each read pass.
  • Queue. The queue job table in queue_runner.db gains a nullable rank_tickets TEXT column (a JSON array of {repo, number}, possibly empty), added with the existing add-column helper (queue.rs:7226).

C. Reading and writing GitHub

C1. Which repos, how often

  • Config keys under board: repos, sync_interval_seconds, checkouts, start_defaults.
  • The repos read are the distinct goal_repo of active lanes, plus board.repos from config (default ["rajeshgoli/session-manager", "rajeshgoli/fractal-algo-rust"]), plus the repo of every open member of an active lane in the last recompute. Within a pass, sm keeps reading newly discovered repos until no new repo appears; this ends because every round adds a repo not yet read. A repo sm cannot read is stale (C4), and a stale repo's tickets are never Ready and cannot be started until a read succeeds.
  • A pass runs every board.sync_interval_seconds (default 60, floor 30). The loop is started next to claims::init_work_claims (http.rs:1477) with a tokio interval and spawn_blocking, like the claims loop (http/claims.rs:637–666).
  • An extra pass runs right after a link write, a lane add, and POST /client/board/refresh. At most one pass runs at a time, and at most one waits behind it; further requests fold into the waiting pass.
  • Transport is gh api graphql through the helper GhCliWorkItemSource uses (http/claims.rs:14–77), with a 30-second timeout. It sits behind a trait BoardSource so tests can substitute a fake, as WorkItemSource does (work_claims.rs:309).

C2. The read query, per repo

query($owner:String!, $name:String!, $cursor:String) {
  rateLimit { remaining resetAt }
  repository(owner:$owner, name:$name) {
    issues(states: OPEN, first: 100, after: $cursor) {
      pageInfo { hasNextPage endCursor }
      nodes {
        number title url updatedAt
        parent { number title url state stateReason closedAt repository { nameWithOwner } }
        blockedBy(first: 50) { totalCount nodes { ...Ref } }
        subIssues(first: 50) { totalCount nodes { ...Ref } }
        closedByPullRequestsReferences(first: 10, includeClosedPrs: true) {
          nodes { number state url repository { nameWithOwner } } }
      }
    }
  }
}
fragment Ref on Issue { number title url state stateReason closedAt repository { nameWithOwner } }

This query was run against fractal-algo-rust on 2026-09-29 and cost 2 points. If blockedBy.totalCount or subIssues.totalCount exceeds 50 for an issue, a follow-up query pages that connection for that issue alone. GitHub caps an issue at 50 blocked-by links and a parent at 100 sub-issues, so this is rare.

C3. What a pass writes

  1. Every open issue returned is upserted into board_items as open. So is every node in parent, blockedBy and subIssues, with its own state, even when it belongs to another repo. That keeps cross-repo blockers fresh on every pass without reading their repo.
  2. For each open issue X, sm replaces X's outgoing edges in board_edges (waiter = X). Each blockedBy node becomes (X waits on node, 'after'). Each subIssues node becomes (X waits on node, 'sub_issue'). A parent P becomes (P waits on X, 'sub_issue'), deduplicated by the primary key. first_seen_at and source of edges that already existed are kept. New edges get source = 'github' unless sm wrote them (C4).
  3. board_prs for X is replaced from closedByPullRequestsReferences.
  4. An item in board_items that was open for this repo but is missing from the open list is fetched with issueOrPullRequest(number:), using the aliased batch of items_query (work_claims.rs:327, 50 per call). sm records closed, stateReason and closedAt, and deletes its outgoing edges. If GitHub returns null (deleted or transferred), the row becomes closed with state_reason = 'missing'.
  5. sm recomputes the model (D), writes board_members and board_ticket_ranks, records events, and hands transitions to pushes (I).

C4. Failures and rate limit

  • A repo's read fails. Its rows stay as they were. board_repo_sync.last_error and last_error_at are set, and a sync_failed event is recorded. Lanes whose goal repo is in that state show "stale since last_ok_at". No pushes fire for tickets in that repo on that pass (I).
  • Rate limit. If rateLimit.remaining is below 200, sm sets rate_limited_until = resetAt for every repo and skips passes until then.

C5. Writing links

  1. sm resolves node ids for both tickets in one aliased query: repository(owner:,name:){ issue(number:){ id parent{number repository{nameWithOwner}} blockedBy(first:50){nodes{number repository{nameWithOwner}}} } }. If either issue doesn't exist, the result is 404 "no such issue: owner/name#N".
  2. If the link already exists (on add) or is already absent (on remove), sm writes nothing and returns already or absent.
  3. Otherwise sm writes the link with one of four mutations:
    • after: addBlockedBy(input:{issueId: waiter, blockingIssueId: blocker})
    • after --remove: removeBlockedBy(input:{issueId: waiter, blockingIssueId: blocker})
    • under: addSubIssue(input:{issueId: parent, subIssueId: child, replaceParent: false})
    • under --remove: removeSubIssue(input:{issueId: parent, subIssueId: child})
  4. If the child already has a different parent, sm writes nothing and returns 422 "#N already sits under owner/name#P; remove that first with sm board under N P --remove". sm never replaces a parent silently.
  5. On success, sm updates board_edges at once, with source = 'sm:<session id>' for an agent or 'sm:owner'. It records link_added or link_removed with the actor, and requests a pass (C1).
  6. Any GitHub refusal (limits, permission) returns 422 with GitHub's message verbatim. A transport failure returns 502.

D. The board model

The model is recomputed from the tables after every pass and after every lane or link change. It is a pure function of board_items, board_edges, board_prs, the active lanes, the active ticket claims (WorkClaimStore::active_claims, work_claims.rs:747) with their holder state (HolderState, work_claims.rs:176), and board_repo_sync.

D1. Definitions

  • waits_on(t) = every b with an edge (t, b), of either kind.
  • Lane members. Start from the goal g. For each open member m, add every b in waits_on(m), and keep going from b only if b is open. Closed members are leaves, because their own blockers no longer matter. g is always a member. If g is closed, the lane ends first (D5) and has no members.
  • State, first match wins:
    1. done: the item is closed.
    2. needs_you: a waiting-on-you record exists for the ticket. That is either of:
      • an owner message (owner_messages.rs) whose state is NeedsYou under derive_message_state (owner_messages.rs:102: blocking, unanswered, unhandled, sender not ended), sent by a session that holds an active claim on the ticket;
      • a doc publish (OwnerDocPublish, owner_docs.rs:40) that is its doc's latest publish while the doc's summary state is ReviewRequested (the rule of still_wanted for review notices, http/follows.rs:568–580). The publish must either come from a session (session_id) holding an active claim on the ticket, or name a PR (pr_number) that work_links ties to the ticket.
      The row keeps the holder and PR details and shows the reason: the message title, or "PR #N waits for your review" (or "DOC TITLE waits for your review" without a PR). Both sources are read at recompute; a message reply, sm doc review or the sender's end clears the state on the next recompute. Message and review changes also request a recompute, so the row updates within seconds rather than at the next GitHub pass.
    3. in_progress: an active ticket claim exists whose holder is not Retired, or a board_prs row is OPEN.
    4. ready: every b in waits_on(t) is closed. This includes having no b, and it requires t not to be in a cycle (D3).
    5. blocked: anything else.
  • Warnings on a member:
    • working_while_blocked: in_progress, and some b in waits_on is open.
    • holder_stopped: the holder state is Stopped.
    • merged_not_closed: open, with a MERGED PR row.
    • cycle (D3).
    • stale: the item's repo is failing its reads (C4).
  • chain(t), for open members. First remove every edge between two tickets of the same cycle (D3). Then chain(g) = 1, and chain(t) = 1 + max chain(w) over open members w with t ∈ waits_on(w).
  • Longest chain. The start s is the open member with the highest chain. Ties go to the lower repo, then the lower number. Each next step is the open member w that waits on the current ticket and has the highest chain, with the same tie-break. The chain ends at g. The lane's "longest chain N" is chain(s).
  • Row order. Groups come in the order needs_you, ready, in_progress, blocked, done. Within the first four groups, rows sort by chain descending, then by fan-out descending (the number of open members that wait on the ticket directly), then by repo and number ascending. Done rows sort by closed_at descending.
  • also_in: the other active lanes that contain the ticket. A ticket's queue rank is the lowest rank among its lanes (board_ticket_ranks).
  • new: joined_at is within the last 24 hours and the ticket was not a member when the lane was added.
  • Not in any lane: for each repo read, the open issues in that repo that belong to no active lane, with their states. Rows are ordered needs_you, ready, in_progress, blocked, then by number.

D3. Loops

Cycles are the strongly connected components with more than one ticket, or a ticket linked to itself, found with Tarjan's algorithm over each lane's open members. A cycle_found event is recorded once per component, keyed by the sorted member list, when it first appears.

D4. Lane adds

  • Adding a lane requires the goal issue to exist and be open. Otherwise the result is 404 or 422 "#N is closed".
  • An already-active lane with the same goal returns 409 with that lane.
  • The goal's repo joins the read set at once, and a pass is requested.

D5. Lane ends

  • When a pass sees an active lane's goal closed, it ends the lane (goal_closed), renumbers the ranks, records lane_ended, and sends the "lane done" push (I).
  • An owner End sets end_reason = 'owner' and sends no push.
  • If an ended goal reopens later, the lane does not come back; you add it again.

G. Start

POST /client/board/start takes {repo, number, provider: "claude"|"codex-fork", model, reasoning_effort, name?, brief?} and goes through these steps:

  1. Guard: the owner guard as in F.
  2. Open ticket: the ticket must be in board_items and open. Otherwise 422 "#N is closed" or 404.
  3. Still Ready: sm recomputes the ticket's state from the current tables (D1), under the same lock as the claim reservation in step 7. Only ready without merged_not_closed proceeds. Otherwise the result is 409 with the reason:
    • "#N is waiting on you";
    • "#N is held by NAME (state)";
    • "PR #n will close #N";
    • "#N waits on #a, #b";
    • "#N's PR merged; close the ticket".
    Start is shown on ready rows only, and the page and app refresh the board after a 409.
  4. Checkout: board.checkouts[repo] if set. Otherwise ~/projects/<name>, if it is a git checkout whose origin URL names the same owner/name. Otherwise 422 "sm doesn't know where owner/name is checked out; set board.checkouts in config".
  5. Name: defaults to <name>-<number>, cut to 32 characters.
  6. Brief: defaults to this text: 
    Work ticket #{number} in {repo}: {title}
{url}

You already hold the claim on #{number}. Run `sm ticket {number} --setup-worktree` and work in the worktree it prints, then follow this repo's CLAUDE.md.
  7. Reserve and create: allocate the session id first with allocate_session_id (sessions.rs:4361), as sm spawn --ticket does. Then reserve the claim for that id with claims::reserve_spawn_ticket (http/claims.rs:449, source Spawn), extended so SpawnTicket's parent is optional: a Start reservation passes none, and the claim's parent_session_id stays NULL, the value root sessions already carry. sm spawn --ticket keeps passing its parent unchanged. Then create a root session (no parent) through the same code path as POST /sessions (create_session, CreateCoreSessionRequest at sessions.rs:10205), with the same id, and working_dir, provider, model, reasoning_effort, name and initial_message = brief. Finally call finish_spawn_ticket to confirm the reservation, or to drop it if creation failed.
  8. Return: 200 {session_id, name}. sm records agent_started and requests a pass.
  • The holder's own sm ticket N --setup-worktree must succeed. It returns AlreadyHeld (work_claims.rs:588) and then creates the worktree. Ticket 3 has a test for this, and fixes the claims path if it refuses.
  • start_defaults come from board.start_defaults {provider, model, reasoning_effort}. The example config sets Claude, Opus with 1M context, high. The model string must be the identifier the model catalog returns (GET /client/session-models). If it is missing from the catalog, the sheet preselects the catalog's first entry and says the default is unavailable.

H. Queue order

H1. At submit

In the create_queue_job handler (route at http.rs:1555), sm picks the claimant session by the first rule below that finds one, and stores on the job, as rank_tickets, the tickets that session's active claims name at that moment: ticket claims as they are, PR claims mapped to their tickets through work_links (repo, pr_number → ticket_number). A job whose rules find no session stores NULL.

  1. requester_session_id, if it has an active claim of any kind (claims_for_session, work_claims.rs:725).
  2. Its ancestors, nearest first, through parent_session_id, up to 8 hops. The first ancestor with an active claim wins.
  3. The holder of the active claim whose worktree_path contains the job's cwd, compared path component by path component. The longest match wins.
  4. Otherwise NULL.

H2. At admission

  • Each admission pass (admit_pending_queue_jobs_conn, queue.rs:3377, which already receives the claims database path) builds a map from job id to lane rank with one query on the claims database: for each job, the lowest current board_ticket_ranks.rank among its rank_tickets. The tickets are fixed at submit, so a claimant that later releases its ticket or claims another does not change the job's lane, while reordering lanes still applies at once.
  • A job with no rank gets u32::MAX.
  • oldest_pending_queue_job (queue.rs:4223) orders by (lane_rank, queued_at, id) instead of (queued_at, id). pending_queue_job_consideration_order (queue.rs:3822) uses the same key, so the queue page's explanations stay true.
  • The rank is read at admission, not stored, so reordering lanes reorders pending jobs at once.
  • Unchanged: the type order (QUEUE_JOB_TYPE_ORDER), per-type limits, perf exclusivity and displacement, cooldowns and resource holds.

H3. Display

Queue job JSON (/queue-jobs, client/queue) gains lane_rank (integer or null) and lane_goal ({repo, number, title} or null), computed when read. Showing them in the queue page and the app's queue sheet is not in scope.

I. Pushes and the Board count

  • When they are decided. At the end of every recompute, sm compares the new member states with board_members before it is rewritten.
  • Ready alert. One per lane per recompute, listing the members whose previous state was anything but ready (blocked, in_progress, needs_you, or done for a reopened ticket) and whose new state is ready. Excluded:
    • tickets whose repo is stale that pass;
    • lanes added since the previous recompute;
    • tickets that were not members before;
    • tickets with the merged_not_closed warning, which need closing, not an agent.
    The title is Ready in lane {rank}, {goal title}. The body is #a, #b, #c can start — CAUSE: up to four numbers, then "+N more". CAUSE, for the first listed ticket:
    • from blocked: the waits_on tickets that closed since the last recompute ("#x closed"), or "a link was removed";
    • from in_progress or needs_you: "NAME let go of it" when a claim ended, or "PR #n closed" when its only open closing PR closed unmerged;
    • from done: "#N reopened".
    kind = "board_ready", and reader_path = "/board#lane-{id}".
  • Lane-done alert. Sent when a lane ends because its goal closed. The title is Lane done: {goal title}. The body is {repo short}#{n} closed · lanes below move up. kind = "board_lane_done", reader_path = "/board".
  • One record per alert. Each alert is an owner notice created with create_notice (owner_push/notices.rs:190). The fields are:
    • user_id = follow_owner_id(config, None) (http/follows.rs:55);
    • session_id = "board", session_name = "sm board";
    • subject_id = "board:{lane_id}:{board_events.id}", using the event recorded for the alert;
    • blocking = false.
    The follow worker delivers it with the notice rules of specs/1580_app_messages_replace_email.html (push, retry, and fallback), unchanged.
  • Clearing. The NoticeWorld implementation (owner_push/notices.rs:364) answers for the two board kinds:
    • opened is true once board_seen.seen_at is later than the notice's created_at;
    • still_wanted for board_ready is true while the lane is active and at least one listed ticket is still ready and unheld;
    • still_wanted for board_lane_done is always true. The lane has already ended when this notice is created, so its lifetime depends only on opened.
    So opening the board on the web or in the app withdraws the phone notification through the existing withdrawal pass (sm#1643). notice_candidates returns nothing for board kinds, because the board creates its notices directly.
  • The count. The Board count is the sum of:
    • board-kind notices for the owner that are unacked and not yet opened;
    • tickets currently needs_you in an active lane whose latest became_needs_you event is later than board_seen.seen_at. A ticket in two lanes counts once.
    POST /client/board/seen acks the notices and moves seen_at, so both parts clear together. Needs you creates no notice and no push. The web nav (J) and the app's bottom bar (K) show the count; 0 shows nothing. unseen.lane_ids in the board JSON lists the lanes contributing to either part.
  • No other alerts. Needs you, lane growth, link changes and loops show on the board only (memo section 8).

Z. FAQ

Why not keep the order in sm's own database? Then GitHub, the plan documents and sm could disagree, and a lost database would lose the plan. GitHub's links already exist, show on both issues, and cross repos. sm keeps only what GitHub cannot: your lane list and ranks.

Why reading every 60 seconds instead of GitHub webhooks? sm has no public webhook receiver, and all its GitHub traffic goes through gh. At 2 points per repo per pass, two repos cost about 240 of the 5,000 hourly points. A merge-to-push delay of up to a minute is acceptable for starting agents.

Why no time estimates? Nobody would keep them current. The count of tickets in a row is honest and costs nothing.

Why is a ticket with an open PR "in progress" even when no agent holds it? A PR that will close the ticket is work under way. The ticket should not tempt you to Start a second agent on it.

What about a parent ticket with no work of its own, like #1651? It becomes Ready when its last sub-issue closes. sm cannot tell whether a final PR remains, so the row offers both Start and "close on GitHub" (J2), and you choose.

Why store the job's tickets instead of its rank? The rank changes when you reorder or a lane ends, and the job should follow that. The tickets it was queued for do not change.

Why is Needs you derived and not set by agents? Agents already tell you they are waiting, with sm send rajesh --blocking or sm doc publish --review, and you answer there. Deriving the state from those records means it cannot drift from what you actually owe, and it clears the moment you answer. A non-blocking message does not count: the agent is not stopped on it.

Why no push for Needs you? The message or the review request already notified you. The board adds what they cannot: where the wait sits on the lane's longest chain.

Does the board replace sm ticket claims? No. Claims say who is on a ticket. The board reads them to decide In progress.
