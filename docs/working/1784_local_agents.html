1784 — Local models as sm agents

Author: Claude Opus 5.5 sm-1784 (2aac7357) · Ticket #1784 · 2026-09-30

Memo

Run local agents as ordinary Claude Code sessions that point at a model server on this Mac, and make sm own the one decision no harness can make: when the model is loaded and how many agents may share it, given everything else the machine is doing. The harness (the program that turns a model into an agent: Claude Code, Codex, opencode) is a solved problem; all three on this machine can already talk to a local model. What is unsolved is contention. A resident coding model takes 85–130 GB of the 256 GB, and your queue jobs alone use 173 GB or more in one sample out of ten, and up to 247 GB. Without sm, the first time both want memory at once the machine swaps, and sm's own memory guard stops one of your queue jobs rather than the model, because the model is invisible to it.

Concretely sm gains four things: a local model host it loads and unloads; a seat limit on how many local agents may run against it; a yield rule that unloads the model before any queue job is starved and resumes the parked agents afterwards; and separate accounting so local tokens never count against your Claude or Codex quota. The first step is a pilot of three tickets ending in a bake-off (a head-to-head run of candidate models on past tickets whose right answer we already know). The build-out is gated on its result, because the open question is not plumbing but whether a local model does useful work in your workflow at all.

Model server
The program that holds model weights in memory and answers HTTP requests. Here: LM Studio 0.4.16, already installed and running as a background service. It speaks both the OpenAI and the Anthropic request formats.
Weights
The model itself. Fixed size, loaded once, shared by every agent using that model. Qwen3-Coder-Next at 8-bit is 85 GB; MiniMax M2.5 at 4-bit is 129 GB.
Context cache
Per-agent working memory the model keeps for the conversation so far (known elsewhere as the KV cache). Grows with the conversation length; one per concurrent agent. This, not the weights, is what limits how many agents fit.
Seat
One agent's concurrent slot on the model. LM Studio calls it a parallel prediction; the model is loaded with a fixed number of them.
Prefill / decode
Prefill is the model reading the prompt; decode is it writing the reply. Both are measured in tokens per second. Agents are prefill-heavy: every turn re-sends the whole conversation.
Host
A new per-session field: where the session's model runs. anthropic (today's Claude), openai (today's Codex), or local.
Yield
sm unloading the model because a queue job needs the memory, after first letting local agents finish the turn they are on (drain) and then holding their next message (park).

Why this is sm's job

LM Studio plus any harness gives you one local agent. It does not know that a queue job is about to take 150 GB, that a perf run wants the GPU quiet, or that three other local agents are already mid-turn. sm knows all three: the queue knows which jobs are running and pending, the utilization recorder samples memory and GPU every five seconds, and the session tracker knows which agents are mid-turn. The figure shows why this matters on this machine specifically.

Three facts from the same data drive the design:

  • Queue jobs are the memory. Queue jobs alone used 49 GB at the median sample, 173 GB at the 90th percentile and 247 GB at the 99th. Background jobs were running 61% of the time.
  • The GPU is shared, too. From 18:00 to 21:00 the GPU averaged 60–76% busy from queue work. A local model decoding at the same time slows both.
  • sm's memory guard would hit the wrong target. When available memory falls below 8 GiB, the guard stops the largest queue job. A model server started outside sm is not a queue job, so the guard would stop your job to protect the model. Part of this design is teaching the guard to unload the model first.
  • Stopping the job that loaded a model does not free it. When you asked me to free the machine tonight, I cancelled the benchmark job. Its process ended, but LM Studio kept MiniMax's 129 GB until I unloaded it by hand, because the model lives in LM Studio's process, not the job's. Only something that knows a model is loaded, and calls LM Studio to unload it, gets the memory back.

So local agents do not pay for themselves by replacing the Low tier; you barely use it. They pay in three other ways, in order of likely value:

  1. Work you skip today because it costs quota. Always-on scouts, log and failure triage, inventory sweeps, and summarising long docs with sm doc cat all become free at the margin.
  2. Moving the mechanical part of Opus work down. Moving 10–20% of Opus-share work saves roughly 5–10% of the weekly Claude quota.
  3. Continuity. When a quota runs out, work today stops until the reset. Local agents keep the Local-tier queue moving.

The bake-off measures whether (1) and (2) are real. If a local agent cannot finish a Low-tier ticket without a human or a top-tier agent cleaning up after it, the value is negative and we stop.

Model choice and how many agents fit

Two models on disk are candidates. The number that decides between them is per-agent context-cache memory, which comes from the model's architecture and so is exact rather than estimated: Qwen3-Coder-Next keeps a full cache on only 12 of its 48 layers; MiniMax M2.5 keeps it on all 62.

Qwen3-Coder-Next, measured on this machine (30 Sep, 21:18, quiet machine; MiniMax's half was cancelled when you needed the machine back):

  • Memory is as predicted. 81 GB after loading, 28 seconds to load, and 95 GB with four agents each holding a 26K-token conversation.
  • One agent is usable. It reads 1,300–1,700 tokens a second and writes 47–58. A 26K-token prompt takes 15 seconds before the first word. For comparison, Claude in the cloud typically answers in a few seconds.
  • Reading is shared, and four agents do not read faster than one. Four agents sending 26K-token prompts at once waited 22–64 seconds each for their first word. Together they still read only ~1,600 tokens a second, the same as one agent. Writing barely scales either: 64 tokens a second in total across four agents, against 58 for one.
  • No reuse of an already-read prompt. Re-sending the same 26K-token prompt with one line added cost 15.3 seconds, the same as the first read. If agent turns behave the same way, every turn re-reads the whole conversation. An agent 60K tokens into a ticket would then wait ~40 seconds per turn, and ~2.5 minutes when four agents read at once.

Hence decision 8: two seats until P1 proves prompt reuse. One fact holds either way: local agents are several times slower per turn than cloud agents. Their value has to come from being free and unmetered, not fast.

How it works

Spawning. sm spawn claude --host local "brief" starts a local agent. sm refuses with a reason if no seat is free or the model cannot be loaded now; the spawn waits the way a queue job waits. The agent's name, children, sm send, reminders and status all behave as for any Claude agent. The app shows a LOCAL badge.

Yielding. The figure below shows a yield from start to finish.

Accounting. Local turns land in the usage ledger like any Claude turn, tagged with host local. They carry zero quota weight, are excluded from the Claude meter fit, and show in the app's Spend view as a separate "Local" line measured in model-busy hours, so you can see what the local tier did and what it cost the machine.

Risks I cannot close from here

  • Prompt size. If the slim profile still sends more than 30K tokens, each new agent spends 20 seconds or more reading its prompt before its first word (the default 84K-token prompt would take about a minute), and every compaction pays that again. The fallback is opencode, at the cost in the harness table.
  • Re-reading every turn. In the benchmark, LM Studio did not reuse a prompt it had just read. If agents' turns behave the same way, every turn re-reads the whole conversation, and an agent 60K tokens into a ticket waits ~40 seconds per turn. P1 checks LM Studio's prompt-cache settings with real agent turns. If reuse cannot be made to work, local agents stay at two seats and short tickets only.
  • Permission mode. Claude Code's auto mode may consult Anthropic's servers to classify actions. If it will not run against a local endpoint, local agents use acceptEdits with a command allowlist, which is stricter.
  • Instruction following. Weaker models ignore standing rules more often (naming themselves, going idle, not polling). Local agents get a short dedicated brief addendum, and the bake-off scores rule-following explicitly.

C. P1: host field and launch profile

C.1 Persisted shape

Add host: Option<String> to SessionRecord (sessions.rs:15687 and the two sibling structs at 15727 and 15830 that carry provider). None means the provider's native host. The only other accepted value in this design is "local". The field is serialised in sessions.json with #[serde(default, skip_serializing_if = "Option::is_none")], so existing records are unchanged on disk. Any other value is rejected at create with 400 unsupported host <x>. host = "local" with a provider other than claude is rejected with 400 host local requires provider claude.

C.2 Entry points

  • CLI: sm spawn claude --host local [--model <id>] … and sm claude --host local. Omitting --model uses the model currently loaded by sm (E). An explicit --model that differs from the loaded model is refused with model <id> is not loaded; loaded: <id>. sm never swaps models to satisfy a spawn.
  • HTTP: POST /client/sessions and the spawn route accept "host": "local". Board start and owner settings (new_agent.provider) do not offer local in P1.
  • --effort is ignored for host local, and the spawn result says so in one line. Local models have no effort setting that Claude Code can pass.

C.3 Launch environment for host local

Exported by managed_session_command after the existing exports, only when host = local:

export ANTHROPIC_BASE_URL=http://127.0.0.1:1234
export ANTHROPIC_AUTH_TOKEN=lmstudio
unset ANTHROPIC_API_KEY
export ANTHROPIC_MODEL=<loaded model identifier>
export ANTHROPIC_SMALL_FAST_MODEL=<loaded model identifier>
export CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1
export SM_HOST=local

The base URL and token come from a new config block local_host: { base_url, auth_token, lms_path } with those defaults. SM_HOST lets hooks and the brief addendum (C.7) know they are local. Test: a unit test in the style of runtime.rs:3498 asserts that the local command contains each export and that a non-local command contains none of them.

C.4 Slim profile

Default Claude Code sessions on this machine send a first prompt of 34K–96K tokens (median 84K across the 39 most recent transcripts; see I.3), because every MCP server, skill and plugin contributes tool definitions. For host local, sm appends these arguments to the Claude launch arguments:

--strict-mcp-config --mcp-config '{"mcpServers":{}}'
--disable-slash-commands
--tools Bash,Read,Edit,Write,Glob,Grep,TodoWrite

User settings still load, so sm's hooks and status line in ~/.claude/settings.json still fire. Do not use --bare: it skips settings-defined hooks, and sm's status detection depends on them. CLAUDE.md still loads because it is the standing contract. P1 measures the resulting first-prompt size by reading the first assistant turn's usage in the transcript (input + cache creation + cache read). It records the number in the P1 PR and in I.3. If the size exceeds 30K tokens, P1 stops and reports; the owner then chooses between trimming further and the opencode fallback.

C.5 Model catalog

/client/session-models with host=local returns exactly one entry, the model sm has loaded (E.2), or an empty list with reason no local model loaded.

C.6 Restore and clear

Restore (--resume) re-runs managed_session_command with the stored host, so the environment is re-applied. This is a correctness requirement, not a nicety. A local session restored without it would resume against Anthropic, bill your quota, and send a local conversation to the cloud. Test: restoring a host-local record produces a command containing ANTHROPIC_BASE_URL. /clear is unchanged.

C.7 Brief addendum

sm prepends a short fixed block, about 150 words, to the spawn brief of every local agent. The block states: your tier is Local; do not delegate or spawn; use sm status on [sm remind]; open a PR and run sm request-review; stop and report if blocked. The text lives in docs/product/local_agent_addendum.md so it can change without a rebuild; sm reads it at spawn.

D. P1: usage accounting

  • Account. In scan_usage_ledger (sessions.rs:416), a record with host = local records account key local instead of the Claude OAuth identity. The accounts table gets one row account_key = local, provider = local. Every quota consumer (burn windows, meter fit, sm usage, Spend) is keyed by account, so local rows fall out of Claude's numbers with no further change. Test: a ledger fixture with one local seat and one Claude seat shows the Claude weekly percent unchanged by the local rows.
  • Price. quota_rates::pricing returns rate 0 with needs_note = false for provider local, never the "unknown model priced as opus" fallback.
  • Model-busy hours. Each local message row already has a timestamp and token counts. B2 computes model-busy hours as the union of [request start, response end] intervals across local rows per hour, from transcript timestamps. P1 only needs the rows stored correctly.

E. P2: sm owns the model

E.1 LM Studio settings (one-time, done by P2's setup script)

E.3 States

unloaded → loading → ready → draining → unloaded, plus yielded: unloaded by sm with desired = true. From yielded, sm returns to loading when the reload condition (F.3) holds.

E.4 Reservation and the memory guard

Reservation = weights on disk + seats × context × cache bytes per token, where cache bytes per token = 2 (key and value) × full-attention layers × KV heads × head dim × 2 bytes. sm reads the numbers from the model's config.json. For Qwen3-Coder-Next: 12 full-attention layers (48 layers, full_attention_interval 4) × 2 × 2 heads × 256 × 2 = 24,576 bytes per token. For MiniMax M2.5: 62 × 2 × 8 × 128 × 2 = 253,952 bytes per token. Examples:

ModelSeats × contextReservation
Qwen3-Coder-Next 8-bit4 × 200K84.7 + 4 × 4.9 = 104.4 GB
Qwen3-Coder-Next 8-bit6 × 200K84.7 + 6 × 4.9 = 114.2 GB
MiniMax M2.5 4-bit4 × 196K128.7 + 4 × 49.8 = 327.9 GB: refused
MiniMax M2.5 4-bit2 × 100K128.7 + 2 × 25.4 = 179.5 GB

If config.json has no recognisable attention layout, sm refuses the load and asks for --reservation <GB>. The yield line is the guard's reserve plus 24 GB (config local_host.yield_margin_bytes), so 32.6 GB of available memory by default. Available memory means the kernel's value that the guard already uses (queue.rs:4519–4542).

The model's memory is wired. In the benchmark, wired memory rose from 9 GB to 98–108 GB while Qwen was answering. Wired memory cannot be compressed or paged out, so the kernel cannot relieve pressure from it; only an unload can. This is why the reservation must be counted in full and why the guard's first action is to unload, not to wait.

Guard change (queue.rs:5263 host_memory_guard_pass): when available memory falls below the yield line and the model state is ready or draining, the pass starts a yield (F.2) instead of stopping a job. When available memory falls below the reserve itself, which means a yield was too slow, the guard force-unloads the model first. It returns to stopping queue jobs only if memory is still under the reserve after the unload. Test: extend host_memory_guard_stops_the_largest_job_of_any_type_only_under_pressure (queue.rs:8756) with a loaded model and assert the model is unloaded and no job is stopped.

E.5 Perf admission

When a perf job reaches the front of admission (queue.rs:3726) and the model is ready, sm starts a yield with reason perf <label>. The perf job waits for the model to reach yielded, counting against its existing wait. While any perf job is running or waiting on its cooldown, reload is blocked.

E.6 Recorder

The utilization recorder adds a nullable local_model_bytes column to host_samples: the summed physical footprint of the LM Studio processes, measured the way job footprint is (utilization.rs:669). This makes the Mac chart able to show the model as its own band.

F. B1: seat limit, drain, park, resume

F.1 Seat limit

A local agent occupies a seat from spawn until it is retired or killed, not only while mid-turn. Idle agents hold their conversation cache in LM Studio, and admitting more agents than seats makes LM Studio evict caches and re-read whole conversations. A spawn with no free seat waits up to --max-wait (default 5 minutes, same flag and semantics as sm queue run) and then fails with no local seat free (4/4 used by …).

F.2 Drain and park

  1. State → draining. sm holds new sm send deliveries, reminders and wakes addressed to local agents in their durable queues. Nothing is lost; delivery is deferred.
  2. sm waits until every local agent's Claude hook state is TurnStopped (sessions.rs:16520), or until 10 minutes pass (local_host.drain_timeout).
  3. lms unload. State → yielded. Every local agent is marked parked, a new activity-state label shown in the app as "parked: model yielded to <reason>".
  4. Any agent cut off mid-turn is flagged resume_needed.

F.3 Reload and resume

Reload condition: desired is true, no perf job is running or in cooldown, and available memory has stayed at or above the reservation plus the yield line for 10 continuous minutes (local_host.reload_hold). On reload, the model is loaded with the same seats and context. Each parked agent's held messages are then delivered in order. An agent flagged resume_needed with nothing held gets [sm] The local model was unloaded while you were working (<reason>). Continue where you left off.

F.4 Worked example

H. P3: bake-off protocol

  1. Pick 8 tickets. Take them from closed tickets merged in the last 30 days whose implementing agent ran at Low or Mid tier. Prefer tickets whose PR diff is under 400 lines and touches fewer than 6 files. Exclude specs and Android-only work. Record each ticket's original token use from usage.db and its wall time from the session record.
  2. Replay each ticket on each model. Use a fresh worktree at the ticket's pre-merge base commit and the original brief, prefixed with C.7. Run Qwen3-Coder-Next at 2 seats × 200K, and at 4 seats if P1 showed prompt reuse working. Run MiniMax M2.5 2 seats × 100K in a quiet window.
  3. Review. Each attempt that produces a PR-equivalent diff goes through sm request-review on a draft PR. Close the draft afterwards and never merge it.
  4. Rescue. If an attempt stalls for 30 minutes or fails review twice, a Mid agent (Opus, high) finishes it. Record the Mid agent's tokens as a percentage of the original.
  5. Score each attempt: finished (y/n), review rounds, rescue % of original tokens, wall time ÷ original wall time, and standing-rule violations (named itself, went idle when told, did not poll, used sm status).
  6. Pass bar (from the memo): at least 5 of 8 reach clean review with rescue at or below 15%, and median wall-time ratio at or below 3. Report both models. The owner picks the resident model from the report.

The report is a memo in docs/working/, published for the owner's review.

I.4 Model throughput

Method. A Python script sends streaming /v1/chat/completions requests to LM Studio 0.4.16 with the model loaded at 131,072 tokens of context and 4 parallel seats (lms load … -c 131072 --parallel 4). Prompts are cut from this repo's CLAUDE.md and lessons.md, and each begins with a unique tag so that concurrent requests cannot share a prefix. Temperature is 0. Time to first token comes from the first streamed content or reasoning delta. Prefill speed is prompt tokens divided by time to first token; decode speed is completion tokens divided by the time after the first token. Footprint is the summed footprint physical footprint of LM Studio's processes, and wired memory comes from vm_stat. Before loading, the script refuses unless reclaimable memory (free + inactive + speculative + purgeable pages) is at least the weights plus 40 GB. It runs as an sm queue background job.

Z. FAQ

Why not make the model server a queue service job? Service jobs count against the global limit of 2 running queue jobs (config.rs:1689). A resident model would permanently take half of your queue's concurrency. The memory guard also treats a service job as just another job to stop, not as the first thing to unload. The model needs its own small state machine, which is E and F.

Why LM Studio and not vMLX, mlx_lm.server or Ollama? LM Studio is already installed and running as a service and already has both models. It serves the Anthropic request format natively, which Claude Code needs; supports parallel requests on MLX since 0.4.2; and has a scriptable CLI with load, unload and estimate. The opencode.json in the repo root points at a vMLX server on port 8010 from an earlier experiment. vMLX would work behind the same design if it gains an Anthropic endpoint, because only E.2's three commands touch the server.

Why not two models at once, a fast one and a smart one? Qwen plus MiniMax is 214 GB of weights before any conversation cache. That leaves your queue nothing.

Could a local agent be a reviewer? Not as the gate. sm request-review stays the correctness gate. A local first-pass review before a Codex review is a later idea for the bake-off to inform.

What if Claude Code changes its request format and LM Studio lags? Claude Code updates itself. A breaking change shows up as local agents failing their first turn. The P3 smoke ticket, re-run on any Claude Code or LM Studio upgrade, catches it. If it recurs, the opencode fallback removes the dependency.

Does this work on a second machine? Not in this design. The host is 127.0.0.1, and the memory logic reads this Mac's memory.

Why keep provider claude instead of adding claude-local? A new provider string would have to be added to every one of the ~25 files that branch on provider (B), for no behavioural difference. The host field touches only the sites that genuinely differ.
