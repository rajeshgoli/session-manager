2416 — Why sm is slow, and six changes that fix it

Author: Claude Opus 5.5 297bfff8 · Ticket #2416 · Measured 2026-10-19, 18:30–19:20 PDT on studio.local

Memo

sm is slow for two reasons that stack. First, the machine was overloaded: eight queue jobs ran at once, four of them full Rust test suites, and each suite can use all 32 cores by itself. Queue jobs run at the same CPU priority as sm-server and the agents, so everything waited in line together. Second, and growing every day, sm-server does work in proportion to every agent that has ever run, not to the handful that are live. It keeps all 2,823 sessions in one 13 MB file, copies that file in memory on most reads, rewrites it whole on most writes, and runs background loops that walk the entire history every few seconds.

I recommend six tickets in three parallel lanes. The first ticket alone removes about 28% of sm-server's CPU and a write storm that follows every account switch. The full set should cut sm-server's CPU by roughly two thirds, make the board page about four times faster, and keep sm responsive when the queue fills the machine, without capping how much work the queue does. Nothing in the plan deletes data or changes what any page shows, except where the decision table below says so.

Session state file
~/.local/share/claude-sessions/sessions.json. One JSON document holding every session record sm has ever created, plus registries (roles, launches, pending reparents). sm-server is its only reader and writer.
Hook
An HTTP call a Claude agent makes to sm-server on each lifecycle event: prompt submitted, tool about to run, turn stopped, status-line update. Agents wait on the reply, so hook latency is agent latency.
Write lock
The single in-process lock every change to the session state file takes. While one change holds it, every other change waits.
Parse cache
sm-server's in-memory copy of the parsed state file. Today every write throws it away, so the next reader parses the whole file again.
Cold segment
The proposed second file for retired or killed sessions that stopped more than 14 days ago. It is read once at startup and rarely rewritten. Every read still sees its sessions; only writes get cheaper.
Nice value
The operating system's CPU priority for a process. 0 is the default; higher numbers yield to lower ones when cores are contended and use any spare cores freely when they are not.

Why it is slow

1. Queue jobs compete with sm on equal terms. The queue admits test jobs by memory, not CPU, and allows six at once. That is the right policy for throughput, but because queue jobs run at the same priority as everything else, a full machine slows sm-server, the sm CLI, tmux and the agents in proportion. At load 66, the queue page went from 0.1 s to 1–2 s with no change in sm's own work.

2. The session state file is one document, copied and rewritten whole. On an idle machine, parsing the file takes 26 ms, copying it in memory 12 ms, and serializing it 10 ms. The diagram shows where those costs land.

3. Background loops walk the whole history. These are the costs that grow without bound:

  • Every 5 s, the message-retry loop visits 23 stopped sessions that each hold a queue-completion notice they can never receive. For each one it takes the write lock and copies all 13 MB, only to find the session stopped. This is the single largest cost: 28% of sm-server's CPU.
  • Every usage scan, once a minute, stamps the current account onto every session, stopped ones included, with one full-file rewrite per changed session. After an account switch that is about 2,800 rewrites, roughly two minutes of holding the write lock. It also overwrites the account that old sessions actually ran on.
  • The local-model card on the queue page, and its 5-second retry loop, read all 16,021 queue jobs ever run. sm queue list --all builds a reply for every one of them and opens the board database about 4,500 times, so it times out.
  • The board page opens the docs database twice for each of 145 docs: 80% of its 0.4 s.
  • Each usage scan reads all 693,000 burn samples (the stored usage-meter readings) twice.

What I am not doing

  • Capping test jobs. You ruled this out: using the whole machine is the point. Nice 10 gives sm priority without lowering the queue's throughput.
  • Agents running builds outside the queue. Some agents run cargo directly in their own shell. Those processes are not niced. The memory guard already kills them past 1 GiB; this plan leaves them alone.
  • The agents inbox catalogue (3%) and tool-call hook writes. Neither is large enough to justify a ticket now. Tool-call hooks still write once per call, but T2 and T3 make each write about eight times cheaper.

FAQ — what changed since the last revision

Revisions 2 to 5 close twelve gaps that four rounds of adversarial review found in the specs for T2 and T3. None changes the plan, the order or the targets. These are the ones you would notice:

  • Rollback stays safe. The first move of old sessions into the cold segment happens only after a restart's handover is final, and after an hour of serving. If a deploy of T3 rolls back during the restart, the old binary finds every session where it expects them.
  • Manual rollback past T3 needs one command. Rolling back by hand to a build without T3, after the first move, would hide old sessions from that build until someone runs sm-server thaw-cold. T3 adds that command and documents it.
  • Order is preserved exactly. Lists of sessions come back in the same order as today, including ties between old sessions with the same name.
  • Moves survive a host crash. Each move is written to disk in a fixed, synced order, so a power loss cannot lose a session.

A. Measurement method and data

A.1 Endpoint benchmark

The benchmark below times read routes that the CLI, web app and phone poll. It reports p50, p90 and max over N runs. It must run against the live server on 127.0.0.1:8420, from a shell where uptime shows the load being compared. Before and after numbers are comparable only when the 1-minute load averages are within 30% of each other.

#!/bin/bash
N=${1:-10}
ID=${SM_BENCH_ID:-<a live session id>}
for p in /health /sessions /client/bootstrap /client/queue /client/board /client/follows \
         /client/notices /client/sessions/$ID /client/usage/meters "/queue-jobs?limit=20"; do
  ts=$(for i in $(seq $N); do curl -s -m 60 -o /dev/null -w "%{time_total}\n" "localhost:8420$p"; done | sort -n)
  echo "$ts" | awk -v p="$p" '{a[NR]=$1} END{printf "%-28s p50 %6.3f  p90 %6.3f  max %6.3f\n",
      p, a[int(NR/2)+1], a[int(NR*0.9)], a[NR]}'
done
printf "load: "; uptime | sed 's/.*averages: //'

B. T1 — Stop needless session work

Files: crates/sm-server/src/sessions.rs, crates/sm-server/src/opencode/outbox.rs, scripts/perf/ (new).

B.1 Retry loop skips stopped and unknown targets without locking

drain_runtime_pending_targets_by_category (sessions.rs ~5598) runs every 5 s from drain_runtime_background_retry_messages, driven by the main.rs background pass "background wake delivery retry".

  • Required. Before calling is_opencode_session or drain_runtime_pending_messages_for_writable_session for a target, read the target's raw record from load_parsed_state() (an Arc, no copy). Skip the target, without taking write_guard, when:
    • the record is absent, or
    • raw_session_is_stopped is true, or
    • handoff_fences_delivery_raw is true.
    These are exactly the conditions under which runtime_session_accepts_background_delivery_raw returns false today before touching tmux.
  • Opencode check. Read the provider from the same borrowed record. Do not call get_session.
  • Re-check under the lock. drain_runtime_pending_messages_for_writable_session still checks under write_guard, because a session can stop between the two checks.
  • Conditional write. It writes the state file only if drain_pending_runtime_messages_raw delivered at least one message or changed the state. That requires an equality check against the pre-drain value, or a changed flag threaded through the drain (implementer's choice). drain_runtime_pending_messages_for_session_category (~5431) gets the same conditional write.
  • Undeliverable messages stay queued. They remain undelivered rows in message_queue.db, exactly as today. A restore or successor handoff delivers them through the existing paths. T1 does not mark, expire or delete them.
  • Test, retry. With 30 stopped targets holding undelivered queue-completion rows and one live target, one retry pass:
    • takes write_guard at most once;
    • leaves sessions.json's inode unchanged if the live target had nothing deliverable;
    • delivers to the live target when it is ready.
  • Test, race. A target that stops between the borrowed check and the locked check is not delivered to.

B.2 Account stamping only on live sessions, one write per scan

  • Required. In scan_usage_ledger (sessions.rs 519), record_session_account_key runs only for records where is_stopped is false.
  • Batch. Collect all the changes, then apply them in one write_guard, load, mutate, write cycle. Records whose key already matches are skipped, as today.
  • Status-line path. The status-line path (record_claude_statusline_burn) keeps calling record_session_account_key for its own session, but skips it if that session is stopped.
  • Unchanged. usage_report_for_session and the ledger keep reading account_key as stored.
  • Test, switch. After a simulated account switch, one scan over 50 stopped and 3 live sessions writes the file once and changes only the 3 live records' account_key.
  • Test, history. A stopped session's account_key never changes after it stops.

C. T2 — Make reads free

Files: sessions.rs, handoff/notes.rs, handoff/store.rs. Starts after T1 merges.

C.1 One shared store per state file

  • Required. All SessionStore values in one process whose canonicalized state_file paths are equal share one parse cache (parsed_state) and one write_lock. Use a process-wide registry keyed by canonical path (for example a static OnceLock<Mutex<HashMap<PathBuf, Weak<Shared>>>>).
  • Instances fixed with no change at their call sites:
    • agent_memory_guard.rs:306: today a fresh store every 2 s, so a full parse every 2 s.
    • runtime.rs:1480: a fresh store per opencode readiness check.
    • local_model.rs:1017.
    • main.rs:419.
  • Behaviour change, deliberate. Two instances in one process can no longer interleave read-modify-write cycles and lose an update.
  • Test. Two instances built from different spellings of one path (a symlink, or a trailing ./) observe each other's writes without a re-parse, and their writes serialize.

C.2 Writes install their result in the cache

  • Required. write_raw_json_value takes the Value by value (or clones once, if a caller keeps using it). It no longer clears the cache unconditionally. Instead it installs Arc::new(ParsedState::new(value)), but only under a stamp that provably names the bytes it wrote:
    1. Write the temp file, flush it, and fstat the temp handle. Record (dev, inode, len, mtime).
    2. Rename it over the state file.
    3. Open the state file path again and fstat that new handle.
    4. If the new handle's (dev, inode, len, mtime) all equal the values from step 1, install the value. Use the stamp from the step 3 fstat, which is the same handle-based stamp parsed_state_at already computes, including ctime.
    5. Otherwise another writer replaced or rewrote the file in between, so clear the cache, as today.
    • Why ctime is not compared. A rename can change it, so it is not part of the comparison. It is still part of the installed stamp, taken from the reopened handle.
    • Why len and mtime are compared. An in-place rewrite keeps the inode but changes mtime (nanosecond resolution on APFS) and usually len. Comparing them rejects it.
    • Residual case. The only case left is a same-length rewrite within the same nanosecond. Nothing in sm writes the file in place, so this is accepted.
  • Test, interleaving. Inject a hook between steps 2 and 3, and run it twice. Once it replaces the file through a rename; once it truncates and rewrites the file in place with different bytes and a later mtime. In both cases the next load_parsed_state must return the other writer's content.
  • Normalization. ParsedState::new runs normalize_opencode_runtime_record as on parse. The installed value must therefore equal what a fresh parse of the written file yields.
  • Test. Write, then load_parsed_state. The result equals serde_json::from_slice(fs::read(file)) after normalization, and no parse ran (count parses with a test-only counter).
  • External writers. A write from outside the process changes the stamp, and the next reader parses, as today.

C.3 A shared session view replaces per-call copies

  • New cache. ParsedState gains view: OnceLock<Arc<SessionsView>>, built on first use per file version. SessionsView holds:
    • the StateSnapshot sessions after into_sessions's alias map and pending adoption proposals;
    • an index from id to position;
    • an index from alias to position;
    • the HandoffDefaults and session_refs map that handoff_view_for_record needs.
    It does not hold handoff_view, because that depends on the work-claims database (see below).
  • Freshness of handoff_view. Each public read call still runs WorkClaimStore::handoff_inherited_by_session once, as load_snapshot does today. It then computes handoff_view only for the records it returns, so freshness is unchanged.
  • Read set. Readers never receive a bare SessionsView. They receive a per-call SessionReadSet, which holds view: Arc<SessionsView> plus inherited: BTreeMap<String, Inherited>, queried once when the read set is made. It offers three methods:
    • iter() yields &SessionRecord whose handoff_view is None. It is for callers that only filter or look up fields.
    • handoff_view(idx) -> Value computes handoff_view_for_record(record, defaults, session_refs, inherited.get(id)).
    • record(idx) -> SessionRecord returns a clone with handoff_view filled in. It is the only way to obtain a record for serialization.
    The shared view is never mutated after it is built.
  • Serialization rule. Any code that builds a SessionResponse (or any JSON that includes handoff_view) from a read set must go through record(idx). Today that is watch_state, list_sessions, list_client_sessions, by-id GETs, and session_response_with_live_activity. Enforce it with types: SessionResponse::from accepts an owned SessionRecord only, so a borrowed record from iter() cannot reach it.
  • Test, freshness. Read /watch/state, change a work claim so handoff_inherited_by_session changes for one session, without touching sessions.json, then read again. The second response's handoff_view reflects the change, and is byte-identical to what main returns for the same sequence.
  • get_session(id). Keep the four resolution steps in today's order: id, alias, a live record's display name, any record's display name. Steps 1–2 use the indexes. Steps 3–4 scan the view without copying. Only the single result is cloned.
  • list_sessions(include_stopped). Clone only the records it returns.
  • Borrowing API. Add pub(crate) fn sessions_read_set(&self) -> Result<SessionReadSet>. Move these hot callers to borrow instead of clone:
    • watch_state
    • session_obligations
    • queue_session_names
    • run_follow_pass
    • live_activity_state
    • opencode_readers supervisor
    • retry_opencode_outboxes
    • is_opencode_session
    • verify_hook_auth_or_secret
    • tool_use_hook
    • local_agent::authenticate_request
    These sit in http.rs files that belong to T5's lane. T2 adds the API and converts only the sessions.rs and opencode/ callers; T5 converts the http callers.
  • Test, equivalence. For a fixture of 200 sessions with aliases, adoption proposals, handoff records and duplicate names, every one of get_session (by id, alias, name and stale name), list_sessions(true|false), list_child_records and resolve_hierarchy_root returns byte-identical JSON before and after T2. Capture the golden output from main in the first commit.

D. T3 — Cold segment

Files: sessions.rs, handoff/transfer.rs, handoff/notes.rs, opencode/*.rs, main.rs (the thaw-cold subcommand and first-sweep gate), scripts/rust_migration/{state_preflight,state_backup,state_restore,final_backup}.py, docs/product/lessons.md. Starts after T2 merges.

D.1 Files and shape

  • Location and format. The cold segment is sessions.cold.json beside the state file: {"version":1,"sessions":[{"anchor":<id or null>,"record":{...}}],"session_runtime_launches":[{"anchor":<launch id or null>,"record":{...}}]}. Each record is the raw JSON exactly as it stood in sessions.json. The hot file's shape does not change.
  • Anchors preserve today's global order. A cold entry's anchor is the id of the nearest record before it, in today's merged order, that is hot. It is null if no hot record precedes it. Cold entries keep their relative order within the file.
  • Merged view. The merged order is defined as:
    1. cold entries anchored to null, in cold-file order;
    2. then, for each hot record in hot-file order, that record followed by the cold entries anchored to it, in cold-file order.
    This reproduces exactly the order the single file had. Launch records use the same rule over launch ids.
  • Anchors at sweep and thaw. When a sweep moves a record cold, it recomputes the anchors of every cold entry from the full merged order before writing. When a thaw moves X (anchored to A) back to hot, X is inserted into the hot file immediately after A, or at the front if A is null. The cold entries that followed X under the same anchor are re-anchored to X, and the entries before X keep A. The merged order is unchanged by either operation.
  • Missing anchor. An anchor whose id is in neither file can only arise from a manual edit. The merge then places that entry among the null-anchored ones and logs a warning naming the id. The next sweep recomputes the anchor.
  • Durable writes. Each file write is:
    1. write the temp file;
    2. fsync the temp file;
    3. rename it over the target;
    4. fsync the parent directory.
    Moving records between the files is two such writes in a fixed order, and the second starts only after the first has completed step 4:
    • a sweep writes cold, then hot;
    • a thaw writes hot, then cold.
    At every crash point a record is therefore in at least one file. The hot state file keeps its existing write (no fsync) for ordinary changes; only writes that move records use the durable sequence.
  • Test, crash points. Inject a failure after each of the four steps of each of the two writes, for both a sweep and a thaw. The thaw case uses the A, X, Y layout above and continues through a following sweep that re-colds X; the order stays A, X, Y with one X, and the sweep case moves two adjacent records with one hot record between them and a third. After a restart, assert two things: every record is visible exactly once in the merged view, and the merged order equals the pre-operation order.
  • Reads. The cold file is read at startup and whenever its stamp changes.
  • Duplicates take the hot content at the cold position. A session id present in both files is merged as follows:
    • Its content is the hot copy.
    • Its position is the cold entry's position.
    • Its occurrence in the hot file is skipped during the merge.
    The next cold rewrite removes the duplicate. The same rule applies to launch ids.
  • Why the position comes from the cold entry. A duplicate exists only between the two writes of a move, and a crash there must not change the order.
    • Thaw. Take hot A, and cold X and Y, both anchored to A. Thawing X first writes hot A, X. If it crashes before the cold rewrite, the merge emits A, then cold X (with the hot content), then cold Y, and skips the hot X. The order is A, X, Y, unchanged.
    • Sweep. A sweep writes cold entries anchored to the post-sweep hot set before the hot file drops them. A crash between the two writes therefore merges each duplicate at its cold position, which equals its old hot position.

D.2 Eligibility to go cold

A session goes cold when all of these hold at sweep time:

  1. raw_session_is_stopped is true and completion_status is retired or killed. A session stopped without either can still be revived by a tmux client attach (revive_stopped_tmux_client_session) and stays hot.
  2. Its stop time is more than 14 days ago. The stop time is the first parseable of stopped_at, completed_at, last_activity; a record with none of them stays hot.
  3. is_em is not true.
  4. It is not the holder of any agent_registrations entry, and not maintainer_session_id.
  5. Every runtime launch for it has status applied or failed. Any other status keeps it hot, including prepared, launching, Opencode's teardown_pending (the opencode_launch_pending predicate, opencode/session_launch.rs ~901) and any status added later.
  6. It is not a key in handoff_deferred_sessions.
  7. It is not the subject, parent or target of any reparent_requests entry that is not terminal.
  8. No hot session names it in parent_session_id, predecessor_session_id or successor_session_id while that hot session is live.

A session's launch records go cold with it; by rule 5 they are all applied or failed. Launch records whose session id is in neither file stay hot. The fixture for D.5 includes a stopped, retired Opencode session with a teardown_pending launch, which must stay hot.

D.3 Sweep

  • When. Every 24 h from the existing daily handoff-notes pass. The first sweep in a process runs only once both of these hold:
    • Its handover is final: handover::wait_peer_exit has returned for the previous server, or the process started with no peer.
    • It has been serving for at least 1 hour.
    A replacement that rolls back during the restart script's health window has therefore never swept, so the old binary resumes with every session in the one file it understands.
  • Manual rollback to a binary without T3. Add sm-server thaw-cold --config <path>. It refuses to run while a server holds the handover socket. Otherwise it moves every cold record back into the hot file in merged order, by the thaw write order, and deletes the cold file. Document it in docs/product/lessons.md under rollback.
  • Order of steps. Under write_guard:
    1. Compute the eligible set.
    2. Rebuild the cold file instead of appending to it. It holds every record that is cold after this sweep, which means the already-cold records plus the newly eligible ones. Each record appears exactly once, carries the content its merged-view copy has, follows the pre-sweep merged order, and has its anchor recomputed. A duplicate left by a crashed thaw therefore collapses back to one entry in its original position.
    3. Write the hot file without them.
    A crash between the two writes leaves duplicates, which D.1 resolves.
  • Limits. At most 1,000 sessions per sweep, oldest first, so today's data takes three daily sweeps to settle.

D.4 Thaw

A thaw moves a session, and its cold launch records, back into the hot file.

  • Order of writes. Write the hot file with the record, then the cold file without it.
  • Position. Defined by the anchor rule in D.1.
  • Thaw and mutation share one critical section. The helper is thaw_locked(&self, guard: &WriteGuard, select: impl Fn(&Value) -> bool) -> Result<usize>. It requires the caller's held write guard, so it cannot run without one. A writer calls it after taking its guard and before load_raw_json_value. The sweep takes the same guard, so a record cannot go cold between the thaw and the mutation.
  • Which writers thaw. Every function that takes write_guard in sessions.rs, handoff/*.rs, opencode/*.rs and owner_settings/store.rs falls into exactly one of four classes. The implementer lists every site with its class in the PR description:
    1. By id. It thaws the ids it targets, including ids it reaches by following a parent, predecessor or successor link inside its own mutation.
    2. By selector. It finds records by a field other than id: tmux name, parent id, provider resume id or name. It thaws every cold record the selector matches. The exception is a selector that, by D.2, can only match hot records; the PR cites the D.2 rule that guarantees it. revive_stopped_tmux_client_session is the known instance: it matches stopped, non-retired codex-fork records, which rule 1 keeps hot.
    3. Top-level only. It writes no session record, for example registries and settings.
    4. Skips stopped records. It provably never mutates a stopped record, for example account stamping after T1.
  • Whole-store writers. These need cold handling:
    • update_session_metadata's is_em flip needs nothing, because cold records never have is_em.
    • transfer_handoff_json repoints, on every session, each field that names the predecessor. Today those fields are parent_session_id and context_monitor_notify (handoff/transfer.rs ~502–513). It is a class-2 writer.
      • Factor the loop's "does this record name the predecessor in a field I repoint" test into one predicate.
      • Under its guard, thaw every cold record that predicate matches, then run the loop. A field added to the loop later is then covered automatically.
      • The view indexes cold records by each repointed field's value.
    • strip_legacy_handoff_fields and maintain_handoff_notes do not modify cold records; legacy fields on cold records are stripped by the sweep before they go cold.
    • scan_usage_ledger account stamping skips stopped records (T1), so it never touches cold ones.
  • Uniqueness checks see both files. allocate_session_id, generate_unique_runtime_launch_id and generate_unique_spawn_launch_intent_id check both files' ids.
  • Restore. restore_core_session*'s claimed-resume-id and transcript exclusion sets are built from the merged view.

D.5 Equivalence test (the convergence criterion)

  • Setup. Build two stores from one fixture: A with every eligible record hot, B with the same records cold.
  • Operations. For each operation below, run it on both stores and assert three things: equal responses, equal merged views (compared as JSON), and equal queue-database effects.
    • every route in the stopped-session inventory: /sessions?include_stopped=true, /history/agents, /watch/state, children with include_terminated, /nodes/{node}/restore-candidates, by-id GETs;
    • get_session by id, alias and name;
    • restore, retire, kill and PATCH of a cold session;
    • a successor handoff whose predecessor has cold children, plus a cold record that is not a child but has context_monitor_notify set to the predecessor;
    • a tmux client attach naming a stopped, non-retired codex-fork session older than 14 days, which stays hot by D.2 and is revived as before;
    • a sweep concurrent with a by-id write to an eligible record. The write must succeed on the thawed record;
    • work-claims session_directory;
    • worktree cleanup candidates.
  • Known difference. The cold file's bytes differ; that is the point.

Z. FAQ

Why not just delete old sessions? Work claims treat a session missing from the store as retired and purged. They end its claims, delete its stale reservations, and stop collecting its worktrees. History, restore candidates, handoff lineage walks and reply routing all read old records. A cold segment keeps every one of those readers unchanged.

Why not SQLite for sessions now? About 170 write sites follow the "lock, copy whole state, mutate, write" pattern, and several mutate many sessions in one step (handoff repointing, reparent). Converting them is a multi-ticket migration with its own crash-safety design. T2 removes the read-side cost entirely, and T3 cuts the write-side cost about four times. If the targets are met, the migration buys little.

Is skipping stopped targets in the retry loop safe? Yes. Today the same targets reach runtime_session_accepts_background_delivery_raw, which returns false for stopped sessions before doing anything. T1 only moves that check before the lock and the copy.

Why does the board page take 0.4 s when the machine is idle? BoardLinks::load calls publishes(doc_id) and reviews(doc_id) for each of 145 docs. Each call opens message_queue.db and prepares a statement. That is 290 opens per page load, and the web board polls every 30 s per open tab.

Why does every tool call rewrite the state file? apply_claude_pre_tool_use_hook records the tool name and activity time, and the time always changes. Coalescing these writes would change what the activity views show between flushes, so the plan leaves them and makes each write cheaper instead.

Do the separate SessionStore instances cause lost updates today? They can. Each has its own write lock, so two instances in one process can interleave read-modify-write cycles. The instances found mostly read, so I have not seen a lost update. C.1 removes the possibility.
