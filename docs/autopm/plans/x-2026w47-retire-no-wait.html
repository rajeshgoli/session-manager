Auto PM plan — retire an agent without the 10-second wait

Author: Auto PM, Claude Opus 5.5 ba0294dd · Experiment x-2026w47-retire-no-wait · Cycle #2666 · Goal #2170 · 2026-11-16

Memo

When Rajesh retires an agent from the web or Android app, sm should answer at once instead of holding the answer for up to 10 seconds while it cleans up the agent's worktree. Today one retire in five freezes for about 10 seconds: the Retire button stays greyed, no "Retired" toast appears, and the terminal page does not move on to the next agent. Neither app uses what the wait returns. The cleanup itself is unchanged and still runs; only the answer stops waiting for it. It ships behind a switch, so no yes is needed.

Terms. To retire an agent is to end it from its Retire button (web terminal page, agent panel, or the Android app). Retiring triggers worktree cleanup: sm refreshes the agent's open pull requests from GitHub, then removes worktrees nothing would lose. The cleanup wait is the up-to-10-second window in which the server holds its answer for that cleanup (RETIRE_CLEANUP_WAIT, crates/sm-server/src/http/worktrees.rs:25). A switch is an on/off setting sm reads live; off means exactly today's behaviour.

Size, honestly: about 8 minutes of frozen screen over the last four weeks (474 s across 49 slow retires), in 10-second pieces, on the screen Rajesh uses most. It is a small, sure win that costs about 3 Codex points that would otherwise expire.

The change

With the switch on, a retire that comes from Rajesh's web or Android app returns as soon as the agent is retired, and the worktree cleanup runs in the background exactly as it does today after the 10 seconds run out. Retires requested by agents, by the sm command line, or by anything else keep today's wait and today's answer, because their callers may read the cleanup results. Nothing on screen changes except timing: the same "Retired" toast with its 10-second Undo, and the same move to the next agent, arrive about 10 seconds sooner in the slow case. With no new screen, there is nothing to mock.

Undo stays safe, with one fix. Undo restores the agent and rebuilds its worktree if cleanup removed it. Today restore checks whether the worktree exists before taking the cleanup lock (rebuild_worktree, crates/sm-server/src/work_claims/worktrees.rs:1769). An Undo that lands mid-cleanup can therefore find the worktree still there, skip the rebuild, and relaunch the agent while the pass removes the worktree under it. The 10-second wait mostly hides this race today; answering at once would expose it. The build ticket fixes it for every retire, switch on or off: restore takes the cleanup lock before its check and holds it until cleanup can no longer count the agent as retired, and both kinds of cleanup (ordinary worktrees and a document reader's checkout) remove nothing from an agent that is live again (A.2a). An Undo pressed mid-cleanup then waits for the pass and comes back with its worktree. Tests cover both orders.

Appendices

A. Behaviour

A.1 Which retires. A request to POST /sessions/{session_id}/retire qualifies when all hold: switches::is_on("autopm.retire-no-wait"); the payload has no requester_session_id (trimmed, non-empty); and owner_surface (crates/sm-server/src/http/owner_events.rs:53) returns android or web for the request, and owner_events::from_agent is false. These are the same tests that make the activity log record the retire as Rajesh's. Every other request is unchanged. The legacy route retire_session_legacy is unchanged.

A.2 What changes. In retire_session_after_auth (crates/sm-server/src/http.rs), on CoreRetireOutcome::Retired, for a qualifying request: run the BTW teardown as today, start the same cleanup work that worktrees::cleanup_after_retire starts (reader worktree cleanup, refresh_open_prs, run_worktree_cleanup with first = this session), in the same order and on a blocking task, without awaiting it; then answer at once with the retire result plus "worktrees": []. Errors from the background work are logged exactly as today's timeout path logs them. Factor the shared work into one function, so both paths start identical work. Every other outcome (409, 403, not found, not child) is unchanged.

A.2a Restore and cleanup are serialized (unconditional). Restore (restore_session_with_work, crates/sm-server/src/http/auto_retire.rs) takes cleanup_lock before testing whether the worktree exists, and holds it through its existing steps in their existing order: any rebuild, the relaunch, and reopening the claims its retire ended (reopen_retired_claims). A cleanup pass that starts afterwards therefore no longer reads the session as retired (retired_sessions, work_claims/worktrees.rs:429). The lock is a non-reentrant std::sync::Mutex: expose a variant of rebuild_worktree that expects the lock held, and confirm nothing else on the restore path takes it. Reader cleanup joins the same rule: cleanup_reader_worktree (crates/sm-server/src/http/ask.rs:224), which today removes a document reader's detached checkout with no lock, takes cleanup_lock, re-reads the session under it, and removes nothing if the session is live (restored). A stopped or retired reader is removed as today, including the existing removal of a stopped reader before a replacement reader starts (ask.rs:374). A reader whose checkout cleanup already removed before the Undo restores exactly as it does today. This fixes an existing race, so it applies whatever the switch says; its only observable effect is that a restore overlapping a cleanup pass waits for the pass and returns with the worktree present, where today it can return with the worktree removed under the running agent. It has no lasting side effects.

A.3 Off equals today. With the switch off, or for a request outside A.1, the handler awaits cleanup_after_retire with RETIRE_CLEANUP_WAIT and returns its outcomes, byte-identical to main. A.2a is the one change that applies with the switch off.

A.4 Example. Rajesh retires agent a1 from the web terminal page; its open PR refresh takes 14 s on GitHub. Switch off: the answer arrives after 10.0 s with worktrees: [{path, removed: false, reason: "cleanup pending"}], the toast shows, and the page moves to the next agent; cleanup finishes 4 s later. Switch on: the answer arrives in about 0.3 s with worktrees: [], the toast and next agent show at once, and cleanup finishes 14 s later. If he presses Undo at 2 s, the restore waits until the cleanup pass releases its lock, rebuilds the worktree if the pass removed it, reopens the claims, and returns a1 live with its worktree present. An agent running sm to retire its child gets today's answer in both cases.

B. Tests

Through scripts/test-rust-isolated.sh, with the cleanup wait injectable so tests do not sleep 10 s:

  1. Off equals today: switch off, owner web retire with a cleanup stub slower than the wait: the response waits for the wait and equals main's, outcomes included.
  2. On, owner: switch on, owner web retire and Android device retire with the same stub: the response returns before the stub completes, with worktrees: []; the stub's cleanup still completes afterwards and removes the worktree it would remove today.
  3. On, not owner: switch on, retire with requester_session_id, and a loopback request without owner auth: both behave as test 1.
  4. Undo during cleanup, worktree not yet removed: switch on, owner retire; a cleanup stub takes cleanup_lock, has read the session as retired, and pauses with the worktree directory still present; restore starts, then the stub removes the directory and releases the lock. The restore completes after the stub, and the session is live with its worktree present (rebuilt). On main this test fails: restore returns while the directory is later removed.
  5. Undo during reader cleanup: a document-reader session is retired; reader cleanup is held just before its removal with the checkout present; restore starts and completes, then reader cleanup proceeds. The checkout is still present and the reader is live. On main the checkout is removed.
  6. Reader replacement unchanged: a document reader that stopped without being retired is cleaned up and a replacement reader for the same document starts, with the switch on and off.
  7. Restore before a pass: restore completes, then a cleanup pass runs: the pass does not read the session as retired and leaves its worktree in place.

E. FAQ

Why not shorten the wait instead of skipping it? Neither app reads what the wait collects, so any wait is pure delay for Rajesh. Agent and CLI callers keep the full wait.

Why not make cleanup faster? Most of the time goes to the GitHub refresh of open PRs, which is network-bound and protects work from being removed. Speeding it changes what cleanup decides; not waiting for it changes nothing about what it decides.

Why not also fix the slow board loads? Board open and board start also have multi-second tails (p90 4.1 s and 4.6 s), but no fixed timeout explains them. They are a hypothesis for a later cycle, measured separately.
