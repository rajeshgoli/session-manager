Memo · 1. Recommended decision

Approve the V3 layout with explicit launch authorization, separate live indicators, and protected bulk updates. A compact row shows the ticket, its agent, each current wait, and its next-launch settings. One shared editor configures selected tickets. Sol / Medium becomes one complete choice.

A preset is a provider, exact model and reasoning effort chosen together. Effort controls how much reasoning the model is asked to do. A launch preference saves those choices and an optional first message without permission to start. An authorization is the owner's explicit permission for one ticket to start when eligible. The board calls this “Start when ready”; “armed” means that permission exists, not that a job is queued or running.

DecisionRecommendation and reason
What stays visible?Ticket state, agent activity, all current queue/review waits and their ages. These answer different operational questions.
How does a shared edit behave?Preview eligible and excluded tickets; save the reviewed change together. If relevant state changes, save nothing and ask for a fresh preview. This prevents stale edits replacing newer work.
Can a future default launch work?No. A lane default fills configuration for future choices. It never grants permission to start unseen tickets. Explicit selections grant that permission.
Does the mockup define new ticket creation?Keep existing Add lane and bug reporting. Defer the illustrative “New ticket” and “Add ticket” shortcuts; a general issue-creation workflow is outside this layout change.

The material authorization-policy departure from the mockup is its “Start new tickets when ready” lane-default switch. This plan excludes that standing authorization. The alternative grants permission to tickets that do not exist yet and needs a separate policy decision.

3. One choice sets the complete launch

Pin Sol / Medium as Codex, gpt-6-sol, medium. Pin Claude defaults beside it; show the currently saved Claude model and effort, including “provider default” when unset. The chips show full model identifiers as well as friendly labels. A model name must not shorten to an ambiguous “Gpt”.

1. Select tickets
Choose rows or visible rows in a lane.
2. Shared setup
Choose a preset, launch behavior and first message once.
3. Review and save
See effective choices, exclusions and exceptions for every ticket.

The shared editor has three independently explicit choices: configuration, first message and launch behavior. Each starts at “Keep each ticket's current choice.” A common value replaces only the chosen field. A ticket exception takes precedence over the common value and stays marked in the preview.

For launch behavior, choose Keep current, Manual, or Start when ready. Manual cancels existing permission to auto-start; it cannot stop an agent that has already started. Start when ready explicitly grants or renews permission and resets failed attempts. Keep current never retries a failed launch.

For the first message, choose Keep current, Use ticket default, or Custom text. Custom text is the exact same text for every selected ticket unless it has an exception. It is not a template engine. The normal ticket default still renders the ticket's identity at launch time. Preview each ticket's default separately.

Example: select eight rows. Two are held, one is a lane goal and one has a merged-but-open warning. The editor says “8 selected · 4 eligible · 4 excluded” and lists each reason. Choose Sol / Medium once, Start when ready once, and one message. Give one eligible ticket a Claude exception. The confirmation shows three Sol launches and one Claude launch, with ready and dependency-blocked counts.

For a single ready ticket, Start opens the same flat configuration fields. One click on Sol / Medium replaces the provider/model/effort sequence; the final Start click submits it. From the board that is at most three clicks: Start, Sol / Medium, Start. No expansion panel is required to see model, effort or first message.

A preset click only edits a form. “Save preferences” saves configuration without starting work. “Authorize N tickets” submits Start when ready. The button describes the strongest action in a mixed selection; its preview lists cancellations and renewed failed authorizations too.

4. Defaults and existing work have different scope

A future lane default is the configuration suggested for tickets first seen anywhere on the board after the default is saved, when they initially belong to that lane. It includes provider, model, effort and first-message choice. It does not include Start when ready. Existing tickets retain their captured choice; changing defaults does not rewrite them.

ActionAffectsDoes not affect
Apply to selectionThe previewed eligible ticket identities, with exceptionsExcluded rows, unseen tickets, lane defaults, live agents
Save future lane defaultTickets new to the entire board after saving, initially in that laneExisting preferences, existing authorizations, lane order
Change provider defaultsThe existing Settings → New agents behaviorPreviously captured explicit configurations
Edit a review policyThe next review request at its existing scopeThe implementation agent's preset or a running review

Resolution means choosing the effective settings when several sources exist. For an unconfigured ticket, preserve the existing recognized Tier choice (a named agent type written on the ticket) first, then its captured lane default, then the last recognized agent type used, then global provider defaults. Once the owner saves a ticket preference, that explicit choice wins. An existing waiting or failed auto-start authorization always displays its own stored choice until explicitly edited. Saving preferences on an armed ticket updates its future launch configuration, while preserving its current permission and attempt count.

If a new ticket appears in multiple lanes at once, capture the default from the highest-priority lane that has one. Show the source lane. A ticket already seen in lane A never captures lane B's default when later added to B, even if it has no saved preference. Later rank changes also preserve its choice. If no lane has a default, the existing source order still applies.

After installation, existing tickets are marked as already seen before any future lane defaults are applied. There is no automatic conversion into armed tickets and no rewrite of running sessions. Existing agent types remain available; the two quick presets do not rename or replace them.

A preview protects against concurrent change. For example, if another tab cancels #1907 while this editor is open, Save must not re-arm it using stale data. If an agent claims it, the server rejects the stale selection before saving any selected item. The user sees which rows changed and explicitly accepts a new preview.

No bulk operation writes to an agent record. A launch preference and an authorization belong to the ticket's next launch. Existing agent controls remain separate.

5. Launch rules stay recognizable

Close-ready means the server has found a container ticket whose parts are complete and which can be closed. The standing Bugs goal is an exception: it stays available as a collection point and offers neither Start nor Close.

Goals are excluded from bulk setup even when they would individually be ready. This preserves the existing lane-selection rule; it does not remove an ordinary goal's conditional single-ticket Start.

Auto-start shows distinct waiting, globally paused and failed states. Pausing does not erase permission. The existing worker tries a launch at most three times, then waits for an explicit retry. Retry shows the saved model and effort, and a renamed agent type cannot silently change them. Cancel removes permission; a historical cancelled record is not displayed as armed.

Readiness is checked again at launch, including claim reservation. Two tabs or a manual start racing an automatic start produce at most one agent. Cancel and Pause wait for an already-entered launch to finish, as today; they prevent subsequent launches and do not promise to reverse one already underway.

The server records early starts and adds the unmet-dependency explanation to the first message. The redesign keeps that behavior, owner authorization and the standing Bugs exception.

D. Saved preferences and future defaults

Persisted records live in the board's SQLite database, where claims and auto_starts can be checked transactionally. Version the new record format at 1 within the existing forward-only schema migration scheme. The externally observable shapes are:

LaunchConfig = {
  provider: "claude" | "codex-fork",
  model: string | null,
  reasoning_effort: string | null,
  brief: string | null
}
TicketPreference = {
  repo, number, config: LaunchConfig, revision: integer,
  source: "ticket" | "lane", source_lane_id: integer | null
}
LaneDefault = { lane_id, config: LaunchConfig, revision: integer }
FirstSeen = { repo, number } // unique globally across board appearances

All configuration fields are required in stored records. Null model/effort means provider runtime default, not a pointer to mutable Settings. Null brief means render the current ticket default at launch; a nonempty brief is literal text. Whitespace-only custom text is rejected; the user chooses Use ticket default instead. Preserve nonblank text byte-for-byte. Existing template placeholder validation remains in Settings. There is no reviewer, workspace, agent name or authorization bit in LaunchConfig.

Create the new tables without changing the existing database schema version backwards. Before enabling default writes, initialize FirstSeen for all current board facts in one transaction; record completion so this initialization is never repeated. On first discovery, use recognized ticket Tier before a lane default. Capture a lane default only if no recognized Tier supplies configuration; select the lowest rank, then lowest lane id among containing lanes with defaults. Capture concrete provider defaults when choosing Claude defaults or global settings; an explicit null remains provider default. Do not backfill a later-created lane default onto FirstSeen tickets. Old rows outside the board receive FirstSeen when first observed; this is discovery time, not GitHub issue creation time. Once FirstSeen exists, adding or moving the ticket to any lane never captures another lane default, including when no preference was captured originally. Leaving and rejoining the board does not delete FirstSeen. State this in the default editor.

Without stored preference/authorization, resolve configuration in this order: recognized Tier; last recognized agent type supplied by the browser's existing LAST_TYPE_KEY; current global provider defaults. The captured lane record, when present, is already a stored preference. Only waiting/failed authorization is the authoritative editable configuration over every preference. Cancelled/started rows are history and do not override preferences. Saving config-only on an authorized ticket updates that authorization's fields but preserves state, attempts and error; it does not re-arm, retry or clear pause. Save the same effective config as its ticket preference. A later explicit Start uses the saved preference as form prefill, while still requiring confirmation.

Preset IDs sol-medium and claude-defaults are stable built-ins, not agent_type names. Sol is the exact triple specified in the memo. Claude resolves Settings at preview. Named agent types retain exact-match validation. A removed/edited type displays Custom while preserving the stored triple; do not silently substitute the new named value. Manage links to existing agent-type/provider settings; custom user-pinned preset CRUD is not added in this change.

Owner endpoints: GET /client/board/launch-default?lane_id=N returns default or null plus revision; PUT takes {lane_id, expected_revision, config}, with config null clearing the default. Missing expected_revision is 400; changed revision is 409, no write. The UI explicitly labels “New to the board and initially in this lane only; does not authorize starts”. No default editor writes a ticket preference or auto_starts row.

E. Selection preview and commit contract

Add owner-authenticated POST /client/board/launch-preview and PUT /client/board/launch-selection. Include both in existing browser owner read/write route tests. Do not grant partner-agent write authority to these new bulk/default endpoints; preserve the existing single-ticket auto-start guard unchanged. Maximum selection is 100 distinct ticket keys, matching per-ticket exceptions only; duplicate keys or exceptions outside selection are 400. No selection means 400. Custom messages are at most 32,000 UTF-8 bytes. Validate provider/effort with current settings validators.

Exception fields replace common fields only when present. Never merge a half-config that retains another provider's model. The token binds the complete resolved intent and the full selected key set, including excluded items; it expires after five minutes. The client does not get to submit a different plan with that token. Token signing/storage is private implementation detail. Response entries use canonical repository identity, sorted repo then number. Preview never authorizes or writes preferences.

Eligibility requires an open board ticket in Ready or Blocked, no holder/reservation, no goal membership in any active lane, no open associated PR, and none of stale/cycle/merged_not_closed warnings. Report every applicable exclusion using stable reason codes not_on_board, closed, lane_goal, held, open_pr, state, stale, cycle, merged_not_closed plus human text. Include done/needs_you/in_progress/close_ready/standing state as detail. Dependency blocking alone is eligible. Single-ticket cancel/retry/edit remain available through the existing surface even if bulk excludes the row.

Acquire the existing auto-start launch lock before the board lock, then use an immediate SQLite transaction that reads current claims/reservations, preferences, authorization records and defaults and commits all selected writes. Check affected configuration/default/settings revisions and the relevant board facts against preview before writing. Relevant facts include existence/open state, holder, associated open PRs, warnings, dependencies, goal membership and auto-start state/attempts/choice. Clock age changes, unrelated board activity and elapsed time alone do not invalidate a preview. Read claims within the write transaction rather than trusting a projection made before it: ordinary claim writes do not all hold board_lock today.

If any relevant selected fact or resolved value differs, return 409 with code:"selection_changed" and per-key reasons, commit nothing and issue no recompute. The browser retains the draft and shows a new preview only on request; it never retries authorization automatically. Expired tokens return 409 preview_expired. Malformed bodies return 400; unavailable preview tokens return 409 preview_expired. Authentication failures use existing 401/403 behavior. All excluded rows remain unchanged. A selection with zero eligible rows is previewable, but commit returns 409 no_eligible_tickets.

For each eligible ticket, apply effective config/message. Behavior keep preserves absent/waiting/failed/cancelled/started permission state and attempts; manual cancels waiting/failed only; when_ready writes fresh waiting authorization with zero attempts and no last_error/session_id. Explicit when_ready can renew failed authorization and is labeled accordingly. No operation edits an existing session, claim, PR, ticket body, review policy, queue job or lane rank. A committed preference change requests recomputation; configuration-only saves do not create permission to launch.

Use monotonically increasing revisions for every authorization mutation, including cancel, failure, success, retry and legacy single/lane writes. This prevents cancel-and-rearm to identical values evading stale detection. In the same database transaction, persist request_id plus token identity and response. Retain these completion records for seven days. Duplicate request_id with the same token returns the stored response even if its preview expired; a different token returns 409. After seven days an old expired token cannot execute anew. After a timeout the browser retries the same request_id/token; it does not create another authorization. Restart tests verify this behavior.

Launch serialization retains process_auto_starts' per-record recheck and claim-time reservation. Include the authorization revision in that recheck so a cancelled then re-created equal-valued record cannot reuse an old launch plan. Settings pause keeps its existing lock. Bulk transaction either precedes a claim (claim cancels/wins at subsequent launch check) or observes it and refuses; it cannot overwrite an already active holder.

Z. Implementation FAQ

Why not reuse the lane PUT repeatedly? It has lane-local all-or-nothing writes but no cross-selection stale-preview contract. Sequential cancellation followed by authorization can partially apply and start work during a later request. The new transaction commits the complete reviewed selection.

Why reject stale/cycle rows in bulk while retaining individual authorization? The existing single-ticket form permits saving an authorization that still cannot execute until readiness returns. The V3 bulk design explicitly excludes unsafe current inputs. Keeping both preserves individual functionality and prevents broad authorization from an unreliable selection.

Does configuration-only editing retry failures? No. It preserves failed state and attempts. Only explicit Retry or Start when ready renews permission. Config-only editing of a waiting authorization can affect a future launch; the preview therefore explicitly says “updates existing authorization” and displays pause state.

Is “Keep current” a hidden write? An all-keep row causes no preference/authorization mutation and no revision bump. It is still counted as eligible in preview but response preferences_count counts changed preference rows only. Excluded rows never write. A fully all-keep selection returns a zero-change success, without recomputation.

Does the new design show every historical job/review? Current jobs and waits remain visible. Historical time and completed work stay in existing details/history surfaces; this work does not introduce a new archive.
