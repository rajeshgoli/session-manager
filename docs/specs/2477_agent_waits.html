2477 — Let an agent record that it waits on another agent

Author: Claude Opus 5.5 eed12fd4 · Ticket #2477 · 21 Oct 2026

Memo

I recommend one new command, sm await. An agent runs it to say "I am blocked until that agent (or that ticket) delivers this, and I expect it by this time." While the wait is open, sm counts the agent as waiting, exactly as it already does when the agent waits on a queue job or a PR review. The idle reminder stops, and the agent list shows Waiting for far-2171 · final weights · 3h. The wait ends by itself when the awaited agent messages the waiter, the awaited ticket closes, the awaited agent retires, or the expected time passes. In the last three cases sm wakes the waiter with one message that says which. Nothing else in sm changes meaning.

Seat
One agent session that sm manages, e.g. far-2139.
Claim
sm's record that a seat owns a ticket or PR, made by sm ticket or sm pr.
Idle reminder
The message [sm claim] Idle 33m, nothing pending. You hold: ticket #2139 (open). sm sends it to a seat that has been idle for 30 minutes, holds an open claim, and is waiting on nothing. It repeats after each further 30 idle minutes that follow activity.
Waiting-on list
sm's per-seat list of things the seat is blocked on: its queue jobs, its PR reviews, and its docs that wait for your review. A non-empty list is the only thing that stops the idle reminder today, and it is what turns the seat amber ("waiting") on the web and phone agent lists.
Agent wait (new)
An entry in the waiting-on list that says "this seat waits on that seat or that ticket for a named deliverable, until a stated time." Created by sm await.
ETA
The time by which the waiter expects the deliverable. Every agent wait has one.

The problem

Seat far-2139 holds #2139. Its next step needs the final model weights from #2171, which another seat is training on the GPU overnight. That seat promised to message far-2139 with the file hashes around Thursday 05:00 UTC. Until then far-2139 has nothing to do. sm sees an idle seat with an open claim and an empty waiting-on list, so every 30 minutes of quiet it sends "nothing pending." Each reply makes the seat active again, which re-arms the next reminder. The seat burns tokens on a false signal, and the agent list shows it as idle when it is in fact blocked.

None of today's tools can say "blocked on that agent":

ToolWhy it does not cover this
sm board after 2139 2171Records that one ticket starts after another. It says nothing about a seat being blocked right now, and #2171 closing wakes nobody. It was already recorded in this case.
sm status "Waiting for …"Free text for you to read. sm does not interpret it.
sm wait <seat> <seconds>Holds the shell open until the other seat goes idle. Idle is not delivered: a training seat goes idle many times before the weights exist. It also blocks for at most the seconds given.
Dummy queue jobWorks, but it is a lie in the queue and holds a slot.

How it works

A wait names either a seat or a ticket. Wait on a seat when a specific agent promised you something (the 2139 case). Wait on a ticket when you need it finished but do not care which agent finishes it; then a message from any seat that holds the ticket counts as delivery, and the ticket closing ends the wait too.

A wait may also name a queue job, as queue:<job id> or the bare job_… id: it must be pending or running when the wait opens, and it ends (job_ended) at the first claim sync pass after the job ends or leaves the queue, with [sm await] Queue job <label> (<id>) <state>. Your wait on it for "<for>" ended. to every waiter except the session the queue already woke with the result (its notify target, else its requester). Or it may name work outside sm as <kind>:<id>, at most 100 characters with no spaces (modal:ap-12, gh-run:4567, cron:3fa9); sm cannot see that work, so only the ETA, sm await --cancel <kind>:<id> or the waiter's retire ends it (sm#2611). Neither kind is ever delivered by a message, and neither has an awaited_by. A target with a colon is never read as a seat.

I made two smaller calls myself. The command is sm await because sm wait already means the blocking shell poll and I do not want to change its meaning. The board shows a holder's open wait in place of Idle or Stalled on its ticket (sm#2611; rule 5a of the ticket clock in 1710_web_redesign.html), and the idle reminder ends with the sm await command.

Appendices

A. Command line

sm await <target> --for "<deliverable>" --until <eta>   # open or update a wait
sm await                                                  # list my waits and waits on me
sm await --cancel [<target>]                              # end one wait, or all of mine
  • Caller. Requires CLAUDE_SESSION_MANAGER_ID; the caller is the waiter. Outside a managed session: exit 1, sm await must run inside a managed session (CLAUDE_SESSION_MANAGER_ID).
  • <target>. #N or owner/repo#N is a ticket target; the bare #N form resolves the repo the same way sm ticket N does from the caller's working directory. Anything else is a seat, resolved exactly like an sm send recipient (full id, id prefix, or friendly name). Errors (HTTP 400, CLI prints the detail and exits 1): Session <target> not found; Session <target> is retired; you cannot wait on yourself; ticket number must be a positive integer; and, for a bare #N that reaches the server unqualified, a ticket target needs its repo: owner/repo#N. A --for or --until without a target, or a target without both, is refused by the CLI before any request.
  • --for. Required. 1–200 characters after trimming, no newline; otherwise 400 for must be one line of 1 to 200 characters.
  • --until. Required. Either a duration in the sm queue run syntax (45m, 6h, 2d), measured from now, or an RFC 3339 timestamp. Must be later than now and no later than now + 72 h; otherwise 400 until must be in the future and within 72h.
  • Re-running with the same waiter and target replaces for and until and keeps the original created_at (the age shown on the agent list counts from the first registration). Output line starts Updated wait on … instead of Waiting on ….
  • Output on open: Waiting on <name> (<id8>) for "<for>" until <Ddd DD Mon HH:MM UTC>. For a ticket: Waiting on #N "<title>" for … until …., with "<title>" left out while the title is unknown. A seat with no name shows its short id alone.
  • List output: two sections, Waiting on: and Awaited by: (each left out when empty), one line per open wait: far-2171 (4c1d2e3f) · "hashes" · until Thu 22 Oct 05:30 UTC · 3h (target, or waiter under Awaited by; age since the wait opened, as 12m, 3h or 2d). Nothing open: No open waits.
  • --cancel with a target ends that wait and prints Cancelled wait on <target>. (404 / exit 1 no open wait on <target> if none; a retired seat may be named); without a target it ends all the caller's open waits and prints Cancelled N waits. (Cancelled 1 wait.).

B. Stored record

A new table in the work-claims database (the one holding work_claims), created by WorkClaimStore::ensure_schema.1

CREATE TABLE IF NOT EXISTS agent_waits (
    id                TEXT PRIMARY KEY,     -- "wait_" + 12 lowercase hex
    waiter_session_id TEXT NOT NULL,
    target_kind       TEXT NOT NULL CHECK (target_kind IN ('seat','ticket','job','external')),
    target_session_id TEXT,                 -- seat waits only
    repo              TEXT,                 -- ticket waits only, canonical slug
    number            INTEGER,              -- ticket waits only
    target_ref        TEXT,                 -- job id, or the outside reference (sm#2611; a table from before it is rebuilt once)
    deliverable       TEXT NOT NULL,
    created_at        TEXT NOT NULL,        -- RFC 3339 UTC
    updated_at        TEXT NOT NULL,
    until_at          TEXT NOT NULL,
    ended_at          TEXT,
    end_reason        TEXT CHECK (end_reason IN
        ('delivered','ticket_closed','target_retired','job_ended','expired','cancelled','waiter_retired')),
    end_message_id    TEXT                  -- queue message sm sent at the end, if any
);
CREATE UNIQUE INDEX IF NOT EXISTS agent_waits_open ON agent_waits
    (waiter_session_id, target_kind, IFNULL(target_session_id,''), IFNULL(repo,''), IFNULL(number,0), IFNULL(target_ref,''))
    WHERE ended_at IS NULL;

A ticket wait inserts an unsynced work_items row for the ticket if none exists, and the tracked set2 gains SELECT repo, number FROM agent_waits WHERE ended_at IS NULL AND target_kind = 'ticket', so the claim sync fetches the ticket every pass while the wait is open. Every change writes an event in the existing events table: wait.opened, wait.updated, wait.ended (payload: wait id, target, deliverable, until, and for wait.ended the reason and message id), on the waiter's session and, for ticket waits, the ticket.

  • The claim sync pass runs every work_claims.sync_interval_seconds (default 300, minimum 60), so the three sync-time endings land within one interval. The wait step runs before Check C (the idle reminder) in run_sync_pass, so a wait that ends in a pass is no longer in the waiting-on list when that pass decides on reminders.
  • A ticket counts as answered when GitHub answered for it in this pass or its cached state is already closed, since the sync never re-polls a closed item.
  • If several triggers hold in one pass, the reason is the first in this order: waiter_retired, ticket_closed, target_retired, expired. One wait produces at most one message.
  • A stopped (not retired) waiter keeps its waits; a stopped target seat does not end a wait.
  • Restoring a retired seat, including the retire-then-successor path of an Auto PM handoff, reopens the waits its retire ended (waiter_retired at or after the retire), as it reopens claims; a reopened wait past its ETA ends as expired at the next sync pass.
  • Ending a wait and enqueueing its message happen in one transaction on the work-claims database, as the existing checks do with enqueue_important_in_conn.
  • After a wait ends, the idle reminder's normal re-arm rule applies unchanged: the end message makes the seat active, so a reminder comes at the earliest 30 idle minutes later.

D. Waiting-on list and agent views

The session feed (session_obligations)4 adds one waiting_on entry per open wait, on the waiter:

{"kind": "agent_wait", "id": "wait_3f9a2c1d0b7e",
 "label": "far-2171 · #2171 end.pt and fitted.pkl hashes",
 "state": "waiting", "since": "2026-10-21T22:10:04Z", "until": "2026-10-22T05:30:00Z",
 "target_kind": "seat", "target_session_id": "4c1d2e3f", "target_name": "far-2171",
 "repo": null, "number": null, "title": null, "until_text": "Thu 22 Oct 05:30 UTC",
 "waiter_session_id": "7e317fcd", "waiter_name": "far-2139", "for": "#2171 end.pt and fitted.pkl hashes"}

The label is <target> · <for>; the target is the seat's friendly name (else its 8-character id) or #N. Because the entry is in waiting_on, three things follow with no further code: Check C skips the seat (IdleSession.waiting), watch_view shows an idle waiter as waiting, and waiting_since includes it. The target seat's feed entry (for ticket waits: every seat with an active claim on the ticket) gains the same view in "awaited_by". Every feed entry carries awaited_by, empty when none. A retired waiter's waits are left out of the feed until the next sync pass ends them. The browser watch page and sm watch show each as Awaited by far-2139 · <for> · until <ETA>; the phone app ignores the field.

Clients that count waits by kind add agent_wait → "agent wait(s)": sm watch (obligation_context) and the Android waitingSummary list. The browser watch page and single-wait rendering everywhere already use the label and need no change.

The agents list on the web and the phone takes its section from http/watch.rs (agent_facts). An open wait puts the seat in Waiting, ordered by the wait's since, and the seat is never flagged stalled while it lasts. When no queue job, review or queue delivery is shown, the jobs line reads Waiting · far-2171-h3 · #2171 hashes · until Thu 22 Oct 07:01 UTC in amber; otherwise it appends · <label>. A wait older than web_watch.waiting_long_minutes stays in Waiting, not Waiting long: the agent stated an ETA, and the ETA-expiry message covers lateness.

F. Task-complete listing

At sm task-complete of a seat that open waits target (directly, or through a ticket it claims), sm sends that seat, in addition to any Check B message:

Several waiters are joined with ; in one message. The waits stay open. The added AGENTS.md bullet (decision 5) is the only policy text; sm messages state facts.

Z. FAQ

Does this extend the claim lifecycle? It extends the claim machinery, not the claim record. The wait lives in the claims database, is checked by the claim sync pass, writes to the claims event log, and its messages travel the same way as [sm claim] messages. It is not a new state of a claim because the idle reminder decides per seat, a seat can hold several claims, and a seat can wait on another agent while holding no claim at all.

How is this different from sm board waiting? That command marks a ticket as waiting on you, outside sm. An agent wait is a seat waiting on another seat or ticket. They do not interact.

Why not end the wait when the target goes idle, like sm wait? A seat goes idle many times before it delivers; idle says nothing about the deliverable.

What if a seat is replaced (handoff)? Open waits follow the work, as claims do: a successor keeps its predecessor's waits, and a wait on the predecessor becomes a wait on the successor, so the successor's sm send delivers it. A seat that retires without a successor ends the waits on it with a message.

Why 72 hours? Long GPU jobs here run overnight to two days. Three days covers that with margin while still forcing a look within a working stretch.
