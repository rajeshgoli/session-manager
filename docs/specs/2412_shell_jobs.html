2412 — Adopt heavy agent commands into the queue instead of killing them

Author: sm-2412 cbf8008e · Ticket #2412 · 2026-10-19

Memo

I recommend that sm stop killing an agent's command the moment it passes 1 GB. Instead, sm adopts the command into the queue as a running shell job. sm sets memory aside for it and stops it only if the Mac actually runs short of memory. The process-tree watch that makes this possible also shows, for every provider, what an idle agent has left running in the background.

Today's rule costs more than it saves. The guard killed 121 agent commands in the last 10 days, about 12 a day. Most were rustc or pytest at 1.1–2.3 GB, and the largest was 17 GB. Over the last 7 days the Mac had at least 100 GB free 95% of the time, and less than 20 GB free 0.04% of the time. Each kill costs an agent a wake, a re-read of the notice, and a resubmit. It protects against a risk that the host memory guard, which already stops queue jobs when memory runs short, handles better.

Queue job
Work submitted with sm queue run. sm starts it when its type has a free slot and the Mac has the memory, and wakes the agent when it ends.
Shell job (new)
A command an agent started from its own shell that sm took over as a queue job after it passed 1 GB. It is already running, so it never waits and takes no slot. It shows in the Queue screen and in sm queue list with type shell.
Reservation
The memory sm sets aside for a shell job when it adopts it: 16 GB or 8 GB (decision 2). It decides which job stops first when memory runs short. It is not a tripwire.
Memory reserve
Existing rule: sm keeps at least 8 GB free, rising to a quarter of the Mac's memory (64 GB) while macOS reports memory pressure. The host memory guard stops queue jobs one at a time, largest first, while free memory is below the reserve.
Headroom
Free memory, minus the memory reserve, minus what running queue jobs are expected to need beyond what they use now. A shell job is expected to need its reservation. Any other job's --memory is a ceiling, not an expectation: a job under ten minutes old is expected to reach it, and after that the expectation is the larger of its peak so far and its use projected 15 minutes ahead on its last 15 minutes' trend, never above the ceiling.
Background job (new)
A command an agent left running after its turn ended, such as a watcher (until grep -q Ready dev.log) or a dev server. sm reads it from the agent's process tree.

Works the same for Claude, Codex and local agents

I started a Codex agent and a local agent, had each run sleep 180, and read their process trees. All three providers run a command as a child process of the agent program, so one rule covers them: the command is the child of the agent program, together with everything under it. They differ in what wraps the command and in what else the agent program keeps running. The table shows those differences.

The table forces two fixes. First, sm must watch every window of a session. Today it maps each session to one pane, so it sees a local agent's commands only by accident of listing order. Second, the agent's own helpers must never be shown as background jobs. sm ignores children that started within 10 seconds of the agent program, which covers MCP servers and startup helpers, plus a built-in list of known helpers: the Codex three above and caffeinate. The 1 GB adoption still applies to helpers. A helper that large should be visible.

Commands an agent detaches

You asked whether sm can see a command that an agent starts with nohup … &, after the shell that started it has exited. Yes, through the process group. When the shell exits, macOS hands the command to the system's root process (PID 1) and forgets its parent. macOS also hides another process's environment from sm, so the agent's id there cannot be read. What survives is the process group, a number every process carries and inherits. Each command an agent starts gets a group named after the shell that ran it, and a detached command keeps that group.

I checked this on my own session: ( nohup sleep 306 & ) left sleep with parent 1 and group 34017, the PID of the shell Claude had started for the command, which had already exited.

So sm records the group of every command it sees under an agent, with the agent's id. A process whose parent is 1 and whose group is on that record belongs to the agent: sm adopts it at 1 GB and shows it as a background job, like any other. The shell behind a detached command lives only milliseconds, too short for a 2-second sample. sm therefore also asks macOS to notify it each time an agent program starts a process (a kernel fork event) and records the group at that instant. In the test above the notice arrived while shell 34017 was still alive.

What stays out of reach: a command that deliberately leaves its group (setsid, or a daemonizer that forks twice and starts a new group). That is rare in agent work, and sm does not attempt it.

Risks

  • A runaway shell job grows faster than the guard can act. The 2026-10-08 incident climbed 260 GB in six minutes. The host memory guard checks every second and stops the job that is over its reservation first, so a runaway goes before anything well-behaved. That is the same protection queued jobs have today.
  • A command that calls setsid or a daemonizer moves to a new process group and cannot be traced back to its agent (see "Commands an agent detaches"). That is rare in agent work. A plain nohup … & is traced.
  • A server restart while shell jobs run. sm records each job's process identity. After a restart it keeps jobs whose process is still the same one and ends the rest.

FAQ — what changed since the last revision

Reservation sizes. They are now 16 GB and 8 GB, sized from last week's queue readings, where the first revision used 10 GB and 5 GB. You asked for numbers from data.

Detached commands. A command an agent detaches with nohup … & is now traced to its agent, adopted at 1 GB and shown as a background job. The first revision called this out of reach. A. Adoption

The agent memory guard (crates/sm-server/src/agent_memory_guard.rs) keeps its 2-second pass, its trigger (queue_runner.memory.agent_process_max_bytes, 1 GiB), its harness and exempt lists, and its tree walk from each live session's tmux pane. What changes is the response to a victim.

  1. Panes. live_agent_panes returns every pane of each session's tmux session (list-panes -a -F '#{session_name} #{pane_pid}', keeping all pids per name rather than the last). A local agent therefore contributes both its agent window (launch-attach.sh → opencode attach) and its serve window (launch-serve.sh → owner → supervisor → opencode serve).
  2. Command root. For an over-limit process P in a pane's tree, the root R is the ancestor of P (or P itself) whose parent is a harness process (basename claude, codex, codex-fork or opencode, wherever it sits in the tree) or, if there is no harness above P, the pane process. Examples, all observed live on 2026-10-19:
    • Claude: claude → zsh -c …eval 'cargo test' → cargo → rustc, where rustc passes 1 GiB, gives R = the zsh.
    • Codex: codex-fork → cargo → rustc gives R = cargo. Codex runs single commands without a wrapper shell.
    • Local agent: … supervisor → opencode serve → pytest gives R = pytest. opencode attach in the other window is also a harness, but no commands run under it.
    The job covers R and every descendant. The harness's own children that are helpers (E) are still roots for adoption, so a 1 GiB helper becomes a visible shell job and is not killed silently.
  3. Detached commands. The guard keeps a group record: process group → (session id, root PID, root identity). It is filled from three sources:
    • every command root whose process group equals its own PID, seen in a pass;
    • on macOS, a kqueue EVFILT_PROC watch with NOTE_FORK | NOTE_EXIT on every harness process found in a pane walk. On each NOTE_FORK the guard lists that harness's children (proc_listchildpids) and records each new child's group. On NOTE_EXIT it drops the watch. Watches run on one dedicated thread, which adds watches for harnesses the pass reports.
    • on Linux, which has no fork notice, the 2-second pass only, plus CLAUDE_SESSION_MANAGER_ID read from /proc/<pid>/environ of any process whose parent is 1.
    An entry is dropped when no listed process carries its group. In each pass, a process whose parent is PID 1 and whose group is on the record is a command root for that session: the walk treats it like a harness child for adoption (steps 4–7) and for background jobs (E), its descendants included. Example, observed 2026-10-19: ( nohup sleep 306 & ) gave sleep PID 34026, parent 1, group 34017, and the fork notice on claude listed 34017 before it exited. Not covered: a process that calls setsid or setpgid into a new group.
  4. Already adopted. If R's PID and process identity match a running shell job, nothing happens. The guard never adopts or kills inside an adopted tree.
  5. Headroom. available − effective_memory_reserve_bytes(memory_min_free_bytes) − Σ max(0, expected_bytes − current_bytes), summed over running queue jobs that have memory_bytes. available comes from host_memory_capacity(), and current_bytes is the job's latest sampled memory (0 if unknown). For a shell job expected_bytes is its reservation. For any other job (sm#2490) it is shell::expected_bytes: memory_bytes while the job is under 10 minutes old (since started_at) or has no running sample in the utilization database; otherwise min(memory_bytes, max(peak, current_bytes, current_bytes + max(0, slope) × 15 min)), where peak is the job's largest running COALESCE(footprint_bytes, rss_bytes) in job_samples and slope the least-squares slope of those readings over the last 15 minutes. The guard reads this history only on a pass where a command passes the limit. Tests: queue/shell/tests.rs (a_declared_ceiling_counts_in_full_until_the_job_has_history, a_flat_job_is_expected_at_its_peak_not_its_ceiling, a_growing_job_is_expected_where_its_trend_reaches_capped_at_its_ceiling). If host memory cannot be read, the guard does not adopt and stops the command as today.
  6. Reservation. Headroom ≥ 100 GiB gives 16 GiB. Headroom ≥ 20 GiB gives 8 GiB. Anything lower gives no adoption: the guard stops R's tree, records the kill in agent_process_kills as today, and sends the no-headroom form of the stop message. The constants are SHELL_JOB_RESERVATION_TIERS = [(100 GiB, 16 GiB), (20 GiB, 8 GiB)].
    Worked example: 256 GiB Mac, 140 GiB available, reserve 8 GiB, one perf job under ten minutes old with --memory 40G, using 15 GiB. Headroom = 140 − 8 − 25 = 107 GiB, so the reservation is 16 GiB. A second adoption a moment later counts this job's 16 GiB as unused (it uses about 1 GiB), so it sees 92 GiB and reserves 8 GiB.
  7. Label. The label comes from R's arguments. For zsh|bash|sh -c <script> where the script contains eval '<cmd>' (Claude's wrapper), the label is cmd with '\'' unescaped. For -c or -lc <cmd> (Codex, opencode), it is cmd. Otherwise it is R's full arguments. Trailing < /dev/null and && pwd -P >| … are dropped. Whitespace is collapsed and the label is cut to 120 characters with "…". The full text goes in argv as a single element.

C. Running, ending, stopping

  • Tracking. On each 2-second pass, the guard checks every running shell job. When no listed process carries its group, the job finishes, exit code NULL: memory_exceeded if the host guard marked it memory_terminating, cancelled if a cancel marked it cancelling, otherwise ended with no message. At server start, queue recovery keeps a shell row only while its group exists and its root PID still carries the recorded root_identity (a group number can be reused once the command ends); it finishes one adopted before the last boot as host_restart, and finishes the rest; a kept row still marked cancelling or memory_terminating has its group signalled again (SIGTERM, then SIGKILL after the cancel grace), because no other path resumes a stop the restart interrupted; it never probes a wrapper or exit receipt for them.
  • Usage. The guard sums footprint over R's subtree each pass and stores the latest value and the peak in memory, keyed by job id. The latest value is what current_bytes in A means. /client/queue reads this as the job's usage.memory_bytes, and the utilization recorder samples it like other running jobs.
  • Stopping. Any stop (host memory guard, owner Stop or sm queue cancel) uses the queue's existing stop for the job's process group: SIGTERM to the group and to descendants that left it, then SIGKILL after the stop grace. The group is the command's own, never the harness's, so nothing else is signalled. The stop message (Figure 4) goes through the message queue with category queue-completion, so it waits for the agent to be idle.
  • Stop message. It names the stop time in UTC, the command, its PID, and when the agent started it. A cancel note is appended. Then one cause sentence (host pressure with free and reserve figures, owner Stop, agent's own cancel, or no headroom at adoption). Then the resubmit line: sm queue run --type <type> --label <slug> --memory <ceil(1.5 × peak) GB> -- <label command>. A command with shell syntax (anything beyond words, paths and -_./=:,+@%) is passed as zsh -lc '<command>'. --memory is at least 2G. --type tests is filled in only when the command, after any leading cd … && segments, starts with cargo test|nextest|build|check|clippy, pytest (any path), python[3] -m pytest, jest, npx jest, gradle, gradlew, or scripts/test / ./scripts/test. Otherwise the line keeps the literal <type>, followed by the three-line guide in Figure 4. The slug is the first two words of the command (basenames), lowercased, with every other character turned into -.

D. Host memory guard order

host_pressure_victim orders candidates as follows. First, shell jobs whose current bytes exceed their reservation. Then owner-forced runs. Then everything else. Ties break by size, largest first. The 512 MiB floor stays. A shell job's resident size comes from C's usage map, not the process-group listing. The stop goes through C's PID-tree stop when type = shell.

E. Background jobs

  • Definition. A command root (A steps 2 and 3) that is not a helper, found while the session's activity state is not working or thinking. A root is a helper when any of these holds:
    • It started no more than 10 seconds after its harness process started. This covers MCP servers and the Codex REPL helpers, which start with the agent.
    • Its basename is in the built-in list caffeinate, codex-code-mode-host, node_repl.
    • Its arguments contain cua-repl.
    • Its basename is in the new config list queue_runner.memory.background_ignore_commands (default empty).
    The rule is the same for every provider. Example: an idle Codex agent with cua-repl, node_repl and npm run dev under codex-fork shows one background job, npm run dev.
  • Snapshot. The guard pass publishes {session_id → [{pid, command, started_at, memory_bytes, shell_job_id?}]} to an in-memory map. It is not persisted. command is the label rule from A step 7. shell_job_id is set when the root is also a shell job. Arguments are read once per (pid, identity) and cached.
  • Activity. An agent whose turn has stopped and whose snapshot is non-empty reports activity_state = "waiting", as Claude does today from its footer. The process tree is now the source for every provider, and the Claude footer reading stays as a fallback when no snapshot exists.
  • Facts. facts.jobs in http/watch.rs: when there are no queue jobs and the snapshot has one entry, the text is "◷ Watching: <command, cut to 40>". With two or more, it is "◷ N in background". Both use the new tone "background", which the app and web render in cyan. Queue jobs, including shell jobs, keep their existing text, with the background count appended as " · N in background".
  • API. GET /watch/state carries each agent's background_jobs (the snapshot list without entries that are shell jobs, empty while the agent is working) and facts.background, their count; the app and web read agents from it. An idle agent with a non-empty snapshot reports activity_state = "waiting" in every session listing.

Z. FAQ

Why not grow the reservation when a shell job exceeds it? The reservation affects only the stop order and later headroom. Growing it would protect a misbehaving job against honest ones, which reverses decision 3.

Why not count shell reservations in perf admission? Perf admission already measures live free memory against the reserve. An unused shell reservation is memory a perf run may borrow, and if both grow, the host guard stops the shell job first when it is over its reservation.

Why not a separate table? As queue_jobs rows, shell jobs inherit the Queue screen, sm queue list, cancel, utilization sampling and the host guard with no new read path.
