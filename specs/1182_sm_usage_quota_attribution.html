sm usage — per-seat quota attribution

proposed  2026-08-10  ·  session-manager  ·  tracked as 1182

The problem

An orchestrator cannot see what it is spending. It knows which seats it spawned; it does not know how much quota they burned, so it cannot decide whether to expand lanes, and owner-set budget caps are unenforceable because nothing attributes usage to a seat.

The fleet runs several projects, each with its own orchestrator, drawing on a shared pool of provider accounts — today one Claude account and two Codex accounts, with the counts changing as workload grows. Quota is owned by the account; demand comes from seats; projects sit in between and cannot see each other. An orchestrator in project A therefore cannot answer "how much of this account is left" from its own subtree, because seats it never spawned are drawing on the same pool.

Three questions have to be answerable, and today none of them are:

  1. How much have I and my seats burned, as a fraction of the account's current window?
  2. How does that break down — which of my seats is expensive, and how much is me rather than them?
  3. How much headroom is left on this account, including usage from projects I cannot see?

Only sm can answer them. The providers publish account-level burn but know nothing about seats; the transcripts on disk record tokens but know nothing about lineage. The spawn tree exists in exactly one place, which is why this belongs here.

The solution

Two layers. The account total is measured; only the split across seats is derived.

LAYER 1 — MEASURED (first-party, exact, zero token cost)
  claude:primary → 5h 9% · week 8% · week/Fable 7% · resets 2026-08-16T16:00Z
  codex:acct-a  → 10080-min window 31% · resets @1786825765

LAYER 2 — DERIVED (sm's contribution)
  units(seat, w)  = Σmodel,bucket tokens × weight[model][bucket]
  share(seat, w)  = units(seat, w) / units(all seats on account, w)
  burn(seat, w)   = account_burn(w) × share(seat, w)

Both providers publish their own burn percentage, machine-readable, at zero token cost — verified on this machine and listed in Appendix A. sm reads those numbers rather than modelling them, so there is no denominator to estimate and no account-level error. Everything sm reports is the product above.

Account identity is a timeline, not a label. One account per provider is signed in at a time, and switching means signing out, signing back in, and resuming. So sm polls one small file per provider, records "provider P was account A from T1 to T2", and books each message to whichever interval holds its timestamp. A seat straddling a switch splits correctly on its own, because every message carries its own time.

Subagent usage lands on the parent seat for free. Sidechain transcripts live in a separate file but carry the same sessionId as the parent, so they map to the same seat by construction. The care needed is de-duplication (Appendix C.3), not routing.

Why model weighting is the crux

A seat holds one model for its lifecycle. Model changes happen, but only when the owner makes them, and they are rare. So seats do not converge toward a common model mix — they stay separated by family, which is exactly the condition under which naive attribution fails worst.

Attributing by raw token count treats a Luna token and a Sol-at-xhigh token as equal. They are not, by a wide margin, and the error does not average out — it is systematic, and it always runs the same direction: economy seats are charged for burn they did not cause, and premium seats are let off. A report with that bias is worse than no report, because a cap set on it would throttle the cheap seats while the expensive ones run unchecked.

Two independent effects compound, and both must be captured:

  • Rate per token — published spread is 10× end to end across Claude families (Fable $10/$50 per MTok down to Haiku $1/$5; Opus to Sonnet only 1.67×) and 25× across Codex families (Sol $5/$30 down to Luna $0.20/$1.20). Weighting handles this.
  • Tokens per unit of work — a premium seat at high reasoning effort emits far more tokens for the same task than an economy seat. Token counting already captures this, provided reasoning tokens are counted at the output rate and not double-counted (Appendix A.6).

Multiplied together these produce the order-of-magnitude gaps seen in practice: a 25× rate gap between Sol and Luna, times a volume gap from running Sol at high effort, lands near the ~100× difference observed in real use. Neither factor alone explains it, which is why the design needs both a weight table and honest token accounting.

The providers give part of the split and withhold the rest. Claude's premium-scoped weekly meter, combined with a published ratio, yields an exact premium-versus-everything-else decomposition — no fitting required (Appendix D.3). It says nothing about Opus versus Sonnet, which is the split covering 136 of the Claude seats. Codex says nothing at all: across 93,825 real rate-limit events on this machine, every sample carries limitId: "codex" and a null limitName — one shared account-wide bucket all models draw from together. Codex's own client agrees the rates differ, offering at 90% to switch the user to Luna "for lower credit usage"; it just never says by how much. Anthropic likewise confirms the premium model "uses [your limits] faster than other Claude models" and publishes no coefficient.

Where the weights come from

Published API prices give a starting ratio, but subscription quota weighting is not published and need not match API pricing — Anthropic states only that the premium model "uses [your weekly limits] faster than other Claude models", with no coefficient anywhere. So the residual weights are fitted from data sm already collects, with price ratios as the prior.

One large piece, though, does not need fitting at all. The premium-scoped weekly meter is a sub-cap of the overall weekly pool, sized at a published 50%, which makes the premium family's share of account burn exactly computable from two first-party numbers. Only the models below the premium tier — Opus versus Sonnet versus Haiku, and all three Codex families — have to be inferred. Appendix D.3 derives both.

Burn samples are cumulative and arrive every few minutes. Each consecutive pair yields one equation:

Δburni = Σm wm · Δtokensm,i + εi

Different seats are active in different intervals, so the model mix varies naturally across samples — the system is identifiable without any deliberate experiment. Solve by non-negative least squares, ridge-regularised toward the price prior so it degrades to the prior rather than to noise when data is thin. Within a model, hold the bucket ratios (input : output : cache-write : cache-read) at their published values, leaving one free scalar per family: three or four unknowns per provider, not twenty.

Claude's premium-scoped weekly figure supplies a second, independent equation series constraining the Fable weight specifically — note that weekly_all and weekly_scoped are percentages of different caps, so they are two separate observations rather than one comparison.

The honest limit is convergence time, not permanent error. Burn is reported as an integer percent, so each equation carries roughly ±0.5 percentage points of quantisation noise. Individual intervals are therefore useless and the fit needs a full window of samples. Expect the prior to govern for the first week or two and the fitted weights to take over after that. Until the fit is well-conditioned, sm usage labels its weights prior rather than fitted and says so in the output.

Decisions taken

Enforcement posture

Report only. sm usage answers when asked. No warnings, no spawn refusal. Caps are recorded on the seat and rendered against, but nothing blocks on them.

What a cap is measured against

The current account's measured burn. A cap of two sevenths means two sevenths of whichever account the seat is running on, as that account currently reports it.

Unattributed usage

A separate unassigned seat per account. Shares then sum to 100% and the gap is visible. Expected to be small, since work normally goes through sm; if it grows large that is itself a finding worth surfacing rather than hiding.

Provider coverage in v1

Both providers, per seat. Account-level Codex burn is nearly free, but per-seat Codex attribution is the point of the feature, not a follow-up.

Delivery surface

sm usage, a burn column on sm children, and an HTTP endpoint. sm children is where an orchestrator already looks when deciding to expand lanes, and it is a one-line change to format_child_line. sm status is deliberately excluded: it is global and cross-project, so a burn figure there would sit against a different denominator than the caller's and invite exactly the misreading this feature exists to prevent.

Scope and sequence

Phase 4 is optional for a useful v1. Everything through Phase 3 — measured account burn, per-seat token attribution, the exact premium decomposition, per-account subtree rollups — works without any fitted weight. Phase 5 can ship in PRIOR mode (C.8) — the exact premium term plus a prior-weighted proportional split of the remainder, with residual: unknown — which is honest, correctly model-weighted, and answers the orchestrator's question well enough to act on. The fitted path buys absolute burn and a real coverage figure, and it carries most of this design's remaining complexity: segment keying, the unobserved-burn intercept, provider-lag alignment, and credit-metered filtering. Build it when the proportional report proves insufficient, not on principle.

Phase 2 is unusually cheap. The statusLine payload already carries rate_limits.five_hour.used_percentage and .seven_day.used_percentage, the hook already POSTs to an endpoint sm owns, and hooks/context_monitor.sh lines 53–56 currently drop both fields on the floor. Forwarding them is a jq filter change plus two struct fields.

The scoped weekly limit is a sub-cap, not a second budget

This is the single most important semantic in the whole design, and it is officially documented: "Fable 5 draws from your plan's regular weekly usage limits and uses them faster than other Claude models", and "You can use up to 50% of your weekly usage limits on Fable 5 at no extra cost."

So a premium-model token decrements both meters; every other model's tokens decrement only weekly_all. weekly_scoped is a ceiling on how much of the one pool the premium model may consume, not a separate pool. Consequences:

  • Exhausting the scoped meter does not stop work. The user is offered two paths — continue on paid usage credits, or switch models and keep working against the remaining overall pool. Shipped UI copy: "You've reached your Fable 5 limit", "Buy more to keep using Fable 5, or switch models to keep working.", and even a runway hint, "try /model opus [N] more runway".
  • Exhausting the overall pool stops everything only when extra usage is disabled. With extra_usage.is_enabled true — as on this account, with a $148.85 monthly ceiling — reaching 100% spills into paid credits exactly as the scoped cap does, so seats keep working and their continued output is credit-metered rather than blocked. Treating overall exhaustion as an unconditional hard stop would report every non-premium seat as blocked while it is visibly still running, and would keep classifying its post-cap work as quota usage. Any unused scoped headroom is moot either way: it was never a balance, only an unused fraction of a ceiling.
  • Therefore the binding limit is model-dependent: a premium seat is blocked by whichever of the two meters hits 100% first; every other seat is blocked only by weekly_all. The report must say which one binds (C.8).

Do not hard-code the premium model. The scoped slot has moved repeatedly — Opus-specific when weekly limits launched (Aug 2025), removed and re-pointed at Sonnet (Nov 2025), now Fable. Team Premium seats scope Sonnet today while Max scopes Fable, so the answer differs by plan on the same date. The legacy hard-coded fields seven_day_opus / seven_day_sonnet survive in the schema but read null; the live path is the generic scope.model.display_name pointer. Read it, map it to a model family, and treat "which model is scoped" as data.

The 50% ratio is plan-dependent too. It applies to Max, Team Premium, and Enterprise Premium seats. On Pro and Standard Team the premium model is not included in weekly limits at all — it runs purely on paid credits, so there is no sub-cap to reason about. Key the ratio off organizationRateLimitTier rather than assuming.

Two different 50%s — do not conflate them. Alongside the sub-cap ratio, this machine's feature-flag cache currently carries tengu_rate_limit_promo_notices with "+50% weekly limits promo through Aug 19" — a temporary boost to the overall weekly cap, unrelated to the premium sub-cap. It matters beyond naming: a promo starting or ending changes the denominator that every reported percentage is relative to, mid-window. See D.4.

Parsing rules that matter:

  • Sparse rolling merge. A null field means "no update", not "cleared". Merge non-null values onto the last snapshot; never overwrite wholesale.
  • Key windows by (limitId, windowDurationMins), not by primary/secondary position — the same window has been observed in either slot.
  • windowDurationMins: 300 = 5 h, 1440 = daily, 10080 = weekly, 43200 = monthly, 525600 = annual.
  • resetsAt is Unix seconds. session_id is literally "unknown"; the file path identifies the session.
  • Field-name skew. Rollout JSONL and the exec stream use snake_case (used_percent, window_minutes, resets_at); the app-server v2 surface — which is what the codex-fork stream carries — uses camelCase (usedPercent, windowDurationMins, resetsAt). Historical files may carry resets_in_seconds (relative) instead of an absolute reset.
  • All models share one bucket. Across 93,825 real rate-limit events in 442 local event streams, limitId is "codex" in every sample carrying data and limitName is null in all of them. rateLimitsByLimitId — the multi-bucket map in GetAccountRateLimitsResponse — never appears, because the fork records the sparse account/rateLimits/updated stream rather than the batched read response. A limitId: "premium" bucket appears 4 times with primary and secondary both null, i.e. never carrying usage. The per-model bucket mechanism is real in the protocol (headers are templated x-{limit_id}-primary-used-percent, and limit_name can hold a model slug) but is not in use on this account. Treat Codex as one shared account-wide bucket.
  • credits is {"hasCredits": false, "unlimited": false, "balance": "0"} in every sample — this account has never been observed on credit metering despite the April 2026 rollout. rateLimitReachedType is null in all 93,825 samples; the account has not hit a limit locally.
  • Window distribution observed: 85,825 sparse updates carrying only a 10080-min primary; 7,962 full snapshots carrying 300-min primary + 10080-min secondary; 33 carrying a 43200-min primary. This is the concrete reason to merge sparsely and key by (limitId, windowDurationMins) rather than by slot.
  • planType ∈ free, go, plus, pro, prolite, team, self_serve_business_prolite, self_serve_business_usage_based, business, ent26, enterprise_cbp_automation, enterprise_cbp_usage_based, enterprise, edu, unknown. There is no "Max" plan — "Codex Max" names the model gpt-5.1-codex-max. This account reports pro, and the wire format does not distinguish Pro 5× from Pro 20×.

sm parses this event today but reads only tokenUsage.last.totalTokens for context occupancy and discards tokenUsage.total (sessions.rs:3423-3462, with a doc comment noting the omission). total is the cumulative per-thread spend this feature needs; take deltas between consecutive observations.

Verified numerically on a real sample: inputTokens 14274 + outputTokens 311 = totalTokens 14585 exactly, while reasoningOutputTokens is 115 — inside the 311. Source confirms it: the CLI prints reasoning as a parenthetical annotation on output and never adds it to the total. Summing reasoning alongside output double-counts every reasoning token, which would inflate exactly the high-effort premium seats this design exists to measure. Carry it as an informational column only.

Model and effort per turn

The token event carries no model. Model and reasoning effort arrive on a separate notification keyed by the same threadId:

{"event_type":"thread/settings/updated","payload":{
  "threadId":"019fc223-0000-7000-0000-000000000000",
  "threadSettings":{"model":"gpt-5.6-sol","modelProvider":"openai","effort":"high",
    "serviceTier":"default",
    "collaborationMode":{"mode":"default",
      "settings":{"model":"gpt-5.6-sol","reasoning_effort":"high", ...}}}}}

Attribution recipe: join each thread/tokenUsage/updated to the most recent preceding thread/settings/updated for the same threadId. Settings change mid-thread — the user switches with /model, and Codex itself nudges a switch at 90% (below) — so this must be a temporal lookup, not a one-time read. The rollout-file equivalent is a type: "turn_context" line carrying model and effort per turn.

This is strictly better than reading SessionRecord.model: it is per-turn, it captures mid-session model changes, and it needs no fallback for seats recorded as unset. Keep the registry value only as a backstop when no settings event precedes the first token event.

Codex nudges model switches on quota pressure — precedent worth knowing: RATE_LIMIT_SWITCH_PROMPT_THRESHOLD = 90.0 and NUDGE_MODEL_SLUG = "gpt-5.6-luna". At 90% of the shared bucket the TUI offers to switch to Luna "for lower credit usage". Codex therefore agrees that models burn the shared bucket at materially different rates — it just never tells a client what those rates are.

C.2 Line filter

Keep a line only if all hold:

  1. Raw bytes contain "usage":{ — a cheap prefilter before any JSON parse.
  2. None of id, cwd, model, speed, costUSD, version, sessionId, requestId, isApiErrorMessage, cache_read_input_tokens, cache_creation_input_tokens is explicitly null. (content: null is allowed.)
  3. It deserialises with message.usage present.
  4. version, if present, starts with N.N.N.
  5. sessionId, requestId, message.id, message.model, if present, are non-empty.
  6. timestamp parses.

message.model == "<synthetic>" marks an error entry (isApiErrorMessage: true): count its raw tokens in totals, exclude it from the per-model breakdown, give it weight 0. Its usage counters are zero anyway.

Cache-creation split: prefer usage.cache_creation.ephemeral_5m_input_tokens and ephemeral_1h_input_tokens when the nested object exists, since they carry different weights; fall back to the flat cache_creation_input_tokens at the 5-minute rate.

C.2b Quota-metered versus credit-metered

Not every token a seat spends draws on quota. Some are paid for with credits and move no meter at all. The distinction has to be decided once at ingest and then carried everywhere, because a token that costs money but consumes no quota belongs in a spend report and must stay out of every quota calculation.

A message is credit-metered when either holds at its timestamp:

  1. Plan exclusion. The plan never includes that model in quota — on Pro and Standard Team the premium model runs purely on credits (A.1). Every one of its messages is credit-metered from the outset, regardless of meter state.
  2. Post-exhaustion spill. The meter that would have governed it already reads 100% and extra_usage.is_enabled is true, so work continued on credits.

Everything else is quota-metered. The flag lives on message_ledger, is a dimension of the seat_tokens rollup and part of its primary key, and propagates from there:

  • The fit excludes credit-metered rows entirely (D.4). They consumed no quota, so including them tells the regression that tokens moved the meter less than they did, dragging every fitted weight downward after any exhaustion event.
  • The within-family premium apportionment excludes them (D.3), so credit-funded work cannot claim quota burn that earlier seats caused.
  • Reports show them separately as spend, never folded into a burn percentage.

Dropping the flag during materialisation is the failure to watch for: the ledger would be right, every rollup consumer would be wrong, and nothing would look broken. If credit_metered is not in the rollup key, paid tokens silently rejoin the quota arithmetic.

C.3 Dedupe — the correctness-critical step

The same assistant message appears in several files after resume, fork, and subagent runs. A subagent transcript replays parent messages with new requestIds and inflated cache_read_input_tokens. Naive summing roughly doubles a busy seat.

key_exact = hash(message.id, requestId)
key_loose = hash(message.id, NULL)

on new entry E:
  msg_id = alias[key_exact]
  if msg_id is null and sidechain-ness differs for this message.id:
      msg_id = alias[key_loose]           # sidechain replay of a parent message
  if msg_id is not null:
      if should_replace(E, ledger[msg_id]):
          reverse ledger[msg_id] from the rollup      # see below
          overwrite ledger[msg_id] with E
          apply E to the rollup
      alias[key_exact] = msg_id       # ALWAYS - E's exact key may be new
      alias[key_loose] = msg_id
  else:
      msg_id = insert ONE ledger row for E
      alias[key_exact] = msg_id
      alias[key_loose] = msg_id           # two keys, one row

should_replace(cand, prev):
  if cand.isSidechain != prev.isSidechain:
      return prev.isSidechain               # the non-sidechain copy ALWAYS wins
  if total_tokens(cand) != total_tokens(prev):
      return total_tokens(cand) > total_tokens(prev)   # streamed rewrite: keep the fuller
  return cand.usage.speed is set and prev.usage.speed is not

total_tokens = input + output + cache_creation_total + cache_read. The first rule is the one that matters: preferring the non-sidechain copy regardless of token count is exactly what prevents subagent cache-read inflation from being counted.

Replacement must reverse the earlier contribution

Scanning is incremental, so the two copies of a message frequently arrive in different scans — a subagent file is often read before the parent file is next appended to. By the time the preferred copy shows up, the inferior one has already been aggregated. A dedupe register that stores only a hash and a token total cannot undo that: it does not know which seat, model, window, or bucket the earlier contribution landed in. The inflated cache-read numbers would survive, or worse, be counted alongside the replacement.

So message_ledger stores the full contribution of every accepted message, and replacement is a three-step transaction:

  1. Resolve msg_id through message_alias — exact key first, loose key only on a sidechain mismatch.
  2. If should_replace is true, subtract the incumbent's stored buckets from its seat_tokens row (which may be a different seat, model, or bucket than the newcomer's), then add the newcomer's, then overwrite the single ledger row in place. If false, discard the newcomer and change nothing.
  3. Commit all writes together. A crash between them would leave a rollup that no longer matches the ledger.

Upsert the candidate's exact alias on every accepted match, including a loose one. A loose match happens precisely when the candidate's requestId differs from the incumbent's — so its exact key is, by construction, not yet registered. Leave it unregistered and the next sighting of that same copy misses the exact key, and now also skips the loose fallback because sidechain-ness matches the row it just replaced. It inserts a second contribution and the double-count returns. Write both keys every time.

Both lookup keys point at one row; neither owns a copy of the contribution. Writing the message under both an exact and a loose key as two ledger rows would double every accepted message in any rebuild, and replacing only the matched row would leave the other stale — reintroducing the inflation this design exists to prevent, in a form that looks like clean data. The alias table exists solely to keep that impossible: one message, one row, many names for it.

Cumulative sources need a persisted baseline

Codex reports tokenUsage.total as a running lifetime figure per thread, so a contribution is the difference between consecutive observations. A scanner that resumes at a saved byte offset has no in-memory predecessor for the first event it reads: it either treats the whole cumulative figure as one delta — adding the thread's entire history a second time — or skips the event and loses real usage. Neither is detectable downstream, because both produce plausible numbers.

codex_thread_cursor persists the last observed totals per thread alongside the event seq they came from, and ledger rows carry source_ref/source_seq so the cursor can be rebuilt from the ledger if it is ever lost. Claude needs none of this — its transcript reports per-message usage, not a running total — which is exactly why the asymmetry has to be written down rather than assumed.

seat_tokens is therefore a materialised rollup, not a source of truth. Any bucket can be rebuilt by re-aggregating message_ledger over (account_key, window_kind, window_start, bucket_ts), which is the recovery path when the two disagree and the reason the rollup index exists. Codex thread totals need the same treatment for a different reason: tokenUsage.total is cumulative, so a re-read of the same thread must diff against the last recorded total rather than add to it.

C.6 Model resolution

Every token bucket must carry a resolved model, never unset. Resolution order:

  1. Claude: message.model on the transcript line. Authoritative and per-message, so a mid-session model change is captured exactly. Observed aliases: claude-opus-5, claude-fable-5, claude-opus-4-8, claude-sonnet-5.
  2. Codex: the most recent thread/settings/updated preceding the token event for that threadId, giving both model and effort per turn (A.6). Mid-session model changes are captured.
  3. Codex fallback: SessionRecord.model for the seat, when no settings event precedes the first token event on a thread.
  4. Either, when both are absent or the record says unset: the provider launch config default at the time the seat started (claude.default_model, codex.default_model, codex_fork.default_model). Persist the resolved value so a later config change cannot retroactively rewrite history.

C.7 Window assignment and the timeline join

For each deduped message:

  1. account_key = the account_timeline row covering (provider, timestamp).
  2. window_start = derived per window by walking back from the observed resets_at by the window length. Claude's reset plus a known 5 h / 7 d length fixes the boundaries exactly; Codex supplies windowDurationMins directly.
  3. Record one message_window row per window the message falls inside — typically the 5-hour window and the overall week, plus the scoped week when the model is the scoped one. A message is not "in" a single window; it is simultaneously spending against every window that is open when it lands.
  4. Accumulate into seat_tokens per window at minute granularity, so buckets align with burn_samples for the fit.

Window membership is many-per-message, which is why it is a join table rather than a column. Putting window_kind on the identity row forces a choice: record one window and the message vanishes from every other report and fit, or write a row per window and break the one-row-per-message invariant that makes the alias table and the rebuild correct. Neither is acceptable, so identity and window membership are stored separately. Reversal then subtracts the contribution from every mapped window, not just one.

Messages whose sessionId maps to no seat accumulate under the reserved seat id unassigned.

C.7b Bootstrap — messages older than the first poll

On first deployment, and after any usage.db rebuild, the current 5-hour and weekly windows already contain messages whose timestamps predate the first account_timeline row. The covering-interval lookup returns nothing for them. Left undefined, the first report either drops up to seven days of per-seat usage or refuses to attribute it — while the provider cheerfully reports the full cumulative burn those messages caused, so the numbers visibly fail to reconcile exactly when someone is looking at them for the first time.

On the first poll for a provider, write a bootstrap interval: from_ts = the earliest message timestamp in any window still open, account_key = the account observed by that first poll, is_assumed = 1. Messages inside it attribute normally but are marked assumed.

The assumption — that the account signed in now is the account that was signed in for the whole pre-deployment stretch — is usually right, because switching is manual and rare. It is wrong if a switch happened before sm started watching, and nothing on disk can settle that (transcripts carry no account identity, A.4). So:

  • Report windows overlapping a bootstrap interval as partial, with the assumed portion stated.
  • Exclude bootstrap intervals from the weight fit entirely. An interval whose account attribution is a guess must not calibrate coefficients everything else depends on.
  • Close the bootstrap interval at the first genuinely observed poll; from there on attribution is real.

C.7a Coverage — burn that has no local tokens at all

unassigned and unobserved are different problems, and only the first is solved by scanning harder. unassigned is usage that is on disk but maps to no seat. unobserved is burn with no local artefact whatsoever — the account used from another machine, from claude.ai in a browser, or from a transcript since deleted. Normalising shares over observed tokens alone forces them to sum to 100%, which silently redistributes that invisible burn across the seats that are visible, inflating every one of them while the reported unassigned gap sits at zero and looks reassuring.

Once weights are fitted they convert units to burn points absolutely, not just proportionally, which makes the shortfall measurable:

predicted_burn = Σm wm · unitsm   over every observed message in the window
residual_burn  = max(0, account_burn − predicted_burn)   ← the unobserved remainder
coverage      = predicted_burn / account_burn

Seats are then reported in absolute burn points rather than as a normalised share, and the three parts add up to the account figure by construction:

Σ known seats  +  unassigned  +  residual  =  account_burn

This is only sound if the weights were not themselves fitted through the unobserved burn — otherwise the residual is absorbed into w and reads zero no matter how much is missing. D.4 covers how the unobserved component is estimated first and how the fitted label is gated on it. Where the two are collinear, coverage is a lower bound rather than a measurement.

Before the fit converges this cannot be computed honestly. With prior weights the unit-to-burn conversion is a guess, so the residual would be an artefact of the prior rather than a measurement. In that state, fall back to proportional shares, report residual as unknown rather than as a number, and mark known-seat figures as possibly inflated by invisible usage. Reporting unknown is the honest output here; a confident zero is not.

Coverage is worth surfacing in its own right. It answers "how much of this account's burn can sm actually see", which is the health metric for the whole feature — a coverage figure that drifts downward means work is escaping the fleet, and every attributed number is quietly getting less trustworthy.

C.8 Report

There are two modes, and which one applies depends on whether the weights for that window and cap segment have converged. They must not be mixed.

units(seat, w, m) = Σb tokens[m][b] × bucket_ratio[b]  (bucket-weighted, per model, quota-metered only)

PREMIUM TERM — per window; never fitted  (scoped plans only; D.3)
  w = weekly_all    → premium_pts = weekly_scoped_pct × r  (convert to pool points)
  w = weekly_scoped → premium_pts = weekly_scoped_pct     (already in scoped-cap points)
  w = session_5h   → no exact term exists; fit/apportion all families
  burnprem(seat)  = premium_pts(w) × unitsprem(seat) / Σseats unitsprem

FITTED — absolute conversion over the remaining families
  burnrest(seat)  = Σm ∉ premium weight[account, w, segment, m] × units(seat, w, m)
  burn(seat, w)    = burnprem(seat) + burnrest(seat)
  residual(w)     = max(0, account_burn(w) − Σall seats burn(seat, w))
  → Σ seats + unassigned + residual = account_burn  by construction

PRIOR — proportional over the remainder; residual not computable
  wu(seat)         = Σm ∉ premium prior_w[m] × units(seat, w, m)
  burnrest(seat)  = (account_burn(w) − premium_pts(w)) × wu(seat) / Σseats wu
  burn(seat, w)    = burnprem(seat) + burnrest(seat)
  residual(w)     = unknown; seat figures flagged possibly-inflated

The conversion factor r belongs to exactly one window. weekly_scoped_pct × r expresses premium burn in overall-pool points, so it is correct for weekly_all and wrong everywhere else. Applied to weekly_scoped it makes the seat values sum to r × account_burn instead of the scoped percentage — every premium seat under-reported by half. Applied to session_5h it imports seven days of premium burn into a five-hour window and simultaneously drops the premium family from that window's fit. There is no scoped 5-hour meter, so the 5-hour window has no exact term at all and every family is fitted or apportioned there.

Note that in the weekly_scoped window every unit is premium by definition, so that report contains only premium seats and their values sum to weekly_scoped_pct.

"Exact" describes the family total, not the per-seat split. The measured premium contribution is distributed across locally observed premium seats, so premium usage from a browser or another machine is silently pushed onto visible seats and never reaches the C.7a residual — the same coverage failure, confined to one family. Estimate premium coverage the same way as the general case (D.4): intervals with zero local premium units but a moving scoped meter measure unobserved premium burn directly, and that amount is reserved as premium residual before apportioning the rest. Where it cannot be estimated — too few such intervals, or premium off-machine use concurrent with fleet activity — label the premium per-seat split proportional and possibly inflated rather than presenting it as absolute. The family total stays exact either way; only its division is in question.

The premium term is exact in both modes and must never be fitted. D.3 deliberately removes that family from the regression, so requiring a fitted coefficient for every model would leave an implementation with two bad choices: drop premium seats from the report, or apply a stale prior to the one family whose contribution is actually known. Either corrupts seat totals and the residual. Compute the premium term first, then fit or apportion only what remains.

The proportional fallback still applies the per-model prior. Aggregating bare bucket-weighted units would treat a Sol token and a Luna token as equal despite a 25× documented spread — reintroducing exactly the bias this design exists to remove, in the mode most likely to be running. Sparse accounts may sit in prior mode indefinitely, so this path has to be right on its own terms, not merely a placeholder until the fit lands.

Do not normalise once the fit has converged. Scaling observed units to 100% and multiplying by the whole account burn silently redistributes the residual across visible seats — which is exactly the failure C.7a exists to prevent, reintroduced one section later. The proportional formula is the pre-convergence fallback only, and it is the reason the residual reads unknown in that state rather than zero.

Select the weight by (account, window_kind, segment_id, model). A weight is denominated in percentage points of one specific cap, so applying a weekly coefficient to a 5-hour report — or a pre-promo coefficient after a promo — produces a confidently wrong number.

Report the binding limit, not just the biggest number. A seat on the scoped premium model is blocked by whichever of weekly_all and weekly_scoped reaches 100% first; every other seat is blocked only by weekly_all (A.1). So the headroom a seat actually has is:

Both operands must be in pool units before they can be compared.

headroom(seat) = 100 − weekly_all_pct                                if the seat's model is not scoped
headroom(seat) = min(100 − weekly_all_pct, r × (100 − weekly_scoped_pct))   if it is

The two percentages are denominated in different caps and cannot be compared raw. weekly_all_pct is a fraction of the pool C; weekly_scoped_pct is a fraction of the scoped cap r·C. Multiplying the scoped remainder by r converts it into pool units. Skipping that conversion roughly doubles the reported premium runway — the single most consequential arithmetic error available in this design, because it inflates exactly the number an orchestrator uses to decide whether to launch more premium seats.

These diverge sharply in practice. An account at weekly_all 8% / weekly_scoped 7% has 92 pool points of headroom for a Sonnet seat but only 0.50 × 93 = 46.5 for a premium seat — half as much, not marginally more. Run premium-only and the scoped meter climbs twice as fast per point of pool, so it reaches 100% with roughly half the pool untouched: the account reads "50% used" while premium seats can no longer run for free. Surfacing weekly_all alone, or taking an unscaled minimum, would show an orchestrator ample headroom its own seats cannot reach.

Headroom means "free headroom", not "can it run at all". With extra usage enabled a seat at 0 headroom keeps working on credits (A.1, C.2b) — so report exhaustion as a switch from quota to spend, not as a stop. An orchestrator deciding whether to expand lanes needs both facts: no quota left, and work continuing at a price.

With --include-children, walk descendants using the existing preorder helper (collect_descendants_preorder, sessions.rs:5906-5928), then group by (account_key, window_kind) and compute each group separately.

Never aggregate a subtree into one number. A subtree routinely spans providers — the sm children example below has Codex and Claude children under one parent — and units carry weights denominated in different caps. Summing them either charges Codex work against a Claude denominator or drops it silently, and both produce a plausible-looking figure. There is no meaningful single "subtree burn"; there is one figure per account per window, and the report renders each.

The same applies to caps: a usage_cap_fraction is evaluated per account (decision 2), so a subtree spanning two accounts is measured against each independently. The default and compatibility flag --since-reset restrict output to the current window; --history also prints the last three closed windows from window_ledger.

D.3 Deriving the premium share exactly, then fitting the rest

Because the scoped meter is a sub-cap of known size (A.1), the premium family's contribution to account burn is arithmetic, not inference. Writing C for the overall weekly cap, the scoped cap is r·C with r = 0.50 published:

premium_share_of_pool  = weekly_scoped_pct × r
rest_share_of_pool     = weekly_all_pct − (weekly_scoped_pct × r)

worked, from this account: 7 × 0.50 = 3.5 points of the pool from the premium model
                       8 − 3.5 = 4.5 points from everything else
                       → the premium family is 44% of this week's burn

This settles the question that motivated the weighting work in the first place — whether premium tokens get over- or under-penalised. They get neither: their share of the pool is read off two first-party numbers and a published constant. Any premium seat's own burn is then that 3.5 points apportioned by its share of premium bucket-weighted units, not its share of raw premium tokens.

The per-model scalar cancels within the family; the bucket ratios do not. Cache reads weigh 0.1× input and output weighs 5× input (D.1), so two premium seats with identical raw token counts — one cache-read dominated, one output dominated — differ by a factor of fifty in quota units. Apportioning by raw tokens would hand them equal burn. Use Σb tokens[b] × bucket_ratio[b] per seat; the model scalar divides out of both numerator and denominator, which is why this split needs no fitted weight.

Apportion only over tokens that actually consumed quota. Once the scoped meter reaches 100% and extra usage is enabled, premium work continues on paid credits and stops drawing on the capped pool. Those post-cap tokens are still in the ledger, so dividing the fixed pool contribution over every premium token in the window would let credit-funded work claim quota burn that earlier seats actually caused — penalising the seat that ran first for the spending of the seat that ran after.

Split the window at the exhaustion marker: mark ledger rows written after the scoped meter hits 100% as credit_metered, exclude them from the within-family quota apportionment, and report them separately as spend. They cost real money and belong in the report — just not in this denominator.

It also strengthens the fit for everything else. Substituting the premium term out of the overall equation removes one unknown and the family with the widest price spread, leaving a better-conditioned system over the sub-premium models alone.

D.4 Fitting the remainder

Within a window, burn is cumulative and monotone. For consecutive burn samples i and i+1 on the same account and window, with the premium contribution already subtracted:

Δburni = Σm wm · Δunitsm,i + εi

where Δunitsm,i = Σb tokens[m][b] in (ti, ti+1] × bucket_ratio[b]

Run one fit per (account, window_kind, segment). A weight converts tokens into percentage points of a particular cap, and the 5-hour cap and the weekly cap are different sizes, so the same token delta moves them by different amounts. One blended fit across windows would be meaningless in both.

Procedure:

  1. Bucket seat_tokens by minute; align to burn samples by timestamp, within one window kind and one cap segment. Filter to credit_metered = 0 — paid tokens moved no meter, so feeding them to the regression understates every weight (C.2b).
  2. Coalesce consecutive intervals until Δburn ≥ 1 percentage point, so quantisation noise does not dominate.
  3. Solve non-negative least squares for w, ridge-regularised toward the D.1/D.2 prior.
  4. Record condition number and residual RMS in model_weights.
  5. Accept the fit only if the condition number is below threshold and at least N intervals contributed; otherwise keep the prior and label output prior.

Identifiability. The fit needs intervals in which model mixes differ. With many seats on different families active at different times this is satisfied naturally, but it is not guaranteed — if the fleet runs one family exclusively for a week, that week yields no information about the others. Report conditioning rather than silently returning an arbitrary solution from a singular system.

Unobserved burn must be estimated before w, not after

There is a circularity here that has to be broken explicitly. When the account is also used off-machine, Δburn contains consumption the regressors know nothing about. NNLS is non-negative and wants to explain Δburn, so it absorbs that unexplained burn into inflated model weights wherever the two overlap in time. Those weights then make predicted_burn approach the full account burn, coverage reports near 100%, the C.7a residual collapses to zero, and visible seats are overcharged — with every number looking healthy. Treating the omission as ε does not save it: ε is assumed zero-mean, and this term is strictly non-negative.

Break it by measuring the unobserved component from intervals where it is the only possible explanation:

Zero-activity intervals: Δunitsm = 0 ∀m, yet Δburn > 0
  → that burn is unobserved by definition. Estimate the rate u = Δburn / Δt from them.

Then fit on active intervals against the corrected target:
  (Δburni − u·Δti) = Σm wm · Δunitsm,i + εi

These intervals genuinely occur — the fleet is idle overnight while the account is used from a browser or another machine. Carry u as an explicit non-negative intercept in the regression as well, regularised toward the zero-activity estimate, so the two agree or the disagreement is visible.

Provider lag will masquerade as off-machine usage unless samples are aligned. cachedUsageUtilization was observed six minutes stale (A.1), so an increment caused by local tokens can surface during a later interval in which Δunits = 0. Counting that as unobserved "by definition" inflates u, which then subtracts real local burn from active intervals and corrupts every absolute weight — in the direction that makes coverage look worse and weights look smaller, so it will not announce itself.

Two defences, both required:

  1. Timestamp each sample by provider effective time, not poll time. Claude's fetchedAtMs is exactly this and must be used as the sample's clock. The statusLine push carries no equivalent, so prefer ~/.claude.json samples for fitting and treat statusLine samples as liveness only. Codex's resetsAt pins the window but not the sample instant — use arrival time and widen the guard band accordingly.
  2. Require a quiet band before the interval. Only count an interval toward u if local units were zero for at least the maximum observed staleness before it opened — twice that, to be safe. An interval that merely happens to be quiet is not evidence; an interval preceded by a long enough silence is.

Track observed staleness (now − fetchedAtMs) as a running maximum and derive the guard band from it rather than hard-coding a constant, so the band adapts if provider behaviour changes.

Gate the fitted label on u being well-determined, not just on the condition number. Concretely: require a minimum number of zero-activity intervals, and require the intercept's confidence interval to exclude implausible values. Without that, hold the prior — an absolute weight fitted through unmeasured burn is worse than an admitted approximation, because it produces a confident coverage figure that is wrong in the flattering direction.

The residual risk, stated plainly: if off-machine usage is concurrent with fleet activity rather than interleaved with it, no intercept can separate the two — they are collinear over the observation window. That is a real limit of this method, not an implementation gap. When it applies, coverage is a lower bound on visible burn rather than a measurement, and the report says so. The mitigation is behavioural, not statistical: usage that goes through sm is observable, and the coverage figure is precisely the incentive to keep it there.

Segment the fit at every cap change. Reported burn is a percentage of a cap that can move: promotional boosts (this account currently carries a "+50% weekly limits" promo expiring Aug 19), plan changes, and Anthropic's periodic limit adjustments all rescale the denominator without announcing themselves in the utilization payload. A Δburn straddling such a change is not a valid equation and will silently corrupt the weights. Detect a change three ways — a promo notice in the feature-flag cache, a shift in organizationRateLimitTier, and a burn percentage that decreases without a window reset — and start a new fit segment at each. Never pool observations across a boundary; prefer discarding a segment to fitting through one.

Codex has no scoped meter, so all three families there are fitted from the single shared bucket with no exact term to substitute out. Expect Codex weights to converge more slowly than Claude's and to carry wider error bars. Report them separately rather than presenting one blended confidence.

  • Timeline join: message before / inside / after a switch; message inside the uncertainty window.
  • Codex sparse merge: a null field must not clear a previously-observed value; window keyed by (limitId, windowDurationMins) across a primary/secondary swap.
  • Share arithmetic: shares sum to 1.0 including unassigned.

Integration (tests/read_only_http.rs, real router via oneshot):

  • /hooks/context-usage carrying a rate_limits block → a burn_samples row.
  • GET /sessions/{id}/usage with and without include_children.
  • Chaining: two Stop hooks with different transcript paths → two seat_sessions rows, no data loss.

Fixture corpus: a redacted transcript set with a hand-computed expected answer, covering one parent, one subagent, one compaction, one resume, and two model families. This is the regression net for the dedupe and weighting logic.

Live check: sm usage --account account totals must equal claude -p "/usage" exactly — both read the same first-party number, so any disagreement is an ingest bug, not a modelling error.

I.1 Branch topology

I.2 Phase order and what may run concurrently

The dependency graph is not a straight line — phases pair up, and running the pairs concurrently roughly halves wall-clock time. A phase may start as soon as its dependencies have merged into the epic branch, regardless of whether other phases are still in review.

  Phase 0 (chaining) ─────┐
                          ├──▶ Phase 3 (token ledger) ──┐
  Phase 1 (identity) ──┐  │                             ├──▶ Phase 4 (weights/fit) ──▶ Phase 5 (surfaces)
                       └──┴──▶ Phase 2 (burn ingest) ───┘

  concurrent pair 1:  Phase 0  ‖  Phase 1
  concurrent pair 2:  Phase 2  ‖  Phase 3
  then sequential:    Phase 4, then Phase 5

So Phase 0 and Phase 1 start together in two worktrees. When Phase 1 merges, Phase 2 may begin even while Phase 0 is still in review; when Phase 0 merges, Phase 3 may begin. Phase 4 needs both 2 and 3 merged. Do not start a phase whose dependency is merely "in review" — the ledger schema is shared and rebasing half-built phases onto a changed schema costs more than the wait.

I.3 Review protocol per phase

Follow docs/working/pr_review_process.md independently for each phase PR, with these epic-specific rules layered on top:

  • Only P1 items force a re-review. This matches the existing exit criteria: unresolved P1 means exit criteria are not met; P2 or lower means they are met.
  • Do not loop on P2s. A review that comes back with only P2/P3 items — or a second review that is again P2-only — is an exit, not another cycle. Fix what is cheap, then merge.
  • Carry the rest forward. Unfixed P2/P3 items fold into the next phase's scope. Record them in the epic PR description so nothing is silently dropped.
  • Prefer sm request-codex-review <pr-number> and let Session Manager wake you, rather than polling.
  • On merge: delete the phase branch, remove its worktree, return to the epic branch.

I.4 Interruption protocol

Workflow breakage outside this epic — a broken build on main, a failing service, anything blocking other agents — outranks the epic. When it happens:

  1. Stash or commit work-in-progress on the current phase branch. Leave the worktree in place; do not delete it.
  2. Write a handoff before touching the breakage. Not after — the interruption is exactly when context is most likely to be lost.
  3. Fix the breakage.
  4. Re-read the handoff, re-enter the worktree, resume.

The handoff must survive repeated compaction — the maintainer may compact several times while working an unrelated fire. Write it to ~/.local/share/claude-sessions/handoffs/1182-epic-<YYYYMMDD-HHMM-tz>.md, matching the existing convention on this machine. Rewrite the file — do not append — so the newest one is always complete on its own. It must state:

Do not use sm handoff for this. That command clears the session's context and hands it the document — it is a context-reset tool, not a bookmark. Using it mid-phase would discard the working state this file exists to protect.

Re-reading is self-enforced. Nothing replays the handoff automatically; the maintainer has to remember to open it after the interruption and resume from it. Treat that as a standing obligation, and re-read before touching the phase branch, not after starting work on it.

The two failure modes are not symmetric — bias hard toward writing. Forgetting to re-read is recoverable: the file is on disk and the owner can point at it. Forgetting to write one is not — once context is gone the state cannot be reconstructed by anyone. So write the handoff even when the interruption looks trivial and even when you expect to be back in a minute. A redundant handoff costs a few seconds; a missing one costs the epic.

  • Epic branch name, and the exact commit the epic branch is at.
  • Every phase: not-started / in-worktree / in-review / merged, with its PR number and worktree path.
  • The phase currently in hand, what was done, and the precise next action.
  • Carried-forward P2/P3 items not yet folded in.
  • Anything learned that contradicts this spec — that is the highest-value line in the file.
