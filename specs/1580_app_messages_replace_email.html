1580 — Agents message you in the sm app instead of by email

Author: sm-1580-spec-author 45bbc8a4 · Ticket #1580 · Revision 4

Memo

An agent that needs you runs sm send rajesh with markdown, exactly as it messages another agent. Your phone buzzes with the agent's name and the message title. Tapping it opens the message in the sm app, rendered the way memos render today. You reply in a box at the bottom, or select passages and comment on as many as you like, as in a memo review, and press Send. The agent receives your reply as an ordinary message, the same way it receives an sm send from another agent, and answers with another sm send rajesh.

Doc reviews keep working exactly as today, plus a buzz. sm doc publish --review still requires an open pull request; it now also notifies your phone, and the tap opens the doc. Your review goes to GitHub and wakes the agent with [sm review]. Two additions: No review needed clears a request you won't act on, and if the agent has ended by the time your review lands, Assign to a new agent starts one on the pull request with your review as its task.

Email stops being the channel and becomes the safety net. Today sm send rajesh quietly sends email, because email is the only way the server can reach you.1 After this change it goes to the app. The server emails you the same message only if your phone does not confirm it showed the notification within 15 minutes, or if phone notifications are not set up. This is the rule the follow-an-agent feature already uses. With that fallback, sm email rajesh has no job left, so it becomes a deprecated alias of sm send rajesh.

Nearly everything reuses pieces that already ship: the phone notification sender and its email fallback from following agents, the memo renderer and the select-and-comment reader from doc reviews, and the email path for the fallback. What is new: a message page, replies that go to the agent, a Messages list on each agent's card, and your name as a config setting instead of hard-coded text.

Message
What sm send rajesh creates: markdown from one agent to you, with a title, at most 25,000 characters. Like every sm send today, it is stored in the sm server's database, not in git. It has its own page in the app and on sm web.
Reply
What you send back from a message page: your overall text plus any comments on selected passages, sent together with one Send. The agent receives it as one message.
Blocking message
A message the agent marks with --blocking because it cannot continue without you. A message without it is for your information: you asked for it, and the agent carries on working.
Waiting for Rajesh
What an agent's card shows while a blocking message it sent you, or a review it asked for, has no answer. It ends when you reply or review, tap Handled (No review needed on a doc), or the agent ends. While it lasts, sm does not nudge the agent for sitting idle on claimed work.
Notification
The Android notification Google delivers to your phone while the app is closed. It carries only the agent name, the title and a link. The app fetches the message itself from the sm server when you tap.
Confirmation
The phone telling the sm server "I showed this notification". No confirmation within 15 minutes means the phone is off, notifications are muted, or the app is out of date, and the server sends email instead.
Owner name
A new config.yaml setting, owner_name, set to Rajesh on your Mac. Every text sm writes to an agent about you uses it: the reply header, [sm review], "Waiting for Rajesh", the follow message. Nothing in the code says "Rajesh" any more.

How it works

An example round trip

The agent runs:

sm send rajesh --blocking <<'EOF'
# Keep the old fills table or drop it?
The migration copies every row into `fills_v2`. I recommend dropping `fills`
after one week of both tables agreeing. Confirm?

Nothing reads `fills` after the cutover.
EOF
# prints: Sent to rajesh in the sm app (blocking) → https://sm.rajeshgo.li/messages/msg_3f9a2c1d

You comment on the last sentence and type "Otherwise yes, drop it." The agent receives:

[Input from: Rajesh via sm app] Re: "Keep the old fills table or drop it?" (msg_3f9a2c1d)
Otherwise yes, drop it.

> Nothing reads `fills` after the cutover.
The month-end recon does. Check it first.

The first line has the same shape as the header an agent sees on a message from another agent ([Input from: <name> (<id>) via sm send]),2 so the agent treats it as conversation and answers with sm send rajesh. Each comment carries the passage it refers to, as review comments do. "Rajesh" in the header is your owner_name setting.

What you see

Where you find messages later

Each agent's card in the app gets a Messages list above Docs: one row per message, newest first, with the title, a state (New, Read, Replied, Handled, or Needs you for an unanswered blocking message) and its age. An unanswered blocking message also shows in the card's existing "Waiting for" line as Waiting for Rajesh · <title>, the way a review request shows Waiting for owner review today. The message page lists your earlier replies under the message. On a laptop, every link in the fallback email and in sm send's output opens the same page on sm web.

A. Message states and waiting

A message's state is derived from its columns (Appendix C); there is no state column. First match wins.

StateConditionShown as
repliedA row in owner_message_replies exists for the messageReplied
handledhandled_at setHandled
needs_youblocking = 1 and the sender session is still in the registry and neither retired nor killedNeeds you
readfirst_viewed_at setRead

Unread (for the 5-message cap, D1) means first_viewed_at IS NULL. Viewed means the message page was served as HTML (not ?format=json), or the owner replied or tapped Handled; each sets first_viewed_at if null.

Each message in state needs_you adds to its sender's waiting_on in project_session_obligations3: {kind: "owner_message", id, label: "OWNER · <title>", since: created_at}. Check C, the idle nudge for claimed work, skips any session whose waiting_on is non-empty4, so a blocking message suppresses the nudge with no change to the claims code. The owner_review entry a review request adds today already does the same; that entry is now omitted when the doc's author is retired or killed, and when the latest publish's review request was dismissed (C1).

B. CLI and config

B1. sm send <human>

sm send <human> [--title "..."] [--blocking] [text...]      # or markdown on stdin / "-"
  • Target resolution. Unchanged up to the fallback: virtual target, then lookup_identifier_exact. Where the CLI today calls send_registered_email_fallback, it first asks GET /humans/{target}. A human match posts POST /humans/{canonical}/messages (D1). No match keeps today's registered-user email fallback (POST /email/send). rajesh, rajeshgoli, user and operator resolve through the existing human aliases.
  • Body. read_send_text as today: positional text, -, or piped stdin. The text is markdown.
  • Title. --title if given (trimmed, 1–120 characters, else error). Otherwise the server derives it (D2).
  • Flags. --title and --blocking are errors when the resolved target is not a human: --title/--blocking only apply to a message to a person. --urgent and --wait with a human target are errors: --urgent/--wait do not apply to a message to a person; use --blocking.
  • Sender. Requires CLAUDE_SESSION_MANAGER_ID; without it: sm send to a person needs a managed session, so the reply has somewhere to go.
  • Multiple targets. A human inside a comma list is an error before anything is sent: send to <target> on its own, not in a list. resolve_send_target checks GET /humans/{t} for each target first.
  • Output. Sent to <canonical> in the sm app → <reader_url>, with (blocking) before the arrow when set. A 400 or 429 prints the server's detail and exits 1.

B2. sm email

  • When the recipient resolves to a human (today's GET /humans/{t} check), sm email prints to stderr sm email to a person is deprecated; use sm send <person>, then behaves exactly as B1 with --subject as --title and the resolved body as the text. --cc and --html with a human stay errors, as today.
  • Recipients that are not humans (the email bridge's users: map) keep today's behaviour.

B3. sm doc publish

  • --review is unchanged: it still needs an open PR5. There is no --notify flag.
  • The payload gains checkout_root: the absolute path of the repo's main checkout, the parent of git rev-parse --path-format=absolute --git-common-dir run in the file's repo. For a file in a linked worktree this is the main checkout, which outlives the worktree. Omitted if the command fails. The server stores it only when it is an absolute path.
  • With --review, the success line becomes Review requested. OWNER is notified in the sm app; the review arrives as a GitHub PR review on #N, and sm wakes you with [sm review].

B4. sm lookup <human>

Human recipient: rajesh
Aliases: rajeshgoli, user, operator
Default delivery: sm app (email if the phone does not confirm within 15 minutes)
Send markdown with: sm send rajesh [--blocking] <<'EOF' … EOF

B5. owner_name

  • New top-level config.yaml key owner_name: a string, trimmed, 1–40 characters; default Owner when absent or blank. sm-server --check-config prints owner name: <value>.
  • It replaces every hard-coded owner name in non-test code: OWNER_NAME in http/docs/review.rs6 (the [sm review] wake and "OWNER wrote:"), and DEFAULT_FOLLOW_MESSAGE in the app's WatchModels.kt7. Tests set the key to Rajesh where their expected strings use it, so today's expected wake text is unchanged. The build greps the server, CLI and app sources for the literal Rajesh and leaves it only in tests and fixtures.
  • It is used by: D4 (reply header), D1 (cap message), A (waiting label), D5 (assign task), B3 (publish output, from the server's publish response) and the app (G).
  • The app gets the value from a new top-level field owner_name on GET /client/follows, which the watch refresh already calls; the Follow dialog builds its default message from it. Until the first response arrives, the app uses Owner.
  • The implementing agent adds owner_name: Rajesh to the installed config at ~/.config/session-manager/config.yaml and to config.yaml.example as a commented example.

C. Persisted shapes

C1. Retained queue database

The database at sm_send.db_path, where owner_docs and message_queue live8. Add these tables with the same migration pattern.

CREATE TABLE owner_messages (
  id                   TEXT PRIMARY KEY,     -- "msg_" + 8 lowercase hex
  human                TEXT NOT NULL,        -- canonical human recipient, e.g. "rajesh"
  sender_session_id    TEXT NOT NULL,
  sender_session_name  TEXT NOT NULL,        -- display name at send time
  title                TEXT NOT NULL,
  body_markdown        TEXT NOT NULL,        -- at most 25,000 characters (Unicode scalar values)
  blocking             INTEGER NOT NULL DEFAULT 0,
  created_at           TEXT NOT NULL,        -- RFC3339 UTC
  first_viewed_at      TEXT,
  handled_at           TEXT
);
CREATE INDEX owner_messages_sender ON owner_messages(sender_session_id, created_at);

CREATE TABLE owner_message_drafts (      -- passage comments not yet sent
  id          TEXT PRIMARY KEY,          -- same id scheme as owner_doc_drafts
  message_id  TEXT NOT NULL REFERENCES owner_messages(id),
  line        INTEGER,                   -- source line of the markdown; NULL = not placeable
  quote       TEXT NOT NULL,
  body        TEXT NOT NULL,
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);

CREATE TABLE owner_message_replies (
  id                       TEXT PRIMARY KEY,  -- the client's submission_id
  message_id               TEXT NOT NULL REFERENCES owner_messages(id),
  body                     TEXT NOT NULL,     -- overall text, trimmed (may be empty)
  comments_json            TEXT NOT NULL,     -- [{line, quote, body}] in delivered order
  delivered_text           TEXT NOT NULL,     -- exactly what the agent received
  delivered_to_session_id  TEXT NOT NULL,
  created_at               TEXT NOT NULL
);
CREATE INDEX owner_message_replies_message ON owner_message_replies(message_id, created_at);

Nothing is deleted from owner_messages or owner_message_replies, matching message_queue. Drafts are deleted in the transaction that inserts the reply.

Doc publishes. owner_doc_publishes gains two nullable columns: checkout_root TEXT (B3) and review_dismissed_at TEXT (set by No review needed). derive_owner_doc_state9 rule 1 (Review requested) additionally requires the latest publish's review_dismissed_at to be null; a dismissed request falls through to the next rule that matches, usually Read.

D2. Title derivation

When title is absent: the text of the first ATX or setext heading if it is within the first 10 non-blank lines; otherwise the first non-blank line with leading markdown markers (#, >, -, *, digits followed by . and a space or the line's end, so 3.5% stays) and inline markup characters (*, _, `) removed. Whitespace collapsed; the first 120 characters (on a character boundary) with … appended when cut. A title that comes out empty (a line of only markup) is Message. An ATX heading is one to six # followed by a space or the line's end, so #hashtag is not one.

D3. Submitting a reply

  1. Idempotency. If a reply row with id = submission_id exists: same message → return it unchanged; different message → 409. Replies are serialized per message with the draft writes, as doc review submissions are.
  2. Recipient. The sender session if it exists and is not retired or killed, else its parent if that exists and is not retired, else none: the rule the review wake uses13. None → 409 No agent is left to reply to, drafts kept.
  3. Content. Load the message's drafts, ordered by line ascending with NULL last, then created_at. Trim body. Both empty → 400 Nothing to send.
  4. Text. Build delivered_text (D4).
  5. Deliver and record in one transaction on the retained queue database: insert the reply row, delete the drafts, set first_viewed_at if null, and enqueue delivered_text for the recipient on message_queue with delivery_mode = 'sequential', from_sm_send = false and no sender session (so no second header). After commit, when the runtime is enabled, drain that session's pending messages, as the review wake does. Delivery timing is therefore exactly today's sequential sm send: at the recipient's next tool call when busy, at once when idle, on restore when stopped.

D4. Delivered text

[Input from: OWNER via sm app] Re: "<title>" (<message id>)
<overall body, if non-empty>

> <quote line 1>
> <quote line 2>
<comment body>

> <next quote>
<next comment body>

One blank line between the overall body and the first comment, and between comments; no blank line after the header. Each quote is trimmed, capped at 300 characters (… appended when cut) and prefixed > per line.

D5. Assigning a GitHub review to a new agent

  1. Eligibility, checked at assign time, not from the page. review_id names a row in owner_doc_reviews for this doc with status = 'posted' and delivered_to_session_id null (today's review_undelivered), and it is the doc's latest posted review. And the review wake rule13 applied to the doc's current author finds no recipient. Otherwise 409: Review not found when it isn't this doc's or isn't posted; Review is already with <session name> when delivered; A newer review exists; reload when it isn't the latest; The doc has an agent again: <session name> when the wake rule now finds one (another agent took over and republished). A stale page therefore cannot start a second agent.
  2. Where. working_dir = the checkout_root of the doc's newest publish that has one and whose directory exists. None → 409 No local checkout is known for <repo-name>; start the agent yourself.
  3. What. Provider, model and reasoning effort copied from the doc's recorded author session (the one that ended); a value the record lacks is left to the provider default. No parent, no name (the agent names itself per its repo's instructions).
  4. Task. initial_message, created through the same path as POST /sessions with a spawn brief source (kind: positional), so the task is accepted durably with the session: 
    [sm review] Your task is OWNER's latest review of "<title>" on PR #<n> in <owner/repo>. The agent that wrote the doc has ended, so the review is yours.
<the standard review wake text, render_owner_review_wake, unchanged>
Check out the PR branch in your own worktree, run `sm pr` from it to claim the PR, address the review, push, and republish with `sm doc publish <path> --pr <n> --review`.
  5. Record. Set the review's delivered_to_session_id to the new session in the same request, so the banner goes away and a second tap is a 409. When the new agent republishes, the existing authorship rule makes it the doc's author, because the recorded author is retired.
  6. Concurrent assigns for one review are serialized with the doc's review submissions; the second gets the 409.

E. Rendering and the reader client

E1. Message page

  1. Render body_markdown with render_markdown_with_lines inside doc_shell, the same path a .md doc takes14, with title as the page title. Line numbers are source lines of the markdown, so tap-to-comment anchors work unchanged.
  2. Above the body, a line in the shell's meta style: <sender_session_name> · <relative time>, plus · needs you in state needs_you.
  3. Inject the review client (review_client_injection15) with the config in E2.

E2. Client changes (http/doc_client.js)

  • The config gains mode ("review": today's doc behaviour, including today's read-only handling for docs whose PR is not open; "reply"; "read") and apiBase ("/docs/<id>" or "/messages/<id>"); message pages also get replyTo (the recipient's display name, or null), replies and state. api() builds URLs from apiBase instead of the hard-coded /docs/.

F. Notifications and email fallback

F1. Who is notified

user_id must be the identity the app's push tokens are registered under, the owner's signed-in Google email. So: the human's email channel address, lowercased, when it equals (case-insensitively) a google_auth.allowlist_emails entry; else the first allowlist entry; else local_bypass. For doc notices the human is the first configured human by name (the only one on a single-owner install).

F2. Delivery

Extend the follow delivery worker (owner_push::deliver10) to process owner_notices in the same pass, after follows, with the same rules: push to every valid token; success on any token sets notified_at and notified_via='push'; retryable failures back off 30 s, 1, 2, 5, 10 minutes, then email; an invalid token is marked and not retried; no push configured or no valid token → email at once; a push without an ack within 15 minutes → one fallback email; transient email failures retry every 5 minutes for an hour. Notices have no report grace. Runs only when rust_core.runtime_enabled, like follows.

Still wanted? Immediately before every push or email for a notice, including retries and the 15-minute fallback email, the worker re-reads its subject. A message notice is still wanted while the message's state is new, read or needs_you (A). A review_requested notice is still wanted while its publish is the doc's latest publish and the doc's state is review_requested. A notice no longer wanted is closed without sending: notified_at = now (if null; an already-pushed notice keeps its push time), notified_via = 'resolved', and no fallback email follows. So a reply, Handled or No review needed made while a push is retrying stops it.

Repair pass. Every third worker pass (the passes that also sweep follows), for the last 24 hours: every owner_messages row, and every owner_doc_publishes row with review_requested = 1, that has no notice gets one, by the same conflict-safe insert. A subject no longer wanted still gets its row, which the check above closes at once without sending. This covers a notice insert that failed after the message or publish committed, since those live in a different database from the notices.

Z. FAQ

Why is a message reply not a [sm …] marker, when follows and reviews are? Those come from sm on your behalf, or answer something the agent asked sm for. A reply to a message is you talking; the agent should treat it as conversation and answer. The sm send header shape gets that from every existing agent.

Why not deliver replies as urgent? Urgent interrupts the agent mid-step. Sequential delivery already reaches a busy agent at its next tool call and an idle one at once.

Why cap unread messages instead of rate-limiting per minute? A time limit punishes a legitimate burst and still lets a slow loop through overnight. The unread cap measures messages you have not seen, and resets the moment you open one.

What if you read the fallback email instead of the page? Email reading does not mark the message viewed, so a long email-only stretch could hit the cap. The email's link opens the page and resets it.

Why no reviews of docs without a pull request? GitHub is the review system: the review is kept on the PR, outlives the agent, and can be picked up by the next one (which is what Assign relies on). A review held only inside sm has none of that. An agent that wants your eyes on a readout without a review sends sm send rajesh with the link, and you reply to the message.

Why does Assign use the ended agent's type and model? You chose that tier for this work when you started it; a review of the same doc is the same work. The app's general New agent flow (#1396) is not built yet, so a picker would be new native UI for one button.

Why record checkout_root at publish instead of finding the repo at assign time? The author's worktree is usually deleted when it retires, and the server has no other map from a GitHub repo to a directory on your Mac. The main checkout a worktree was made from outlives it.

Why 25,000 characters? It is the length of a long post on X, several printed pages; a message longer than that should be a doc you can review and keep.

What does an old app build do with a message notification? Today's service knows only follow acks, so it never acks a notice. The server then emails after 15 minutes. Stage 3 ships in the same PR, so this only affects a phone that has not updated.

Why a separate notices table rather than rows in owner_follows? A follow has a target, a trigger and a report grace; a notice has none and is born already fired. Sharing the delivery code, not the table, keeps both shapes honest.
