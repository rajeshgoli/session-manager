1569 — Follow agents and queue jobs from the sm app

Author: sm-app-notifications a8d3f4e9 · Ticket #1569 · Revision 3

Memo

You tap Follow on an agent in the sm app. When that agent finishes, your phone shows a notification, and tapping it opens the agent's completion report. You can follow a queue job the same way: tap the bell on a running job, and you're notified when it succeeds, fails, times out or is cancelled. This replaces asking an agent to email you when it's done. The server, not the agent, keeps the promise. The agent's only job is to publish a report and run sm task-complete, which it should do anyway. The server notices, finds the report and pushes the notification. It also tells you if the agent dies before finishing, so silence never has to be read as "still working".

Delivery uses Firebase Cloud Messaging, Google's free push service for Android. It's the only channel that reaches a sleeping phone within seconds without a second app. It costs nothing. It needs about fifteen minutes of setup from you in Google Cloud, in the project that already holds the app's Google sign-in. That setup is the only part I can't do for you.

Follow
A record on the sm server saying "Rajesh wants to know when agent X finishes" or "when queue job Y ends". It fires once and then ends.
Queue job
A command an agent submitted with sm queue run, such as 1679-stage1-prepare-2. The app already lists them on the submitting agent's card.
Push
A notification Google delivers to your phone even while the sm app is closed. The sm server asks Google to send it; Google hands it to your phone.
Push token
The address Google gives your phone's copy of the sm app. The app sends it to the sm server so the server knows where to push.
Completion report
The newest doc the agent published with sm doc publish after you followed it, meaning the same docs you already read in the app.
Service account key
A credential file that lets the sm server ask Google to send pushes. It lives in ~/.config/session-manager/, outside every checkout.

How it works

What you see

Following an agent. The agent's three-dot menu gains Follow. Tapping it opens a dialog with this message already filled in. You can edit it, or clear it to follow silently. The agent receives it as a system message marked [sm follow], the same way it receives [sm task-complete] and [sm review], because it comes from sm on your behalf and not from another agent:

[sm follow] Rajesh is following you from the sm app. When your task is done, commit a
completion report (conclusion first, written for Rajesh), publish it with
`sm doc publish <path>`, then run `sm task-complete`. Publish before
task-complete: the notification links to the newest doc you published.

The message waits for the agent's current turn to end rather than interrupting it. A followed agent shows a bell on its card, and its menu says Unfollow. The first time you follow, Android asks once for permission to show notifications.

Following a queue job. Each queued or running job on an agent's card gets a bell. Tap it to follow; tap again to unfollow. The job's agent receives no message, because there's nothing for it to do.

Being notified. Exactly one notification per follow. The job examples use the 1679-stage1-prepare-2 job you mentioned:

What you need to do in Google Cloud

About fifteen minutes, once. Appendix E has the exact clicks and commands. I'll walk you through them in-session when implementation reaches that point.

  1. In the Firebase console, add Firebase to your existing Google Cloud project (the one holding the app's Google sign-in). Skip Analytics.
  2. Register the Android app li.rajeshgo.sm and save the config file it offers to ~/.config/session-manager/firebase-android.json. The repo is public, so this never enters git.
  3. Create a service account that may only send pushes, and save its key as ~/.config/session-manager/fcm-service-account.json. That's four gcloud commands, or a few console clicks.

Cost: $0. Google doesn't charge for Firebase Cloud Messaging, and this uses nothing else billable.

Decision surface

QuestionRecommendationWhy, in one line
1. Push channelFirebase Cloud Messaging. You already agreed to this.It's free, it arrives within seconds while the phone sleeps, and it notifies as the sm app itself.
2. What triggers a notificationsm task-complete, or the session ending first. A "stalled" alert (idle for 30 minutes with no task-complete) comes later, as its own ticket.Death is the case "email me when done" silently misses. Stall detection needs its own thresholds, so it waits.
3. How long a follow lastsIt fires once, then ends.It matches "tell me when this is done". Re-following is one tap.
4. How the message reaches the agentAs an sm system message marked [sm follow], after the agent's current turn, with no interruption. From your review.It comes from sm on your behalf, not from an agent, so it must not look like an sm send.
5. What passes through GoogleAgent name, report title and a link path. Never report content. The app fetches the report from sm on tap.Titles are enough to decide whether to open it. Content stays between your phone and your Mac.
6. Email if the phone doesn't confirmYes, one email after 15 minutes without confirmation. Also sent immediately when push isn't set up.A notification you never receive is the failure this feature exists to prevent.
7. Follow from sm web (browser)Not now. The app only.Browser notifications are a separate build, and you asked for mobile.
8. Following queue jobsInclude it in this feature: a bell on each queued or running job, one notification when the job ends, and no message to the agent.It reuses the same record, delivery and email fallback, so it adds about a day to the server ticket and a bell to the app.
9. Build orderTwo tickets, in order: (a) server: agent and job follows, triggers, Google sender, email fallback; (b) app: Follow menu, job bells, notifications, opening the report.Each fits one agent without running out of context, and the app ticket builds against the finished server.

Out of scope

Following from the command line or sm web. Notifications about anything other than a followed agent or job ending (reviews, stalls). Following several agents as a group. Each can reuse this push channel later.

A. Follow lifecycle

A follow moves through these states. Each is derived from the columns in Appendix B; there's no separate state column.

StateConditionNext
activefired_at and cancelled_at both nullfired (trigger), cancelled (Unfollow)
cancelledcancelled_at setterminal
firedfired_at set, notified_at nullnotified, when the push is accepted or the email is sent
notifiednotified_at setacked (phone confirms), or email fallback 15 minutes after the push
ackedacked_at setterminal

At most one active follow exists per (owner, session) for agent follows, and per (owner, job) for job follows. Cancelling after fired_at is set does nothing and returns 204, because the notification is already committed.

B. Persisted shapes

New SQLite database. Config key push.db_path, default ~/.local/share/claude-sessions/owner_push.db, resolved with expand_home like mobile_device_db_path1. The server creates the schema on open.

CREATE TABLE push_tokens (
  user_id      TEXT NOT NULL,          -- owner email, lowercase (bearer identity)
  fcm_token    TEXT NOT NULL,
  device_id    TEXT,                   -- mobile_device_enrollments.device_id if the app is enrolled
  device_name  TEXT NOT NULL,
  app_version  TEXT NOT NULL,

  PRIMARY KEY (user_id, fcm_token)
);

  target_kind         TEXT NOT NULL,      -- 'session' | 'queue_job'

  job_label           TEXT,               -- job label at follow time
  job_state           TEXT,               -- terminal state at fire time
  job_exit_code       INTEGER,
  job_started_at      TEXT,
  job_finished_at     TEXT,
  message_text        TEXT,               -- null when followed silently
  created_at          TEXT NOT NULL,
  cancelled_at        TEXT,
  fired_at            TEXT,

  report_title        TEXT,
  report_reader_path  TEXT,               -- e.g. /docs/session-manager/docs/working/x.html?version=abc123

CREATE UNIQUE INDEX owner_follows_one_active_session
  ON owner_follows(user_id, session_id)
  WHERE target_kind = 'session' AND fired_at IS NULL AND cancelled_at IS NULL;
CREATE UNIQUE INDEX owner_follows_one_active_job
  ON owner_follows(user_id, job_id)

CREATE INDEX owner_follows_pending ON owner_follows(fired_at, notified_at);

Revoking a mobile device (sm remove-device, DELETE /client/mobile-terminal/devices/{id}) deletes push_tokens rows with that device_id. The app sends its device key id (DeviceKeyManager.deviceKeyId()), the same id the device registry uses.

C. Server HTTP interface

Every route below uses the same guard chain as POST /client/request-status2: Cloudflare Access, public edge assertion, and owner bearer or local. user_id is the lowercase email from the bearer token. For a local call without one, it is the first google_auth.allowlist_emails entry, or local_bypass when none is configured. JSON bodies, and RFC3339 UTC timestamps.

If an active follow exists: 200 with that follow; no second message is sent and the new text is ignored. Otherwise it inserts the row (target_kind='session'). sm-server --check-config adds a push line: ready (project <id>), not configured, or broken: <reason> (unreadable key file or key without private_key). This mirrors the email bridge readiness line4.

D. Triggers, report lookup, delivery

D1. Firing

  • Task-complete. Inside SessionStore::task_complete5, on both the normal path and the reparent path, after agent_task_completed_at is written: UPDATE owner_follows SET fired_at=:completed_at, fire_reason='task_complete', notify_after=:completed_at WHERE target_kind='session' AND session_id=:id AND fired_at IS NULL AND cancelled_at IS NULL. This is a local SQLite write only. No network I/O happens under the state write guard. A failure is logged and never fails sm task-complete, because the sweep in D2 catches it.
  • Sweep (every 15 seconds, on the server's background runtime). For each active follow:
    • If the session's agent_task_completed_at is later than created_at, fire with task_complete. This catches a missed hook, but not one cleared by later activity; the hook above is primary.
    • Else, if the session is absent from state or raw_session_is_stopped6, fire with session_ended. The two rules above apply to target_kind='session' only. The stopped state is terminal, so the sweep sees every death path: retire, kill, crash reconciliation and the other stop transitions7. None of those sites is modified.
    • Job follows: if the job's state is terminal (succeeded, failed, timed_out, cancelled, displaced, memory_exceeded, process_limit_exceeded, wait_expired)11, fire with job_finished. Copy job_state, job_exit_code, job_started_at and job_finished_at, and set notify_after = fired_at. If the job no longer exists, fire with job_state='unknown'. Job states never leave terminal, so the sweep alone is sufficient and the queue code is not modified.

D2. Report lookup

For agent follows only. Job follows carry no report. Run at delivery time, not at fire time:

SELECT d.id, d.title, d.repo, d.path, p.commit_sha, p.published_at
FROM owner_doc_publishes p JOIN owner_docs d ON d.id = p.doc_id
WHERE p.session_id = :session_id AND p.published_at >= :follow_created_at
  AND d.retracted_at IS NULL
ORDER BY p.published_at DESC LIMIT 1;

The query matches on owner_doc_publishes.session_id (the session that published), not owner_docs.author_session_id8. report_reader_path is the same reader path the watch payload already gives the app for that doc and version. Report grace: if the lookup is empty and now < fired_at + 120s, the worker sets notify_after = fired_at + 120s and waits. After that it sends without a report.

D3. Delivery worker

Runs only on a server with rust_core.runtime_enabled, so a scratch server on copied state never sends. It runs every 5 seconds, sweeping (D1) on every third pass, over follows with fired_at set, notified_at null and notify_after <= now:

  1. Refresh session_name and run the report lookup.
  2. If push isn't configured, or user_id has no valid token, send the email (D4) and set notified_at and notified_via='email'.
  3. Otherwise, send the push (Appendix F) to every valid token. If at least one succeeds: notified_at=now, notified_via='push'. If all fail with retryable errors: increment push_attempts and set notify_after to now plus 30 seconds, 1, 2, 5 or 10 minutes after attempts 1–5. When attempt 6 fails too, fall back to email. An UNREGISTERED or invalid-token error sets that token's invalid_at and doesn't count as retryable.

Ack fallback: a follow with notified_via='push', acked_at null and notified_at + 15 min <= now gets one email, which sets email_sent_at. The email is sent at most once per follow.

Email failures: the email step distinguishes email that is not set up (no bridge, no recipient address) from a send that failed. Not set up is final: the follow is closed out as described in D4. A failed send is retried every 5 minutes for up to an hour, measured from fired_at for a first-choice email and from notified_at + 15 min for the ack fallback. notify_after holds the retry time, and the follow stays pending. After the hour, the follow is closed out with last_push_error = "email failed: …".

D4. Email

It goes through the existing email bridge4, sent as the followed agent so a reply routes to it. The recipient is the configured human whose email channel address equals user_id. When user_id is not an email, it is the only human with an email address. The subject and first body line match the notification title and body (table below). The body adds the sm web reader URL ({public base URL}{report_reader_path}) when there's a report, and the agent's name and id. If the email bridge isn't configured either, the worker logs a warning and sets notified_at with notified_via='email' and last_push_error='no channel', so it doesn't loop.

F. Google push sender

  • Access token: sign a JWT with RS256 using jsonwebtoken and the key file's private_key. Claims: iss=client_email, scope=https://www.googleapis.com/auth/firebase.messaging, aud=https://oauth2.googleapis.com/token, iat=now, exp=now+3600. POST form grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer&assertion=… to https://oauth2.googleapis.com/token via ureq, which is already a dependency. Cache the token until 5 minutes before expires_in.
  • Send: POST https://fcm.googleapis.com/v1/projects/{project_id}/messages:send, bearer access token, 10-second timeout, run off the async runtime (spawn_blocking) like the email bridge: 
    {"message": {"token": "<fcm_token>",
  "android": {"priority": "HIGH", "ttl": "86400s"},
  "data": {"kind": "task_complete|session_ended|job_finished|test", "follow_id": "fol_…",
           "session_id": "…", "job_id": "…", "title": "…", "body": "…",
           "reader_path": "/docs/…" }}}
    The message is data-only, so the app always builds the notification itself and tap handling is identical whether the app is open or closed. reader_path is omitted when there's no report, and job_id for agent follows. All values are strings.
  • Errors: 404 or UNREGISTERED, or 400 INVALID_ARGUMENT naming the token → invalid token. 429 and 5xx → retryable. 401 and 403 → retryable, and logged as a configuration error once per hour.

G. Android app

  • Dependencies: Firebase BoM plus com.google.firebase:firebase-messaging, with no google-services Gradle plugin. SessionManagerApp.onCreate calls FirebaseApp.initializeApp(context, FirebaseOptions) built from the four BuildConfig fields (Appendix E). If any is blank, push is disabled in the app and Follow still works, relying on email.
  • Manifest: POST_NOTIFICATIONS permission. A FirebaseMessagingService subclass, not exported, with the com.google.firebase.MESSAGING_EVENT intent filter. Notification channel agent_follow, named "Agents you follow", with high importance.
  • Token: after sign-in, at every app start, and in onNewToken, call PUT /client/push-token with device_name=Build.MODEL, app_version=SM_APK_HASH and the enrolled device id when one exists. Sign-out calls DELETE.
  • Receive: onMessageReceived posts a notification from data.title and data.body, with notification id = follow_id.hashCode(), so a duplicate replaces rather than stacks. It then calls POST /client/follows/{follow_id}/ack, fire-and-forget, except for kind=test. It acks only when the notification was shown: notifications are enabled for the app, the agent_follow channel is not muted, and posting succeeded. A suppressed notification is never acked, so the email fallback still fires. A push that arrives while the app is signed out is dropped without showing.
  • Tap: a PendingIntent to MainActivity with extras follow_id, session_id and reader_path. MainActivity handles them in onCreate and onNewIntent, following the sm-enroll pattern9. With reader_path, it opens DocReaderOverlay on it; without, it opens Watch with that session's card expanded. That covers job notifications, whose session_id is the submitting agent.
  • Menu: in the agent actions menu10, add Follow or Unfollow above "Retire session". It's disabled when the session is stopped. Follow opens a dialog: a multi-line text field prefilled with the memo's message text, verbatim; a hint line saying "Clear the message to follow without telling the agent"; and buttons Cancel and Follow. On first use on Android 13 or later, it requests POST_NOTIFICATIONS before sending. If you deny it, the follow still proceeds, with a toast: "Notifications off — you'll be emailed instead".
  • Bell: the watch refresh also calls GET /client/follows, and cards of sessions with an active follow show a bell icon next to the status.
  • Job bells: every pending or running job row on the agent card (the "In progress" rows and the "All jobs" disclosure12) shows a bell toggle at its right edge. It is an outline when not followed and filled when followed. Tapping it calls the job follow POST or DELETE, with no dialog. The first job follow requests POST_NOTIFICATIONS exactly as for agents. Finished jobs show no bell.
  • Settings: a "Notifications" group, shown when signed in. It says whether this build has push, and has a "Send test notification" button. The button re-registers the token, calls POST /client/push/test, and shows "Sent to N phone(s)", the failure, or "No phone registered for notifications". Sign-out deletes the phone's token from sm, then deletes it at Firebase (FirebaseMessaging.deleteToken), before clearing the session. If the first step fails, Google reports the token unregistered on the next send and sm stops using it.

Z. FAQ

Why a sweep for session end instead of hooking every stop site? The code has at least nine places that set a session to stopped7. A 15-second sweep over a handful of active follows is one code path that can't miss a new stop site added later. Task-complete gets a direct hook because agent_task_completed_at is cleared by later activity, and a sweep could miss a fast re-task.

Why is the agent message not an sm send? An sm send reads as coming from another agent, and an agent may reply to its sender. [sm follow] comes from sm on the owner's behalf, like [sm task-complete] and [sm review], so the agent treats it as an instruction about how to finish, not a conversation.

Why does a job notification open the agent card and not the job log? The app has no log viewer today, and the card already shows the finished job with its exit state in "Recent job history". A log viewer would be its own ticket.

Why data-only pushes? With a "notification" push, Android draws the notification itself while the app is in the background and hands the app the tap without the data, so tap routing would differ between foreground and background. With data-only and high priority, the app's service runs in both cases.

Why no google-services plugin? The plugin requires google-services.json in the source tree, and the repo is public. Initialising Firebase from BuildConfig fields matches how the app already takes SM_GOOGLE_SERVER_CLIENT_ID.

Why ack plus email instead of trusting Google? Google accepting a push only means Google has it. A phone that's off, uninstalled or on a stale token never shows it, and the server can't tell. The ack is the only proof the notification was shown.
