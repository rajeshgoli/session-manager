An Inbox for agent messages and docs

Author: sm-inbox-designer 519d87fe; revisions 2–3 by sm-1647-inbox-engineer 58b00210 · Approved on PR #1646 · Server: #1647 (shipped) · Android: #1648 · Revision 3 · Builds on specs/1580_app_messages_replace_email.html

Memo

Yes: everything agents address to you, their messages and their docs, belongs in an Inbox, a tab of its own. Watch answers "what are my agents doing?" and is sorted by repo and agent tree. The Inbox answers a different question, "what is waiting on me?", and is sorted by urgency and time. Today those items hang off agent cards, which makes you scan every card to find what needs you, splits one back-and-forth across several pages, and hides a message once its agent's card leaves the screen.

The design adds a third bottom-nav tab, Inbox, next to Watch and Analytics, and the same list on sm.rajeshgo.li. Each row is one thread, in the Gmail sense: everything on one subject, in time order. An agent's messages form one thread, because each agent works one task. A doc forms its own thread, because a doc outlives the agent that wrote it and can pass to another agent, as this one did. A blocking message or a review request puts its thread under Needs you; a plain message or a plain doc publish shows as New. A notification opens the thread, and Back returns to the Inbox, so you can work through several items in a row without passing through Watch. Watch does not change.

There is one Inbox, kept by the server. Whether you answer on the phone or at sm.rajeshgo.li, the thread leaves Needs you on both, and opening it on either withdraws the phone notification, which already ships.

Almost nothing new is stored. Messages, replies, docs, reviews and follow results already sit in the server's database; the Inbox is a new way to list them. The new pieces are the Inbox list (native in the app, a page on sm web), a message-thread page built from the existing message reader, a Done action, and the ability to write to a live agent without waiting for it to write first. A doc thread opens the doc page you already use.

Terms used here

Message
What an agent's sm send rajesh creates today: a titled markdown note stored by the sm server, with its own page at /messages/<id>. Unchanged by this design.
Blocking message
A message sent with --blocking, meaning the agent cannot continue without you.
Doc publish
What sm doc publish <path> creates: a doc in git that the agent wants you to read. Each publish is one revision. Unchanged by this design.
Review request
A doc publish with --pr N --review: the agent asks you to review that revision, and your review goes to GitHub. Unchanged by this design.
Follow result
What you get after tapping Follow on an agent or a queue job: a notification when the agent finishes (with its report) or dies, or when the job ends. Unchanged; it now also lands in the Inbox.
Thread
New. One subject, in time order. Two kinds. An agent thread holds one agent's messages, your replies, and follow results for it and its queue jobs. A doc thread holds one doc: every revision, every review request, and your reviews, whichever agent published them.
Inbox
New. The list of threads, one row each, with the ones that need you on top.
Needs you
A thread with an open blocking message or an open review request. It stays there until you answer (reply, review, or clear it) from the app or sm.rajeshgo.li. Opening it only withdraws the phone notification.
Done
New. Your "I have dealt with this" on a thread. It moves the row out of the open list and clears the open ask in it without sending the agent anything. The row comes back if anything new arrives in the thread.

What is wrong with messages and docs on the Watch page

Four concrete problems with today's layout, all from the shipped design:

  1. Finding what needs you means scanning. Messages and docs sit on each agent's card, and cards are grouped by repo and parent agent. With fifteen agents running, a blocking question from one of them is a line on one card among fifteen.
  2. A back-and-forth is split across pages. Every sm send rajesh makes a new message page, and your reply is stored under the message you answered. When the agent answers your reply, that is a new, unconnected message, whose page does not show the earlier exchange.
  3. History disappears with the agent. The card shows the last 30 days and at most 20 messages1, and a retired agent's card leaves Watch, taking its messages and docs with it. A doc you signed off last week is findable only through the old notification or its path.
  4. Three kinds of "for you" live in three places. Messages are on the card's Messages list, docs on its Docs list, and follow results only in the notification shade.

What a thread is

Gmail groups mail by subject. sm has no subject line, but it has two natural ones: the agent, because each agent works one task, and the doc, because a doc is one piece of work that can pass between agents. Grouping by either needs nothing from agents: they keep calling sm send rajesh and sm doc publish exactly as today.

An agent thread is not the agent page. The Watch card stays the agent page: status, parent and children, terminal, queue jobs, its docs list and its message list. The agent thread shows only what you and the agent said to each other, sorted into the Inbox by urgency. Each links to the other: the thread header opens the terminal, the card opens the thread.

Decision surface

QuestionRecommendationWhy, in one line
1. Is the Inbox its own tab?Yes: bottom nav becomes Inbox · Watch · Analytics. The app still opens on Watch; the Inbox badge tells you when to switch. sm.rajeshgo.li gets the same list at /inbox."What needs me" and "what are agents doing" are different questions with different sort orders.
2. What is one row?One thread: an agent's messages, or one doc across its revisions.Each agent works one task, so the agent is the subject of its messages; a doc can outlive and change agents, so the doc is its own subject.
3. What lands in the Inbox?Messages, doc publishes, review requests, and follow results. Not agent status changes.These are the things addressed to you. Blocking messages and review requests need you; plain messages and plain publishes are for your information.
4. Can you write first?Yes, to any live agent, from its thread.With a reply box on every agent thread, refusing to let you use it until the agent speaks is an artificial limit. The shipped design left this out of scope.
5. What does Done do?One Done per thread that clears the open ask in it (Handled, or No review needed) without messaging the agent. Anything new reopens it.One gesture to clear your list; no separate archive, snooze or per-message clearing.
6. Does the Watch page change?No. Cards keep their Messages and Docs lists.Watch is the agent view; both read the same server state, so they cannot drift.
7. What does the badge count?Only threads that need you (a blocking message or a review request). Unread notes and docs show a dot.A badge that counts FYI items trains you to ignore it.
8. Where do signed-off docs go?A Docs filter in the Inbox lists every doc, with no time limit. Messages keep the 30-day Open list and an unlimited Done list.You go back to read approved docs; messages are rarely reread after a month.
9. How is it built?The Inbox list is native in the app. An agent thread is a new server-rendered page; a doc thread opens the existing doc page. Both show in the app's reader and on sm web.The message page already renders markdown and takes quotes this way, the doc page already does review and Assign, and one page then serves phone and laptop.
10. How many build tickets?Two, in order: (a) server: the Inbox list, the agent-thread page, Done, writing first; (b) Android: the Inbox tab and notification taps opening the thread. Mid tier (Opus 1M, high) for both.The server half is testable on sm web before the app changes, and each fits one agent without compaction.

Not in this design

Browser or desktop notifications on sm web. Search across threads (the Docs and Done filters plus scrolling cover it for now; search can follow if they prove too little). Grouping threads by repo or by parent agent. Messages from agents to anyone other than you. Any change to the Watch page. Changes to how sm send rajesh, --blocking, sm doc publish, the unread cap or the email fallback work: agents see no difference.

B. Server (#1647)

B1. Threads and their items

A thread key is agent:<session_id> or doc:<owner_docs.id>.

ThreadItems (each counts once toward Done)Also shown, not counted
AgentMessages whose sender_session_id is the session; replies to those messages; notes to the session (B6); fired, uncancelled follows whose session_id is the session, which covers queue-job follows the session submittedOn the thread page only: one line per doc publish the session made, newest 100
DocIts publishes (revisions) and its posted reviews—

An agent thread exists once it has one item. A doc publish alone makes no agent thread. A retracted doc has no thread. A session that is in the registry but has no items has a thread page (for writing first) but no Inbox row.

B2. Group

GroupAgent threadDoc thread
needs_youSome message is in state needs_you (blocking, no reply, not handled, sender live)State review_requested and the latest revision's publisher is live
newOtherwise, some message is in state new, or the thread holds more fired follows than it did when last opened (read_follows; never opened counts as zero)State new or updated, or review_requested from an ended publisher

"Live" means the session is in the registry and its completion_status is neither retired nor killed. Example: an agent sends a plain note, then a blocking question, then retires. Its question is no longer needs_you; the thread is new until opened, then earlier.

B3. Done

Table owner_inbox_threads(thread_key TEXT PRIMARY KEY, done_at TEXT, done_items INTEGER, last_read_at TEXT, read_follows INTEGER) in the retained queue DB (sm_send.db_path). Done records the thread's item count. A thread is Done while its item count is at most done_items, so any new item, including your own later reply, brings it back. Counting instead of comparing times keeps a message that lands in the same second as Done from being hidden.

POST /inbox/done with {"thread_key": "…"}:

  • Agent thread: every blocking message from the session with no reply and no handled_at gets handled_at; every unread message from it gets first_viewed_at. 404 when the session has no items and is not in the registry.
  • Doc thread: if the doc is review_requested, dismiss_review (No review needed). 404 when the doc is unknown or retracted.
  • Any other key: 400. Response 200 {"thread_key": "…", "done": true}. Nothing is queued for any agent.

B4. GET /inbox

?filter=open (default), docs or done; anything else is 400. ?format=json returns JSON; otherwise an HTML page in the Watch palette with an Inbox · Watch · History · Guestbook top bar, Open / Docs / Done chips, group headings on Open, and a Done button per row.

B5. GET /inbox/agent/{session_id}

The agent thread's page, server-rendered in the Watch palette. 404 when the session has no items and is not in the registry. Opening it sets first_viewed_at on every unread message from the session (which withdraws their phone notifications through #1645) and sets the thread's last_read_at and read_follows (the fired follows it holds). Items in time order:

  • Message: a bubble on the left with its title, markdown body (paragraphs carry data-sm-line), relative time and state; a needs_you message has an amber border and a NEEDS YOU chip. The bubble's element id is the message id.
  • Reply and note: a bubble on the right with its quotes as blockquotes, its text, and You · 5m ago, plus · to <name> when it went to a parent.
  • Follow: a grey line from the follow notification's title and body, for example sm-1655-engineer finished · Report: bar-feed readout (linking the report) or Queue job 1679-copy-fills succeeded · sm-1679-engineer · ran 38m.
  • Doc publish: a grey line Published: <title> or Asked for review: <title>, linking that revision.

The composer sits at the bottom. With a live recipient (B6) it has quote chips, a text box, Done and Send; tapping a paragraph of a message adds its text as a quote. With none it has Done and No agent is left to reply to. ?at=<message id> scrolls to and highlights that message; without it the page opens at the bottom.

GET /messages/{id} (the page, not ?format=json) serves the same thread page for the message's sender, scrolled to that message, so links in email, agent output, notifications and Watch cards land on the thread. It serves rather than redirects because the app's reader sends a path it does not know to the system browser, and apps built before #1648 do not know /inbox/. ?bottom=1 on either URL opens at the newest item instead; the page reloads that way after a send. The JSON form and the drafts, reply and handled endpoints are unchanged.

B6. POST /inbox/agent/{session_id}/send

Body {"submission_id": "…", "body": "…", "quotes": [{"message_id": "msg_…", "quote": "…"}]}. The submission id is 8–64 letters, digits, - or _. Checks, in order:

  1. At most 100 quotes; text at most the draft-comment limit.
  2. A submission id already stored as a reply to this thread, or as a note to this session, returns the stored send and queues nothing. Stored for another thread: 409.
  3. Unknown session with no messages: 404. No live recipient (the session, else its live parent): 409 No agent is left to reply to.
  4. Each quote must come from a message of this thread (400); empty quotes are dropped. No text and no quotes: 400.

The send is recorded as a reply to the newest needs_you message; else the newest quoted message; else the agent's newest message. With no message at all it is a note. One message is queued for the recipient and delivered at once when the runtime is enabled. The text the agent receives:

[Input from: Rajesh via sm app] Re: "Keep it?" (msg_1a2b3c4d)
> Nothing reads fills.

The month-end recon does.

A note has no Re: part: [Input from: Rajesh via sm app], a newline, the text. Response: the stored reply or note with kind (reply or note), message_id (null for a note), delivered_to_session_id and delivered_to_session_name.

B7. Notices, access, token

  • Notices keep their links: a message notice opens /messages/<id>, which is the thread (B5); a review-request notice opens the doc page.
  • /inbox and /inbox/… reads use the owner page gate, as /messages/ does, and are listed in is_protected_read_surface.
  • Writes accept the page's signed token (X-SM-Doc-Token, subject inbox, minted into both pages) or the ordinary session guard the app uses; both need core writes enabled.

D. Writing first

A message you start before the agent has sent any is a note, in its own table owner_message_notes(id, session_id, body, delivered_text, delivered_to_session_id, created_at) beside the messages, recorded and queued in one transaction under the submission id (queue id owner-note-<id>). Delivery, deduplication and the "no live agent" rule are those of a reply.

Z. FAQ

Why not thread by message, with a --re flag for agents? Agents would have to remember to pass it, and they answer your reply with a fresh sm send. Grouping by agent needs nothing from them and is correct because each agent works one task.

What if one agent raises two unrelated questions? They appear as two message cards in one thread, each with its own title and its own Needs you tag. A send answers the newest open one; Done clears both.

Why is a doc not part of its author's agent thread? A doc can be revised by several agents: the author ends, you review, Assign hands it to a new agent, and that agent publishes the next revision. Keyed by agent, that history would split across two threads. The agent thread keeps a pointer line so its own story still reads in order.

Why do Done and read count items instead of comparing times? Stored times have one-second precision. A message that arrived in the same second as Done, or a follow that fired in the same second the thread was opened, would compare as older and stay hidden.

Why a separate notes table? Making owner_message_replies.message_id nullable needs a table rebuild in SQLite; a notes table beside it holds the same facts with no migration of live rows.

What happened to the single-message page? Its URL now shows the whole thread, scrolled to the message. Its select-and-comment drafts are replaced by tapping a paragraph to quote it. The drafts endpoints stay for any old page left open.

Revision history. Revision 1 had one conversation per agent, only review requests from docs, and a pointer replacing the Watch card's message list. Revision 2 added doc threads and every doc publish, kept Watch unchanged, and made the Inbox one list across phone and web.
