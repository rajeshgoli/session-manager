1651 — Context handoff: a fresh agent takes over the work

Author: sm-handoff-redesign-spec-author 0f52d06d · Closeout: 1657-engineer d39b7441 · Ticket #1651 · Revision 3 · 2026-09-29

Memo

I recommend replacing today's sm handoff with a successor model. When an agent reaches a tipping point, sm asks it to stop at a logical point and post a handoff note. The agent then runs sm handoff --link <url> or sm handoff --path <file>. sm starts a fresh agent of the same kind in the same worktree and moves everything addressed to the old agent onto the new one. That covers its tickets and PRs, pending review and queue wakes, reminders, children and registered roles. Then sm retires the old agent. A default policy decides who gets asked and when. You can change every default, and turn the policy off or change the threshold for any one agent, from sm.rajeshgo.li, the sm app, or sm watch.

Today's command asks the agent to write a markdown file, types /clear into the agent's terminal, and pastes “Read <file> and continue” back in. It has three problems. It keeps one session id across many context windows, so the id no longer restores one line of reasoning. It depends on typing into a terminal and confirming the redraw, the most fragile code path sm has, and it has a separate variant for each provider. It does not work at all for codex-app agents. Starting a fresh agent removes all three problems. The cost is the part the old design never needed: sm must move the agent's work across, and the design below does that exhaustively.

Context usage
How full the agent's model context window is, as a percent, as the provider reports it. Claude reports it on every status-line update. codex-fork reports it in its token events. codex-app reports nothing, so sm has no reading for it. sm already records this reading for every agent of a provider that reports it.
Handoff
One agent (the predecessor) stops, and sm starts a fresh agent (the successor) that inherits its work.
Handoff note
What the predecessor writes for the successor: a PR comment, a ticket comment, or a file. sm does not read it. sm only passes its location to the successor.
Tipping point
An event that makes sm ask an agent to hand off. There are five. Context usage reaches the threshold (starting value 35%). The agent asks for a review, either from Codex with sm request-codex-review or from you with sm doc publish --review, with context usage at or above the review floor (starting value 20%). You press Hand off now. Or the agent decides on its own.
Handoff policy
The rules that decide whether and when sm asks an agent. The default policy applies to every agent. sm stores it, and you edit it from the web, app, or sm watch. An override is a per-agent on/off or threshold that you set the same way. It beats the default.
Obligations
Everything sm addresses to an agent's session id: ticket and PR claims, children, registered roles such as maintainer, pending sm request-codex-review wakes, sm queue run completion wakes, sm remind reminders, undelivered sm send messages, Inbox threads, doc review wakes, and sm worktree keep marks.

What the agent sees, and what the policy controls

The ask is deliberately policy-neutral. It says why sm is asking, what sm will do, and the one command to run. It does not tell the agent how to write the note. Every message sm sends in this feature is listed verbatim in Appendix D. The ask arrives like a [sm claim] notice: at the agent's next turn boundary, never mid-tool-call. A review-request ask is printed directly by sm request-codex-review or sm doc publish --review, so the agent sees it in that command's output.

Agents get no command to read or change the policy. A change takes effect immediately. If you switch an asked agent off, or raise its threshold above its current usage, sm withdraws the ask and tells the agent to continue.

What moves, and what could go wrong

Today nothing in sm moves work between agents. Retiring an agent ends its claims. Its pending review and queue wakes, reminders and undelivered messages are orphaned. Its children keep a parent that no longer exists. So the transfer is the real engineering in this change. Appendix G lists every obligation and exactly what happens to it. Three risks shape the design:

  • Losing the worktree. Retiring an agent deletes its worktree today. sm moves the claims before it retires the predecessor, so the worktree belongs to the successor at retire time, and a live agent working in it also blocks deletion. A test covers exactly this sequence.
  • A crash halfway. sm writes “moving work to <successor>” before it moves anything. Every move is safe to repeat, so a server restart finishes the transfer.
  • Something sm adds later that also addresses a session id. The forwarding pointer catches it at delivery time. A test fails if anyone adds a table with a session-id column without saying whether handoff moves it.

Handoff stays separate from the existing [sm context] gauge alerts, which a parent enables with sm context-monitor. Those keep working unchanged.

Cost

Each handoff costs one successor start-up: reading the note, the PR or ticket, and whatever files it needs. That is roughly what the old /clear-and-reinject cost, since both start from an empty context. The saving is the same as the old design's: a Claude agent at 35% re-reads a third of a large window on every turn, and a fresh one does not.

B. Policy: stored defaults and resolution

The default policy is a top-level key handoff_defaults in the session store[1], next to agent_registrations. It is not in config.yaml, because config is read once at startup[2] and you need to change these on the go. When the key is absent, the built-in starting values apply. The first successful PUT /handoff-defaults writes the full object.

"handoff_defaults": {
  "providers": { "claude": true, "codex-fork": false, "codex-app": false },  // unknown provider = false
  "threshold_percent": 35,        // (0,100]
  "ask_on_codex_review": true,
  "ask_on_doc_review": true,
  "review_floor_percent": 20,     // [0,100]
  "reminder_percent": 50,         // (0,100]; not > effective threshold = no reminder
  "updated_at": "..."
}

GET /handoff-defaults returns the object, with starting values filled in when absent. PUT /handoff-defaults takes any subset of the fields and merges them. It rejects non-finite or out-of-range values with 400, naming the field, the same rule context_monitor thresholds use[3]. Authorization is the same as I.1: owner only. After a successful PUT, sm re-runs the withdrawal check (C.5), and it re-runs the threshold check (C.1) against each running session's latest reading, so lowering the threshold below an agent's current usage asks it immediately.

Effective policy for a session S:

  • enabled = override enabled if not null. Otherwise it is providers[S.provider], false when absent.
  • threshold = override threshold_percent if not null. Otherwise the default threshold_percent.
  • reminder = the default reminder_percent when it is greater than the effective threshold. Otherwise there is no reminder. Example: you override the threshold to 55. The reminder at 50 then does not apply, and there is none.
  • source = "override" if any override field is non-null, else "default".
  • has_gauge = the provider reports context usage (claude, codex-fork)[4].

C. Tipping points: exact rules

C.1 Context threshold. The rule is evaluated after sm stores each accepted context-usage sample. For Claude that is the /hooks/context-usage path. For codex-fork it is the event-stream reader. Both write context_used_percentage before the context-monitor enrolment check[5], so handoff does not depend on sm context-monitor enrolment. The ask fires when all of these hold: the effective policy is on; the handoff key is absent; the session is not stopped; and the sample is ≥ the effective threshold. A sample that jumps from 30% to 41% asks once, and the message says 41%. Stale samples, which today's code already rejects[6], never ask.

C.2 Reminder. In state asked with reminded_at null, the first sample ≥ the effective reminder percent queues D.2 and sets reminded_at. There is never a second reminder. From then on the surfaces show overdue (Appendix I.2). A compaction or context reset does not clear asked. The ask stands until the agent hands off or the ask is withdrawn.

C.3 Review requests. Two commands trigger this rule with the same logic. Codex review: the rule is evaluated in create_codex_review_request[7] after the request is registered successfully, for the requester_session_id (not --notify), with trigger review_request and switch ask_on_codex_review. Doc review: it is evaluated in publish_owner_doc[22] after a publish with "review": true succeeds, for the body's session_id, with trigger doc_review and switch ask_on_doc_review. A publish without --review never asks. The rule fires when the effective policy is on; the command's switch is true; the handoff key is absent; and either has_gauge is false or the latest context_used_percentage is ≥ review_floor_percent. A gauge provider with no reading yet does not ask. When it fires, the response JSON carries "handoff_ask": "<D.1 text>" and state becomes asked. Each CLI (sm request-codex-review, sm doc publish) prints the text on stdout after its existing lines. sm does not also queue it as a message, so the agent never sees it twice. A later review request of either kind, in state asked, does nothing new.

C.4 Hand off now. You call the policy API with "ask_now": true (Appendix I.1). If the handoff key is absent, sm queues D.1 with trigger owner regardless of policy or gauge. Otherwise it returns 409 with the current state.

C.5 Withdrawal. After any change to an override or to the default policy, sm re-checks every session in state asked whose trigger is context. If the policy is now off, or its current usage is below the new threshold, sm removes the handoff key and queues D.3. It cancels any undelivered ask or reminder first, using the same category-cancel that context alerts use[8]. Asks with trigger review_request, doc_review or owner are withdrawn only when the policy is turned off. Setting the policy to off always withdraws an asked state, whatever the trigger. The states accepted and later are never withdrawn: the agent has already committed.

Delivery. Asks, reminders and withdrawals are queued with delivery mode important and message category context_handoff. Sender is the session itself, as with context alerts, so a completed handoff can cancel leftovers by category.

E. The sm handoff command

sm handoff --link <url>
sm handoff --path <file>
sm handoff <file>            # same as --path <file>

Exactly one of the three forms is required. With no argument the command errors with sm handoff needs --link <url> or --path <file>. The old default of HANDOFF.md is gone. The command must run inside a managed session (SESSION_MANAGER_ID set). It is self-directed only, as today.

Client-side checks: --path must name an existing regular file. The CLI canonicalizes it to an absolute path. --link must parse as an http or https URL. Neither is fetched or read.

F. Starting the successor

F.1 When. sm starts the successor on the first transition of the predecessor to idle while its state is accepted. That is the existing idle detection that drives [sm task-complete] and stop-notify: the Claude Stop hook, codex-fork turn-complete, and codex-app idle. If the predecessor is already idle when sm handoff returns, for example because the command ran as the turn's final action and the idle event raced ahead, sm starts immediately. There is no timeout. An agent that keeps working after sm handoff keeps showing handing off until its turn ends.

F.2 What is copied. The successor copies provider, model, reasoning_effort, working_dir, node and parent_session_id from the predecessor record[9]. Model and effort must be passed explicitly. Today's spawn path does not inherit them from anyone[10]. A root predecessor gives a root successor, and root retire protection applies to it as before. The successor is created through the same core create path as sm spawn, with no --ticket reservation, because claims move in place (G).

F.3 Name. Take the predecessor's name. If it ends in -h<k>, where k is an integer ≥ 2, replace that with -h<k+1>. Otherwise append -h2. Examples: sm-1651-engineer → sm-1651-engineer-h2 → sm-1651-engineer-h3. And sm-pr-1660-reviewer-2 → sm-pr-1660-reviewer-2-h2. Names are not unique in sm today[11], and this rule does not make them so.

F.4 Brief. The successor is created with no initial prompt. sm sends the brief as its first message, with delivery mode important, only after Appendix G completes. That way the successor never acts before it holds the work. sm types the brief only into an empty, ready input box: it first waits for the successor's composer as a spawn brief does. Every delivery path applies the same check to handoff messages (the brief and the D.7 parent notice), so a brief that finds the composer not ready stays queued, and the background retry sweep delivers it once the composer is ready. A drain over all of the successor's messages stops at a held brief; a drain limited to one category (a reminder, a queue completion) can still deliver its message first in that window. Lines whose value is empty are omitted.

[sm handoff] You are taking over from <pred name> (<pred id>), which stopped at <pct>% context.

“Original brief” follows the lineage back. sm uses the first ancestor in the predecessor chain that has a spawn-brief artifact[12], so -h3 still sees the brief -h1 was spawned with.

F.5 Failure. If creation fails, sm sets state failed, records the error, queues D.6 to the predecessor, and moves nothing. If the successor record exists but the agent process dies before the brief is delivered, it is handled like any spawned agent that dies. Its work is already moved, and you see it as a stopped agent holding the claims. sm does not retry automatically.

G. Moving the work

Order. (1) Write successor_session_id on the predecessor, predecessor_session_id on the successor, and state transferring. (2) Apply every row below. (3) Deliver the brief (F.4). (4) Retire the predecessor (H). (5) Queue D.7 and cancel leftover context_handoff messages from the predecessor. (6) Set state done.

Recovery. On startup, any session in state transferring resumes at step 2. Every row is an update of the form WHERE <column> = predecessor, so repeating it is harmless. A session found in spawning at startup, with no successor id written, goes to failed with error server restarted while starting the successor, and D.6 is queued.

H. Retire, cleanup, forwarding

H.1 Retire. The predecessor is retired through the core retire path with ServerLifecycle authority. Root protection does not block a server-driven handoff. The terminal provenance reason is handed_off, with the successor id. Claim ending at retire[17] finds no active claims, because they have moved. Worktree cleanup[18] gathers no candidates from moved claims. As a second guard, cleanup never deletes a path that is the working_dir of a live session. A test checks the whole sequence on a managed worktree.

H.2 Forwarding. live_recipient[19] becomes: the session while it has not ended; else, if it has a successor_session_id, the result of live_recipient on the successor, following the chain; else its parent when that has not ended; else nobody. The same resolution applies when sm send, sm remind, sm request-codex-review --notify, sm queue run --notify or sm context-monitor enable name an ended session by id or by exact name. sm send prints D.8. The chain walk stops after 32 hops. A cycle cannot form, because a successor is always newly created.

I. Owner controls: API and surfaces

I.1 API. PUT /sessions/{id}/handoff-policy, body:

{ "enabled": true | false | null,          // omitted = unchanged, null = inherit
  "threshold_percent": 45 | null,          // omitted = unchanged, null = inherit
  "use_default": true,                     // clears the override entirely
  "ask_now": true }                        // Hand off now (C.4)

Authorization, for this route and for /handoff-defaults: owner only. The request passes the existing session gate[20]. A request that carries a requester_session_id, or an X-SM-Session header, gets 403 handoff policy is owner-only. Ticket 1 makes the sm client send X-SM-Session: <id> on every request whenever SESSION_MANAGER_ID is set. Today it sends no session header. The callers that pass are the web page and the app, both authenticated remotely, and sm watch run from your own terminal, which has no SESSION_MANAGER_ID. Agents are semi-trusted. An agent that deliberately strips its identity on loopback could pass as you, which is accepted, as on every other owner route today. Response: the effective policy object from I.2. The web page's calls also require Origin to match the page's host.

GET /sessions/{id}/handoff-policy returns the same object.

I.2 Session JSON. Three places add the same object: SessionResponse (and so the app's client/sessions), the web /watch/state session entry, and the sm watch data source. SessionResponse also gains context_percent, which today only /watch/state has.

Key H opens a prompt modelled on rename (n): on, off, default, an integer 1–100 (sets the threshold), or now (arm then confirm within 5 s, like K). Key P opens the default policy as a list of the B fields. Enter edits the selected field, and each edit is one PUT /handoff-defaults. The help overlay lists H and P.

Z. FAQ

Why not keep /clear and just add the triggers? The triggers would work on it, but everything else argues against it. Restoring an agent by id would bring back a mix of context windows. The /clear path needs a provider-specific confirmation for every provider. codex-app has no clear command sm can drive. And the parent and you cannot tell from sm watch that the agent changed. A fresh agent gets all of these for free. The price is Appendix G, which is written out in full.

Why move claims in place instead of having the successor run sm ticket --take? --take ends the old claim with reason taken, sends a [sm claim] notice to an agent that is about to retire, and starts a fresh claim without the worktree path. Moving in place keeps the worktree link, which is what protects the worktree from deletion at retire. It also keeps the claim history continuous.

Why wait for the predecessor's turn to end instead of retiring at sm handoff? The command runs inside the agent's turn. Agents often run it just before a final git push or comment. Retiring then would kill the push.

What if the successor starts working before it reads the note? Its first message is the brief, and the brief's first instruction is to read the note. It has no other prompt.

What about an agent that hands off to itself repeatedly? Each handoff is a new agent with a fresh context. A successor is asked again only when it reaches the threshold again. Repeated review requests from the same agent, or its successor, within one context window ask at most once, because the state is not absent.

Why store the defaults in sm rather than in config.yaml? sm reads config only at startup, and changing it means a server restart through the restart script. You want to tune the threshold from your phone. The stored object is small, validated on write, and shown by every surface. Nothing else reads it.

Why not a per-model threshold, since 35% of a 1M window is much more than 35% of 200K? You asked for a percentage. Per-agent overrides already cover the model you want to treat differently. If you find yourself overriding by model repeatedly, a per-model threshold in handoff_defaults is a small follow-up.

Does this change sm context-monitor or the [sm context] alerts? No. They keep working as today and are independent. A parent that wants gauge alerts for a child still enables them. The only link is that handoff cancels the predecessor's pending [sm context] alerts, and the monitor settings copy to the successor.

What if the note path is inside the worktree and uncommitted? That is fine. The successor runs on the same machine in the same working directory, so it can read the file.
